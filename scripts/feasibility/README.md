## Boundary and fairness

- One controller starts/closes/resets runs. Two or three buy-only API processes serve traffic. One ERP authority owns pacing and resilience. This proves buyer-path concurrency, not production run-control/SSE/idle-stop coordination.
- All modes use the actual `ReserveOrderService`, durable `PostgresBuyPersistence`, worker order transitions, ERP dispatch/attempt/uncertainty reconciliation, and idempotent notification recording. Demo uses the unchanged Redis Lua and BullMQ order delivery. No-Redis constructs no Redis client: stock/idempotency/holds and a leased queue are PostgreSQL-backed. No-queue uses Redis stock and an awaited HTTP chain to the ERP authority, after the admission session has been released.
- PostgreSQL stock uses one atomic `SELECT proof_reserve(...)`: run eligibility precedes replay, an idempotency-key advisory transaction lock serializes duplicates, and a conditional inventory update protects stock. Sold-out requests do not rewrite the stock row. Winner holds are committed before the existing durable acceptance workflow. Equal protections do not imply equal SQL/commit counts.
- PostgreSQL enqueue uses the exact reserved acceptance session through `withRunAdmissionLockAndSession`. No nested checkout, extra pool, global session, or asynchronous context trick is used. Its poll interval is 10 ms; claim/renew/ack are short statements, with a 30 s lease and generation fencing. Processing leases are renewed every 5 s. Record this polling overhead, rather than presenting it as inherent PostgreSQL latency.
- Every API uses the identical observational counter collector, a 250 ms PostgreSQL snapshot and mandatory final `/metrics` flush. Native Redis Lua counters remain real additional Redis-path work. Stock, holds, idempotency, orders and ERP ledger are independently authoritative. Immutable k6 points reconcile started/completed/outcome counts with all API observers before a cell is valid. Missing observer evidence, dropped/unstarted requests, protocol failures or unresolved business work invalidate a clean Redis speed claim.
- Accepted queued answers are 202/`reservation_secured`; inline confirmed answers are 200/`order_confirmed` with `status: confirmed`. A proven undispatched inline deadline persists a failed order; an unknown dispatched ERP result returns `confirmation_unresolved`, preserving its durable control record. In no-queue mode `/reconcile-uncertain` sets the actual scheduled confirmation's explicit `allowDispatch: false` policy: only local evidence and ERP lookups are allowed, including when lookup reports unknown or unresolved evidence disappears. Unknown remains durably escalated; it never triggers a background replay POST after the buyer deadline. Ordinary queued recovery keeps its existing replay policy. Unresolved/escalated records invalidate clean performance conclusions. Reset aborts in-flight calls, closes stock eligibility and advances the durable generation before teardown.
- Notifications are recorded through the same actual durable handler inline after confirmation in every experimental mode. No notification BullMQ queue or visitor dashboard is part of this lab. Persisted missing notifications invalidate the cell; this is not a claim of full production recovery/notification topology validation.
- No-Redis still shares the same store Machine with an idle Redis server, preserving hardware. It makes no Redis calls in its API/authority/controller composition. Store CPU samplers read cgroup files and make no Redis commands.

Default topology generated by `infra/fly/feasibility/lab.mjs` with `lab.json`: core performance-6x/12 GiB (controller, three APIs, authority, Mock ERP and Caddy), stores performance-2x/4 GiB (PostgreSQL 17, Redis 7, observer), runner performance-16x/32 GiB (k6 2.0.0). No public IP is allocated. PostgreSQL pool maximum is 10 for each API, 10 for the authority and 10 for Mock ERP, plus controller pool 3: 53 aggregate potential connections with three APIs, 43 with two. Setup has a temporary pool of one outside measurement. Every comparison retains identical hardware/process/pool settings.

Historical configurations, calibration exclusions and retained measurements are recorded only in task 02 Working Notes. Keep their raw packets unchanged; generator headroom and delivery timing must pass the registered protocol before interpreting comparative results.

The stores share a separate Machine in `cdg`. Start with `storeDelayMs: 0`. If RTT is too small, set an explicitly disclosed egress `tc netem` delay on the stores' `eth0`; it affects PostgreSQL and Redis together. `/rtt` measures actual protocol round trips before each run. Netem capability was separately verified on a disposable Fly Machine; any new constraint requires a separately registered comparison. Do not infer RTT from the configured delay alone.

## Matrix and raw evidence

Inside the runner, a small smoke plan may execute several cells on one kernel:

```sh
cd /lab
mkdir -p /results
node scripts/feasibility/make-plan.mjs redis smoke 1 /results/smoke-plan.json
node scripts/feasibility/run-matrix.mjs /results/smoke-plan.json /results/smoke
```

Plan arguments: comparison `redis` or `queue`; preset `smoke`, `surge-5k`, `slow-erp-5k`, `ca-300x10` or `sold-out`; paired repetitions (default six); output JSON. The source plan defines the interleaved sequence; odd/even pairs reverse mode order. Plans may supply an explicit `runs` array with mode, snapshot, pair and optional warmup. Record warmups separately. Every cell recreates application processes, consistently including the cold API boundary.

**Retained hosted studies with 10,000 VUs require one explicit `plan.runs` cell per invocation and a fresh runner kernel for every cell.** Do not execute the full paired source plan continuously on one VM. The retained reproduction procedure is:

1. Freeze and hash the reviewed source plan, image manifests, topology and admission protocol before dispatch. Expand its interleaved sequence into separate one-cell plans while preserving each cell's mode, snapshot, pair and warmup fields; each emitted plan must have `runs: [cell]`. Hash every emitted plan. Preserve the source plan alongside them.
2. Before each cell, verify the named runner app belongs to `playground-416` and is not a production target. Stop only that lab runner, wait for `stopped`, start it, wait for `started`, and record `/proc/sys/kernel/random/boot_id`. Require a changed UUID from the preceding cell. Keep the core and store Machines at the registered configuration. The all-role `lab.mjs stop/start` commands above are session lifecycle commands, not the per-cell runner transition. The fresh runner boundary follows [HD-07](../../docs/decisions/hosted_deployment.md#hd-07-the-api-starts-and-stops-the-runner-for-each-run).
3. Confirm core application readiness from the runner. Invoke `node scripts/feasibility/run-matrix.mjs <one-cell-plan.json> <unique-cell-results-directory>` inside `/lab`. Capture guest output and require the actual `FEASIBILITY_MATRIX_COMPLETE 1` sentinel, matching run ID, and one actual record. A host success exit status alone is insufficient.
4. While the runner is still started, export the entire cell directory to a unique local directory. Verify file lengths, every SHA-256 in the run completion manifest, the one-cell plan hash, record/run/mode/pair agreement and observed boot UUID. Save the completion capture and a verification marker. The bounded downloader below is the reference path. A reviewed SFTP fast path is acceptable only after a full probe agrees with that reference and it preserves the same per-file verification gates. Do not export during load.
5. Stop the runner only after export verification succeeds. If verification fails, preserve the guest artifacts while recovering export; do not classify the cell as retained. Keep every failure and partial packet in the exclusion ledger. Repeat from step 2 for the next interleaved cell.
6. Offline, audit and aggregate the individual immutable packets/JSONL analyses. Verify the expected number of individual completions and distinct boots. Retain all per-cell completion captures; do not synthesize a `FEASIBILITY_MATRIX_COMPLETE 12` sentinel or present a partial records index as a completed matrix. Apply each comparison's preregistered CPU/profile rules without borrowing a differently scoped exception from another comparison.

Multi-cell execution remains useful for local checks and appropriately small smoke runs; it is not the retained hosted default. The exact retained plans, verified packet paths, results and costs live in [task 02 Working Notes](../../working_docs/backlog/redis_and_order_queue_proof/02_feasibility_checkpoint.md#working-notes).

Constant-arrival runs cap HTTP attempts at `ratePerSecond × durationSeconds`: the single-process scenario's zero-based `iterationInTest` is checked before `buyer_started` or HTTP. Any extra boundary iteration returns immediately and increments `buyer_capped_iterations`. This is cap-only: duration, rate and VUs are unchanged; shortages are neither refilled nor tolerated. The pinned k6 timer/context boundary can emit one extra scheduled iteration ([executor source](https://github.com/grafana/k6/blob/v2.0.0/lib/executor/constant_arrival_rate.go#L289-L336)). Final records retain nullable raw `droppedIterations` and `cappedIterations` from `summary.json`; an absent metric stays `null`. Any positive `dropped_iterations` invalidates `noReportedDroppedIterations`, even when completed HTTP counts equal the target, because a boundary extra could otherwise conceal a dropped slot. A cap does not relax exact planned-delivery accounting. Earlier raw calibrations remain unchanged.

The runner writes per-run immutable k6 JSON compressed with gzip, raw summary/stdout/stderr, mode/run tags, final durable/counter/inventory evidence, actual RTT, and 1 s CPU/memory samples for core, both store containers and runner across dispatch and drain. CPU/memory probes support cgroup v2 and the combined/separate v1 cpuacct and memory mounts observed on Fly (HD-44); samples record the version and normalize CPU time to microseconds. Missing measurements remain explicit; CPU claims require real coverage of their preregistered scope, and whole-trace completeness cannot be inferred from a covered interior window. Response completion and order confirmation timestamps are separate. Each run has a SHA-256 completion manifest; an invocation writes `records.json` only after every requested teardown and prints `FEASIBILITY_MATRIX_COMPLETE <count>`. A retained one-cell invocation must actually print count one.

**Do not trust `flyctl machine exec`'s host exit status:** it has returned zero for a failed guest. Require the explicit matrix completion sentinel and expected count. The artifact downloader uses a validated guest success prefix, bounded compressed chunks, expected lengths, full SHA-256 verification and run completion manifests. It saves files directly without dumping points into model output:

```sh
node infra/fly/feasibility/download.mjs infra/fly/feasibility/lab.json <runner-machine-id> /results/smoke .tmp/feasibility-results/smoke
```

Keep raw evidence before teardown; report every retained repetition, median/range and paired differences, including failed cells. For Redis claims require full planned delivery, all observer accounting, settled business invariants, CPU evidence and clean responses. For no-queue report deadline/error counts alongside winner latency, avoiding survivorship claims based only on the buyers who confirmed before the deadline. The generator must have CPU/memory headroom; missing/dropped work is not store throughput. Review per-process utilization and RTT before increasing offered rates or tightening a pool. ## Offline analysis

Offline evidence analysis is available in `analyze-results.mjs` for this three-API lab with six core CPUs and two shared store CPUs. Each cell's runner allocation comes from its immutable `run.json` `runner.cpuCount`: eight or sixteen CPUs are recognized; missing or unsupported counts leave allocation fractions null. Captured runner memory and its provenance also come from that run file. Pass the local matrix directory, a common window's start/end seconds relative to the first buyer, the core's observed `getconf CLK_TCK`, and the evidence classification. It streams and rehashes raw points, reconstructs request wall times with nanosecond timestamps, separates missing metrics from zero, and reports CPU only where actual samples bracket the requested window. All-trace peaks include initialization and drain; the interior peak uses only whole sample intervals inside the common window. Store samples have approximately one-second boundary uncertainty. Verify the applied Machine metadata before interpreting allocation fractions. Save the JSONL output beside the raw matrix; excluded calibration evidence must keep that classification.
