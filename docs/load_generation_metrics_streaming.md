# Load Generation and Metrics Streaming - Decisions & Rationale

This document defines the implemented load generation and metric streaming behavior. The demo flow starts traffic from API-owned preset run snapshots. The load orchestrator owns k6 execution, but the public/admin product contract is a discriminated traffic config plus generated `runId` and generated `saleOfferId`.

The implemented reference boundary is one API-owned current demo run, with one API process as the sole maintenance authority, one Next.js web process, one worker runtime, and one file-journaled traffic execution in a single load-orchestrator process. The single Caddy dashboard proxy/edge remains only an ingress path. Distributed k6 execution, horizontally coordinated orchestrator slots, horizontally replicated application services, hosted benchmark isolation, and benchmark evidence are not implemented by this local contract.

## Confirmed Decisions

| Decision Area | Choice | Rationale |
| :-- | :-- | :-- |
| Public/admin traffic model | Preset run snapshots with explicit buyer-spike or steady-arrival traffic mode | Keeps user-facing controls aligned with benchmark intent rather than raw k6 virtual users or ramp stages. |
| Scenario owner | `apps/load-orchestrator` | The load orchestrator owns k6 execution and parameterization; browser clients never create high-volume traffic. |
| Contract source | `@checkout-surge/contracts` demo run and load schemas | Dashboard controls, orchestrator routes, parser output, and run summaries use shared schemas with separate traffic-execution and API-owned run lifecycle vocabulary. |
| Public/admin preset split | Preset visibility, editability, and API policy caps separate public-safe demonstrations from admin-operated experiments | Keeps public controls bounded while still allowing authenticated operators to run focused checks and higher-pressure demos. |
| Purchase behavior | Every preset traffic run targets the API buy endpoint with the snapshot's `trafficConfig.quantityPerAttempt`, generated idempotency and per-attempt correlation IDs, generated `runId`, and generated `saleOfferId` | Preserves the limited-inventory benchmark surface, honors the accepted traffic snapshot independently of inventory sizing, and isolates repeated runs. |
| k6 wrapper API | Fastify service in `apps/load-orchestrator` | Keeps run control testable with the same HTTP service pattern used by the API gateway. |
| k6 runtime boundary | The reference runtime packages k6 inside the load-orchestrator container | k6 is an external binary, but it belongs to the load-generation service runtime. Host-installed k6 is only a convenience path for host-native development. |
| k6 parameter passing | Generate a temporary k6 script from validated preset traffic snapshots | Avoids shell interpolation risks and keeps run inputs contract-driven. |
| k6 output parsing | Stream JSON points for live windows and bounded fallback evidence; use k6 `--summary-export` as the authoritative terminal aggregate | Keeps live feedback incremental while terminal counts, rates, percentiles, and HTTP phases use k6's end-of-test aggregation. |
| Metric forwarding | Load orchestrator posts bounded, single-flight batches of windowed k6 metrics to the API at `/internal/load/metrics` | The API remains the owner of dashboard recovery state and SSE fan-out while k6 execution stays isolated in the load service. |
| Start recovery projection | The API commits the `starting` run and initializes run inventory before delegating the frozen execution intent to the load orchestrator | A browser recovery read can show the new run even when the start call has an ambiguous network outcome. |
| Traffic execution durability | The load orchestrator keeps one atomic persistent execution slot, records acceptance before spawn and completion before delivery, and retains the slot until API acknowledgement | A restart or transient HTTP failure must not lose traffic ownership or its terminal report. |
| Traffic cancellation | Authenticated `POST /traffic/current/abort` optionally fences by run ID and confirms process exit before success | One child-process supervisor retains the execution slot while stopping and must observe child exit/reap within `K6_CANCELLATION_TIMEOUT_MS`, 10 seconds by default and at most 15 seconds; it never reports a persisted `cancelled` traffic lifecycle. |
| HTTP versus business outcomes | k6 samples map only to `traffic.scheduled_request_rate`, `traffic.latency`, and `traffic.failure_rate` | Business outcomes are derived separately from reservations, orders, ERP attempts, and notification records. |
| Dashboard run control | The dashboard server starts API-owned demo runs from presets; the API delegates accepted traffic snapshots to `apps/load-orchestrator`; browser recovery reads come from the API via `/api/dashboard/recovery` | This preserves service ownership: UI starts runs through the API lifecycle while k6 execution stays isolated in the load service. |
| Overlap policy | Start buttons are disabled while the API-owned demo run is `starting`, `active`, or `draining`; load starts are accepted only after the API establishes the new recovery baseline | Client-side prevention improves operator clarity, while API start acceptance is the source of truth. |
| Run-summary persistence | The API owns run-summary storage in PostgreSQL; the load orchestrator reports traffic completion and HTTP summaries, then API-owned services write immutable terminal run summaries | This preserves the repository boundary that `apps/load-orchestrator` does not use `@checkout-surge/db`, and keeps demo-run completion tied to run-scoped business outcomes while still recording exceptional terminal failures. |
| Canonical transport evidence | Completion reports and stored run summaries carry one `transportAttemptCounts` object with planned, started, response-completed, interrupted, and unstarted totals | The two transport equations are enforced once rather than synchronizing copies across HTTP, delivery, and supposed API-lifecycle summaries. |
| Summary split | Stored run summaries keep canonical `transportAttemptCounts`, response-only `httpSummary`, plan/quality-only `trafficDeliverySummary`, and `businessOutcomeSummary` separate | This makes client attempt delivery, HTTP outcomes, traffic fidelity, and asynchronous order/ERP completion comparable without copying totals or conflating statuses. |
| Traffic delivery quality | The API enriches traffic delivery summaries with `trafficDeliveryStatus` (`complete`, `warning`, `degraded`, or `failed`) derived from canonical planned and unstarted attempt counts | The load orchestrator reports raw client-attempt counts and k6 delivery diagnostics; API finalization decides whether under-delivery is warning-level, degraded, or a major traffic-fidelity failure. |
| Live versus history split | Live dashboard recovery is current-run focused and can reconstruct recoverable runs from durable `demo_runs`; `/watch` observes the current run and persisted terminal run summaries are shown on `/run-history` | Historical summaries should not appear as the live current run after reset or reconnect, while durable `starting`, `active`, and `draining` run state must not disappear after API process churn. |
| Per-order realtime presentation target | The browser no longer consumes per-order realtime events; Task 40 removes their transitional server/contracts path and the remaining live recent-activity presentation residue while retaining aggregate consistency lag and focused durable order diagnostics | The dashboard exists to explain aggregate surge behavior, not to provide customer order tracking. No sampled recent-activity exception is selected. |

## User-Facing Traffic Model

Public and admin preset traffic is modeled as one of two modes:

- `buyer-spike`: `buyerCount`, `duplicateEachBuyerAttempt`, `startDelaySeconds`, and `maxDurationSeconds`.
- `steady-arrival-rate`: `ratePerSecond`, `startDelaySeconds`, `durationSeconds`, and optional advanced k6 VU controls for admin custom runs.

The API validates this shape against environment-backed buyer, emitted-attempt, request-rate, duration, start-delay, and VU caps before a run can start. The load orchestrator translates buyer-spike snapshots into k6 `per-vu-iterations` plans and steady-arrival snapshots into k6 `constant-arrival-rate` plans. Raw ramp stages and think time remain implementation details. k6 VU sizing stays automatic for public presets and for admin steady-arrival runs that leave the advanced VU controls blank. Automatic steady-arrival sizing preallocates `min(ratePerSecond, 10_000)` VUs and allows up to `max(preallocated VUs, min(2 * ratePerSecond, 10_000))`; explicit controls are preserved unchanged and must specify both values with `maxVus >= preAllocatedVus`. The API checks both automatic and explicit resolved values against the active deployment hard caps rather than silently clamping them. Public-custom VU limits apply only when advanced controls are explicitly supplied, so an otherwise valid automatic public rate remains usable.

Every preset traffic start includes the API-generated `runId` and generated `saleOfferId`. Those identifiers are included in each buy attempt so the API can validate run sale eligibility without returning to the old fixed active-sale window as the demo lifecycle.

The API's focused traffic-execution HTTP gateway owns service authentication, correlation propagation, request/response validation, exact run binding, and bounded start/status/abort calls. Run lifecycle consumes only its start capability, while maintenance consumes only its exact-run abort capability. If the API cannot confirm a complete start response, it leaves the durable run intent in `starting` instead of guessing that traffic failed. The API lifecycle poller replays the exact run ID and immutable snapshot; the orchestrator either accepts that intent or reports its existing ownership. The orchestrator journal fences a different run, converts orphaned accepted/executing evidence after its own restart into one durable failed completion, and gives that record to the same completion-delivery coordinator used for natural results. Repeated startup initialization shares that one reconciliation operation. The coordinator is the only owner from `completion_pending` persistence through matching API acknowledgement, while the execution store serializes the conditional report-publication and acknowledged-completion transitions so conflicting evidence or a changed slot cannot be overwritten. The journal accepts only the current strict request, state, timestamp, and completion-report shapes. A malformed or pre-current journal fails with the durable `execution.json` path and field-level validation detail; operators rebuild disposable pre-release state instead of translating it.

For steady-arrival traffic, `ratePerSecond` means scheduled checkout iterations per second, not new virtual users per second. k6 reuses VUs as workers: if a `/buy` iteration finishes quickly, the same VU can run another later iteration. This does not collapse multiple attempts into one buyer in Checkout-Surge because the generated k6 script derives a unique idempotency key from the global scenario iteration. For example, `50` requests per second for `10` seconds plans `500` unique checkout attempts against the run sale offer; the required VU pool depends on iteration duration and generator capacity, not directly on the `500` planned attempts.

Both generated scenario modes use a fixed five-second k6 `gracefulStop`. It lets already-started iterations finish after the steady scheduling duration or buyer-spike maximum duration without scheduling replacement iterations. This window is an execution detail and is not included in planned-request counts or terminal execution-plan diagnostics.

The generated steady-arrival script caps HTTP attempts at that planned total before constructing an attempt, so executor overscheduling cannot make the started-request count exceed the accepted plan. An early-returned k6 iteration is still distinct from the executor's `dropped_iterations`; delivery reporting uses the explicit attempt-start and response-completion counters, with `http_reqs` only as the documented completion fallback. This cap currently relies on k6's globally unique scenario iteration identity within the supported single-process execution model; distributed k6 execution remains outside the supported scope.

k6 sends each attempt's correlation ID in both the buy body and `x-correlation-id`. It discards response bodies and classifies business results from the API's case-insensitively read `x-checkout-outcome` header: `202` is accepted only for public outcome `reservation_secured` or `reservation_pending_persistence`, while sold out requires `409` with outcome `sold_out`. Internal Redis `idempotent_replay` decisions project to the public `reservation_secured` outcome and never appear on this wire boundary. Missing or contradictory status/outcome evidence is unexpected; there is no response-body fallback. Ordinary API callers still receive the contract-valid JSON response body.

Zero starting stock is a valid preset configuration for sold-out demonstrations. The load orchestrator keeps the accepted-reservation counter for outcome summaries, but k6 traffic correctness is based on the unexpected-response counter staying at zero. A run with only clean `sold_out` responses is therefore valid traffic behavior rather than a failed traffic run.

When a buyer-spike preset enables `duplicateEachBuyerAttempt`, the load orchestrator may report duplicate accepted HTTP responses for the same buyer/idempotency outcome. Terminal business summaries treat complete duplicate buyer-spike deliveries as durable reservation accounting: accepted reservations represent the unique durable reservation count, not the raw accepted response count. Planned-attempt displays keep the full emitted-attempt total and annotate the duplicate-buyer context.

## Dashboard Recovery Model

The API-owned SSE stream at `/dashboard/events` carries complete `checkout-surge.dashboard-projection` version 1 replacements. The browser parses only that schema and atomically replaces its current view; transitional legacy dashboard-event frames are ignored until Task 40 removes their server/contracts path. The same-origin `/api/dashboard/recovery` route, backed by API `/dashboard/recovery`, returns the exact same complete projection schema and scoped revision semantics. The response carries the request `correlationId` and an explicit nullable `{ runId, saleOfferId }` scope. The `/watch` route is the focused current-run spectator surface, while `/admin` remains the privileged operator surface. Live and recovery remain public demo observability surfaces; admin sign-in gates privileged controls, not telemetry.

Unavailable browser recovery reads retry through the same single-flight path used by manual refresh and stream connection repair. The deterministic policy starts at one second, doubles without jitter, and caps at 30 seconds; an accepted live or HTTP projection cancels the timer and resets the attempt counter. Watch retains its last successful complete projection across a later transport failure and labels it as last-known-good; initial recovery failure and the public/admin start gates remain unavailable and fail closed without claiming a last-known-good view. The initial stream open, first disconnect error in one outage, later reconnect open, and manual repair each request one projection through that path; repeated errors while already disconnected request none, and simultaneous triggers coalesce onto the in-flight HTTP read. When a projection scope is known, that read includes the paired `knownRunId` and `knownSaleOfferId`, allowing the API to prefer a current newer run or recover the exact missed terminal scope with one request. The active-run 30-second polling and trailing-read machinery are gone.

One small browser state owner applies live and HTTP candidates through the same rules. Same-scope state changes only when `revision` is higher. Scoped revisions are never compared across scopes: a coherent nonterminal run can establish a new scope only when its durable `startedAt` is newer than the last accepted run, while an idle-to-run C1 overlap additionally requires the committed projection's `recoveredAt` to be newer than the idle projection. A newer authoritative idle projection can replace a current or terminal scope, but the remembered last run start prevents a delayed old scope from reviving afterward. A terminal projection can advance only its already-active matching scope, so an old or foreign terminal cannot establish another scope. Schema-invalid or incoherent frames, duplicate/lower revisions, and stale scopes are ignored. A live projection racing an HTTP read is compared atomically when each arrives; there is no event buffer, replay, dedupe set, per-metric watermark, or reconstructed total.

Recent completion outcomes are assembled by one PostgreSQL statement. Each selected order and its lateral latest-notification and latest-ERP-attempt projections therefore share one statement snapshot, avoiding both cross-statement lifecycle mixtures and the previous per-order query fan-out. The strict completion-outcome contract remains the final projection boundary, and notification presentation additionally requires the order observed by that statement to be confirmed.

The browser cutover is complete, so retained dashboard views use complete projection fields only: all four gold signals, lifecycle/terminal state, aggregate consistency lag, completion outcomes, and diagnostic aggregates do not depend on ignored legacy events. Task 40 removes advisory `order.status.updated` delivery, per-order `order.consistency_lag` delivery, the unused old browser reducer and its per-order buffers, and the remaining live recent-activity presentation residue together. Investigate a known order through the PostgreSQL-backed `GET /orders/:publicOrderId/status` read or protected Run History; neither creates a storefront. No recent-activity exception is selected. If that decision is revisited, the only permitted live form is a sampled, rate-limited, bounded collection inside the shared revisioned projection, never a second realtime protocol.

The flat recovery payload is the single `checkout-surge.dashboard-projection` version 1 schema, with canonical `run/<runId>/sale-offer/<saleOfferId>` (or global `idle`) scope identity and a Redis-allocated scoped revision. Recovery and live publication call the same `DashboardProjectionService`; the browser uses the direct `DashboardProjection` schema/type, while transitional recovery-named contract aliases remain only for Task 40 cleanup. Idle projections cannot carry run-owned aggregates, and scoped completion outcomes must match the selected run and sale offer. The service reuses the established aggregate readers and serializes builds before allocating a revision so a slow earlier read cannot receive a revision after a newer completed read. Context selection/parse failure rejects the projection before aggregate reads or allocation.

Active-scope revision allocation and exact cleanup serialize on the canonical generated-run inventory hash: allocation atomically verifies run/sale identity and increments, while cleanup atomically deletes the inventory state and revision before removing the remaining Redis namespace. Once retired, an allocation fails instead of recreating revision 1, including when later cleanup or durable deletion must be retried. Redis stores only the latest counter value during a scope's lifetime; there is no projection history or fallback counter.

Task 38 treats each already-validated legacy Redis dashboard event only as a projection dirty signal; it adds no subscription, raw-event store, cache, replay, or duplicate aggregate reader. Ordinary dirtiness is coalesced by scope and publishes no later than a one-second healthy-dependency deadline. There is no meaningful-work/event-count threshold because existing producer aggregation is the measured work boundary. Every lifecycle signal bypasses the timer; terminal signals build the exact run/offer scope so a post-commit terminal row is still selectable. `DashboardProjectionService` keeps actual assembly and cleanup serialized; dirtiness that arrives during a build becomes one trailing build with its own deadline rather than overlapping the earlier operation. Every build/publication attempt has a fresh abort signal and uses the existing `DASHBOARD_RECOVERY_TIMEOUT_MS` deadline (5,000 ms by default). A timeout settles the scheduler attempt, aborts the operation-owned resources, and retains a quiet scope for retry; the retry remains behind the earlier operation's actual cleanup. Real adapters must honor abort as required by the shared operation lifecycle. Shutdown stops admission, discards pending shutdown-only work, aborts the active attempt, and disposes its deadline without requeueing. The scheduler bounds pending scopes at eight in the accepted one-API topology.

Each SSE client writes healthy frames immediately. After socket backpressure, transitional legacy/heartbeat frames retain their existing bounded FIFO behavior while projection frames replace an older pending projection with the same scope ID. A client retains at most eight pending projection scopes, at most 32 total pending complete frames, and at most 256 KiB; crossing a scope/frame/byte bound disconnects only that client. The browser consumes only projections. Heartbeat, total/source admission caps, cancellation, disconnect listener cleanup, and server shutdown behavior remain unchanged.

The bounded Preview 1k measurement selected the largest of six matching active-scope samples at 8,434 UTF-8 bytes. In the common 30-second gate, one active scope produced 1,057 raw Redis events while SSE delivered 22 exact-schema, same-run projection frames. The cadence assertion allowed at most `ceil(30000 / 1000) × 1 + 8 = 38` frames, where eight is a conservative lifecycle/immediate allowance; 22 passed and remained far below the raw-event count. The transitional stream also delivered all 1,057 legacy contract-valid/run-attributable updates, so total data frames were 1,079 plus two non-data setup/heartbeat frames. Those legacy data frames are now ignored by the browser and remain only until Task 40 deletes their producers/fan-out/contracts.

Recovery accepts an optional complete `knownRunId` plus `knownSaleOfferId` pair. One PostgreSQL context query prefers any current `starting`, `active`, or `draining` run and otherwise falls back only to a row matching that exact run-and-sale pair. The hint is advisory: a nonexistent or mismatched pair produces the normal idle projection rather than an internal error, while the internal live-publication exact scope remains strict. The same-origin proxy rejects partial, malformed, or unknown query input with a contract-valid `400 invalid_request` before an upstream call. This lets Task 39 repair a missed terminal or discover a newer active run with one authoritative read without promoting unrelated history, adding a cache, or creating a second protocol.

The load orchestrator keeps terminal aggregation separate from its per-run live aggregator. Live points use epoch-aligned event-time windows (one second by default): valid nonnegative `http_reqs` deltas are summed and divided by the full window duration, `http_req_duration` values produce a window mean, and valid `http_req_failed` observations produce a failure fraction. The final partial window still uses the full configured denominator. Timestamps must satisfy the shared explicit-offset ISO contract; malformed timestamps and points are ignored. Overflow-causing observations are ignored, and a derived non-finite sample is omitted. A point for a finalized or older window is dropped rather than recreating a duplicate partial window. Only the active window is retained.

Inside the API, the internal metric route delegates to a focused traffic-metric ingestion service. That service validates each batch, admits only durable starting or active run lifecycles, bounds and serializes pending work, retains accepted samples, and then attempts advisory publication with the request correlation ID. A separate Redis-backed dashboard traffic-metric store owns the run-scoped list bound, TTL, reset fence checks, publication result parsing, recovery reads, clear, and state inspection. Both are constructed in the API composition root; neither creates Redis clients.

Every real k6 run writes `<run temp dir>/summary.json` through `--summary-export`. After the child closes, completion waits for stdout drain and then reads this file before constructing the immutable report. The completion-delivery coordinator must durably publish that report before the child supervisor removes the work directory or any API send begins. The parser accepts the pinned runtime's flat export and wrapped `{ values: ... }` summaries, ignores unknown fields, and scans balanced JSON objects when using the best-effort stdout fallback. Missing, invalid, and unreadable exports have distinct typed warnings. Raw stdout and raw summary JSON are never included in the report or logs.

Terminal fields choose evidence independently. The explicit `checkout_attempts_started` counter records an attempt immediately before `http.post()`, while `checkout_responses_completed` records a response immediately after `http.post()` returns; the latter falls back to `http_reqs` when explicit completion evidence is unavailable. The three exact Surge outcome counters (`checkout_reservation_accepted`, `checkout_sold_out_rejections`, and `checkout_unexpected_responses`), `iterations`, and `dropped_iterations` prefer summary values, including authoritative zero, then fall back to observed point sums. Typed diagnostics identify `summary_export`, `point_stream`, or unavailable evidence for each field. Reports reconcile `plannedRequests = startedRequests + unstartedRequests` and `startedRequests = completedRequests + interruptedRequests`. The failure rate prefers the k6 rate summary; its request-count contribution is `Math.round(failureRate × completedRequests)`, while Surge's established sold-out-aware domain failure formula remains unchanged. The counter rename is a hard cutover: active k6 processes must be restarted so one run cannot mix aliases or double count.

The summary supplies request-duration p95 and all six HTTP phases: blocked, connecting, TLS handshaking, sending, waiting, and receiving. Each phase contains nullable average and p95 values. A missing phase may use a point-stream average with a null p95. Point fallback retains only sums and counts; it never retains an unbounded duration array, so request-duration p95 is omitted when the export cannot provide it.

Metric ingestion accepts one through 100 already-windowed samples, matching the load producer's maximum batch size. Before any database admission begins, the focused traffic-metric ingestion service reserves one of at most ten accepted/queued batches per process and serializes the admitted batches so only one performs Redis work at a time; a newer process-capacity overflow batch remains acknowledge-and-drop and never waits for a database connection or row lock. Missing runs return canonical `404 resource_not_found`; terminal, draining, traffic-terminal, or reset-fenced runs return `409 traffic_report_rejected`, with the exact lifecycle or fence cause retained in structured details and the request body's correlation ID. For each admitted queue slot, the ingestion service opens a PostgreSQL transaction, locks the durable run row, checks its demo and traffic lifecycle, and holds that row lock through the bounded Redis retention/publication operation. Reset or terminalization therefore cannot invalidate an admitted batch through an API-owned PostgreSQL check-then-write race. Reset also installs a private run-scoped Redis fence before aborting traffic. Each queued batch uses at most two Redis `EVAL` commands rather than one round trip per sample. The Redis-backed dashboard traffic-metric store owns both commands: the first atomically fence-checks and appends/trims/expires the bounded recovery samples, so a fence or retention failure rejects ingestion. Only after retention succeeds does the ingestion service generate, validate, and serialize one distinct dashboard event per attempted sample, warning and continuing past invalid events. The store's second command fence-checks again and attempts every valid payload in one bounded batch with an isolated `redis.pcall(PUBLISH, ...)` per payload. Its typed, indexed result lets the ingestion service warn only for an individually failed metric while proving later payloads were still attempted. Rejection of the whole publication command remains advisory and conservatively warns for every payload whose transport outcome is unknown; neither publication failure mode fails an already-retained request or stops later queued batches. There is no atomic or distributed transaction across PostgreSQL and Redis: the PostgreSQL transaction deliberately holds the run row lock during Redis work to serialize API-owned lifecycle transitions, while the Redis fence remains the cross-system reset backstop. `clearRun(runId)` atomically retains the fence and deletes only that run's metric list. An out-of-band Redis fence can still win between retention and publication, in which case publication is suppressed; no later admitted batch can publish or recreate the projection. Unrelated run metrics, immutable summaries, inventory, and SSE connections are untouched.

The observed throughput retains the reserved metric name `traffic.scheduled_request_rate` for contract compatibility but uses unit `requests_per_second`; it is not the configured steady-arrival target. Production uses the default shared one-second producer window. The watch surface names that width, labels throughput `Observed HTTP request rate`, and renders it as `requests/s`. It gives that rate, window mean latency, and window failure rate equal rank. A request-rate point with any older/raw unit is not presented as observed.

For protocol-baseline work, the existing runtime load smoke accepts the opt-in `--dashboard-delivery-baseline` flag. It establishes the canonical Redis subscription and one SSE client, drains the first complete SSE setup frame, then opens one shared fixed 30-second gate immediately before starting the seeded `preview-1k` preset. The start request consumes part of that window; callbacks before the gate or at/after its deadline are excluded, so asynchronous shutdown cannot change the snapshot. The gate counts the Redis producer channel before API fan-out, complete SSE frames/data messages at the connected client, distinct schema-validated start scope identities, legacy contract-valid messages at Task 36's historical comparison boundary, and separately exact-schema projection frames plus same-run attribution. It rejects projection delivery above the one-second cadence/scoped envelope or at/above raw-event volume. The same path retains Task 37's at-most-six matching active/draining recovery reads, 500 ms apart, and reports the largest serialized projection with sample count and occupancy. This is bounded measurement instrumentation, not another load harness or transport. Task 36's legacy baseline, Task 37's size decision, and Task 38's cadence result are recorded in their respective working records.

k6 stdout is consumed as bounded newline framing with a 64 KiB default maximum line length. Split chunks and a final unterminated line are preserved; an oversized line is discarded through its next newline. A separate strict 256 KiB byte tail supports opportunistic summary recovery without retaining raw stdout indefinitely. Consumption is serialized with metric forwarding. The metric batcher permits one send at a time, bounds pending samples to ten batches by default, and drops/reports the newest sample on overflow. Process completion waits for stdout drain, final-window flush, all active/final metric batches, and terminal summary ingestion before sending lifecycle completion.

k6 stderr is framed into logical lines independently of stream chunks. Completion diagnostics retain only the newest 50 lines, truncate each retained line to 500 characters, and record observed, retained, and truncated counts. The same typed diagnostic snapshot records the exact resolved executor/VU plan, k6 version, CPU/file-descriptor facts, and best-effort Linux TCP settings. Probe failures yield null facts and do not fail a run.

The k6 child-process supervisor owns one explicit execution lifecycle (`idle`, `starting`, `running`, `stopping`, `exited`) from accepted spawn work through stream disposition, observed close, and temporary work-directory removal. It publishes starting run identity before asynchronous work-directory setup, so an accepted cancellation can prevent spawn. Exact-run abort, orchestrator shutdown, natural exit, and executing-journal publication failure converge on that owner. Cancellation has one end-to-end runtime setting, `K6_CANCELLATION_TIMEOUT_MS`, with a 10,000 ms default and a validated 15,000 ms maximum; graceful stopping and forced termination divide that budget internally, but their signal and timer sequence is not an external contract. Abort acknowledgement waits for observed child exit/reap, not in-flight metric transmission, summary reading, completion persistence/delivery, or work-directory cleanup. Cancellation shutdown additionally joins the supervisor's non-rejecting stream/work-directory disposition after confirmed reap without waiting for discarded metric work. Natural-completion shutdown instead lets the supervisor finish stdout draining, terminal metric aggregation, and summary ingestion, waits for the coordinator to persist the produced report, releases supervisor-owned work-directory cleanup, and then joins the coordinator's existing bounded delivery attempt. The supervisor produces that completion result but does not persist it or send/retry the API completion request.

Each internal metric or completion request has a fresh five-second deadline by default. Metric production failures and API admission rejections remain best-effort from the load orchestrator's perspective: they do not fail k6 traffic, even though the API now returns a correlated non-success instead of acknowledging stale output. Completion delivery has one serialized attempt in flight and retries the same durable record after `COMPLETION_DELIVERY_RETRY_INTERVAL_MS`, 5,000 ms by default and at most 60,000 ms. Every attempt receives a fresh request deadline and abort signal. Shutdown cancels the scheduled retry and joins only an existing bounded attempt, so startup, normal completion, and shutdown cannot create competing sends. After API acceptance, the journal moves to `completed` only when one serialized conditional write still finds the same run and immutable report; changed or conflicting evidence is not overwritten. A timeout, non-success, malformed/mismatched acknowledgement, or stale/conflicting completion therefore remains unacknowledged rather than being falsely marked `completed`.

The API allows only one current demonstration run, but `/dashboard/recovery` is not limited to process-local memory. Without a known-scope hint, recovery resolves one durable `starting`, `active`, or `draining` row from `demo_runs` once and uses that selection for every run-owned read. With a complete known-scope hint, the same query still prefers that current run and otherwise may select only the exact known run as a terminal fallback. It returns the run's frozen `configSnapshot` so the dashboard can restore the accepted configuration panel after refresh or reconnect. With neither a current nor requested known run, `scope` is null and inventory, business outcome, consistency lag, completion outcomes, and traffic metrics remain empty/null; recovery never substitutes a catalog offer or unrelated terminal-history row. Queue and ERP remain independently readable global health projections. The load orchestrator owns only traffic execution (`starting`, `active`, `succeeded`, or `failed`); the API maps successful traffic completion to demo-run `draining` and owns final `completed` or `failed` transitions. Terminal dashboard states are sticky for the same run, and finalized recovery timestamps come only from API-owned finalization. Persisted run summaries are immutable historical records; they are not promoted into live recovery state when no current or explicitly known run is selected.

The load orchestrator reports `transportAttemptCounts` as the single report and journal object for the five transport totals, and the API persists that same canonical object. HTTP evidence contains response outcomes and timing only; delivery evidence contains traffic mode, mode-specific plan dimensions, completed/dropped iteration diagnostics, and the API-derived quality status. One shared pure contract helper derives the buyer-spike or steady-arrival execution plan from the frozen accepted snapshot; script generation and API completion admission both use it. Completion admission requires the canonical planned count to match that execution plan, both canonical transport equations to hold, mode-specific delivery identity (buyer count or rate/duration/VUs) to agree with the accepted run, and runner start/completion timestamps to be coherent. These equations reject overshoot instead of assigning it a delivery status. If the API already recorded `trafficStartedAt`, the runner-reported start must match exactly; otherwise it cannot precede the required API-owned run `startedAt`. A legitimate completion that beats the activation compare-and-set supplies the durable `trafficStartedAt`; the later start acknowledgement still loses its guarded update and cannot resurrect the run. The API derives delivery status once when admitting the current completion: zero `unstartedRequests` is `complete`; unstarted ratios through 1% are `warning`, through 5% are `degraded`, and larger shortfalls are `failed`. Persisted finalization and history readers require that current status and all current transport and diagnostic fields without rewriting old names, supplying missing persisted fields, or accepting contradictory values. Completed and dropped iterations remain diagnostic evidence and do not replace the transport equations.

The first validated completion obtains a PostgreSQL row lock, verifies the active/starting traffic lifecycle, inserts the immutable finalization evidence, and claims `draining` in one transaction. Exact semantic redelivery may re-drive pending enrichment and finalization, including after terminal summary persistence. A conflicting duplicate returns `409 traffic_report_rejected` with mismatch field/expected/actual details before it can close admission, enrich, or finalize using different evidence. API-owned enrichment fields are excluded from the immutable orchestrator-evidence comparison, and caller-supplied delivery-quality labels are rejected by the real completion contract; classification remains API-owned. A missing run returns `404 resource_not_found`, while a first completion for the wrong lifecycle returns `409 traffic_report_rejected` with lifecycle details.

Within API-owned finalization, successful k6 execution and exact request delivery are distinct. A run can complete with `warning` or `degraded` traffic delivery quality when business invariants pass, while major under-delivery can finalize the run as failed with `traffic_delivery_major_shortfall` after drainable accepted work settles. Unexpected checkout responses are a separate correctness failure, `traffic_outcome_unexpected_responses`, and take precedence over delivery shortfall and a generic traffic-process failure after business drain.

Finalization also reconciles the typed k6 accepted-response counter with run-scoped secured reservations and orders in PostgreSQL. A fully evidenced duplicate buyer spike normalizes response pairs to unique expected accepts; incomplete or mismatched delivery never applies that normalization. Missing durable evidence drains until `accepted_response_accounting_timeout`. Coherent durable reservation/order counts above the k6 counter remain authoritative and complete with a structured `traffic_outcome_counter_underreported` warning in load-run diagnostics. Reconciliation is read-only and terminal writing remains atomic and idempotent.

API startup does not terminalize `starting` or `active` rows merely because the API process restarted; traffic ownership lives in the load orchestrator's durable journal, and the explicit startup reconciliation owner periodically resumes the same start. Durable `draining` runs remain draining while that owner independently closes Redis admission and completes pending enrichment at startup. The focused traffic-completion service owns immutable report acceptance and the handoff to `DemoRunFinalizationService`; the request-facing run-lifecycle service owns starts only. The dedicated pending-persistence recovery owner starts separately and alone discovers deadline-bounded run-scoped pages and schedules their retries. Drain timeout never permits a terminal transition while pending Redis state is nonzero or unreadable. Later owner passes and restarts continue bounded idempotent recovery until pending state reaches zero; an exhausted hold remains visibly unresolved and keeps the run draining until explicit reset. Only after convergence does finalization capture fresh inventory and write the immutable summary. The shared terminal summary writer is used by normal finalization, admin recovery, traffic-start failure, and initialization-failure paths so every terminal demo run has one summary-backed history record.

Historical run summaries are available through the separate Run History surface. Public users can read paginated summaries, and authenticated admins can delete one, selected visible summaries, or all summaries with explicit confirmation.
