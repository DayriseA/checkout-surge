1. Fly.io in two minutes

Fly.io rents small virtual machines in datacenters around the world, and starts or stops them in seconds through an API. You pay mostly for the time they run. Everything else (networking, secrets, disks) is organized around those machines.

The account space: organization
The top-level container that owns apps, billing, tokens and one private network. This project uses one organization that holds only the demo's apps (named in Hosted Operations).
A named group of machines: app
An app is not a running thing by itself. It is a name plus shared resources: its Machines, secrets, public IP addresses, certificates and volumes. Every flyctl command names its app with -a.
A small virtual computer: Machine (a Firecracker microVM)
A lightweight virtual machine that runs a container image. Each Machine has an ID, a config (image, size called guest, environment variables, files, services, metadata) and a state such as started or stopped. A stopped Machine starts fast because its root filesystem is already assembled on its server. A Machine can also run several containers side by side (a multi-container Machine), which is how the core is packaged.
Where it runs: region and host
A region is a datacenter location with a three-letter code. A host (Fly also says worker) is one physical server in a region. Every Machine lives on exactly one host. When creating a Machine you can give a prioritized list such as <region>,eu: Fly tries the first region, then any region of the eu group.
What it runs: image and registry
Code ships as a container image. Images are pushed to Fly's registry (registry.fly.io/<app>:<label>) and a Machine config points at one image reference.
A disk that survives restarts: volume
A slice of an NVMe drive on the same physical server as its Machine. One volume attaches to one Machine. Because the disk is physically in that server, the volume pins its Machine to that host: the Machine cannot start anywhere else. Fly takes daily snapshots of volumes by default.
The private network: 6PN
All Machines of an organization share a private IPv6 network (a WireGuard mesh). Each Machine gets a private address, visible to it as FLY_PRIVATE_IP, and names under .internal resolve to those addresses. This traffic goes Machine to Machine directly, without Fly Proxy.
The front door: Fly Proxy and public IPs
Public traffic reaches Fly's edge on Anycast addresses (shared IPv4, routed by hostname, and a dedicated IPv6), where Fly Proxy terminates TLS and forwards each request to a Machine whose config declares a service for that port. Nothing is exposed without a service. Fly Proxy can also autostart a stopped Machine when a request arrives and autostop it when traffic is gone. Every app gets a <app>.fly.dev hostname.
Passwords and keys: secrets
Each app has an encrypted vault. Fly injects the secrets as environment variables when a Machine boots, so a Machine sees a new value only at its next start. flyctl secrets set --stage stores a value without restarting anything.
Why flyctl secrets list shows "Staged". Its status column follows Fly releases, which fly deploy or fly secrets deploy create. This project deploys through the Machines API and never makes a release, so every secret shows Staged, always. That is normal: compare the DIGEST column to see a change, and never run flyctl secrets deploy (Hosted Operations).
Who may act: tokens
Programs authenticate to Fly with a token sent as Authorization: Bearer …. A deploy token covers one app; an organization token covers every app of the organization; flyctl auth login gives you a personal session. Tokens can be listed and revoked with flyctl tokens.
What it costs: billing
A started Machine is billed per second, by size. A stopped Machine costs only the storage of its root filesystem. A volume is billed for its provisioned size whether its Machine runs or not; snapshots are billed by the data they store. Shared IPv4 and IPv6 addresses are free; outbound traffic is metered. Prices are on Fly's pricing page; this project's own observations are in Reference Runtime Measurements.

Two dashboard messages that look alarming and are not

"Suspended" on an app. In the dashboard, an app whose Machines are all stopped is shown as Suspended. It only means nothing is running; it is not an administrative suspension (a Fly staff answer on the community forum). Here it is the normal resting state of the core and runner apps, and of the gate app between visits. Do not confuse it with the Machine state suspended (a Machine paused with its memory saved to disk), which this project does not use.

"Run at least 2 machines". Fly recommends at least two Machines per app so that one failed host does not take the app down (App availability). The dashboard's banner repeats that general advice. It does not fit this demo, by design:

  • The core is one authoritative Machine whose data is disposable (HD-05). When its host fails, the gate recreates a fresh core elsewhere (HD-34). A second core would double the cost and need data replication, and one API process stays the sole maintenance authority (HD-51).
  • The runner exists to run one load test at a time and is recreated on another host when its own fails (HD-17).
  • The gate holds no state and sleeps between visits (HD-31); the guard is a one-shot scheduled job.

The trade-off is deliberate: a demo used a few hours per month accepts a slower visit after a host failure in exchange for near-zero idle cost. The banner can be ignored.

1. Fly.io en deux minutes

Fly.io loue de petites machines virtuelles dans des centres de données du monde entier, et les démarre ou les arrête en quelques secondes par une API. On paie surtout le temps où elles tournent. Tout le reste (réseau, secrets, disques) s'organise autour de ces machines.

L'espace du compte : organization (organisation)
Le conteneur de plus haut niveau, qui possède les apps, la facturation, les jetons et un réseau privé. Ce projet utilise une organisation qui ne contient que les apps de la démo (nommée dans Hosted Operations).
Un groupe nommé de machines : app
Une app ne tourne pas en elle-même. C'est un nom plus des ressources partagées : ses Machines, ses secrets, ses adresses IP publiques, ses certificats et ses volumes. Chaque commande flyctl désigne son app avec -a.
Un petit ordinateur virtuel : Machine (une microVM Firecracker)
Une machine virtuelle légère qui exécute une image de conteneur. Chaque Machine a un identifiant, une config (image, taille appelée guest, variables d'environnement, fichiers, services, métadonnées) et un état comme started (démarrée) ou stopped (arrêtée). Une Machine arrêtée redémarre vite, car son système de fichiers racine est déjà assemblé sur son serveur. Une Machine peut aussi faire tourner plusieurs conteneurs côte à côte (multi-container Machine) : c'est ainsi qu'est empaqueté le core.
Où elle tourne : region (région) et host (hôte)
Une région est un centre de données identifié par un code de trois lettres. Un hôte (Fly dit aussi worker) est un serveur physique dans une région. Chaque Machine vit sur un seul hôte. À la création d'une Machine, on peut donner une liste par ordre de préférence comme <région>,eu : Fly essaie la première région, puis n'importe quelle région du groupe eu.
Ce qu'elle exécute : image et registry (registre)
Le code est livré sous forme d'image de conteneur. Les images sont poussées dans le registre de Fly (registry.fly.io/<app>:<étiquette>) et la config d'une Machine désigne une référence d'image.
Un disque qui survit aux redémarrages : volume
Une portion d'un disque NVMe sur le même serveur physique que sa Machine. Un volume se rattache à une seule Machine. Comme le disque est physiquement dans ce serveur, le volume épingle sa Machine à cet hôte : elle ne peut démarrer nulle part ailleurs. Par défaut, Fly prend un instantané (snapshot) quotidien des volumes.
Le réseau privé : 6PN
Toutes les Machines d'une organisation partagent un réseau privé IPv6 (un maillage WireGuard). Chaque Machine reçoit une adresse privée, qu'elle voit dans FLY_PRIVATE_IP, et les noms en .internal se résolvent vers ces adresses. Ce trafic va directement de Machine à Machine, sans passer par Fly Proxy.
La porte d'entrée : Fly Proxy et IP publiques
Le trafic public arrive à la périphérie de Fly sur des adresses Anycast (IPv4 partagée, routée par nom d'hôte, et IPv6 dédiée). Fly Proxy y termine le TLS et transmet chaque requête à une Machine dont la config déclare un service pour ce port. Rien n'est exposé sans service. Fly Proxy peut aussi démarrer automatiquement (autostart) une Machine arrêtée quand une requête arrive, et l'arrêter (autostop) quand le trafic cesse. Chaque app reçoit un nom <app>.fly.dev.
Mots de passe et clés : secrets
Chaque app a un coffre chiffré. Fly injecte les secrets comme variables d'environnement au démarrage d'une Machine : une Machine ne voit une nouvelle valeur qu'à son prochain démarrage. flyctl secrets set --stage enregistre une valeur sans rien redémarrer.
Pourquoi flyctl secrets list affiche « Staged ». Sa colonne de statut suit les releases de Fly, que créent fly deploy ou fly secrets deploy. Ce projet déploie par l'API Machines et ne crée jamais de release : chaque secret reste Staged, toujours. C'est normal : comparez la colonne DIGEST pour voir un changement, et ne lancez jamais flyctl secrets deploy (Hosted Operations).
Qui a le droit d'agir : tokens (jetons)
Les programmes s'authentifient auprès de Fly avec un jeton envoyé dans Authorization: Bearer …. Un deploy token (jeton de déploiement) couvre une app ; un organization token (jeton d'organisation) couvre toutes les apps de l'organisation ; flyctl auth login ouvre une session personnelle. flyctl tokens liste et révoque les jetons.
Ce que ça coûte : facturation
Une Machine démarrée est facturée à la seconde, selon sa taille. Une Machine arrêtée ne coûte que le stockage de son système de fichiers racine. Un volume est facturé pour sa taille provisionnée, que sa Machine tourne ou non ; les instantanés sont facturés selon les données stockées. Les IPv4 partagées et les IPv6 sont gratuites ; le trafic sortant est mesuré. Les prix sont sur la page de tarifs de Fly ; les observations du projet sont dans Reference Runtime Measurements.

Deux messages du tableau de bord, inquiétants en apparence seulement

« Suspended » sur une app. Dans le tableau de bord, une app dont toutes les Machines sont arrêtées apparaît Suspended. Cela veut seulement dire que rien ne tourne ; ce n'est pas une suspension administrative (réponse d'un membre de l'équipe Fly sur le forum). Ici, c'est l'état de repos normal des apps core et runner, et de l'app gate entre deux visites. À ne pas confondre avec l'état de Machine suspended (Machine mise en pause avec sa mémoire sauvegardée sur disque), que ce projet n'utilise pas.

« Run at least 2 machines ». Fly recommande au moins deux Machines par app, pour qu'un hôte en panne ne fasse pas tomber l'app (App availability). Le bandeau du tableau de bord répète ce conseil général. Il ne convient pas à cette démo, par choix :

  • Le core est une Machine unique qui fait autorité, et ses données sont jetables (HD-05). Quand son hôte tombe, la gate recrée un core neuf ailleurs (HD-34). Un second core doublerait le coût et demanderait de répliquer les données, et un seul processus API reste l'unique autorité de maintenance (HD-51).
  • Le runner sert à un test de charge à la fois, et il est recréé sur un autre hôte quand le sien tombe (HD-17).
  • La gate ne garde aucun état et dort entre les visites (HD-31) ; le guard est une tâche planifiée ponctuelle.

Le compromis est voulu : une démo utilisée quelques heures par mois accepte une visite plus lente après une panne d'hôte, en échange d'un coût quasi nul au repos. Le bandeau peut être ignoré.

2. Machine lifecycle

A Machine moves between a few lasting states. The Machines API (https://api.machines.dev) and flyctl machine … drive every move.

created→ started⇄ stopped→ destroyed
StatePlain meaning
createdThe Machine exists but has never been started.
startedRunning and reachable. Billed per second.
stoppedExited, on its own or on request. It stays on its host with its root filesystem and can start again.
destroyedDeleted for good. A new Machine gets a new ID.
starting, stopping, replacing, …Short transitions. replacing means an update is being applied; the gate shows its "updating" page then.

Prepared, not started: skip_launch

Creating or updating a Machine with skip_launch writes its config without booting it. The deploy script uses it for every Machine, so a deploy never starts anything, then waits for the Machine to settle in stopped (HD-24). One exception: the guard, because a scheduled Machine created or updated with skip_launch was observed never to run on schedule again (HD-41). flyctl machine update --skip-start sets the same flag.

Why a stopped Machine reserves nothing

A stopped Machine keeps its place on its host (its root filesystem stays there, which is why it starts fast), but no CPU or memory is held for it. Others can fill the host meanwhile. So Fly can refuse a start for lack of capacity, and can refuse an update that needs more room, either with an error or by reverting it after accepting it. This project has seen both: refused starts (HD-17, HD-34) and refused or reverted updates (HD-55, HD-56).

A Machine without a volume can simply be recreated on a host with room. A Machine with a volume cannot move, because its disk is in that server: this is why the core, when its host is full or dead, is recreated fresh and empty elsewhere instead.

Locks: leases, nonces and TTLs

A lease is a temporary lock on changing one Machine, so that two programs do not modify it at once. Taking a lease returns a nonce, a random value that proves you hold it; the holder sends it in the fly-machine-lease-nonce header with each change. Fly fails an update sent without the nonce while the Machine is leased; the project observed that a stop or destroy sent without it waits until the lease ends, then runs (HD-37).

Every lease has a TTL (time to live, in seconds) and expires on its own. If its holder dies, the lease stays until then: flyctl machine leases view shows it, and flyctl machine leases clear frees it, only when you know the holder is gone (Hosted Operations). In this project, leases are advisory coordination between our own programs, not a security boundary; who holds which lease, and what the others do when they meet it, is in Hosted Runtime. The TTLs are set in infra/fly/deploy.mjs and in the gate and API code.

Is the server reachable: host status

Each Machine reports host_status: ok, unreachable (the Machines API cannot reach the host) or unknown. When it is not ok, Fly returns only part of the config (metadata can be missing), grants no usable lease, and changes will probably fail. The gate, the API and the guard therefore act on such a Machine without a lease, and never destroy one they cannot identify (HD-34, HD-47, HD-42).

Labels: metadata

A Machine carries key–value metadata. The project finds its Machines by role (core, runner, …), never by a hardcoded ID, and uses recreate=requested as the recreation mark on the core.

Cron-like Machines: scheduled Machines

A Machine with a schedule (hourly, daily, weekly or monthly) is started by Fly's scheduler at roughly that interval, counted from its creation, not at a precise time. It runs, exits, and waits stopped for the next interval. The guard is one (infra/fly/gate/guard-machine.json).

2. Cycle de vie d'une Machine

Une Machine passe par quelques états durables. L'API Machines (https://api.machines.dev) et flyctl machine … pilotent chaque passage.

created→ started⇄ stopped→ destroyed
ÉtatEn clair
createdLa Machine existe mais n'a jamais démarré.
startedElle tourne et répond. Facturée à la seconde.
stoppedElle s'est arrêtée, d'elle-même ou sur demande. Elle reste sur son hôte avec son système de fichiers racine et peut redémarrer.
destroyedSupprimée définitivement. Une nouvelle Machine reçoit un nouvel identifiant.
starting, stopping, replacing, …Transitions brèves. replacing signifie qu'une mise à jour s'applique ; la gate affiche alors sa page « mise à jour ».

Préparée, pas démarrée : skip_launch

Créer ou mettre à jour une Machine avec skip_launch écrit sa config sans la démarrer. Le script de déploiement l'utilise pour chaque Machine, si bien qu'un déploiement ne démarre jamais rien, puis il attend que la Machine se pose en stopped (HD-24). Une exception : le guard, car une Machine planifiée créée ou mise à jour avec skip_launch n'a plus jamais été lancée par le planificateur (HD-41). flyctl machine update --skip-start pose le même drapeau.

Pourquoi une Machine arrêtée ne réserve rien

Une Machine arrêtée garde sa place sur son hôte (son système de fichiers racine y reste, d'où son démarrage rapide), mais aucun processeur ni aucune mémoire ne lui est réservé. D'autres peuvent remplir l'hôte entre-temps. Fly peut donc refuser un démarrage faute de capacité, et refuser une mise à jour qui demande plus de place, soit par une erreur, soit en l'annulant après l'avoir acceptée. Le projet a vu les deux : démarrages refusés (HD-17, HD-34) et mises à jour refusées ou annulées (HD-55, HD-56).

Une Machine sans volume peut simplement être recréée sur un hôte qui a de la place. Une Machine avec volume ne peut pas bouger, car son disque est dans ce serveur : c'est pourquoi le core, quand son hôte est plein ou mort, est recréé neuf et vide ailleurs.

Verrous : leases, nonces et TTL

Un verrou (lease) est un verrou temporaire sur la modification d'une Machine, pour que deux programmes ne la modifient pas en même temps. Prendre un verrou renvoie un nonce, une valeur aléatoire qui prouve qu'on le détient ; le détenteur l'envoie dans l'en-tête fly-machine-lease-nonce à chaque modification. Fly fait échouer une mise à jour envoyée sans le nonce tant que la Machine est verrouillée ; le projet a constaté qu'un arrêt ou une suppression envoyés sans lui attendent la fin du verrou, puis s'exécutent (HD-37).

Chaque verrou a un TTL (durée de vie, en secondes) et expire de lui-même. Si son détenteur meurt, le verrou reste jusque-là : flyctl machine leases view l'affiche, et flyctl machine leases clear le libère, seulement quand on sait le détenteur disparu (Hosted Operations). Dans ce projet, les verrous coordonnent nos propres programmes ; ce ne sont pas une barrière de sécurité. Qui tient quel verrou, et ce que font les autres quand ils le rencontrent, est décrit dans Hosted Runtime. Les TTL sont fixés dans infra/fly/deploy.mjs et dans le code de la gate et de l'API.

Le serveur répond-il : host status

Chaque Machine indique host_status : ok, unreachable (l'API Machines ne joint pas l'hôte) ou unknown. Quand il n'est pas ok, Fly ne renvoie qu'une partie de la config (les métadonnées peuvent manquer), n'accorde aucun verrou utilisable, et les modifications échoueront probablement. La gate, l'API et le guard agissent donc sur une telle Machine sans verrou, et ne suppriment jamais une Machine qu'ils ne savent pas identifier (HD-34, HD-47, HD-42).

Étiquettes : metadata (métadonnées)

Une Machine porte des métadonnées clé–valeur. Le projet retrouve ses Machines par leur role (core, runner, …), jamais par un identifiant codé en dur, et utilise recreate=requested comme marque de recréation du core.

Des Machines façon cron : scheduled Machines (Machines planifiées)

Une Machine dotée d'un schedule (hourly, daily, weekly ou monthly) est démarrée par le planificateur de Fly à peu près à cet intervalle, compté depuis sa création, pas à heure précise. Elle tourne, se termine, et attend arrêtée l'intervalle suivant. Le guard en est une (infra/fly/gate/guard-machine.json).

La démo tourne au plus quelques heures par mois : chaque Machine dort quand elle ne sert pas et se réveille à la demande. L'hébergement exécute les mêmes images de production que la topologie locale, plus la configuration Fly sous infra/fly/ (Runtime Topology).

The request path

  1. The visitor opens the gate's fly.dev URL. Fly Proxy receives it on the gate app's public IPs, terminates TLS, and starts the gate Machine if it sleeps.
  2. The gate checks the core's state through the Machines API and probes the core's Caddy. While the core is not ready, the gate answers every URL with its own page (start button, booting, updating, relocating, …) and status 503 (pages).
  3. Once the core is ready, the gate relays every request (pages, API, live updates) to the core's Caddy at its 6PN address. The core has no public address of its own.
  4. During a run, the runner sends the k6 burst straight to the core's API over 6PN; it never crosses the gate.

Sleeping and waking

  • The gate uses Fly Proxy's autostart and autostop (its services in infra/fly/gate/machine.json): a visit wakes it, and it stops once traffic is gone. The first request to a sleeping gate waits a few seconds.
  • The core never starts on its own. Its start page has a button that sends a POST; the gate then takes the core's lease, starts the core, releases the lease and redirects the visitor. Bots that only fetch pages cannot wake it (waking the core).

The idle stop

The core's API stops its own Machine once there is no run in progress and no counted visitor activity for the idle period (HD-20). Every page shows a countdown with a "stay awake" button. Health checks, status polling and open live connections do not count. If the idle stop ever fails, the guard stops a core awake beyond its cap. The idle period is coreIdleStopAfterMs in apps/api/src/services/core-idle-stop.ts; the guard's thresholds are defaultGuardThresholds in apps/gate/src/guard.ts.

The runner, once per run

The runner stays stopped between runs (HD-07). For each run, the API updates it with the run's size and the core's current 6PN address, starts it from a fresh boot, and waits until it is ready. When the run ends, the API asks the runner to exit, with a Fly stop only as a fallback. Before sending any traffic, the API checks that the runner runs the same commit as itself (version handshake).

Recovery and relocation

  • Core recovery (Hosted Runtime). When a wake keeps failing for capacity or a dead host, when the core's host is not ok, when the core carries the recreation mark, or when no core exists, the gate creates a new empty volume and a new core Machine from the core config the last deploy left in the gate Machine. Placement tries the home region, then any region of eu. The new core installs fresh (migrations and seed on an empty database: run history and admin edits are lost). The old core is destroyed only once the new one is healthy. Visitors see the relocating page, or the fresh-install page for a requested recreation.
  • Runner relocation (Hosted Runtime). A refused start is retried in place, then the runner is recreated from the deployed runner config; a refused or reverted update recreates it at once. The new runner goes to the core's region first, then eu. At each run start, a runner in another region than the core is moved back (HD-36).

The home region is named in infra/fly/deploy.mjs and apps/gate/src/core-recovery.ts.

Deploys

One script, infra/fly/deploy.mjs, deploys one commit to the three apps. It runs from the workstation (node infra/fly/deploy.mjs all) and from GitHub Actions on every push to main (HD-49). The steps:

  1. Build each image on Fly's remote builder, label it with the commit, push it to the app's registry.
  2. Wait for an awake core to go to sleep (a visitor's session is never cut, unless you pass --force), take the lease, and read the core again under it (HD-45).
  3. Update the runner, then the core, with their full configs from infra/fly/<app>/ and skip_launch. Because whole configs are sent, a change made by hand on Fly is reverted by the next deploy. Then update the gate and the guard.
  4. Leave copies for recovery: the runner config inside the core's API container, the core config inside the gate Machine.
  5. Compare the core's and the runner's versions, even after a failed step, and fail on a mismatch (HD-46).
  • Same commit again. A runner that already has the config to deploy is left untouched, even during a run. The rest still happens: a documentation-only push to main rebuilds and waits for the core to sleep, so batch such commits.
  • --fresh-core and the recreation mark. For a change the existing core data cannot use, deploy with --fresh-core: the core gets the recreate=requested metadata, and the next visitor wake recreates it fresh. Later deploys carry the mark over, so only a wake clears it (HD-48). A deploy whose core update is refused by a full host sets the same mark by itself (HD-56); the version check then counts the core at the version waiting in the gate.
  • One at a time. CI never cancels a running deploy, and a workstation deploy must not overlap a CI one. A deploy killed while it holds a lease leaves that lease until it expires.

Commands and failure messages: Hosted Operations.

Secrets and tokens

  • App secrets (passwords, session and cookie secrets, the control token shared by the core and the runner) live in each app's vault, and each core container lists only the ones it needs in infra/fly/core/machine.json. The full table is in Hosted Runtime.
  • Machines API tokens inside Machines are app-scoped deploy tokens: the gate and the guard hold core and runner tokens; the core's API holds a runner token and a core token for its own idle stop. No personal or organization token ever goes into a Machine. Deploy access can read an app's secrets, so a compromised gate means control of the core and runner apps; the exposure is financial (HD-26).
  • The CI token is one organization deploy token stored as the GitHub repository secret FLY_API_TOKEN (HD-50). It has an expiry and nothing warns before it: renew it ahead of time.
  • Rotation follows one pattern: stage the new value with flyctl secrets import --stage, let each holder restart (Machines read secrets only at start), check it works, then revoke the old token. Never print a value. Step by step: Hosted Operations.

Le chemin d'une requête

  1. Le visiteur ouvre l'URL fly.dev de la gate. Fly Proxy la reçoit sur les IP publiques de l'app gate, termine le TLS, et démarre la Machine gate si elle dort.
  2. La gate lit l'état du core par l'API Machines et sonde le Caddy du core. Tant que le core n'est pas prêt, la gate répond à toute URL par sa propre page (bouton de démarrage, démarrage en cours, mise à jour, relocalisation, …) avec le statut 503 (pages).
  3. Une fois le core prêt, la gate relaie chaque requête (pages, API, mises à jour en direct) vers le Caddy du core, à son adresse 6PN. Le core n'a pas d'adresse publique.
  4. Pendant un run, le runner envoie la rafale k6 directement à l'API du core par le 6PN ; elle ne passe jamais par la gate.

Sommeil et réveil

  • La gate utilise l'autostart et l'autostop de Fly Proxy (ses services dans infra/fly/gate/machine.json) : une visite la réveille, et elle s'arrête quand le trafic cesse. La première requête vers une gate endormie attend quelques secondes.
  • Le core ne démarre jamais seul. Sa page de démarrage a un bouton qui envoie un POST ; la gate prend alors le verrou du core, le démarre, rend le verrou et redirige le visiteur. Les robots qui ne font que lire des pages ne peuvent pas le réveiller (réveil du core).

L'arrêt sur inactivité

L'API du core arrête sa propre Machine quand il n'y a ni run en cours ni activité visiteur comptée pendant la durée d'inactivité (HD-20). Chaque page affiche un compte à rebours avec un bouton « rester éveillé ». Les sondes de santé, l'interrogation du statut et les connexions en direct ouvertes ne comptent pas. Si l'arrêt sur inactivité échoue, le guard arrête un core éveillé au-delà de son plafond. La durée d'inactivité est coreIdleStopAfterMs dans apps/api/src/services/core-idle-stop.ts ; les seuils du guard sont defaultGuardThresholds dans apps/gate/src/guard.ts.

Le runner, une fois par run

Le runner reste arrêté entre les runs (HD-07). Pour chaque run, l'API le met à jour avec la taille du run et l'adresse 6PN actuelle du core, le démarre à neuf, et attend qu'il soit prêt. À la fin du run, l'API demande au runner de se terminer ; l'arrêt par Fly ne sert qu'en secours. Avant d'envoyer du trafic, l'API vérifie que le runner exécute le même commit qu'elle (vérification de version).

Recréation et relocalisation

  • Recréation du core (Hosted Runtime). Quand un réveil échoue sans cesse faute de capacité ou d'hôte vivant, quand l'hôte du core n'est pas ok, quand le core porte la marque de recréation, ou quand aucun core n'existe, la gate crée un volume vide et une nouvelle Machine core à partir de la config du core que le dernier déploiement a laissée dans la Machine gate. Le placement essaie la région d'origine, puis n'importe quelle région de eu. Le nouveau core s'installe à neuf (migrations et seed sur une base vide : l'historique des runs et les réglages admin sont perdus). L'ancien core n'est détruit qu'une fois le nouveau en bonne santé. Les visiteurs voient la page de relocalisation, ou la page d'installation à neuf pour une recréation demandée.
  • Relocalisation du runner (Hosted Runtime). Un démarrage refusé est retenté sur place, puis le runner est recréé à partir de la config runner déployée ; une mise à jour refusée ou annulée le recrée aussitôt. Le nouveau runner va d'abord dans la région du core, puis dans eu. À chaque début de run, un runner hors de la région du core y est ramené (HD-36).

La région d'origine est nommée dans infra/fly/deploy.mjs et apps/gate/src/core-recovery.ts.

Déploiements

Un seul script, infra/fly/deploy.mjs, déploie un commit sur les trois apps. Il tourne depuis le poste de travail (node infra/fly/deploy.mjs all) et depuis GitHub Actions à chaque push sur main (HD-49). Les étapes :

  1. Construire chaque image sur le builder distant de Fly, l'étiqueter avec le commit, la pousser dans le registre de l'app.
  2. Attendre qu'un core éveillé s'endorme (la session d'un visiteur n'est jamais coupée, sauf avec --force), prendre le verrou, et relire le core sous ce verrou (HD-45).
  3. Mettre à jour le runner, puis le core, avec leurs configs complètes tirées de infra/fly/<app>/ et skip_launch. Comme la config entière est envoyée, une modification faite à la main sur Fly est annulée au déploiement suivant. Puis mettre à jour la gate et le guard.
  4. Laisser des copies pour la recréation : la config du runner dans le conteneur API du core, la config du core dans la Machine gate.
  5. Comparer les versions du core et du runner, même après une étape en échec, et échouer si elles diffèrent (HD-46).
  • Le même commit, à nouveau. Un runner qui a déjà la config à déployer n'est pas touché, même pendant un run. Le reste a bien lieu : un push sur main qui ne change que la documentation reconstruit et attend que le core dorme ; regroupez ces commits.
  • --fresh-core et la marque de recréation. Pour un changement que les données du core existant ne supportent pas, déployez avec --fresh-core : le core reçoit la métadonnée recreate=requested, et le prochain réveil par un visiteur le recrée à neuf. Les déploiements suivants conservent la marque : seul un réveil l'efface (HD-48). Un déploiement dont la mise à jour du core est refusée par un hôte plein pose lui-même cette marque (HD-56) ; la vérification de version compte alors le core à la version qui attend dans la gate.
  • Un à la fois. La CI n'annule jamais un déploiement en cours, et un déploiement depuis le poste ne doit pas chevaucher celui de la CI. Un déploiement tué alors qu'il tient un verrou laisse ce verrou jusqu'à son expiration.

Commandes et messages d'échec : Hosted Operations.

Secrets et jetons

  • Les secrets des apps (mots de passe, secrets de session et de cookie, jeton de contrôle partagé par le core et le runner) vivent dans le coffre de chaque app, et chaque conteneur du core ne liste que ceux dont il a besoin dans infra/fly/core/machine.json. Le tableau complet est dans Hosted Runtime.
  • Les jetons de l'API Machines dans les Machines sont des jetons de déploiement limités à une app : la gate et le guard détiennent des jetons core et runner ; l'API du core détient un jeton runner et un jeton core pour son propre arrêt sur inactivité. Aucun jeton personnel ou d'organisation n'entre jamais dans une Machine. Un accès de déploiement peut lire les secrets d'une app : une gate compromise donne le contrôle des apps core et runner ; le risque est financier (HD-26).
  • Le jeton de la CI est un jeton de déploiement d'organisation, stocké comme secret du dépôt GitHub FLY_API_TOKEN (HD-50). Il expire, et rien ne prévient avant : renouvelez-le à l'avance.
  • La rotation suit toujours le même schéma : préparer la nouvelle valeur avec flyctl secrets import --stage, laisser chaque détenteur redémarrer (les Machines ne lisent les secrets qu'au démarrage), vérifier que tout fonctionne, puis révoquer l'ancien jeton. N'affichez jamais une valeur. Pas à pas : Hosted Operations.
