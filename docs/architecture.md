# Architecture — Checkout-Surge

## Purpose

Checkout-Surge demonstrates that a Node.js service can absorb a limited-inventory checkout surge without overselling, without overwhelming a slow downstream business dependency, and without sacrificing API responsiveness. The public demo target is the `surge-10k` shape: about 10,000 synthetic buy attempts in roughly 1 second, generated by k6 against the API. The architecture is not specific to short promotional flash sales; the same pressure appears in ticket launches, product drops, presales, and other scarcity-driven purchase flows. The demo uses a mock ERP to make the downstream dependency concrete, but the same boundary could represent payment capture, fraud/risk checks, warehouse allocation, fulfillment, tax calculation, accounting, supplier APIs, or other fragile business systems. This document describes the implemented architecture.

---

## System Overview

The system is intentionally split into five independent processes:

| Component | Role |
| :-- | :-- |
| `apps/api` — Fastify API gateway | Owns the buy path: validates requests, executes the Redis reservation, enqueues work, returns immediately. |
| `apps/worker` — BullMQ worker | Owns background workflows: pulls order jobs from the queue, applies frozen run retry/admission/breaker policy, calls the downstream confirmation service, persists state transitions, and runs dispatch, ERP-result, and notification recovery workflows. |
| `apps/mock-erp` — Mock ERP / downstream business system | Simulates a legacy downstream dependency with run-supplied or fallback latency/TPS/error behavior and persists successful idempotent confirmation results. |
| `apps/load-orchestrator` — k6 wrapper | Durably owns one traffic execution at a time, triggers synthetic buyer traffic from accepted run snapshots, provides authenticated run-fenced cancellation with confirmed bounded process termination, parses k6 JSON output, streams live metrics, and retries natural completion delivery to the API until acknowledged. |
| `apps/web` — Next.js dashboard | Owns the public demo picker, current-run spectator view, admin operator surface, signed visitor-cookie issuance, hardened admin sessions, and thin server-side proxying for dashboard reads and controls. Public run budgets remain API-owned. |

The dashboard (`apps/web`) is a demo and operator surface, not a customer storefront. High-volume buyers are k6-generated synthetic API attempts, not browser sessions. Public visitors use `/` to start curated read-only presets or a bounded run-scoped `public-custom` run, then observe the active run at `/watch`. Admins use `/admin` to inspect public presets, save editable admin presets, use the persisted `Custom` scratch preset, and start runs from accepted configuration snapshots.

The watch route initializes from a server recovery snapshot and hands live ownership to a small client composition. Contract-validated SSE frames feed a pure reconciliation reducer; a separate recovery coordinator serializes authoritative reads and performs exactly one follow-up when events arrive during an in-flight recovery. The admin page validates the signed session on the server, renders only the sign-in island for anonymous visitors, and server-loads authenticated reads. Current-run, runtime-policy, preset/start, maintenance, and ERP controllers retain independent mutation state so one operation does not disable or clear unrelated features.

The reference runtime must preserve this split with separate containers for the application services. In particular, k6 belongs inside the load-orchestrator runtime image; installing k6 directly on a developer host is only a convenience path for host-native development.

The dashboard is exposed as a single browser origin in the reference runtime. HTTP dashboard reads and controls use same-origin `apps/web` routes. The web server calls the API for run lifecycle/read operations and the Mock ERP for its retained diagnostic controls; the API calls the load orchestrator after accepting a run. The API owns the browser-facing SSE stream at `/dashboard/events` and subscribes to internal Redis Pub/Sub dashboard events for live fan-out. Caddy routes `/dashboard/events` from the dashboard origin directly to the API service, while the rest of the dashboard origin remains routed to the web service. Dashboard observability stays public for the demo; admin access gates only privileged controls. Direct service ports are available through the debug override for health checks and troubleshooting, but the normal operator path does not require browser access to them.

When direct service ports are exposed for local debugging, their browser CORS allow-lists should be configured with `WEB_ORIGIN`. Leaving `WEB_ORIGIN` unset keeps wildcard development behavior, but the reference compose runtime pins it to the dashboard proxy origin.

## Dashboard Realtime Model

Dashboard realtime is a live observability path, not a command transport or an event ledger. Dashboard commands and reads continue to use HTTP routes, while the API streams browser-facing telemetry with SSE and receives internal dashboard events from Redis Pub/Sub.

The API is the only browser-facing realtime owner. API and worker services publish validated transport-neutral dashboard events to the `dashboard-events` Redis channel, and each API process keeps one shared Redis subscriber for fan-out to its connected SSE clients. Browser connections are in-memory sinks only; they do not create Redis subscriptions and the gateway does not build per-client event backlogs. If a client write fails or applies backpressure, that SSE connection is closed and the browser relies on native `EventSource` reconnect.

SSE events are best-effort live hints. Publish failures are logged but must not break checkout, metric ingestion, worker processing, or demo controls. Redis Pub/Sub gaps, page refreshes, tab resumes, and stream reconnects are recovered through `/dashboard/recovery`, which returns the latest dashboard state rather than missed stream events. The dashboard discards live events received while a recovery snapshot is in flight so stale realtime data cannot overwrite the fresh baseline, then runs a follow-up recovery if anything arrived during that window. A fresh `run.started`, or a fresh nonterminal `run.updated` whose start time proves it is newer than the displayed run, establishes a new browser scope: the dashboard installs that run snapshot, immediately clears inventory, traffic metrics, queue, ERP, business outcome, consistency lag, and recent completion projections, and requests serialized authoritative recovery. Same-run lifecycle updates retain those projections. Foreign, terminal, timestamp-stale, and older-start lifecycle events cannot replace the displayed run. A received in-scope terminal run event also triggers one final recovery for that run ID so final inventory, queue, ERP, and outcome projections settle from backend truth. The system intentionally does not maintain SSE event IDs, `Last-Event-ID` cursors, replay buffers, Redis Streams, or durable admin event logs for this demo surface.

Fresh Redis reservation decisions and successful API-owned BullMQ handoffs dirty an API-composed dashboard snapshot publisher. Queue scheduling covers both request-path deterministic enqueues and successful pending-persistence reconciliation handoffs. The publisher keeps a bounded latest value per inventory scope and one global queue scope, performs at most one inspection/publication operation at a time, and emits the existing full `InventoryStatus` and `QueueStatus` contracts. It uses `inventory.lastUpdatedAt` and `queue.updatedAt` as event observation times so a delayed read cannot appear newer than its source. Reads and publishes are advisory and never participate in reservation, reconciliation, persistence, or enqueue correctness. Idempotent reservation replays do not dirty inventory; deterministic replay enqueue success may refresh the queue snapshot.

Enqueue publication alone cannot describe worker dequeue, retry, or terminal failure changes. After a queue snapshot observes backlog or active work, the API snapshot scheduler owns at most one unref'd two-second timer that marks the global queue scope dirty again. Its existing single-flight drain re-inspects and publishes coherent full queue status until a final snapshot observes no queued or active work. New enqueues replace the latest publication context and trigger immediate coalesced inspection without multiplying timers. Shutdown cancels the delayed refresh and drains only work already pending or in flight.

The API recovery read combines Redis-backed run-scoped live metrics with durable demo-run state. A `starting` run is a durable API intent: the API lifecycle poller replays the exact run ID and frozen configuration until the load orchestrator's single-slot journal confirms ownership. The orchestrator retains accepted/executing/completed evidence across restarts and retries completion delivery until the API acknowledges it. A completion claim moves the run to `draining` with an explicit pending enrichment state; finalization cannot terminalize that run until enrichment has durably concluded. On API startup and each lifecycle poll, `draining` runs have sale closure, pending completion enrichment, and pending-persistence reconciliation repaired so business finalization can continue after process churn. Current-run recovery includes the frozen run configuration snapshot so a refreshed or second dashboard tab shows the accepted traffic, inventory, ERP, and backpressure configuration rather than reconstructing it from editable preset drafts.

Admin reset is an API-owned recovery workflow. It durably claims each recoverable run as failed, closes Redis admission, installs a run-scoped metric-ingestion fence, and requests Task-33 confirmed cancellation using the exact run and correlation IDs. Only after cancellation succeeds does it clean reset-owned queue work, capture the final business and inventory state, write the immutable summary, and delete that run's live traffic projection. A mismatch is a `409` and cannot abort another run. An abort, admission, queue, or summary failure leaves a durable `failed/admin_reset` row without a summary; under the global run-start advisory lock, start admission detects that incomplete transition and returns `409 demo_reset_incomplete` until reset repair writes the summary. Historical admin-reset runs with summaries, including a projection-clear retry, do not block a successor. Projection failure also prevents reset success and leaves idempotent retry coordinates, but its already-confirmed abort and immutable summary permit the retry to clear only the remaining live metric key without re-aborting a successor or duplicating history. The reset does not flush Redis, delete history or inventory, or disconnect SSE clients.

Targeted smoke teardown is a distinct API-owned maintenance workflow. It briefly pauses both physical queues to close the worker-claim race, refuses non-terminal, ownership-inconsistent, malformed, or already-active work, transactionally deletes exactly one generated-owned durable graph while retaining retry coordinates, and converges that run's Redis and non-active BullMQ state. The queue adapter serializes quiescence leases within the API process, so an overlapping retry cannot enter until the prior request finishes its release path. Pre-commit refusal and post-commit Redis or receipt-completion failure restore queues safely, while a post-commit queue-convergence failure deliberately retains only maintenance-owned pauses so workers cannot claim orphaned jobs. A durable ownership marker beside each physical BullMQ queue stores the exact owning run ID. Claims use an atomic claim-or-compare operation: only the same run can adopt, re-pause, restore, or clear retained ownership after API restart, while a different run receives `run_queue_maintenance_owned_by_other_run` without reaching preflight or cleanup. Partial acquisition rolls back only markers newly claimed by that request and never touches a foreign marker; genuinely pre-paused queues remain untouched. The receipt keeps every post-commit failure retryable after the run row has gone. Deployments with multiple API replicas must route this protected mutation through one maintenance authority because FIFO lease serialization is process-local.

## The Buy Path

Every run-scoped purchase attempt follows the same two-phase flow.

**Phase 1 — Fast path (API, synchronous reservation)**

1. Starting a public or admin preset creates a `demo_runs` record with an immutable configuration snapshot, clones the baseline sale offer into a generated run sale offer, initializes durable inventory, and initializes Redis inventory with authoritative run identity and accepting state plus a lifecycle/read cache projection.
2. k6 sends the `runId` and generated `saleOfferId` with each synthetic buy attempt.
3. A Redis Lua script is the first persistence operation. It atomically validates inventory scope, the request's run identity, and the authoritative accepting state, failing closed when the run ID is omitted, mismatched, or closed and rejecting run IDs on catalog inventory.
4. The same uninterrupted Lua operation checks idempotency, decrements `remainingStock`, and creates the pending-persistence visibility sentinel and self-sufficient recovery record. Eligibility is ordered before idempotency replay. Run closure updates the state inspected by this script atomically, so reservations before closure may succeed and reservations after closure reject without mutation.
5. An accepted generated-run hold enters a PostgreSQL session advisory lock shared with terminal transitions. Inside that fenced boundary, persistence verifies the durable run/sale ownership and non-terminal status. A hold that won the narrow Redis-to-PostgreSQL race against a terminal transition is atomically reversed instead of becoming a durable purchase.
6. On success, the API writes the reservation, initial order, and two lifecycle events in one PostgreSQL transaction; publishes a deterministic BullMQ job; atomically promotes the accepted idempotency response while removing pending metadata; publishes bounded dashboard updates; and returns `202 Accepted` with a `reservation_secured` response. A worker-owned dispatch scanner reasserts committed queued orders if the immediate enqueue is lost.
7. On sold-out: the API returns a `409 sold_out` response directly from the Redis stock decision without writing per-loser idempotency records or emitting per-loser dashboard events. Sold-out pressure is aggregated and flushed as periodic `inventory.sold_out_rejection` metrics instead.
8. On duplicate accepted requests or idempotency conflicts: the API replays or rejects from the Redis idempotency record without changing stock.

**Phase 2 — Slow path (worker, seconds to minutes)**

9. The worker picks up the queued job, resolves the frozen retry policy, acquires a Redis run-scoped concurrency lease, applies the run-scoped circuit breaker and ERP behavior, and advances the order through `queued → processing → confirmed` (or `failed`).
10. Mock ERP success is first-write-wins in a PostgreSQL result ledger. Worker recovery records and an autonomous scanner preserve accepted downstream results or retryable handoff failures across process/job failures; malformed poison jobs are recorded in a durable dead-letter audit table.
11. After successful confirmation, the worker enqueues and records a simulated notification. A notification scanner reasserts missing notification jobs, and failed deterministic BullMQ jobs are removed so scanner redelivery is not blocked.
12. The worker publishes transport-neutral dashboard realtime events to Redis Pub/Sub on every state transition.
13. The dashboard reflects the outcome through the API-owned SSE stream, latest-state recovery reads, and k6 metric-stream summaries for high-volume sold-out pressure.

This split is the core architectural bet: callers are never blocked by slow downstream confirmation, and the buy path remains fast regardless of what is happening in the queue.

## The Four Signals

The dashboard surfaces four signals that make system behavior visible under load:

| Signal | What it shows |
| :-- | :-- |
| **Request surge** | API requests per second as the k6 burst hits. |
| **Queue depth** | BullMQ backlog depth, which grows when downstream throughput lags behind the reservation rate. |
| **Inventory drain** | Remaining stock countdown as reservations succeed. |
| **Consistency lag** | p95 delta between the initial buy timestamp and the final downstream confirmation. |

## Failure Modes Absorbed

### 1. Overselling under concurrent load

The Redis Lua script is the exclusive gate for stock decisions. It reads and decrements `remainingStock` in a single atomic operation; no number of simultaneous requests can reserve the same unit twice. The first request that decrements from 1 to 0 succeeds; every subsequent concurrent attempt reads 0 and receives a sold-out response. This guarantee holds regardless of API instance count because the Lua script runs on a single Redis node and cannot be interrupted mid-execution.

### 2. Duplicate or retried buy requests

Each accepted request carries a client-supplied idempotency key scoped to the generated run sale offer. After the Lua script confirms that the inventory still accepts that run, it checks this key before any accepted stock decision. Retries for accepted or pending reservations replay the stored outcome without consuming additional stock while the run remains accepting; closure fails closed before replay. Retries with the same key but different parameters are rejected as an idempotency conflict rather than silently producing a different accepted result. Sold-out responses are intentionally not stored per request, which keeps the losing side cheap during public scarcity-driven spikes.

For duplicate buyer-spike traffic, repeated accepted idempotency replays can increase the raw accepted HTTP response count without increasing durable stock reservations. Finalization and terminal run summaries therefore count complete duplicate buyer-spike deliveries by durable unique reservations, while planned attempts still show the full emitted duplicate-attempt total.

### 3. Partial persistence failures (Redis succeeds, PostgreSQL fails)

If the Redis stock hold succeeds but the subsequent PostgreSQL write fails, the system preserves the Redis hold and returns `reservation_pending_persistence` rather than silently discarding a secured unit. The hold is tracked by a sentinel, companion recovery record, and global index created atomically with the stock decision; reconciliation reads that index in bounded batches. The inventory status endpoint exposes the pending count and the age of the oldest hold while PostgreSQL is unavailable. An eligible request retry can reconcile the hold while admission remains open. After closure, API startup and run finalization invoke the autonomous reconciler without reopening `/buy`: it restores or finds the durable reservation/order, reasserts the deterministic queue job, marks the durable pending row reconciled, promotes Redis, and clears the sentinel. A definitively invalid run/sale attribution reverses the hold atomically. Unresolved work remains visible and blocks normal finalization until the documented drain-timeout policy applies.

### 4. Downstream slowness and TPS exhaustion

The mock ERP, standing in for a slow downstream business system, applies the ERP behavior captured in the run snapshot, including latency, TPS cap, failure mode, and outage-style behavior. The worker's Redis lease gate caps simultaneous in-flight handlers per run across worker processes; jobs that cannot acquire a lease are delayed with bounded deferral rather than entering the downstream call. The queue depth signal makes this buffer effect visible in the dashboard. The API reservation path is unaffected by downstream latency because it never calls the mock ERP directly.

### 5. Downstream outage (partial or total)

The worker selects a circuit breaker per run and immutable threshold configuration, with a separate catalog/missing-snapshot fallback. One run cannot open another run's breaker. After the configured consecutive failure threshold, the circuit opens and downstream attempts fail fast into the job's frozen retry/backoff policy. When the reset window elapses, the circuit moves to half-open and admits one probe. On success, the circuit closes and normal processing resumes. Run-qualified breaker snapshots are published to separate bounded Redis keys for active-run dashboard status.

### 6. API responsiveness under queue pressure

The API process and the worker process are fully decoupled. The API's buy path touches PostgreSQL and BullMQ only after Redis accepts a reservation. Sold-out attempts stay on the Redis-first losing path and return without durable writes or per-loser dashboard publication. The request path does not wait for queue inspection or downstream confirmation; bounded advisory queue refresh runs behind the composition-owned scheduler. Queue depth itself does not block API responses, but accepted-heavy runs can still consume shared PostgreSQL, Redis, and CPU capacity, so API PostgreSQL pool sizing, worker PostgreSQL pool sizing, and aggregate worker scanning concurrency are intentionally tunable.

For the public one-second presets, the API listener backlog is also explicit. The default `API_LISTEN_BACKLOG=8192` avoids relying on Node's lower default accept queue when k6 opens thousands of connections in a very short window.

### 7. Admin surface abuse

Public-facing controls are narrowly scoped: curated read-only preset starts, bounded run-scoped public custom starts, public run-budget enforcement, one-active-or-draining-run gating, and traffic buyer-count/emitted-attempt/request-rate caps enforced by the API. Editable admin presets, `Custom` scratch saves, reset, recovery actions, run-history deletion, and any retained global ERP diagnostic controls require an authenticated admin session and are proxied through the Next.js dashboard server rather than called directly from browser clients. All caps are environment-configured and validated at service startup, not hardcoded in route handlers.

### 8. Dashboard read amplification

The public SSE fan-out applies atomic process-local total and per-source connection caps before registering a client. Dashboard recovery acquires a small process-local concurrency permit and an atomic Redis global/per-source fixed-window budget before touching PostgreSQL, Redis projections, or BullMQ. Rejections return retry guidance, limiter failures fail closed, and the default three concurrent recovery builds stay below the default API PostgreSQL pool of ten.

### 9. Lost queue and completion handoffs

The worker scans old `queued` orders and reasserts deterministic order jobs, so an API crash after commit cannot strand an order. The load orchestrator records acceptance before spawn, durably journals completion before delivery, and retains ownership until the API acknowledges the exact report. The API stores the first completion report per run and makes enrichment/finalization idempotently re-drivable. These boundaries turn process crashes and ambiguous HTTP results into replayable work rather than silent loss.

## Key Design Constraints

- The API never calls the mock ERP directly. All downstream confirmation interaction passes through the BullMQ queue.
- Inventory state lives in Redis as the fast authoritative source; PostgreSQL holds the durable business record.
- Run sale-offer stock eligibility is authoritative in the Redis inventory state and enforced inside the atomic stock decision before any PostgreSQL read. Accepted generated-run persistence is then fenced against terminal transitions by the shared PostgreSQL advisory lock and durable ownership/status check.
- `@checkout-surge/contracts` is the single source of truth for shared types and Zod schemas across all services.
- The API owns browser-facing SSE fan-out on `/dashboard/events`; API and worker publish transport-neutral dashboard realtime events through Redis Pub/Sub.
- Dashboard realtime is best-effort observability. Latest-state recovery reads are the resynchronization strategy, not stream replay.
- API deployment traffic caps are enforced from the seven `DEMO_MAX_*` settings (buyers, total requests, request rate, duration, start delay, preallocated VUs, and max VUs) and overlaid onto the durable public policy on every read/start/update. Compose mirrors those settings into the one-shot setup service only so first-seed public values are validated and compatibility-stored against the deployed caps. PostgreSQL remains authoritative for admin-tunable public budgets, defaults, and limits after first bootstrap.
- Dashboard browser traffic uses the public web origin; internal service URLs and control tokens stay server-side.
