# Architecture — Checkout-Surge

## Purpose

Checkout-Surge must demonstrate that a Node.js service can absorb a limited-inventory checkout surge without overselling, without overwhelming a slow downstream business dependency, and without sacrificing API responsiveness. The public demo target is the `surge-10k` shape: about 10,000 synthetic buy attempts in roughly 1 second, generated by k6 against the API. The architecture is not specific to short promotional flash sales; the same pressure appears in ticket launches, product drops, presales, and other scarcity-driven purchase flows. The demo uses a mock ERP to make the downstream dependency concrete, but the same boundary could represent payment capture, fraud/risk checks, warehouse allocation, fulfillment, tax calculation, accounting, supplier APIs, or other fragile business systems. This document is the target architecture that implementation work must realize.

---

## System Overview

The completed system must be intentionally split into five independent processes:

| Component | Role |
| :-- | :-- |
| `apps/api` — Fastify API gateway | Owns the buy path: validates requests, executes the Redis reservation, enqueues work, returns immediately. |
| `apps/worker` — BullMQ worker | Owns background workflows: pulls order jobs from the queue, calls the downstream confirmation service with retry and circuit-breaker logic, persists state transitions, and records simulated post-confirmation notifications. |
| `apps/mock-erp` — Mock ERP / downstream business system | Simulates a legacy downstream dependency with configurable latency, TPS cap, error rate, and forced-outage controls. |
| `apps/load-orchestrator` — k6 wrapper | Triggers synthetic buyer traffic from accepted run snapshots, parses k6 JSON output, and streams live metrics to the API for dashboard recovery and live fan-out. |
| `apps/web` — Next.js dashboard | Owns the public demo picker, current-run spectator view, admin operator surface, admin session checks, public preset cooldown/rate limiting, and thin server-side proxying for dashboard reads and protected control actions. |

The dashboard (`apps/web`) is a demo and operator surface, not a customer storefront. High-volume buyers are k6-generated synthetic API attempts, not browser sessions. Public visitors use `/` to start curated read-only presets or a bounded run-scoped `public-custom` run, then observe the active run at `/watch`. Admins use `/admin` to inspect public presets, save editable admin presets, use the persisted `Custom` scratch preset, and start runs from accepted configuration snapshots.

The reference runtime must preserve this split with separate containers for the application services. In particular, k6 belongs inside the load-orchestrator runtime image; installing k6 directly on a developer host is only a convenience path for host-native development.

The dashboard should be exposed as a single browser origin in the reference runtime. HTTP dashboard reads and controls use same-origin `apps/web` routes, while `apps/web` calls the API, mock ERP, and load orchestrator through private server-side URLs. The API owns the browser-facing SSE stream at `/dashboard/events` and subscribes to internal Redis Pub/Sub dashboard events for live fan-out. Caddy routes `/dashboard/events` from the dashboard origin directly to the API service, while the rest of the dashboard origin remains routed to the web service. Dashboard observability stays public for the demo; admin access gates only privileged controls. Direct service ports can remain available for health checks and debugging, but the normal operator path does not require browser access to the API, mock ERP, or load orchestrator ports.

When direct service ports are exposed for local debugging, their browser CORS allow-lists should be configured with `WEB_ORIGIN`. Leaving `WEB_ORIGIN` unset keeps wildcard development behavior, but the reference compose runtime pins it to the dashboard proxy origin.

## Dashboard Realtime Model

Dashboard realtime is a live observability path, not a command transport or an event ledger. Dashboard commands and reads continue to use HTTP routes, while the API streams browser-facing telemetry with SSE and receives internal dashboard events from Redis Pub/Sub.

The API is the only browser-facing realtime owner. API and worker services publish validated transport-neutral dashboard events to the `dashboard-events` Redis channel, and each API process keeps one shared Redis subscriber for fan-out to its connected SSE clients. Browser connections are in-memory sinks only; they do not create Redis subscriptions and the gateway does not build per-client event backlogs. If a client write fails or applies backpressure, that SSE connection is closed and the browser relies on native `EventSource` reconnect.

SSE events are best-effort live hints. Publish failures are logged but must not break checkout, metric ingestion, worker processing, or demo controls. Redis Pub/Sub gaps, page refreshes, tab resumes, and stream reconnects are recovered through `/dashboard/recovery`, which returns the latest dashboard state rather than missed stream events. The dashboard discards live events received while a recovery snapshot is in flight so stale realtime data cannot overwrite the fresh baseline, then runs a follow-up recovery if anything arrived during that window. A received terminal run event also triggers one final recovery for that run ID so final inventory, queue, ERP, and outcome projections settle from backend truth. The system intentionally does not maintain SSE event IDs, `Last-Event-ID` cursors, replay buffers, Redis Streams, or durable admin event logs for this demo surface.

The API recovery read combines process-local live metrics with durable demo-run state. On API startup, `starting` and `active` runs left behind by a process restart are marked failed with `api_restart_interrupted_run`, sale eligibility is closed, and the normal immutable run-history summary is written. Durable `draining` runs remain visible through recovery so business finalization can continue after API process churn. Current-run recovery includes the frozen run configuration snapshot so a refreshed or second dashboard tab shows the accepted traffic, inventory, ERP, and backpressure configuration rather than reconstructing it from editable preset drafts.

## The Buy Path

Every run-scoped purchase attempt follows the same two-phase flow.

**Phase 1 — Fast path (API, synchronous reservation)**

1. Starting a public or admin preset creates a `demo_runs` record with an immutable configuration snapshot, clones the baseline sale offer into a generated run sale offer, initializes durable inventory, and initializes Redis inventory with authoritative run identity and accepting state plus a lifecycle/read cache projection.
2. k6 sends the `runId` and generated `saleOfferId` with each synthetic buy attempt.
3. A Redis Lua script atomically validates inventory scope, the request's run identity, and the authoritative accepting state, failing closed when the run ID is omitted, mismatched, or closed and rejecting run IDs on catalog inventory.
4. The same uninterrupted Lua operation checks idempotency, decrements `remainingStock`, and creates the pending-persistence visibility sentinel for the generated sale offer. Eligibility is ordered before idempotency replay. Run closure updates the state inspected by this script atomically, so reservations before closure may succeed and reservations after closure reject without mutation.
5. On success: the API writes the reservation and initial order record to PostgreSQL, publishes a BullMQ job, atomically promotes the accepted idempotency response while removing the pending sentinel, publishes bounded dashboard updates, and returns `202 Accepted` with a `reservation_secured` response immediately.
6. On sold-out: the API returns a `409 sold_out` response directly from the Redis stock decision without querying PostgreSQL, writing per-loser idempotency records, or emitting per-loser dashboard events. Sold-out pressure is aggregated and flushed as periodic `inventory.sold_out_rejection` metrics instead.
7. On duplicate accepted requests or idempotency conflicts: the API replays or rejects from the Redis idempotency record without changing stock.

**Phase 2 — Slow path (worker, seconds to minutes)**

8. The worker picks up the queued job, applies the active run's accepted backpressure policy, calls the mock ERP / downstream business system with the run-scoped ERP behavior, and advances the order through `queued → processing → confirmed` (or `failed`).
9. After successful confirmation, the worker enqueues and records a simulated notification so the demo shows the post-confirmation workflow without using a real provider.
10. The worker publishes transport-neutral dashboard realtime events to Redis Pub/Sub on every state transition.
11. The dashboard reflects the outcome through the API-owned SSE stream, latest-state recovery reads, and k6 metric-stream summaries for high-volume sold-out pressure.

This split is the core architectural bet: callers are never blocked by slow downstream confirmation, and the buy path remains fast regardless of what is happening in the queue.

## The Four Signals

The dashboard surfaces four signals that make system behavior visible under load:

| Signal | What it shows |
| :-- | :-- |
| **Request surge** | API requests per second as the k6 burst hits. |
| **Queue depth** | BullMQ backlog depth, which grows when downstream throughput lags behind the reservation rate. |
| **Inventory drain** | Remaining stock countdown as reservations succeed. |
| **Consistency lag** | p95 delta between the initial buy timestamp and the final downstream confirmation. |

## Failure Modes Absorbed

### 1. Overselling under concurrent load

The Redis Lua script is the exclusive gate for stock decisions. It reads and decrements `remainingStock` in a single atomic operation; no number of simultaneous requests can reserve the same unit twice. The first request that decrements from 1 to 0 succeeds; every subsequent concurrent attempt reads 0 and receives a sold-out response. This guarantee holds regardless of API instance count because the Lua script runs on a single Redis node and cannot be interrupted mid-execution.

### 2. Duplicate or retried buy requests

Each accepted request carries a client-supplied idempotency key scoped to the generated run sale offer. After the Lua script confirms that the inventory still accepts that run, it checks this key before any accepted stock decision. Retries for accepted or pending reservations replay the stored outcome without consuming additional stock while the run remains accepting; closure fails closed before replay. Retries with the same key but different parameters are rejected as an idempotency conflict rather than silently producing a different accepted result. Sold-out responses are intentionally not stored per request, which keeps the losing side cheap during public scarcity-driven spikes.

For duplicate buyer-spike traffic, repeated accepted idempotency replays can increase the raw accepted HTTP response count without increasing durable stock reservations. Finalization and terminal run summaries therefore count complete duplicate buyer-spike deliveries by durable unique reservations, while planned attempts still show the full emitted duplicate-attempt total.

### 3. Partial persistence failures (Redis succeeds, PostgreSQL fails)

If the Redis stock hold succeeds but the subsequent PostgreSQL write fails, the system preserves the Redis hold and returns `reservation_pending_persistence` rather than silently discarding a secured unit. The hold is tracked in a Redis `pending-persistence` sentinel created atomically with the stock decision. The inventory status endpoint exposes the pending count and the age of the oldest hold, giving operators visibility to inspect or reconcile without requiring distributed rollback coordination. If PostgreSQL commits but Redis promotion fails, the API truthfully returns `reservation_secured` while pending visibility remains until a retry finds the durable rows and self-heals the promotion.

### 4. Downstream slowness and TPS exhaustion

The mock ERP, standing in for a slow downstream business system, applies the ERP behavior captured in the run snapshot, including latency, TPS cap, failure mode, and outage-style behavior. When that dependency is slow, the active run's backpressure policy caps simultaneous in-flight confirmation calls. Excess jobs accumulate in BullMQ rather than piling onto the downstream system. The queue depth signal makes this buffer effect visible in the dashboard. The API reservation path is unaffected by downstream latency because it never calls the mock ERP directly.

### 5. Downstream outage (partial or total)

The worker runs a circuit breaker around all downstream confirmation calls. After a configured number of consecutive failures, the circuit opens and workers stop issuing requests for a reset window. Orders remain safely queued in BullMQ rather than being lost or hammered against an unavailable service. When the reset window elapses, the circuit moves to half-open and probes one request. On success, the circuit closes and normal processing resumes.

### 6. API responsiveness under queue pressure

The API process and the worker process are fully decoupled. The API's buy path touches PostgreSQL and BullMQ only after Redis accepts a reservation. Sold-out attempts stay on the Redis-first losing path and return without durable writes or per-loser dashboard publication. The API does not poll the queue, share its event loop with worker processing, or wait for downstream confirmation. Queue depth itself does not block API responses, but accepted-heavy runs can still consume shared PostgreSQL, Redis, and CPU capacity, so API PostgreSQL pool sizing, worker PostgreSQL pool sizing, and worker concurrency are intentionally tunable.

For the public one-second presets, the API listener backlog is also explicit. The default `API_LISTEN_BACKLOG=8192` avoids relying on Node's lower default accept queue when k6 opens thousands of connections in a very short window.

### 7. Admin surface abuse

Public-facing controls are narrowly scoped: curated read-only preset starts, bounded run-scoped public custom starts, public run-budget enforcement, one-active-or-draining-run gating, and traffic buyer-count/emitted-attempt/request-rate caps enforced by the API. Editable admin presets, `Custom` scratch saves, reset, recovery actions, run-history deletion, and any retained global ERP diagnostic controls require an authenticated admin session and are proxied through the Next.js dashboard server rather than called directly from browser clients. All caps are environment-configured and validated at service startup, not hardcoded in route handlers.

## Key Design Constraints

- The API never calls the mock ERP directly. All downstream confirmation interaction passes through the BullMQ queue.
- Inventory state lives in Redis as the fast authoritative source; PostgreSQL holds the durable business record.
- Run sale-offer eligibility is authoritative in the Redis inventory state and enforced inside the atomic stock decision; PostgreSQL is not queried for every losing buy attempt.
- `@checkout-surge/contracts` is the single source of truth for shared types and Zod schemas across all services.
- The API owns browser-facing SSE fan-out on `/dashboard/events`; API and worker publish transport-neutral dashboard realtime events through Redis Pub/Sub.
- Dashboard realtime is best-effort observability. Latest-state recovery reads are the resynchronization strategy, not stream replay.
- Public traffic caps are enforced as `DEMO_MAX_BUYERS`, `DEMO_MAX_TOTAL_REQUESTS`, `DEMO_MAX_REQUESTS_PER_SECOND`, `DEMO_MAX_TRAFFIC_DURATION_SECONDS`, and `DEMO_MAX_TRAFFIC_START_DELAY_SECONDS`; retained global ERP diagnostic caps are also read from environment variables, never hardcoded.
- Dashboard browser traffic uses the public web origin; internal service URLs and control tokens stay server-side.
