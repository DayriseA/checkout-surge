# Architecture — Checkout-Surge

## Purpose

Checkout-Surge demonstrates that a Node.js service can absorb a limited-inventory checkout surge without overselling, without overwhelming a slow downstream business dependency, and without sacrificing API responsiveness. The public demo target is the `surge-10k` shape: about 10,000 synthetic buy attempts in roughly 1 second, generated by k6 against the API. The architecture is not specific to short promotional flash sales; the same pressure appears in ticket launches, product drops, presales, and other scarcity-driven purchase flows. The demo uses a mock ERP to make the downstream dependency concrete, but the same boundary could represent payment capture, fraud/risk checks, warehouse allocation, fulfillment, tax calculation, accounting, supplier APIs, or other fragile business systems. This document describes the implemented architecture.

---

## System Overview

The supported local system is intentionally split into exactly five independent application processes:

| Component | Role |
| :-- | :-- |
| `apps/api` — Fastify API gateway | Owns the buy path: validates requests, executes the Redis reservation, enqueues work, returns immediately. |
| `apps/worker` — BullMQ worker | Owns background workflows: pulls order jobs from the queue, applies frozen run retry/admission/breaker policy, calls the downstream confirmation service, persists state transitions, and runs dispatch, ERP-result, and notification recovery workflows. |
| `apps/mock-erp` — Mock ERP / downstream business system | Simulates a legacy downstream dependency with run-snapshot-first, global-fallback latency/TPS/error behavior and process-local idempotent confirmation replay. |
| `apps/load-orchestrator` — k6 wrapper | Durably owns one traffic execution at a time, triggers synthetic buyer traffic from accepted run snapshots, samples generator resource utilisation for completion diagnostics, provides authenticated run-fenced cancellation with confirmed bounded process termination, parses k6 JSON output, streams live metrics, and retries natural completion delivery to the API until acknowledged, parking permanently rejected reports in a durable terminal state instead of retrying them forever. |
| `apps/web` — Next.js dashboard | Owns the public demo picker, current-run spectator view, admin operator surface, signed visitor-cookie issuance, hardened admin sessions, and thin server-side proxying for dashboard reads and controls. Public run budgets remain API-owned. |

The dashboard (`apps/web`) is a demo and operator surface, not a customer storefront. High-volume buyers are k6-generated synthetic API attempts, not browser sessions. Public visitors land on the project overview at `/` and use `/demo` to start curated read-only presets or a bounded run-scoped `public-custom` run, then observe the active run at `/watch`. Watch renders a phase-aware narrative (checking, unavailable, idle, starting, active, draining, completed, failed) derived from the accepted projection by one pure presentation helper: the frozen accepted configuration snapshot stays visible through the run, a finished run's recap and exact `/run-history` link are retained after the live projection clears (with shared-runtime status refreshed rather than frozen), and the idle state server-loads the latest completed run through the existing history read. A public start also hands its accepted run identity to Watch as an explicit `acceptedRunId` query parameter: Watch resolves that exact run through the public history detail read (server-side first, then bounded same-origin client retries with a manual retry after exhaustion) and shows a distinct accepted-result section that never substitutes an earlier history row, while the live panels keep following the shared current run. Admins use `/admin` to inspect public presets, save editable admin presets, use the persisted `Custom` scratch preset, duplicate presets into editable admin copies, archive accidental operator-created copies, and start runs from accepted configuration snapshots.

The public, watch, and authenticated admin routes initialize current-run recovery as pending and hand authoritative recovery to the shared browser coordinator, which uses the signed same-origin BFF instead of a credentialless server read. Watch and authenticated Admin parse only contract-valid complete projection SSE frames and feed them to one small atomic comparison owner; HTTP candidates use the same rules, so a racing response is compared rather than buffered or replayed. The initial stream open, first disconnect in one outage, and later reconnect open use one current-read path with at most one read in flight plus one queued batch, with paired known-scope hints when available; a trigger arriving during a read is served by one fresh read started after it settles, triggers in that window share the fresh read, and unmount discards the queued read. While the stream stays disconnected, a successful recovery that returns a nonterminal projection schedules one follow-up authoritative read after a fixed 2-second delay, stopping on terminal convergence, stream reopen, or unmount; failed reads keep the existing bounded backoff. Admin retains the last-known-good current-run projection after a read failure or stream disconnect, labels its authoritative observation time and stale, disconnected, or unsupported-live-update state, and blocks local starts while the read has failed or freshness is stale, disconnected, or unsupported; the API's one-active-run admission check remains authoritative. The admin page validates the signed session on the server, renders only the sign-in island for anonymous visitors, and server-loads its other authenticated reads. Current-run, runtime-policy, preset/start, maintenance, and ERP controllers retain independent mutation state so one operation does not disable or clear unrelated features.

The reference runtime preserves this split with one container and one process for each application service. The API process is the sole maintenance authority, the load-orchestrator process owns one journal, and the worker is one runtime. k6 is installed inside the load-orchestrator runtime image; installing k6 directly on a developer host is only a convenience path for host-native development. The single Caddy dashboard proxy/edge described below is an ingress and routing boundary, not a sixth application process or another authority.

The dashboard is exposed as a single browser origin in the reference runtime. HTTP dashboard reads and controls use same-origin `apps/web` routes. The web server calls the API for run lifecycle/read operations and the Mock ERP for its retained global fallback fault-injection controls; after accepting a run, the API delegates traffic through one focused HTTP gateway that owns load-orchestrator URLs, service authentication, correlation propagation, response validation, and deadlines. Run lifecycle depends only on the gateway's start capability, and maintenance depends only on its exact-run abort capability. The API owns the browser-facing SSE stream at `/dashboard/events`, subscribes to internal Redis Pub/Sub dirty signals, and assembles bounded complete projections for live fan-out. Caddy routes the exact `/dashboard/events` path from the dashboard origin directly to the API service, while the rest of the dashboard origin remains routed to the web service. Direct Next.js usage retains the same browser path through a web-owned byte-stream proxy to the server-only API base URL. Dashboard observability stays public for the demo; admin access gates only privileged controls. Direct service ports are available through the debug override for health checks and troubleshooting, but the normal operator path does not require browser access to them.

Browser-facing Next.js proxy routes adopt or generate one normalized correlation ID per request and forward it to the selected backend. They construct outbound headers from an explicit allow-list of required server-owned assertions rather than copying browser headers, validate every upstream error against the shared canonical envelope, and return an authoritative `x-correlation-id` that agrees with any response-body correlation field. The API, Mock ERP, and load orchestrator install the same request-scoped Fastify correlation behavior before route registration, so response headers, canonical errors, automatic request logs, and ordinary route logs share the selected ID without mutating a process-wide logger.

The API is the only application service that registers a browser CORS plugin. `WEB_ORIGIN` supplies its allowed origin list; when unset, Fastify's `origin: true` behavior reflects and permits the request origin rather than emitting a literal wildcard. The reference Compose runtime pins `WEB_ORIGIN` to the dashboard proxy origin. The web server consumes the same setting separately as the exact-Origin/CSRF and cookie-policy boundary for unsafe admin requests; Mock ERP and the load orchestrator do not register browser CORS allow-lists.

Run-start authorization has two distinct server-side assertions. Every `POST /demo/runs/start` call must carry the shared `CONTROL_SERVICE_TOKEN`, which authenticates the trusted web proxy or another service caller; an admin operator-mode assertion is honored only on that authenticated channel. A public start must additionally carry the HMAC-signed visitor credential issued by the web server, which supplies an anonymous budget principal. Neither credential establishes human identity or production-grade abuse prevention, and hosted use still requires appropriate network controls and rate limiting.

## Dashboard Realtime Model

Dashboard realtime is a live observability path, not a command transport or an event ledger. Dashboard commands and reads continue to use HTTP routes, while the API streams complete revisioned browser projections with SSE and receives internal dashboard dirty signals from Redis Pub/Sub.

The API is the only browser-facing realtime owner. API and worker services publish the small validated internal `dashboard.projection.dirty` signal to the `dashboard-projection-dirty` Redis channel, and the API keeps one shared Redis subscriber that marks projection scopes dirty. This signal is producer coordination, not a second UI protocol. Complete projections publish at the bounded cadence and immediate lifecycle boundary. Browser connections are in-memory sinks only; they do not create Redis subscriptions. A backpressured client retains only the latest pending projection per scope within fixed frame/scope/byte limits; disconnect and native `EventSource` reconnect repair with one current projection read. When the browser fails a connection closed outright (for example an HTTP rejection at the edge), the web app replaces the closed source with at most five bounded backoff attempts (1 through 16 seconds) and, after they fail, offers a full-page reload instead of further application-managed retries.

SSE projections are best-effort complete views. Publish failures are logged but must not break checkout, metric ingestion, worker processing, or demo controls. Redis Pub/Sub gaps, page refreshes, tab resumes, and stream reconnects are recovered through `/dashboard/recovery`, which returns the same complete schema rather than missed stream messages. Same-scope candidates replace only at a higher revision; eligible nonterminal new scopes use durable run start metadata, newer authoritative idle reads may clear a prior scope, and foreign terminal scopes cannot establish a current run. Initial loading and public/admin starts fail closed, while Watch and authenticated Admin label and preserve their last-known-good projection after a failed read. Both derive freshness from the projection's `recoveredAt` timestamp and the shared threshold of three expected live-update intervals; Admin also refreshes after start, reset, and cleanup completion. The system does not maintain SSE cursors, replay buffers, Redis Streams, browser watermarks, incremental reducers, or durable admin event logs for this surface.

Fresh Redis reservation decisions and successful API-owned BullMQ handoffs enter one bounded API source-dirty scheduler. Queue scheduling covers request-path deterministic enqueues and successful pending-persistence recovery handoffs, while replay/reassertion does not. Inventory work coalesces by scope, sold-out work coalesces for 500 ms, and queue work retains one global context. The scheduler emits only the internal dirty signal; it does not read or publish scalar UI events. Queue inspection remains solely to continue dirtying while backlog or active work drains. Complete `InventoryStatus` and `QueueStatus` values are assembled by the projection service. Reads and dirty publication are advisory and never participate in reservation, reconciliation, persistence, or enqueue correctness.

Fresh reservation, order, ERP-attempt, and notification mutations enter the existing bounded 500 ms API/worker business-outcome dirty schedulers. These schedulers now publish only one coalesced internal dirty signal per scope; they do not query or serialize aggregate dashboard payloads. The projection service reads business outcomes and aggregate consistency lag when it builds the next complete view. Replays and detected persistence no-ops do not dirty the scope. Pending maps and shutdown remain bounded, and admin reset clears pending scopes.

Enqueue publication alone cannot describe worker dequeue, retry, or terminal failure changes. After a coherent queue inspection observes backlog or active work, the API source-dirty scheduler owns at most one unref'd two-second timer that marks the current projection dirty again. New enqueues replace the latest publication context without multiplying timers. Shutdown cancels the delayed refresh and drains only work already pending or in flight.

The API recovery read combines Redis-backed run-scoped live metrics with durable demo-run state. It resolves one `starting`, `active`, or `draining` run at assembly start, ordered by required `startedAt` with deterministic creation/ID ties, and uses that immutable selection for every run-owned projection. A current run without `startedAt` or `saleOfferId`, or with a malformed stored configuration snapshot, produces a contextual reader error; the recovery coordinator logs that error and degrades the response to no current scope instead of projecting compatibility state. Recovery never substitutes a catalog offer or terminal-history row when no current run exists: inventory, business outcome, consistency lag, traffic metrics, and run-owned `erp` are then empty/null, while `systemStatus` independently retains the shared physical BullMQ observation and catalog ERP protection. The response identifies the request correlation ID, the selected `{ runId, saleOfferId }` scope, and one projection-level `recoveredAt` observation baseline. Queue `observedAt` is a shared poll clock, while each circuit's `lastChangedAt` advances only on a protection-state transition. A `starting` run is a durable API intent: the explicit startup reconciliation owner replays the exact run ID and frozen configuration until the load orchestrator's single-slot journal confirms ownership. The orchestrator retains accepted/executing/completed evidence across restarts and retries completion delivery until the API acknowledges it or permanently rejects it, in which case the report is parked durably with its rejection reason and the execution slot is released. The internal metric route delegates directly to a focused ingestion service that validates the batch, locks and validates the durable run lifecycle, bounds pending work, and orchestrates retention before best-effort publication. Its composition-injected Redis dashboard metric store owns bounded run-scoped retention, reset fences, publication mechanics, reads, clear, and state inspection. Completion admission belongs to the focused traffic-completion service rather than the run-lifecycle service. Missing, terminal, reset-fenced, or accepted-snapshot-inconsistent output receives a canonical correlated non-success instead of a false acknowledgement. A first completion transaction validates the shared snapshot-derived execution plan and redundant counts/identity/timestamps, persists immutable evidence, and moves the run to `draining` with an explicit pending enrichment state. Exact redelivery strictly validates the stored current completion fields before comparison and can re-drive enrichment/finalization, but conflicting evidence cannot perform those side effects. Finalization cannot terminalize that run until enrichment has durably concluded. Before listening or starting the finalization poller, API startup discovers draining runs once and independently re-drives sale closure and pending completion enrichment for each candidate, so one per-run failure does not block later recovery. Missing sale ownership and partial enrichment are reported as attributable failed recoveries rather than successful effects. Periodic starting-intent reconciliation remains on that explicit owner, while completion enrichment and finalization retain their existing bounded handoffs. Current-run recovery includes the frozen run configuration snapshot so a refreshed or second dashboard tab shows the accepted traffic, inventory, ERP, and backpressure configuration rather than reconstructing it from editable preset drafts.

Admin reset is an API-owned recovery workflow. It durably claims each recoverable run as failed, closes Redis admission, installs a run-scoped metric-ingestion fence, and requests Task-33 confirmed cancellation using the exact run and correlation IDs. Only after cancellation succeeds does it pause the owned queues, wait within the bounded settlement budget for already-active selected work, and remove jobs exactly attributed to those reset run IDs, capture the final business and inventory state, write the immutable summary, delete those runs' live traffic projections, and then publish one exact run/sale scoped projection dirty signal per cleaned run through the ordinary lifecycle publisher (including a projection-clear retry), so an already-connected Watch receives the higher-revision operator-stop projection without a manual refresh; that publication is advisory and never fails the reset. Other generated runs and catalog/unscoped jobs remain intact. A mismatch is a `409` and cannot abort another run. An abort, admission, queue, or summary failure leaves a durable `failed/admin_reset` row with a null `adminResetCompletedAt` marker; under the global run-start advisory lock, start admission detects that incomplete transition and returns `409 run_conflict` with `details.conflictReason = reset_incomplete` until reset repair writes the summary and marker transactionally. Marker-backed historical admin-reset runs, including a projection-clear retry, do not block a successor. Projection failure also prevents reset success and leaves idempotent retry coordinates, but its already-confirmed abort and immutable summary permit the retry to clear only the remaining projection/shared state without re-aborting a successor or duplicating history. A Redis pending-projection run set is recorded before the business completion marker and removed only after metrics, breaker clearing and the advisory publication attempt; retry identity therefore survives metric deletion and API recreation. This set does not gate admission. The reset does not flush Redis, delete history or inventory, disconnect SSE clients, or change process-local global ERP fault injection. The separate operational `pnpm runtime:reset` client is the full-reset path that also requests restoration of Mock ERP defaults.

Reset allows at most 5 seconds for already-active selected order/notification jobs to settle while both queues are paused, using one deadline capped at 25 seconds elapsed since reset processing began. The abort gateway allows 20 seconds and the runtime reset client allows 30 seconds per response; the remaining 5 seconds is reserved for evidence, immutable history and response. The checked Caddy and Fastify configuration has no shorter response deadline. This bounds settlement polling, not all dependency I/O. A timeout returns `run_cleanup_conflict` with `active_settlement_timeout`, restores only reset-owned pauses, and leaves the durable null-marker admission gate in place; remaining work may continue before retry. No worker cancellation is introduced. Dashboard projection version 4 exposes global `resetRecovery` (`ready` or `incomplete`), including startup failures without a sale offer. Reset publishes exact-scope advisory dirty signals at claim, marker completion and full success, so it never emits an idle frame ahead of its own terminal handoff. An idle client that rejects a foreign reset terminal uses the existing single-flight HTTP recovery read. The global `resetRecoveryRunId` identifies an incomplete reset or the latest terminal run when that run was reset, independently of sale scope; this identity survives claim/completion signal coalescing. Watch retains that identity for the existing bounded exact-history lookup after repair, rather than substituting an older report if an idle frame clears the live scope. Explicit launched-result context retains precedence and all stale-frame guards remain unchanged. While `resetRecovery` is `incomplete` and no current run exists, the Watch local technical-details section presents a `recovery incomplete` readiness badge and marks scenario, run and load-generator facts as unavailable instead of reporting readiness or an absent run.


API maintenance has three focused workflow owners: admin reset, old terminal generated-run retention selection, and exact generated-run teardown. They share one `ProcessLocalDemoMaintenanceAuthority`, so reset, retention, and targeted teardown cannot interleave. One BullMQ operation pauses only the order and notification queues that were not already paused, validates every selected-run job before mutation, refuses malformed selected work and, for ordinary teardown, active selected work, removes selected jobs across the supported non-active states, and restores every locally introduced pause in `finally`. It does not drain, obliterate, or clean a whole queue, and it has no lease, distributed pause owner, or active-acquisition state. Only reset rechecks selected jobs during bounded active settlement. The adapter retains only the minimum process-local restoration set after a failed resume, retries it on the next exact cleanup and during close, and never resumes a genuinely pre-paused queue.

Targeted teardown first reads and validates the terminal generated `(runId, saleOfferId)` identity. It completes exact queue maintenance and exact Redis deletion while that durable identity still exists, then transactionally revalidates ownership and deletes exactly that graph as the last irreversible step. Queue, resume, Redis, and database failures therefore remain visible while the same durable coordinates are still available for an idempotent retry; successful deletion has no post-commit infrastructure stage and needs no teardown-receipt table. Before every generated-run order or notification enqueue, including dispatch and recovery publication, the worker acquires the shared PostgreSQL session advisory lock paired with terminal transition's exclusive lock. It validates the fresh nonterminal run/sale identity and immutable configuration and holds that shared lock through the awaited BullMQ add. These two producer-only Redis connections use finite request retries, so an outage surfaces to durable dispatch/notification recovery rather than retaining the PostgreSQL lock indefinitely; consumer connections keep their required blocking behavior. Thus add either completes before terminal cleanup can acquire its lock or is refused after terminalization, and an abandoned add cannot later repopulate a cleaned terminal run. This concrete producer fence removes the need for convergence rescans while preserving normal nonterminal dispatch recovery and the configuration reader's broader read semantics. There are no Redis pause-owner keys, cross-replica claims, or restart ownership protocol; additional API processes remain outside the supported topology.

## The Buy Path

Every run-scoped purchase attempt follows the same two-phase flow.

**Phase 1 — Fast path (API, synchronous reservation)**

1. Starting a public or admin preset creates a `demo_runs` record with an immutable configuration snapshot, clones the baseline sale offer into a generated run sale offer, initializes durable inventory, and initializes Redis inventory with authoritative run identity and accepting state plus a lifecycle/read cache projection.
2. k6 sends the `runId` and generated `saleOfferId` with each synthetic buy attempt.
3. A Redis Lua script is the first persistence operation. It atomically validates inventory scope, the request's run identity, and the authoritative accepting state, failing closed when the run ID is omitted, mismatched, or closed and rejecting run IDs on catalog inventory.
4. The same uninterrupted Lua operation checks idempotency, decrements `remainingStock`, and creates the pending-persistence visibility sentinel and self-sufficient recovery record. Eligibility is ordered before idempotency replay. Run closure updates the state inspected by this script atomically, so reservations before closure may succeed and reservations after closure reject without mutation.
5. An accepted generated-run hold resolves the immutable retry policy from the durable run snapshot before entering admission. It then acquires a shared PostgreSQL session advisory lock for the run; terminal and reset transitions retain the corresponding exclusive lock. Inside that fenced boundary, persistence verifies durable run/sale ownership and non-terminal status. Ordinary accepted holds may therefore persist concurrently, while an exclusive transition waits for every admitted handoff. If the transition wins the narrow Redis-to-PostgreSQL race, cleanup first checks for an exactly matching durable reservation and order. Matching durable evidence is re-enqueued and promoted; only a hold with no durable buy is reversed. This terminal-safe classification lock is private to recovery and never reopens `/buy` admission.
6. On success, the API writes the reservation, initial order, and two lifecycle events in one PostgreSQL transaction and publishes a deterministic BullMQ job with the pre-resolved frozen retry policy before releasing admission. Code inside admission uses the reserved PostgreSQL session for durable operations and must never check out another connection from the same bounded base pool. After admission, the API atomically promotes the accepted idempotency response while removing pending metadata, publishes bounded dashboard updates, and returns `202 Accepted` with a `reservation_secured` response. A worker-owned dispatch scanner reasserts committed queued orders if the immediate enqueue is lost.
7. On sold-out, the API returns a `409 sold_out` response directly from the Redis stock decision without writing per-loser idempotency records or publishing per-loser browser data. A synchronous no-I/O observation enters the shared inventory dirty scheduler, which releases at most one projection-dirty signal per scope at each 500 ms boundary. The resulting complete projection build reads full inventory state and remains the only source of browser inventory values.
8. Other rejected stock decisions retain their source classification rather than presenting as sold out. A closed, mismatched, or otherwise ineligible run returns `409 run_not_accepting_traffic`; `inventory_not_initialized` returns 503, `idempotency_conflict` returns 409, and `quantity_invalid` returns 400. Each response carries the decision once as `outcome`. Duplicate accepted requests replay the public `reservation_secured` response without changing stock; `idempotent_replay` remains private Redis workflow vocabulary.

PostgreSQL is the final integrity boundary for the small durable invariant core. Reservation row existence proves a secured hold; in-progress and terminal orders require `processing_at`, order terminal states require their corresponding transition timestamps, order terminal timestamps cannot precede `queued_at`, and ERP attempts cannot finish before they start. Composite foreign keys bind non-null run/sale attribution to `demo_run_sale_contexts`, bind an order to its reservation's offer/correlation/quantity identity, bind ERP attempts to the order correlation, and bind simulated notifications to their order attribution. The API constructs buy events from one validated hold. In the worker, transition persistence locks the order and validates the delivered job before ERP-attempt persistence consumes it, while notification persistence locks and validates directly; each constructs events from that owned parent boundary. PostgreSQL retains the ordinary event parent foreign keys and their `ON DELETE SET NULL` history behavior rather than procedural bidirectional validation. The reviewed empty-database baseline has no trigger functions or non-internal triggers.

Anonymous `GET /demo/runs/history/:runId` reads use purpose-built summary/run projections and PostgreSQL aggregate queries; they do not fetch recent order, ERP-attempt, notification, or event rows and omit persisted identifiers, correlation data, event sources, free-form diagnostics, and sale-offer IDs. The parallel `GET /admin/demo/runs/history/:runId` path requires the control token and uses bounded newest-first row queries backed by composite B-tree indexes whose leading `run_id` key is followed by the two descending timestamps used by each orders, ERP-attempts, notification, or event query. The web exposes that row-level representation only after validating the admin page session and calling the protected API path server-side. The reviewed baseline creates these indexes with ordinary transactional `CREATE INDEX`.

**Phase 2 — Slow path (worker, seconds to minutes)**

9. The worker picks up the queued job, resolves the frozen retry policy, acquires a process-local run-scoped concurrency permit, applies the run-scoped circuit breaker and ERP behavior, and advances the order through `queued → processing → confirmed` (or `failed`).
   Each actual ERP call records whether that call ended normal confirmation attempts under the delivery budget and existing retryability classification; the normalized attempt row and matching event payload carry the same terminal marker. Protected admin run-history rows return it directly, while anonymous detail exposes only closed status counts and aggregate latency metrics.
10. Mock ERP success is first-write-wins only in its process-local in-memory ledger, so duplicate calls during one process lifetime replay the same result while a restart may forget that simulated history. The worker's PostgreSQL `erp_attempts` boundary owns durable accepted-result idempotency and recovery across process/job failures; malformed poison jobs are recorded in a durable dead-letter audit table.
11. After successful confirmation, the worker enqueues and records a simulated notification. A notification scanner reasserts missing notification jobs, and failed deterministic BullMQ jobs are removed so scanner redelivery is not blocked.
12. Fresh worker mutations dirty the process-local bounded aggregate scheduler, which coalesces transition bursts before publishing one internal projection-dirty signal. The worker does not broadcast individual order status or lag. Aggregate consistency lag is read into the next complete dashboard projection, while per-order status and confirmed lag remain queryable through the durable status diagnostic.
13. The dashboard reflects the outcome through the API-owned SSE stream, latest-state recovery reads, and load-generator observations of sold-out rejections.

This split is the core architectural bet: callers are never blocked by slow downstream confirmation, and the buy path remains fast regardless of what is happening in the queue.

`POST /buy` remains an acceptance surface: an idempotent replay returns the original secured reservation and queued order even after durable processing advances. Public callers read current durable progress through `GET /orders/:publicOrderId/status`. That PostgreSQL-backed projection returns the secured reservation fact, current order status, nullable lifecycle and failure fields, confirmation lag only for confirmed orders, and a chronological lifecycle timeline. Its correlation ID always belongs to the lookup request; persisted correlation IDs, the internal order UUID, and event payload/source data are not exposed.

The dashboard surfaces four signals that make system behavior visible under load:

| Signal | What it shows |
| :-- | :-- |
| **Request surge** | Load-generator checkout attempts started per second in the aligned one-second producer window. |
| **Processing backlog** | Run-owned durable accepted orders awaiting their first processing start. |
| **Inventory drain** | Remaining stock countdown as reservations succeed. |
| **Consistency lag** | p95 time from reservation secured to final downstream confirmation. |

## Failure Modes Absorbed

### 1. Overselling under concurrent load

The Redis Lua script is the exclusive gate for stock decisions. It reads and decrements `remainingStock` in a single atomic operation; no number of simultaneous requests handled by the supported API process can reserve the same unit twice. The first request that decrements from 1 to 0 succeeds; every subsequent concurrent attempt reads 0 and is recorded as a sold-out rejection by Checkout-Surge. The Lua operation runs on the single reference Redis service and cannot be interrupted mid-execution; this atomicity claim is not a broader horizontal-deployment contract.

### 2. Duplicate or retried buy requests

Each accepted request carries a client-supplied idempotency key scoped to the generated run sale offer. After the Lua script confirms that the inventory still accepts that run, it checks this key before any accepted stock decision. Retries for accepted or pending reservations replay the stored outcome without consuming additional stock while the run remains accepting; closure fails closed before replay. Retries with the same key but different parameters are rejected as an idempotency conflict rather than silently producing a different accepted result. Individual sold-out rejections are intentionally not stored per request, which keeps the losing side cheap during public scarcity-driven spikes.

For duplicate buyer-spike traffic, repeated accepted idempotency replays can increase the raw accepted HTTP response count without increasing durable stock reservations. Finalization and terminal run summaries therefore count complete duplicate buyer-spike deliveries by durable unique reservations, while planned attempts still show the full emitted duplicate-attempt total.

### 3. Partial persistence failures (Redis succeeds, PostgreSQL fails)

The atomic reservation Lua operation creates the hold, per-sale pending sentinel, and self-sufficient recovery record before returning. If PostgreSQL then fails, the API returns `reservation_pending_persistence`; it does not release or reapply the inventory decision.

One API application component, `PendingPersistenceRecoveryService`, owns discovery, retry scheduling, and resolution. It enumerates known nonterminal run scopes plus active catalog offers from PostgreSQL and reads only due records from bounded per-sale Redis pages. It applies a configured 300-second/six-attempt exponential-backoff policy by default, honors each persisted deadline across restarts, and bounds whole discovery to two seconds by default. It writes the attempt audit, idempotently materializes or verifies the durable buy, reasserts the deterministic BullMQ job, marks the audit resolved, and only then promotes Redis. Every record attempt owns abortable PostgreSQL, deadline-limited Redis, and abort-disconnectable BullMQ resources; deadline expiry or owner shutdown cancels subordinate operations and drains admitted work. Exact request replay delegates to this same due-time policy, with a three-attempt process-local direct admission cap by default; overload preserves the pending response and retryability. The global pending index and independent startup/finalizer repair entrypoints do not exist.

Exhaustion first marks the retained Redis hold and pending metadata authoritatively exhausted and queryable, then attempts a separately bounded subordinate PostgreSQL audit write. The unresolved state therefore remains visible and blocks terminal finalization even when audit storage is unavailable. Malformed companion metadata, including semantically invalid idempotency keys, is logged and quarantined within its per-sale index so later valid work progresses while the unresolved state remains visible. Finalization only observes authoritative Redis pending state under its existing terminal fence and bounded Redis read; it never schedules or performs repair, and audit projection cannot independently block it. Startup reconciliation, completion enrichment, maintenance, routes, and workers likewise do not own this failure class. Explicit run reset is the generated-run escape hatch.

### 4. Downstream slowness and TPS exhaustion

For ERP fault injection, request-scoped configuration wins over the Mock ERP process-global fallback. The worker attaches the accepted run snapshot's latency, TPS cap, error rate, and forced-outage values to normal run confirmations; global values govern non-run calls and calls without snapshot configuration. Changing the global fallback therefore does not change an accepted run.

The mock ERP, standing in for a slow downstream business system, applies the ERP behavior captured in the run snapshot, including latency, TPS cap, failure mode, and outage-style behavior. Inside the single worker runtime, a process-local gate caps simultaneous in-flight handlers for each run from its frozen configuration; jobs that cannot acquire a permit are delayed with bounded deferral rather than entering the downstream call. BullMQ's configured worker concurrency remains the process-wide execution ceiling and the queue retains the excess work. This boundary does not coordinate or claim fairness across worker processes, and multiple worker runtimes are outside the supported topology. The run-owned durable processing-backlog signal makes the buffer effect visible, while shared BullMQ depth remains system-status context across all runs and visitors. The API reservation path is unaffected by downstream latency because it never calls the mock ERP directly.

### 5. Downstream outage (partial or total)

The worker selects a circuit breaker per run and immutable threshold configuration, with a separate catalog/missing-snapshot fallback. One run cannot open another run's breaker. After the configured consecutive failure threshold, the circuit opens and downstream attempts fail fast into the job's frozen retry/backoff policy. When the reset window elapses, the circuit moves to half-open and admits one probe. On success, the circuit closes and normal processing resumes. Run-qualified breaker snapshots are published to separate bounded Redis keys for active-run dashboard status.

### 6. API responsiveness under queue pressure

The API process and the worker process are fully decoupled. The API's buy path touches PostgreSQL and BullMQ only after Redis accepts a reservation. Sold-out attempts stay on the Redis-first losing path and return without durable writes or per-loser dashboard publication. The request path does not wait for queue inspection or downstream confirmation; bounded advisory queue refresh runs behind the composition-owned scheduler. Accepted generated buys resolve the run policy before shared admission and perform no nested base-pool checkout while admission is held, so lock waiters cannot exhaust the pool around a holder that needs another connection. Queue depth itself does not block API responses, but accepted-heavy runs can still consume shared PostgreSQL, Redis, and CPU capacity, so API PostgreSQL pool sizing, worker PostgreSQL pool sizing, and the worker's process-wide BullMQ concurrency are intentionally tunable.

For the public burst presets, the API listener backlog is also explicit. The default `API_LISTEN_BACKLOG=8192` avoids relying on Node's lower default accept queue when k6 opens thousands of connections in a very short window.

### 7. Admin surface abuse

Public-facing controls are narrowly scoped: curated read-only preset starts, bounded run-scoped public custom starts, public run-budget enforcement, one-active-or-draining-run gating, and traffic buyer-count/emitted-attempt/request-rate caps enforced by the API. Editable admin presets, `Custom` scratch saves, preset archival, reset, recovery actions, run-history deletion, and retained global ERP fallback fault injection require an authenticated admin session and are proxied through the Next.js dashboard server rather than called directly from browser clients. All caps are environment-configured and validated at service startup, not hardcoded in route handlers.

### 8. Dashboard read amplification

The public SSE fan-out applies atomic process-local total and per-source connection caps before registering a client. One process-local dashboard recovery boundary enforces the concurrent-build ceiling plus global and per-source fixed-window request budgets before touching PostgreSQL, Redis projections, or BullMQ. It records only admitted source counts, so the source map is bounded by the configured global request budget and is cleared on the next window. Rate exhaustion returns a retryable `429`; local concurrent-capacity exhaustion returns a retryable `503`. The default three concurrent recovery builds stay below the default API PostgreSQL pool of ten.

### 9. Lost queue and completion handoffs

The worker scans old `queued` orders and reasserts deterministic order jobs, so an API crash after commit cannot strand an order. The load orchestrator records acceptance before spawn, durably journals completion before delivery, and retains ownership until the API acknowledges the exact report. The API stores the first completion report per run and makes enrichment/finalization idempotently re-drivable. These boundaries turn process crashes and ambiguous HTTP results into replayable work rather than silent loss.

## Key Design Constraints

- The API never calls the mock ERP directly. All downstream confirmation interaction passes through the BullMQ queue.
- Inventory state lives in Redis as the fast authoritative source; PostgreSQL holds the durable business record.
- Run sale-offer stock eligibility is authoritative in the Redis inventory state and enforced inside the atomic stock decision before any PostgreSQL read. Accepted generated-run persistence and deterministic enqueue are then covered by shared PostgreSQL admission; terminal/reset transitions use the corresponding exclusive advisory lock. Admission callbacks must not check out another connection from the same bounded base pool.
- `@checkout-surge/contracts` is the single source of truth for shared types and Zod schemas across all services.
- The API owns browser-facing SSE fan-out of complete revisioned dashboard projections on `/dashboard/events`; API and worker publish transport-neutral Redis projection-dirty signals that trigger bounded projection assembly.
- Dashboard realtime is best-effort observability. The browser atomically replaces complete projections and uses one current-projection recovery read for resynchronization, never stream replay or delta reconstruction.
- API deployment traffic caps are enforced from the seven `DEMO_MAX_*` settings (buyers, total requests, request rate, duration, start delay, preallocated VUs, and max VUs). PostgreSQL persists only admin-tunable public budgets, defaults, and limits. The API validates that strict mutable row and combines it with the current environment caps through one effective-policy construction boundary for reads, updates, startup, and run enforcement.
- Dashboard browser traffic uses the public web origin; internal service URLs and control tokens stay server-side.
