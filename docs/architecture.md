# Architecture — Checkout-Surge

## Purpose

Checkout-Surge demonstrates that a Node.js service can absorb a limited-inventory checkout surge without overselling, without overwhelming a slow downstream business dependency, and without sacrificing API responsiveness. The public demo target is the `surge-10k` shape: about 10,000 synthetic buy attempts in roughly 1 second, generated by k6 against the API. The architecture is not specific to short promotional flash sales; the same pressure appears in ticket launches, product drops, presales, and other scarcity-driven purchase flows. The demo uses a mock ERP to make the downstream dependency concrete, but the same boundary could represent payment capture, fraud/risk checks, warehouse allocation, fulfillment, tax calculation, accounting, supplier APIs, or other fragile business systems. This document describes the implemented architecture.

---

## System Overview

The supported local system is intentionally split into exactly five independent application processes:

| Component | Role |
| :-- | :-- |
| `apps/api` — Fastify API gateway | Owns the buy path: validates requests, executes the Redis reservation, enqueues work, returns immediately. |
| `apps/worker` — BullMQ worker | Owns background workflows: pulls order jobs from the queue, applies frozen run retry/admission/breaker policy, calls the downstream confirmation service, persists state transitions, and runs dispatch, ERP-result, and notification recovery workflows. |
| `apps/mock-erp` — Mock ERP / downstream business system | Simulates a legacy downstream dependency with run-supplied or fallback latency/TPS/error behavior and persists successful idempotent confirmation results. |
| `apps/load-orchestrator` — k6 wrapper | Durably owns one traffic execution at a time, triggers synthetic buyer traffic from accepted run snapshots, provides authenticated run-fenced cancellation with confirmed bounded process termination, parses k6 JSON output, streams live metrics, and retries natural completion delivery to the API until acknowledged. |
| `apps/web` — Next.js dashboard | Owns the public demo picker, current-run spectator view, admin operator surface, signed visitor-cookie issuance, hardened admin sessions, and thin server-side proxying for dashboard reads and controls. Public run budgets remain API-owned. |

The dashboard (`apps/web`) is a demo and operator surface, not a customer storefront. High-volume buyers are k6-generated synthetic API attempts, not browser sessions. Public visitors use `/` to start curated read-only presets or a bounded run-scoped `public-custom` run, then observe the active run at `/watch`. Admins use `/admin` to inspect public presets, save editable admin presets, use the persisted `Custom` scratch preset, duplicate presets into editable admin copies, archive accidental operator-created copies, and start runs from accepted configuration snapshots.

The public, watch, and authenticated admin routes initialize current-run recovery as pending and hand authoritative recovery to the shared browser coordinator, which uses the signed same-origin BFF instead of a credentialless server read. Contract-validated SSE frames on watch feed a pure reconciliation reducer. Events racing an authoritative read are coalesced into the reducer's bounded projection and order windows; ordinary telemetry is replayed without another read, while accepted new-run scope and matching terminal convergence signals can request at most one immediate trailing read per recovery generation. The admin page validates the signed session on the server, renders only the sign-in island for anonymous visitors, and server-loads its other authenticated reads. Current-run, runtime-policy, preset/start, maintenance, and ERP controllers retain independent mutation state so one operation does not disable or clear unrelated features.

The reference runtime preserves this split with one container and one process for each application service. The API process is the sole maintenance authority, the load-orchestrator process owns one journal, and the worker is one runtime. k6 is installed inside the load-orchestrator runtime image; installing k6 directly on a developer host is only a convenience path for host-native development. The single Caddy dashboard proxy/edge described below is an ingress and routing boundary, not a sixth application process or another authority.

The dashboard is exposed as a single browser origin in the reference runtime. HTTP dashboard reads and controls use same-origin `apps/web` routes. The web server calls the API for run lifecycle/read operations and the Mock ERP for its retained diagnostic controls; the API calls the load orchestrator after accepting a run. The API owns the browser-facing SSE stream at `/dashboard/events` and subscribes to internal Redis Pub/Sub dashboard events for live fan-out. Caddy routes the exact `/dashboard/events` path from the dashboard origin directly to the API service, while the rest of the dashboard origin remains routed to the web service. Direct Next.js usage retains the same browser path through a web-owned byte-stream proxy to the server-only API base URL. Dashboard observability stays public for the demo; admin access gates only privileged controls. Direct service ports are available through the debug override for health checks and troubleshooting, but the normal operator path does not require browser access to them.

Browser-facing Next.js proxy routes adopt or generate one normalized correlation ID per request and forward it to the selected backend. They construct outbound headers from an explicit allow-list of required server-owned assertions rather than copying browser headers, validate every upstream error against the shared canonical envelope, and return an authoritative `x-correlation-id` that agrees with any response-body correlation field. The API, Mock ERP, and load orchestrator install the same request-scoped Fastify correlation behavior before route registration, so response headers, canonical errors, automatic request logs, and ordinary route logs share the selected ID without mutating a process-wide logger.

The API is the only application service that registers a browser CORS plugin. `WEB_ORIGIN` supplies its allowed origin list; when unset, Fastify's `origin: true` behavior reflects and permits the request origin rather than emitting a literal wildcard. The reference Compose runtime pins `WEB_ORIGIN` to the dashboard proxy origin. The web server consumes the same setting separately as the exact-Origin/CSRF and cookie-policy boundary for unsafe admin requests; Mock ERP and the load orchestrator do not register browser CORS allow-lists.

Run-start authorization has two distinct server-side assertions. Every `POST /demo/runs/start` call must carry the shared `CONTROL_SERVICE_TOKEN`, which authenticates the trusted web proxy or another service caller; an admin operator-mode assertion is honored only on that authenticated channel. A public start must additionally carry the HMAC-signed visitor credential issued by the web server, which supplies an anonymous budget principal. Neither credential establishes human identity or production-grade abuse prevention, and hosted use still requires appropriate network controls and rate limiting.

## Dashboard Realtime Model

Dashboard realtime is a live observability path, not a command transport or an event ledger. Dashboard commands and reads continue to use HTTP routes, while the API streams browser-facing telemetry with SSE and receives internal dashboard events from Redis Pub/Sub.

The API is the only browser-facing realtime owner. API and worker services publish validated transport-neutral dashboard events to the `dashboard-events` Redis channel, and each API process keeps one shared Redis subscriber for fan-out to its connected SSE clients. Browser connections are in-memory sinks only; they do not create Redis subscriptions and the gateway does not build per-client event backlogs. If a client write fails or applies backpressure, that SSE connection is closed and the browser relies on native `EventSource` reconnect.

SSE events are best-effort live hints. Publish failures are logged but must not break checkout, metric ingestion, worker processing, or demo controls. Redis Pub/Sub gaps, page refreshes, tab resumes, and stream reconnects are recovered through `/dashboard/recovery`, which returns the latest dashboard state rather than missed stream events. The public stream uses `load.run.updated`, `dashboard.metric.observed`, `order.status.updated`, and `business.event.recorded`; Surge additionally retains `business.outcome.snapshot` as an explicitly cumulative full-replacement projection. The dashboard derives lifecycle from the run snapshot status. A fresh nonterminal run snapshot whose start time proves it is newer establishes a new browser scope, clears the old scope-derived projections, and requests serialized authoritative recovery. A coherent nonterminal run hint that is too old to establish scope after an idle recovery remains rejected for direct application but requests the same serialized authoritative recovery, preventing a later-committed start from being stranded. An in-scope terminal status triggers final recovery. Replaceable run, scalar metric, and aggregate snapshot messages have no event identity; durable order transitions and durable business events retain stable IDs for deduplication. Invalid Redis messages are isolated before fan-out and logged with a stable parse stage plus bounded category/name/run/correlation metadata; raw messages and unbounded payloads are never logged. The system intentionally does not maintain SSE cursors, replay buffers, Redis Streams, or durable admin event logs for this demo surface.

Fresh Redis reservation decisions and successful API-owned BullMQ handoffs dirty an API-composed dashboard observation publisher. Queue scheduling covers both request-path deterministic enqueues and successful pending-persistence reconciliation handoffs; a reconciliation that freshly materializes and enqueues a durable buy also dirties the business-outcome projection before Redis promotion, while replay/reassertion does not. The publisher keeps a bounded latest value per inventory scope and one global queue scope and performs at most one coherent inspection/publication operation at a time. An inventory read emits literal scalar observations for `inventory.remaining` and cumulative `inventory.sold_out_rejection`; a queue inspection emits `queue.depth`. Complete `InventoryStatus` and `QueueStatus` objects remain recovery-owned. Fresh sold-out decisions synchronously dirty the inventory producer without performing I/O; one cumulative authoritative inventory read is released per dirty `(runId, saleOfferId)` at the 500 ms boundary. The pending sold-out map holds at most 64 scopes; overflow drops and logs the oldest pending sold-out scope synchronously without transport I/O. Redis advances the sold-out observation timestamp atomically with its cumulative count, so newer cumulative pressure can apply after stock stops changing. Reads and publishes are advisory and never participate in reservation, reconciliation, persistence, or enqueue correctness. Idempotent reservation replays do not dirty inventory; deterministic replay enqueue success may refresh queue depth.

Full business-outcome and consistency-lag replacement events are rebuilt behind one bounded 500 ms dirty scheduler in the API process and one in the worker runtime. Fresh reservation/order/ERP-attempt/notification mutations only mark `(runId, saleOfferId)` dirty; replays and detected persistence no-ops do not. Each scheduler permits one projection operation in flight and retains mutations observed during a read for a later window. Its pending map holds at most 64 dirty scopes in addition to the current previously captured batch, which is itself bounded to at most 64 scopes; pending overflow drops and logs the oldest pending scope. Shutdown gives pending work five seconds to finish. The individual operation already in flight at the deadline is not abortable, but the scheduler abandons its remaining captured/pending scopes so no later database or Redis operation starts after dependencies begin closing. Terminal completion does not retain a separate per-run aggregate: pending-only 500 ms state either publishes within its window or is superseded by the terminal recovery/finalization read; admin reset explicitly clears pending scopes. The single-instance reference contract therefore bounds aggregate SQL reads without a global lease; retained coordination that could tolerate duplicate cumulative publications is implementation residue, not supported replica behavior, and later simplification work owns its removal.

Enqueue publication alone cannot describe worker dequeue, retry, or terminal failure changes. After a coherent queue inspection observes backlog or active work, the API observation scheduler owns at most one unref'd two-second timer that marks the global queue scope dirty again. Its single-flight drain re-inspects the complete queue state but publishes only canonical `queue.depth` until a final inspection observes no queued or active work. Authoritative recovery returns the complete queue object. New enqueues replace the latest publication context and trigger immediate coalesced inspection without multiplying timers. Shutdown cancels the delayed refresh and drains only work already pending or in flight.

The API recovery read combines Redis-backed run-scoped live metrics with durable demo-run state. It resolves one `starting`, `active`, or `draining` run at assembly start, ordered by effective start (`startedAt` falling back to `createdAt`) with deterministic creation/ID ties, and uses that immutable selection for every run-owned projection. Recovery never substitutes a catalog offer or terminal-history row when no current run exists: inventory, business outcome, consistency lag, completion outcomes, and traffic metrics are then empty/null, while global queue and ERP health remain independently readable. The flat response identifies the request correlation ID, the selected `{ runId, saleOfferId }` scope (including `saleOfferId: null` for a visible legacy run), and one `recoveredAt` observation baseline. A `starting` run is a durable API intent: the API lifecycle poller replays the exact run ID and frozen configuration until the load orchestrator's single-slot journal confirms ownership. The orchestrator retains accepted/executing/completed evidence across restarts and retries completion delivery until the API acknowledges it. Internal metric and completion admission locks and validates the durable run lifecycle; missing, terminal, reset-fenced, or accepted-snapshot-inconsistent output receives a canonical correlated non-success instead of a false acknowledgement. A first completion transaction validates the shared snapshot-derived execution plan and redundant counts/identity/timestamps, persists immutable evidence, and moves the run to `draining` with an explicit pending enrichment state. Exact redelivery can repair enrichment/finalization, but conflicting evidence cannot perform those side effects. Finalization cannot terminalize that run until enrichment has durably concluded. Before listening or starting the finalization poller, API startup discovers draining runs once and independently re-drives sale closure, pending completion enrichment, and pending-persistence reconciliation for each candidate, so one per-run failure does not block later recovery. Missing sale ownership and partial reconciliation are reported as attributable failed recoveries rather than successful effects. Periodic lifecycle recovery continues the same idempotent work after startup. Current-run recovery includes the frozen run configuration snapshot so a refreshed or second dashboard tab shows the accepted traffic, inventory, ERP, and backpressure configuration rather than reconstructing it from editable preset drafts.

Admin reset is an API-owned recovery workflow. It durably claims each recoverable run as failed, closes Redis admission, installs a run-scoped metric-ingestion fence, and requests Task-33 confirmed cancellation using the exact run and correlation IDs. Only after cancellation succeeds does it clean reset-owned queue work, capture the final business and inventory state, write the immutable summary, and delete that run's live traffic projection. A mismatch is a `409` and cannot abort another run. An abort, admission, queue, or summary failure leaves a durable `failed/admin_reset` row without a summary; under the global run-start advisory lock, start admission detects that incomplete transition and returns `409 demo_reset_incomplete` until reset repair writes the summary. Historical admin-reset runs with summaries, including a projection-clear retry, do not block a successor. Projection failure also prevents reset success and leaves idempotent retry coordinates, but its already-confirmed abort and immutable summary permit the retry to clear only the remaining live metric key without re-aborting a successor or duplicating history. The reset does not flush Redis, delete history or inventory, or disconnect SSE clients.

Targeted smoke teardown is a distinct API-owned maintenance workflow. It briefly pauses both physical queues to close the worker-claim race, refuses non-terminal, ownership-inconsistent, malformed, or already-active work, transactionally deletes exactly one generated-owned durable graph while retaining retry coordinates, and converges that run's Redis and non-active BullMQ state. The queue adapter serializes quiescence leases within the sole API maintenance process, so an overlapping retry cannot enter until the prior request finishes its release path. Pre-commit refusal and post-commit Redis or receipt-completion failure restore queues safely, while a post-commit queue-convergence failure deliberately retains only maintenance-owned pauses so workers cannot claim orphaned jobs. A durable ownership marker beside each physical BullMQ queue stores the exact owning run ID. Claims use an atomic claim-or-compare operation: only the same run can adopt, re-pause, restore, or clear retained ownership after API restart, while a different run receives `run_queue_maintenance_owned_by_other_run` without reaching preflight or cleanup. Partial acquisition rolls back only markers newly claimed by that request and never touches a foreign marker; genuinely pre-paused queues remain untouched. The receipt keeps every post-commit failure retryable after the run row has gone. Process-local FIFO serialization is part of why additional API processes are outside the supported topology; later simplification work owns removal of coordination retained only for replica scenarios.

## The Buy Path

Every run-scoped purchase attempt follows the same two-phase flow.

**Phase 1 — Fast path (API, synchronous reservation)**

1. Starting a public or admin preset creates a `demo_runs` record with an immutable configuration snapshot, clones the baseline sale offer into a generated run sale offer, initializes durable inventory, and initializes Redis inventory with authoritative run identity and accepting state plus a lifecycle/read cache projection.
2. k6 sends the `runId` and generated `saleOfferId` with each synthetic buy attempt.
3. A Redis Lua script is the first persistence operation. It atomically validates inventory scope, the request's run identity, and the authoritative accepting state, failing closed when the run ID is omitted, mismatched, or closed and rejecting run IDs on catalog inventory.
4. The same uninterrupted Lua operation checks idempotency, decrements `remainingStock`, and creates the pending-persistence visibility sentinel and self-sufficient recovery record. Eligibility is ordered before idempotency replay. Run closure updates the state inspected by this script atomically, so reservations before closure may succeed and reservations after closure reject without mutation.
5. An accepted generated-run hold resolves the immutable retry policy from the durable run snapshot before entering admission. It then acquires a shared PostgreSQL session advisory lock for the run; terminal and reset transitions retain the corresponding exclusive lock. Inside that fenced boundary, persistence verifies durable run/sale ownership and non-terminal status. Ordinary accepted holds may therefore persist concurrently, while an exclusive transition waits for every admitted handoff. If the transition wins the narrow Redis-to-PostgreSQL race, cleanup first checks for an exactly matching durable reservation and order. Matching durable evidence is re-enqueued and promoted; only a hold with no durable buy is reversed. This terminal-safe classification lock is private to recovery and never reopens `/buy` admission.
6. On success, the API writes the reservation, initial order, and two lifecycle events in one PostgreSQL transaction and publishes a deterministic BullMQ job with the pre-resolved frozen retry policy before releasing admission. Code inside admission uses the reserved PostgreSQL session for durable operations and must never check out another connection from the same bounded base pool. After admission, the API atomically promotes the accepted idempotency response while removing pending metadata, publishes bounded dashboard updates, and returns `202 Accepted` with a `reservation_secured` response. A worker-owned dispatch scanner reasserts committed queued orders if the immediate enqueue is lost.
7. On sold-out: the API returns a `409 sold_out` response with `simulatedStatus: sold_out` directly from the Redis stock decision without writing per-loser idempotency records or emitting per-loser dashboard events. A synchronous no-I/O observation dirties the shared inventory scheduler; at most one coherent inventory read per dirty scope occurs at each 500 ms boundary and produces canonical `inventory.remaining` and cumulative `inventory.sold_out_rejection` observations. Full inventory state remains recovery-owned.
8. Other rejected stock decisions retain their source classification rather than presenting as sold out. A closed, mismatched, or otherwise ineligible run returns `409 run_not_accepting_traffic` with `simulatedStatus: sale_not_active`; `inventory_not_initialized` returns 503, `idempotency_conflict` returns 409, and `quantity_invalid` returns 400, each with `simulatedStatus: null`. Duplicate accepted requests replay the secured response without changing stock.

PostgreSQL is the final integrity boundary for these durable lifecycle writes. Reservation and order terminal states require their corresponding transition timestamps, in-progress and terminal orders require `processing_at`, order terminal timestamps cannot precede `queued_at`, and ERP attempts cannot finish before they start. ERP attempts and linked order events must agree with their referenced parent attribution; reservation-only events agree directly with their reservation, while fully unlinked events remain supported. Parent attribution changes are rejected when they would invalidate existing children. These current constraints, functions, and triggers are installed directly by the reviewed empty-database baseline.

Anonymous `GET /demo/runs/history/:runId` reads use purpose-built summary/run projections and PostgreSQL aggregate queries; they do not fetch recent order, ERP-attempt, notification, or event rows and omit persisted identifiers, correlation data, event sources, free-form diagnostics, and sale-offer IDs. The parallel `GET /admin/demo/runs/history/:runId` path requires the control token and uses bounded newest-first row queries backed by composite B-tree indexes whose leading `run_id` key is followed by the two descending timestamps used by each orders, ERP-attempts, notification, or event query. The web exposes that row-level representation only after validating the admin page session and calling the protected API path server-side. The reviewed baseline creates these indexes with ordinary transactional `CREATE INDEX`.

**Phase 2 — Slow path (worker, seconds to minutes)**

9. The worker picks up the queued job, resolves the frozen retry policy, acquires a Redis run-scoped concurrency lease, applies the run-scoped circuit breaker and ERP behavior, and advances the order through `queued → processing → confirmed` (or `failed`).
   Each actual ERP call records whether that call ended normal confirmation attempts under the delivery budget and existing retryability classification; the normalized attempt row and matching event payload carry the same terminal marker. Protected admin run-history rows return it directly, while anonymous detail exposes only closed status counts and aggregate latency metrics.
10. Mock ERP success is first-write-wins in a PostgreSQL result ledger. Worker recovery records and an autonomous scanner preserve accepted downstream results or retryable handoff failures across process/job failures; malformed poison jobs are recorded in a durable dead-letter audit table.
11. After successful confirmation, the worker enqueues and records a simulated notification. A notification scanner reasserts missing notification jobs, and failed deterministic BullMQ jobs are removed so scanner redelivery is not blocked.
12. Fresh worker mutations dirty the process-local bounded aggregate scheduler, which coalesces transition bursts into cumulative `business.outcome.snapshot` replacements rather than querying on every transition. Separately, a worker-owned bounded single-flight queue publishes write-derived `order.status.updated` events; it admits or drops each confirmed-status/canonical `order.consistency_lag` metric pair as one group before publishing the individual advisory events. This per-order path never reads aggregate tables.
13. The dashboard reflects the outcome through the API-owned SSE stream, latest-state recovery reads, and k6 metric-stream summaries for high-volume sold-out pressure.

This split is the core architectural bet: callers are never blocked by slow downstream confirmation, and the buy path remains fast regardless of what is happening in the queue.

`POST /buy` remains an acceptance surface: an idempotent replay returns the original secured reservation and queued order even after durable processing advances. Public callers read current durable progress through `GET /orders/:publicOrderId/status`. That PostgreSQL-backed projection returns the current reservation and order states, nullable lifecycle and failure fields, confirmation lag only for confirmed orders, and a chronological lifecycle timeline. Its correlation ID always belongs to the lookup request; persisted correlation IDs, the internal order UUID, and event payload/source data are not exposed.

## The Four Signals

The dashboard surfaces four signals that make system behavior visible under load:

| Signal | What it shows |
| :-- | :-- |
| **Request surge** | API requests per second as the k6 burst hits. |
| **Queue depth** | BullMQ backlog depth, which grows when downstream throughput lags behind the reservation rate. |
| **Inventory drain** | Remaining stock countdown as reservations succeed. |
| **Consistency lag** | p95 delta between the initial buy timestamp and the final downstream confirmation. |

## Failure Modes Absorbed

### 1. Overselling under concurrent load

The Redis Lua script is the exclusive gate for stock decisions. It reads and decrements `remainingStock` in a single atomic operation; no number of simultaneous requests handled by the supported API process can reserve the same unit twice. The first request that decrements from 1 to 0 succeeds; every subsequent concurrent attempt reads 0 and receives a sold-out response. The Lua operation runs on the single reference Redis service and cannot be interrupted mid-execution; this atomicity claim is not a broader horizontal-deployment contract.

### 2. Duplicate or retried buy requests

Each accepted request carries a client-supplied idempotency key scoped to the generated run sale offer. After the Lua script confirms that the inventory still accepts that run, it checks this key before any accepted stock decision. Retries for accepted or pending reservations replay the stored outcome without consuming additional stock while the run remains accepting; closure fails closed before replay. Retries with the same key but different parameters are rejected as an idempotency conflict rather than silently producing a different accepted result. Sold-out responses are intentionally not stored per request, which keeps the losing side cheap during public scarcity-driven spikes.

For duplicate buyer-spike traffic, repeated accepted idempotency replays can increase the raw accepted HTTP response count without increasing durable stock reservations. Finalization and terminal run summaries therefore count complete duplicate buyer-spike deliveries by durable unique reservations, while planned attempts still show the full emitted duplicate-attempt total.

### 3. Partial persistence failures (Redis succeeds, PostgreSQL fails)

If the Redis stock hold succeeds but the subsequent PostgreSQL write fails, the system preserves the Redis hold and returns `reservation_pending_persistence` rather than silently discarding a secured unit. The hold is tracked by a sentinel, companion recovery record, and global index created atomically with the stock decision; reconciliation reads that index in bounded batches. Failed records are atomically moved to the back of both sorted indexes so a retryable oldest record cannot starve later pages. The inventory status endpoint exposes the pending count and the age of the oldest hold while PostgreSQL is unavailable. An eligible request retry can reconcile the hold while admission remains open. After closure, API startup and run finalization invoke the autonomous reconciler without reopening `/buy`: it restores or finds the durable reservation/order, reasserts the deterministic queue job, marks the durable pending row reconciled, promotes Redis, and clears the sentinel. Terminal-safe cleanup checks exact durable attribution first and reverses only when PostgreSQL proves there is no durable buy. Promotion and reversal each atomically update the per-sale pending set, companion hash, global index, and relevant hold/idempotency/inventory state.

Each reconciler invocation processes at most one bounded page. A periodic lifecycle poll can invoke one global page and then one per-run finalizer page, so a sale may advance twice during the same poll. Drain timeout can select a failed outcome, but it cannot waive pending-hold convergence: any nonzero or unreadable Redis pending count keeps the run in `draining` across later polls and API restarts. Whether unresolved pending persistence crossed the traffic boundary comes from the durable traffic-completion inventory snapshot, so a restart after a global cleanup pass cannot change the eventual timeout reason. An absent boundary snapshot remains valid legacy/no-inventory evidence, while a present malformed snapshot is corrupt durable evidence and blocks finalization. The final business, recovery, pending-sentinel, and inventory reads run through the terminal writer's transaction facade while its exclusive run lock is held; this avoids an unfenced read and a nested base-pool checkout. The in-fence inventory reread uses a required signal-aware operation with a fixed two-second whole-operation deadline. API composition owns its short-lived Redis client and disconnects it on abort and normal completion. A timeout returns no prepared summary, so the PostgreSQL transaction and advisory xact lock end without a terminal transition or event and a later poll can retry. Redis supplies the terminal snapshot's sold-out count, and it must equal the paired durable sold-out aggregate before the run and summary can commit. The earlier traffic-completion inventory observation remains boundary evidence and is not copied as terminal state.

### 4. Downstream slowness and TPS exhaustion

The mock ERP, standing in for a slow downstream business system, applies the ERP behavior captured in the run snapshot, including latency, TPS cap, failure mode, and outage-style behavior. The single worker runtime's retained Redis lease gate caps simultaneous in-flight handlers per run; jobs that cannot acquire a lease are delayed with bounded deferral rather than entering the downstream call. The lease mechanism remains truthful implementation detail pending later simplification, not support for multiple worker runtimes. The queue depth signal makes this buffer effect visible in the dashboard. The API reservation path is unaffected by downstream latency because it never calls the mock ERP directly.

### 5. Downstream outage (partial or total)

The worker selects a circuit breaker per run and immutable threshold configuration, with a separate catalog/missing-snapshot fallback. One run cannot open another run's breaker. After the configured consecutive failure threshold, the circuit opens and downstream attempts fail fast into the job's frozen retry/backoff policy. When the reset window elapses, the circuit moves to half-open and admits one probe. On success, the circuit closes and normal processing resumes. Run-qualified breaker snapshots are published to separate bounded Redis keys for active-run dashboard status.

### 6. API responsiveness under queue pressure

The API process and the worker process are fully decoupled. The API's buy path touches PostgreSQL and BullMQ only after Redis accepts a reservation. Sold-out attempts stay on the Redis-first losing path and return without durable writes or per-loser dashboard publication. The request path does not wait for queue inspection or downstream confirmation; bounded advisory queue refresh runs behind the composition-owned scheduler. Accepted generated buys resolve the run policy before shared admission and perform no nested base-pool checkout while admission is held, so lock waiters cannot exhaust the pool around a holder that needs another connection. Queue depth itself does not block API responses, but accepted-heavy runs can still consume shared PostgreSQL, Redis, and CPU capacity, so API PostgreSQL pool sizing, worker PostgreSQL pool sizing, and aggregate worker scanning concurrency are intentionally tunable.

For the public one-second presets, the API listener backlog is also explicit. The default `API_LISTEN_BACKLOG=8192` avoids relying on Node's lower default accept queue when k6 opens thousands of connections in a very short window.

### 7. Admin surface abuse

Public-facing controls are narrowly scoped: curated read-only preset starts, bounded run-scoped public custom starts, public run-budget enforcement, one-active-or-draining-run gating, and traffic buyer-count/emitted-attempt/request-rate caps enforced by the API. Editable admin presets, `Custom` scratch saves, preset archival, reset, recovery actions, run-history deletion, and any retained global ERP diagnostic controls require an authenticated admin session and are proxied through the Next.js dashboard server rather than called directly from browser clients. All caps are environment-configured and validated at service startup, not hardcoded in route handlers.

### 8. Dashboard read amplification

The public SSE fan-out applies atomic process-local total and per-source connection caps before registering a client. Dashboard recovery acquires a small process-local concurrency permit and an atomic Redis global/per-source fixed-window budget before touching PostgreSQL, Redis projections, or BullMQ. Rejections return retry guidance, limiter failures fail closed, and the default three concurrent recovery builds stay below the default API PostgreSQL pool of ten.

### 9. Lost queue and completion handoffs

The worker scans old `queued` orders and reasserts deterministic order jobs, so an API crash after commit cannot strand an order. The load orchestrator records acceptance before spawn, durably journals completion before delivery, and retains ownership until the API acknowledges the exact report. The API stores the first completion report per run and makes enrichment/finalization idempotently re-drivable. These boundaries turn process crashes and ambiguous HTTP results into replayable work rather than silent loss.

## Key Design Constraints

- The API never calls the mock ERP directly. All downstream confirmation interaction passes through the BullMQ queue.
- Inventory state lives in Redis as the fast authoritative source; PostgreSQL holds the durable business record.
- Run sale-offer stock eligibility is authoritative in the Redis inventory state and enforced inside the atomic stock decision before any PostgreSQL read. Accepted generated-run persistence and deterministic enqueue are then covered by shared PostgreSQL admission; terminal/reset transitions use the corresponding exclusive advisory lock. Admission callbacks must not check out another connection from the same bounded base pool.
- `@checkout-surge/contracts` is the single source of truth for shared types and Zod schemas across all services.
- The API owns browser-facing SSE fan-out on `/dashboard/events`; API and worker publish transport-neutral dashboard realtime events through Redis Pub/Sub.
- Dashboard realtime is best-effort observability. Latest-state recovery reads are the resynchronization strategy, not stream replay.
- API deployment traffic caps are enforced from the seven `DEMO_MAX_*` settings (buyers, total requests, request rate, duration, start delay, preallocated VUs, and max VUs) and overlaid onto the durable public policy on every read/start/update. Compose mirrors those settings into the one-shot setup service only so first-seed public values are validated and compatibility-stored against the deployed caps. PostgreSQL remains authoritative for admin-tunable public budgets, defaults, and limits after first bootstrap.
- Dashboard browser traffic uses the public web origin; internal service URLs and control tokens stay server-side.
