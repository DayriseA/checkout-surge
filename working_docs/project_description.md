# Checkout-Surge - Project's Blueprint

This document is designed to serve as the project's "Internal RFC" or "Design Doc."

---

## Project Goal:

To demonstrate expertise in building resilient, high-performance distributed systems capable of handling extreme limited-inventory checkout spikes while gracefully managing slow, legacy downstream dependencies (ERPs).

---

## 1. High-Level Architecture

The system is designed as a series of decoupled microservices that communicate via a high-speed Redis layer and asynchronous queues.

### Core Components:

1.  **The Dashboard Simulation UI (Frontend):** A React/Next.js dashboard with a public demo picker, current-run live watch route, admin operator console, and run history. There is no customer storefront requirement.
2.  **The API Gateway (Backend):** A high-throughput **Node.js (Fastify)** server that handles the initial "Buy" requests.
3.  **The Load Orchestrator (The "Hammer"):** A wrapper around **k6** that simulates many concurrent users (e.g. 10,000+, configurable) and streams performance metrics back to the dashboard.
4.  **The Mock ERP (The "Bottleneck"):** A specialized service designed to simulate a legacy system with configurable latency and failure rates.
5.  **The Real-Time Dashboard:** A specialized dashboard UI to trigger request surges, configure ERP constraints through the admin route, monitor active runs via SSE backed by Redis Pub/Sub dashboard events, and verify aggregate run outcomes.

For the purposes of this project, the frontend is a demo/operator surface rather than a customer storefront. Public visitors use `/` to choose curated presets or a bounded run-scoped public custom run, `/watch` to observe the current active run, and `/run-history` to inspect public-safe historical details; trusted operators use `/admin` for preset editing, recovery, deletion, and diagnostics. The 10,000+ synthetic buyers are generated by k6 as direct API traffic, not by browser clients, so a customer storefront would be distracting scope. Logical route isolation and explicit access protection for the admin surface are sufficient for this project, rather than requiring full deployment-level separation.

The deployed demo access model is documented in `docs/admin_access_protection.md`: public visitors may inspect public dashboard surfaces and use only tightly capped demo controls, while authenticated admin operators use a server-side dashboard session/proxy path for reset, chaos, and full load-run controls. Dangerous-control caps are environment-configured and enforced server-side.

The project is a realistic systems simulation: external actors such as buyers, the ERP, and notifications are simulated, but the concurrency path, Redis reservation logic, queueing behavior, persistence model, worker backpressure, and observability signals are real implementation concerns.

## 2. Technical Feature Set & Deep Dives

### A. Inventory Management (The Redis "Hot Path")

- **Problem:** Traditional Database ACID transactions are too slow for 10k+ requests per second.
- **Solution:** Use Redis for **Atomic Inventory Reservation**. Before any database record is touched, the system uses Redis `DECR` (or a Lua script) to check and reserve stock for the active sale offer.
- **Benefit:** Prevents overselling atomically. 

### B. Asynchronous Order Processing (The Buffer)

- **Problem:** The downstream business system cannot handle the spike; hitting it directly would crash it.
- **Solution:** Once Redis secures stock for the active sale offer, the system enqueues order-processing work into a **Redis-backed Queue (BullMQ)**.
- **API Experience:** The caller receives a "Reservation Secured" response immediately. The final "Order Confirmed" outcome is emitted once the background worker successfully talks to the ERP.

### C. The Mock ERP & Backpressure

- **Configuration:** Each accepted run freezes its ERP settings:
  - `erpConfig.latencyMs`: Artificial delay (e.g., 500ms).
  - `erpConfig.maxTps`: Max transactions per second before it returns `429 erp_capacity_exceeded` with `Retry-After: 1`. A forced outage or an injected error returns 503 instead.
- **Run configuration (implemented):** Every purchase uses the ERP configuration frozen in its accepted run. There are no global purchase fallback controls.
- **Worker Strategy (implemented):** Dispatch is paced at the ERP's *declared* capacity through the order-process queue's native BullMQ rate limit and global concurrency, configured by the API from the accepted snapshot — not by a learned or additively-increasing rate. On top of that, the worker keeps durable per-scope capacity cooldowns (honouring the ERP's `Retry-After`), a **separate availability circuit** with at most one probe per scope per five seconds, worker-wide and per-scope in-flight ceilings, and request deadlines derived from observed latency. Capacity feedback and availability feedback are deliberately distinct signals. Adaptive limiters would only be needed if the downstream capacity were unknown; here it is declared.

### D. The Load Generator (Orchestrated k6)

- **Engine:** k6 (Go-based), triggered through a project-owned wrapper service. The reference development and demo runtime should run this wrapper in its own container with k6 installed inside the image, so Dev Containers, Codespaces, and hosted environments share the same load-generation assumptions. Host-native execution remains a convenience workflow for fast local iteration, not the architectural baseline.
- **Integration:** A wrapper service triggers k6 scripts via CLI and parses the JSON output stream. The wrapper owns the k6 binary/runtime boundary; the API, dashboard, worker, and ERP services must not depend on host-installed k6.
- **Reporting:** Metrics (p95 latency, requests/sec, failure rate) are sent to the API, projected into dashboard recovery state, and forwarded to the Simulation Dashboard over SSE.
- **Run Outcomes:** k6 can validate immediate HTTP responses from the API, but asynchronous business completion must be tracked by Checkout-Surge itself through durable order, ERP, and simulated-notification records tied to the load run.

## 4. Key Performance Metrics to Showcase

To prove your expertise, your dashboard must visualize these four "Gold Signals":

1.  **Request Surge:** The 10k scarcity-driven purchase attempts hitting the API in < 1 second.
2.  **Queue Depth:** The "Pressure Cooker" effect—thousands of jobs waiting in Redis while the ERP processes them slowly.
3.  **Inventory Drain:** The millisecond-accurate countdown of stock as Redis processes the burst.
4.  **Consistency Lag:** The time difference between the initial buy request and the final ERP confirmation.

---

## 5. Infrastructure Tuning (The "Expert" Touch)

To ensure the system survives the "Hammer," the following OS-level optimizations will be documented:

- **`ulimit -n 65535`**: Increasing file descriptors for high concurrent connections.
- **TCP Fast Open**: Reducing latency for repeated connections.
- **Load Balancer Config**: Configuring Nginx/Caddy to handle massive header buffers.

## 6. Project Roadmap

Items 1 to 8 are delivered; items 9 and 10 remain future work. The durable roadmap shape is:

### Primary Track (Node.js / Fastify)

1.  **Foundation:** Define delivery constraints, repository layout, local infrastructure, cross-service conventions, and automated testing agreements.
2.  **Shared platform:** Establish the domain model, PostgreSQL/Drizzle schema, shared contracts, structured logging, correlation IDs, health checks, and baseline tests.
3.  **Thin vertical slice:** Connect the initial dashboard, Fastify API, and persistence path so the system is runnable before high-scale behavior lands.
4.  **Redis reservation hot path:** Implement run-scoped atomic inventory reservation, idempotency, pending-persistence visibility, and inventory-status projection.
5.  **Asynchronous business pipeline:** Move successful reservations through BullMQ workers, order state transitions, ERP attempts, resilience controls, and simulated post-confirmation notification records.
6.  **Dashboard and load orchestration:** Add API-owned SSE/recovery, public/admin dashboard surfaces, durable presets, k6 traffic execution, metric streaming, and immutable run-history summaries.
7.  **Access protection and runtime topology:** Protect public/admin controls, containerize the reference local runtime, run k6 inside the load-orchestrator image, and validate dashboard-triggered load runs through the Caddy single-origin proxy.
8.  **Run lifecycle finalization:** Treat k6 traffic completion separately from business completion, keep API-owned runs in `starting -> active -> draining -> completed | failed`, and finalize summaries only after run-scoped business work settles.
9.  **Hosted deployment readiness:** Define hosted packaging, reverse-proxy/connection handling, operational validation, and infrastructure tuning once the local reference runtime is stable.

### Optional Follow-Up Track (Go port - Side-by-Side Benchmark)

10. **Optional Go comparison:** Re-implement the API Gateway and background worker in **Go (Gin/Fiber)**. All other services (Redis, Postgres, k6, dashboard) remain shared.
    - Each backend manages its own isolated Redis inventory namespace (e.g., `inventory:node` vs. `inventory:go`) to ensure a fair, independent comparison.
    - The Simulation Dashboard gains a split-screen panel showing both backends under identical synthetic load, visualizing p95 latency, memory usage, RPS, and queue drain rate in real time.
    - This phase targets **Backend/Platform/SRE** positioning, while the Node.js track targets **Senior Full-Stack** positioning.
