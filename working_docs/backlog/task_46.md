## Current behavior and the scope leak

- `PostgresDashboardRecoveryContextReader.readContext(now)` first queries `demoRuns` for statuses `starting`, `active`, or `draining`, orders by `demoRuns.updatedAt DESC`, and takes one row. If found, `toDemoRunSnapshot()` returns the run contract and the context returns its optional `saleOfferId`.
- If that query finds no row, the same reader performs a second query against `saleOffers`: `purpose = "catalog"`, `isActive = true`, `saleStartsAt <= now`, and `saleEndsAt >= now`, ordered by `updatedAt DESC`, limited to one. It then returns `{ currentRun: null, saleOfferId: catalogOffer?.id ?? null }`. This is the defect: an absence of current-run authority is silently converted into catalog scope.
- `DashboardRecoveryService.getRecovery()` turns any non-null `context.saleOfferId` into a projection scope. It adds `runId` only when `context.currentRun` exists. Consequently the catalog fallback invokes inventory plus `readBusinessOutcomeSummary()`, `readConsistencyLagSummary()`, and `readRecentCompletionOutcomes()` with sale-offer-only filters. Those readers deliberately prefer `runId = ...` when supplied and otherwise fall back to `saleOfferId = ...`; the recovery fallback therefore exposes catalog reservations/orders/notifications as if they were the current demo.
- The run-scoped business reader counts secured reservations, order states, retrying orders, pending persistence, notifications, and the run-level sold-out outcome. The lag reader joins orders to reservations and computes confirmed/pending counts plus average, p95, maximum, and oldest-pending age. Completion recovery orders up to eight rows by the latest lifecycle timestamp and enriches each with its latest ERP attempt and notification. These are useful projections, but none is valid current-run recovery when no current run was resolved.
- Traffic metrics are read using `trafficMetricReader.readRecent(context.currentRun?.runId ?? null)`. The concrete Redis reader returns `[]` for `null`, but the service still calls the port; strict no-run behavior should be explicit in the application service rather than depend on one adapter's convention.
- Queue and ERP are global operational-health projections, not sale-offer/run records. They may still be read without a current run. Inventory, business outcomes, consistency lag, completion outcomes, and traffic metrics are run/sale-context projections and must remain empty/null when current-run resolution yields no scope.
- Each projection is isolated through `readSafely()`. A failed context read degrades to `{ currentRun: null, saleOfferId: null }`; other failures log `Dashboard recovery projection unavailable.` with `{ err, projection }` and use the contract's null/empty fallback. Preserve this per-projection degradation and do not turn recovery into an all-or-nothing read.

## Embedded `checkout-forge` behavior

### Current-run resolution and ordering

- `checkout-forge/apps/api/src/services/dashboard-recovery-service.ts::DashboardRecoveryService.getRecovery({ correlationId })` calls `getCurrentLoadRun()` before requesting any snapshot. It then calls `DashboardSnapshotService.getSnapshot({ correlationId, runId: currentLoadRun?.runId ?? null })`; traffic metrics and a terminal summary are also derived only after that run has been selected.
- `getDurableCurrentRun()` asks `DemoRunRepository.listRecoverableRuns(["starting", "active", "draining"])` and takes its first row. `checkout-forge/apps/api/src/repositories/demo-run-repository.ts::listRecoverableRuns()` filters with `inArray(demoRuns.status, statuses)` and orders by `demoRuns.startedAt DESC`. The selected durable row is converted by `currentLoadRunFromDemoRun()` to `{ runId, presetName, status, startedAt, trafficEndedAt, finalizedAt, errorMessage, configSnapshot }` and validated by `dashboardCurrentLoadRunSchema`.
- Forge also maintains an in-memory `DashboardRecoveryStateService`. If only durable or only in-memory state exists, that value wins. If both describe the same run, in-memory lifecycle state wins and durable `configSnapshot` fills a missing in-memory snapshot. If they describe different runs, the later `startedAt` wins. `DashboardRecoveryStateService.observeCurrentLoadRun()` rejects cross-run updates unless the incoming run is a newer `starting` run, refuses terminal-to-nonterminal regression, and clears remembered traffic metrics when accepting a new run.
- Latest traffic metrics are returned only when a current run exists and are filtered with `metric.runId === currentLoadRun.runId`. The state service keeps only recognized traffic metric names, retains the newest `observedAt` value per metric name, and returns them sorted lexicographically by `metricName`; this is latest-per-name state, not a chronological recent-sample list.

### Snapshot filtering and no-current-run behavior

- `checkout-forge/apps/api/src/services/dashboard-snapshot-service.ts::getSnapshot()` resolves one `snapshotScope` containing `runId` and `saleOfferId`. With an explicit recovery `runId`, `getSnapshotDemoRun()` uses `getDemoRunById()`; otherwise it asks `getActiveDemoRun()`, whose durable filter is again `starting|active|draining`, ordered by `startedAt DESC`.
- Inventory is read only when the resolved run supplies a sale offer. Orders, consistency lag, order-status rows, recent-order rows, and notifications use `runId` first, then `saleOfferId`, and finally `sql\`false\`` when neither exists. Thus an empty scope produces zero run outcomes and empty order collections rather than falling through to catalog/global business data. Recent orders are ordered by `queuedAt DESC` and limited to ten; status snapshots are ordered by `queuedAt ASC, id ASC`.
- Queue health and ERP resilience remain globally readable. This is the useful boundary to preserve in Checkout Surge: no current run means no run-owned business projection, not that infrastructure health becomes unreadable.

### Self-describing response contract

- `checkout-forge/packages/contracts/src/dashboard.ts::dashboardRecoveryResponseSchema` returns these top-level fields: `correlationId`, `observedAt`, `snapshot`, `currentLoadRun`, `latestTrafficMetrics`, and `terminalRunSummary`. `snapshot` is itself self-describing with its own `correlationId` and `observedAt`, plus `inventory`, `queue`, `erp`, `runOutcomes`, `consistencyLag`, `orderStatuses`, `recentOrders`, and optional/null `appliedBackpressurePolicy`.
- `terminalRunSummary` is looked up by exactly `currentLoadRun.runId`, and only if that current load run is `completed` or `failed`; otherwise it is `null`. It is not a "latest summary" fallback. This prevents a historical summary from being relabeled as current recovery.
- The route `checkout-forge/apps/api/src/routes/dashboard-recovery.ts::registerDashboardRecoveryRoutes()` obtains the request correlation ID and passes it into the service. The response `observedAt` is captured by the recovery service after its reads; the nested snapshot independently captures its observation time when snapshot assembly begins. Neither timestamp is an event-time watermark for individual rows.

## Reference limitations and target compatibility

- Forge's behavior is evidence for scope and response semantics, not a drop-in design. Its durable lookup excludes terminal rows, while its in-memory service may retain a just-finalized terminal run; after process restart the same terminal run is no longer recoverable. This makes `terminalRunSummary` availability dependent on process history. Checkout Surge's current durable definition is explicitly a blocking/current run (`starting|active|draining`) and its run-history contracts own terminal artifacts; do not introduce restart-dependent terminal-current semantics merely to copy this field.
- Forge resolves recovery once and then its snapshot service can resolve again when passed `null` (`getActiveDemoRun()`). A run starting between those reads could make the snapshot describe a run that `currentLoadRun` says is absent. Checkout Surge should pass one resolved context through all run-scoped reads and must not perform a second implicit current-run or offer fallback.
- Forge's in-memory-versus-durable arbitration is unnecessary here because Checkout Surge already reconstructs the current run from PostgreSQL and stores recent traffic samples in Redis keyed by run ID. Do not add an in-memory source of truth, and do not let Redis metric state select a run.
- Forge's `latestTrafficMetrics` contract is latest-per-name and sorted by metric name. Checkout Surge's existing `recentMetrics` is a chronological retained sample window (the Redis adapter returns the last 20 in list order). Preserve the target semantic and field name unless a separately scoped contract migration explicitly changes all web consumers.
- Checkout Surge web reducers use `recoveredAt` as the baseline watermark: events with `occurredAt < recoveredAt` are ignored. Keep `recoveredAt` and its meaning compatible. Adding an `observedAt` alias with a different capture time would create two competing freshness clocks; prefer one documented recovery observation timestamp.
- A strict Zod response means additive fields require coordinated contract, API, and web fixture changes. Avoid a wholesale Forge-shaped nesting/rename (`snapshot`, `currentLoadRun`, `latestTrafficMetrics`) that would churn the existing dashboard without improving authority. Add only target-native metadata that lets a consumer identify the request, resolved scope, and freshness while retaining existing flat projection fields.

## Required target adaptation

1. Remove the catalog-offer query and the `saleOffers`/date-filter imports from `PostgresDashboardRecoveryContextReader`. If there is no `starting|active|draining` `demoRuns` row, return `{ currentRun: null, saleOfferId: null }`. Since offer-window time is no longer part of context resolution, simplify `DashboardRecoveryContextReader.readContext(now)` to `readContext()` (or otherwise make the unused clock parameter disappear consistently). Do not substitute the newest terminal run, a run-history summary, a generated offer found independently, or any catalog offer.
2. Make current-run selection represent run creation recency rather than mutation recency. Use an effective-start ordering equivalent to `coalesce(demoRuns.startedAt, demoRuns.createdAt) DESC`, then `demoRuns.createdAt DESC`, then `demoRuns.id DESC` as a deterministic tie-breaker. `updatedAt DESC` can let a stale recoverable row that received a late update displace the genuinely newer run. The normal invariant should still be one recoverable run; deterministic ordering is defensive recovery, not permission to blend multiple runs.
3. Derive one immutable context/scope for the entire recovery call. A current run with a sale offer produces `{ runId, saleOfferId }`; no current run produces no scope. If a legacy/corrupt current row lacks `saleOfferId`, keep the `currentRun` visible, allow metrics to use its `runId`, but return null/empty sale-offer-dependent projections and log/represent the missing scope honestly. Never broaden a run-ID read to sale-offer-only when the run ID is known.
4. Skip inventory, business outcome, lag, completion-outcome, and traffic-metric ports when no current run exists. Return `inventory: null`, `businessOutcome: null`, `consistencyLag: null`, `recentCompletionOutcomes: []`, and `recentMetrics: []`. Continue reading queue and ERP as global health. If a current run exists but its sale offer is missing, only `recentMetrics` may still be read by run ID.
5. Extend `dashboardRecoveryResponseSchema` with request/scope metadata without replacing the established flat projections. Add `correlationId: correlationIdSchema` and `scope: z.object({ runId: uuidSchema, saleOfferId: uuidSchema.nullable() }).strict().nullable()`. `scope: null` must unambiguously mean no current run was selected; a selected legacy run is `{ runId, saleOfferId: null }`, not "no run." Retain `currentRun`, all existing projection fields, and `recoveredAt`, and enforce `scope.runId === currentRun.runId` plus matching sale-offer identity whenever both are present.
6. Pass `request.correlationId` from `registerDashboardRoutes()` into `DashboardRecoveryService.getRecovery(...)`, matching the existing thin-route/application-service boundary. Capture `now` once before context/projection reads. Use that exact instant for lag measurement, completion display-state derivation, `recoveredAt`, and the recovery metadata; do not call `new Date()` independently for competing top-level timestamps.
7. Keep `recoveredAt` as the recovery baseline used by the web freshness guard, captured once at assembly start as it is today, and document its ordering rule: an SSE event strictly older than the baseline is stale; an equal-time event remains eligible and is then checked against run/sale-offer scope. Do not infer freshness from database `updatedAt`, metric list position, or response arrival order. A later recovery response supersedes an earlier one only according to this baseline and the browser's serialized recovery workflow.
8. Preserve graceful degradation, but do not confuse degradation with absence of scope. A context-read failure must produce `currentRun: null`, `scope: null`, and empty/null run projections while queue/ERP may still succeed; it must be warned as `dashboard_run_context`. A scoped projection failure retains the selected `currentRun` and `scope` and degrades only that projection. Do not fall back to a different run/offer after any error.
9. Update API/web call sites and fixtures for the additive metadata. The web should continue using the same flat fields and `recoveredAt`; it may use explicit `scope` to reject cross-run events, but task 28 remains the owner of reducer reset/re-recovery behavior on scope changes. Keep compatibility with task 44's bounded metric delivery and task 45's advisory failure containment: recovery reads retained metrics, not Pub/Sub delivery success.

## Stale, cross-run, and no-run cases

- **No recoverable row:** return `currentRun: null`, `scope: null`, null/empty run projections, plus independently recovered queue/ERP and request/freshness metadata. An active catalog offer must have no effect.
- **Old terminal data only:** do not promote it into current recovery, even if its offer remains active or its summary is the newest. It belongs to run history.
- **Multiple recoverable rows:** select exactly one newest effective start deterministically and scope every projection to that run ID. Never merge inventory from one run with outcomes or metrics from another; warn if useful, but do not broaden scope.
- **Late metric/list contents:** ask the metric reader for the selected run ID only. Redis data under another run's key cannot appear. Samples older than the recovery instant may legitimately be part of the retained baseline; `recoveredAt` governs subsequent SSE application, not deletion of historical samples.
- **Context changes during assembly:** the response describes the single context selected at the start of the read. A run starting or finalizing concurrently is reconciled by the next recovery/SSE cycle. Do not re-resolve halfway through and produce a mixed response.
- **Projection failure:** retain the selected scope and freshness metadata so a client can distinguish "this run, projection unavailable" from "no current run." Never use catalog or prior-run values as degraded defaults.
