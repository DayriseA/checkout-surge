## Task details

- **Priority:** P4 — pulled into the P0 cluster: apply opportunistically while the surrounding fencing/outbox entries rewrite these services
- **Area:** API architecture
- **Source:** donor comparison (Opus graded better; GPT at parity)
- **Solved elsewhere:** Opus implements this as four small lifecycle application services with narrow, explicitly injected ports. Use the following as concrete donor context rather than requiring access to that worktree:
  - `apps/api/src/services/run-start-service.ts` owns only start validation, durable provisioning, inventory initialization, sale-eligibility opening, traffic delegation, promotion to `active`, and failure compensation. Its `RunStartServiceDeps` accepts `PresetConfigSource`, `CurrentRunSource`, `RunStore`, `TrafficRunLauncher`, `RunSummaryWriter`, `PublicRunBudget`, `RunSaleEligibility`, and an `InitializeRunInventory` function, plus deployment values, `generateId?: () => string`, `now?: () => Date`, and an optional logger. The read contracts expose only `findPresetBySlug`, `getActivePublicRuntimePolicy`, `getCurrentRun`, and `getRunById`; the service never imports a database or Redis client.
  - `apps/api/src/services/run-store.ts` is the lifecycle write port. `RunStore` names the allowed transitions (`createRun`, `markActive`, `markFailed`, `markDraining`, `markTrafficFailed`, `markCompleted`, and `failDrainingRun`) and defines `RunAlreadyInProgressError` at the port boundary so the start workflow can map the durable single-active-run conflict without knowing PostgreSQL error details. `apps/api/src/services/postgres-run-store.ts` is the adapter. Keep read and write capabilities separate; do not replace them with a broad repository exposing raw persistence operations.
  - `apps/api/src/services/traffic-run-launcher.ts` separates the `TrafficRunLauncher` port from `HttpTrafficRunLauncher`. The HTTP adapter receives a replaceable `FetchLike`, timeout, and base URL, validates the acknowledgement, and translates transport failures to `TrafficRunLaunchError`. This lets the start-service tests record launch requests and exercise compensation without network I/O.
  - `apps/api/src/services/run-finalization-service.ts` owns the draining-to-terminal decision and depends on `FinalizationReader`, `RunStore`, `RunSummaryWriter`, `PendingPersistenceReconciler`, and `RunSaleEligibility`. `apps/api/src/services/finalization-store.ts` defines the query-shaped `FinalizationReader` (`listDrainingRuns`, unsettled-order and missing-notification counts, and finalization input) and supplies `PostgresFinalizationStore`. The awaitable `finalizeReadyRuns()` contains the business workflow; `start()`/`stop()` only manage polling and a non-overlap guard. `now` makes settle-timeout decisions deterministic.
  - `apps/api/src/services/startup-reconciliation-service.ts` has the narrower `StartupReconciliationRunSource` and only requests `Pick<RunStore, "markFailed">`, a summary writer, eligibility authority, reconciler, clock, and logger. It fails interrupted `starting`/`active` runs and leaves `draining` runs recoverable. `apps/api/src/services/demo-reset-service.ts` follows the same pattern with `ResetRunSource`, `Pick<RunStore, "markFailed">`, `ClearRunLiveState`, and `QueueCleaner`; it makes the required ordering (fail, close eligibility, capture summary, clear live state, then clear queues) directly testable.
  - `apps/api/src/services/run-summary-writer.ts`, `apps/api/src/services/run-sale-eligibility.ts`, and `apps/api/src/services/queue-cleaner.ts` are capability boundaries shared by those workflows. Their concrete PostgreSQL, Redis, and BullMQ implementations remain outside the lifecycle services. `apps/api/src/index.ts` is the composition root: it constructs `PostgresRunStore`, `PostgresRunSummaryWriter`, `RedisRunSaleEligibility`, `PendingPersistenceReconciler`, `PostgresFinalizationStore`, `HttpTrafficRunLauncher`, and the inventory/cleanup functions, then injects them into the four services. Routes receive the already-composed services and remain thin.
  - The unit-test pattern is directly reusable. `apps/api/test/unit/run-start-service.test.ts` uses recording implementations of every port plus fixed IDs and time to assert provisioning/delegation order and each failure-compensation path. `apps/api/test/unit/run-finalization-service.test.ts` drives `finalizeReadyRuns()` directly with fake readers/stores and a fixed clock to cover settled, blocked, timed-out, shortfall, and lost-transition cases. `apps/api/test/unit/startup-reconciliation-service.test.ts` and `apps/api/test/unit/demo-reset-service.test.ts` record collaborator calls to assert status-specific behavior and destructive ordering. The donor also retains infrastructure-backed coverage in `apps/api/test/api/run-finalization.test.ts`, `apps/api/test/api/startup-reconciliation.test.ts`, `apps/api/test/api/demo-runs.test.ts`, and `apps/api/test/api/demo-reset.test.ts`; ports supplement rather than replace adapter integration tests.

  **Mapping to the current branch:**

  **Adaptation caveats and verification:** the donor uses different contract names and lifecycle payload shapes, so copy the dependency direction and capability granularity, not donor types or behavior verbatim. The current services already accept `now?: () => Date` (and `generateId` where relevant); retain those seams instead of introducing a second clock abstraction unless multiple services need a shared clock contract. Avoid a big-bang `ILifecycleRepository`, passing concrete infrastructure clients through disguised callback bags, or relocating business ordering into adapters. Retain or add infrastructure coverage for each new PostgreSQL/Redis/queue/outbox adapter and run the affected API typecheck/unit/integration checks required by the enclosing P0 task.
