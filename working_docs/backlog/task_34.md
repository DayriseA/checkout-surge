## Current ownership and behavior

- `apps/api/src/services/demo-maintenance-service.ts:DemoMaintenanceService.reset()` selects every `starting | active | draining` run, captures its outcome/inventory, writes a failed terminal summary through `PostgresTerminalDemoRunSummaryWriter`, closes run-sale eligibility, and finally calls `DemoQueueMaintenance.cleanResetOwnedQueues()`. It has no load-orchestrator dependency and therefore cannot stop the k6 child. Task 6 must first change the durable ordering so reset fences the transition, closes admission, and drains/cleans before writing the immutable summary; this task must not regress that ordering.
- `apps/api/src/routes/admin-maintenance-routes.ts` exposes `POST /admin/demo/reset` (`adminDemoResetPath`). The route accepts no body, requires `x-control-service-token`, delegates to the service, and returns `adminDemoResetResponseSchema`. The current helper returns `401 control_token_required` for either a missing or incorrect token. Keep the route thin and preserve that repository vocabulary unless authentication is deliberately standardized in a separate change.
- `apps/load-orchestrator/src/application/traffic-execution-service.ts` and `apps/load-orchestrator/src/application/k6-runner.ts` own traffic execution, but the base has start only. Task 33 adds the authenticated `/traffic/current/abort` contract and a long-lived, run-ID-fenced cancellation owner that waits for confirmed child exit. This task consumes that port from the API; it must not signal processes or reproduce cancellation state in the reset route.
- `apps/api/src/services/demo-run-service.ts:HttpTrafficExecutionGateway` is the existing API-to-orchestrator adapter for start. Extend this boundary (or extract a focused `HttpTrafficAbortGateway`) rather than issuing `fetch` from `DemoMaintenanceService` or the route. It already owns the load-orchestrator base URL, control token, correlation header, JSON parsing, and upstream error translation.
- Surge has no Forge-style in-memory dashboard recovery cache. `DashboardRecoveryService` derives the current run from PostgreSQL and reads recent run traffic from `RedisDashboardTrafficMetricStore`; that store owns `demo-run:{runId}:traffic-metrics`, caps it, and refreshes a 24-hour TTL. `DashboardEventFanout` owns only connected SSE clients and a heartbeat timer, not recoverable dashboard data. Consequently an explicit Surge dashboard clear means terminalizing the durable current run and deleting/resetting the affected run's live metric projection; it does **not** mean disconnecting SSE clients, flushing Redis, deleting immutable history, or clearing catalog inventory.
- `apps/mock-erp/src/application/chaos-control-service.ts:ErpChaosConfigStore` owns the mutable process-local global chaos config and retains the startup defaults. `reset()` is already idempotent and restores those defaults via `update()`. `apps/mock-erp/src/routes/chaos-routes.ts` exposes authenticated `POST /chaos/reset` (`erpChaosResetPath`) and returns `erpChaosStatusSchema`; `GET /chaos` is the read surface. Missing/wrong control tokens currently return `401 control_token_required`. The `ChaosConfirmationDecisionProvider` separately owns one-second TPS windows; the existing reset does not clear that map. Treat that as a documented short-lived limitation unless reset semantics are intentionally expanded with a provider reset port.
- `scripts/runtime-reset.mjs` is currently a single-service client: it requires `CONTROL_SERVICE_TOKEN`, sends only `POST ${API_BASE_URL}/admin/demo/reset`, omits an explicit correlation ID, prints the API payload, and exits on non-2xx. It never reads `MOCK_ERP_BASE_URL` or calls `/chaos/reset`, so a successful command can leave forced outage, latency, TPS, or error-rate settings active.
- Task 31 owns retention cleanup and run Redis namespace deletion. Task 32 owns terminal-only targeted run teardown and removal of the smoke script's direct SQL/Redis cleanup. Neither task is permission for global data deletion here; reset recovers the live demo and reset-owned queues but preserves durable run history.

## Verified `checkout-forge` evidence

### Traffic abort and API recovery

- `checkout-forge/apps/api/src/services/load-orchestrator-client.ts:LoadOrchestratorClient.abortCurrentRun()` posts JSON to `/load/runs/current/abort` with `x-control-service-token`, `x-correlation-id`, and `cache: "no-store"`; it validates successful payloads with `loadRunAbortResponseSchema`. Transport failures become `LoadOrchestratorAbortError(502)`, while non-2xx responses retain the upstream status and payload. `apps/api/test/load-orchestrator-client.test.ts` proves authentication/correlation propagation and 409 conflict surfacing.
- `checkout-forge/apps/api/src/services/demo-run-recovery-service.ts` accepts a `DemoRunTrafficAborter` port. `recoverActiveRun()` discovers recoverable durable runs, writes failed lifecycle/finalization state and terminal summaries, then calls `abortCurrentRun({ runId, reason, correlationId })`. Abort 409 is mapped to `load_run_conflict`; other abort failures become `502 load_orchestrator_abort_failed`. It emits the failed dashboard event only after the abort succeeds.
- The run ID is an essential fence. An API reset for run A must never issue an unfenced abort that can kill a concurrently started run B. Task 33's no-current response is an idempotent success; a requested/current run mismatch is a conflict, not a no-op.
- Do not copy the reference ordering unchanged. Forge commits terminal state before attempting the abort, so an abort failure can leave the database saying `failed` while k6 still sends requests. Forge's orchestrator also returns immediately after sending SIGTERM rather than after observing child exit; Task 33 explicitly corrects that. In Surge, use Task 6's transition fence, close admission, request a run-ID-fenced and confirmed traffic abort, clean/drain reset-owned work, then capture/write the terminal result. The exact fence transaction belongs to Task 6; the abort call belongs at the application-service boundary before reset can report completion.

### Dashboard clear

- `checkout-forge/apps/api/src/services/demo-reset-service.ts:DemoResetService.resetDemo()` first invokes active-run recovery, then clears both reset-owned queues, calls `DashboardRecoveryStateService.clear()`, and calls `SoldOutDashboardMetricAggregator.clear()`. `apps/api/test/demo-reset-service.test.ts` records the order `recover -> queue clears -> dashboard clear -> sold-out clear` and proves no later clear occurs when recovery/abort fails.
- `checkout-forge/apps/api/src/services/dashboard-recovery-state-service.ts:clear()` sets the in-memory current run to `null` and clears its latest traffic-metric map. This prevents an old current run or k6 sample from being served after reset. The sold-out aggregator clears both totals and pending coalesced emissions.
- Surge's equivalent state is not structurally identical. Add an explicit dashboard-live-state reset port owned by the API projection adapter, with a run-scoped operation such as `clearRun(runId)` on `RedisDashboardTrafficMetricStore`. Keep its key construction private to that adapter/package. Invoke it for the reset run IDs after they are fenced/terminal and traffic is confirmed stopped. Repeated deletion must be a safe no-op. Do not call `DashboardEventFanout.close()` (that is shutdown), do not erase terminal summaries, and do not invent a broad Redis flush. If a reset event is needed for connected browsers, add only a contract-valid, run-correlated event; the authoritative recovery read must still return no active run and no stale metrics.

### Mock ERP and multi-service operational reset

- `checkout-forge/apps/mock-erp/src/server.ts` exposes `POST /internal/chaos/reset`, guarded by the same control token. It replaces current controls with configured defaults and returns the normal chaos status contract with correlation and observation time. The mutation is idempotent. Forge distinguishes missing-token 401 from wrong-token 403; Surge currently uses 401 for both, so copy the protected behavior rather than silently changing status vocabulary.
- `checkout-forge/scripts/runtime-reset-client.mjs:resetRuntime()` normalizes `API_BASE_URL` and `MOCK_ERP_BASE_URL`, generates one UUID correlation ID, and sends that ID and the same control token to `POST /internal/demo/reset` and `POST /internal/chaos/reset`. It validates HTTP success and returns both parsed payloads. `scripts/runtime-reset.mjs` is only a CLI wrapper around that reusable client.
- The Forge client starts both requests with `Promise.all`, but this is not a robust partial-failure contract: a rejected fetch throws before structured inspection, both non-2xx responses are checked one at a time, and output does not clearly report when one service reset succeeded and the other failed. Reuse the shared-client separation and common correlation ID, not the weak failure reporting.

## Target implementation map

1. **Consume Task 33's abort contract at the API boundary.** Extend the API's traffic gateway with `abortCurrent({ runId, reason, correlationId })` (names may follow Task 33's final contract). It must send the exact run ID, control token, and canonical correlation ID; parse the typed response; preserve 409 mismatch distinctly; and translate transport, 5xx, malformed-body, and unconfirmed-termination failures into stable API errors without leaking tokens or upstream internals.
2. **Compose abort into `DemoMaintenanceService.reset()`.** Keep reset orchestration in the application service and infrastructure construction in `apps/api/src/index.ts`. For every recoverable run selected under Task 6's reset fence, close admission and abort the matching live traffic before terminal capture can be declared complete. Since the orchestrator owns at most one current execution, `no_current_run` is acceptable only when the API can still prove the selected run is fenced and no newer run was targeted; a mismatched current run must fail with 409 and leave that other run untouched.
3. **Preserve safe reset ordering.** The intended combined sequence is: acquire/revalidate the Task 6 terminal-transition fence; close run sale eligibility; request and await confirmed traffic cancellation for the fenced run; drain/clean reset-owned queues and settle the state required by Task 6; capture business/inventory outcome and write the immutable failed summary; explicitly clear that run's dashboard live metric state; then report the API reset result. Late traffic/completion callbacks must be fenced by Task 33 and unable to reopen or overwrite the terminal run. Do not clear dashboard state when abort or terminalization fails, because that would hide an unresolved live run.
4. **Make dashboard clearing explicit and scoped.** Add a small injected port to `DemoMaintenanceService`, implemented by the existing Redis traffic-metric store or a focused projection reset adapter. Clear metrics for each successfully reset run after durable terminalization. Also fence `DemoRunService.ingestMetrics()` against the durable run lifecycle (or an equivalent reset generation): today authenticated `POST /internal/load/metrics` unconditionally appends and publishes, so an already in-flight batch can recreate the key immediately after `clearRun()`. Metrics for a terminal/reset generation must be acknowledged-and-dropped or rejected according to one documented contract and must not be published to SSE. Decide whether `AdminDemoResetResponse` needs a count/flag such as cleared live projections; if extended, update shared contracts, proxy consumers, and tests together. A Redis clear failure must be logged with run/correlation IDs and must not be reported as full success without a documented retry/degraded result.
5. **Add a reusable multi-service reset client.** Extract the request logic from `scripts/runtime-reset.mjs` into `scripts/runtime-reset-client.mjs` (or an equivalently focused module). Normalize `API_BASE_URL` (default `http://localhost:4000`) and `MOCK_ERP_BASE_URL` (use the repository's configured local default), require `CONTROL_SERVICE_TOKEN`, generate/accept one correlation ID, use bounded request timeouts, and call Surge's actual routes: `POST /admin/demo/reset` and `POST /chaos/reset`. Send `accept`, `x-control-service-token`, and `x-correlation-id` to both; do not send an empty JSON body/content-type.
6. **Define partial failure instead of hiding it.** Avoid an unqualified `Promise.all` rejection. Reset the API workflow before restoring ERP defaults so chaos is not changed underneath Task 6's drain/final capture; regardless of the API outcome, make a bounded attempt to reset ERP and collect both results. On any failure, throw/return one structured aggregate containing each service's URL-safe name, status/outcome, response correlation ID when available, and sanitized body/message. The CLI exits non-zero but prints which service succeeded, which failed, and the shared correlation ID, so an operator can retry safely. Both endpoints and the dashboard clear are idempotent, and API retry must rely on Task 6's conditional terminal writes rather than duplicate summaries.
7. **Keep service ownership intact.** The script coordinates service APIs only. It must not call Redis, PostgreSQL, BullMQ, or process signals. The API owns durable run recovery, admission, queues, and dashboard projections; the load orchestrator owns the child/execution slot; Mock ERP owns global chaos state; Task 32 owns targeted historical teardown. Do not move any of those concerns into route files or the CLI.

## Failure, race, and security invariants

- Reset success means all of the following are true: no matching k6 child can still emit traffic; admission is closed; reset-owned queue work is handled according to Task 6; every recovered run has exactly one terminal failed artifact containing the final captured outcome; its live dashboard projection is cleared; and Mock ERP global chaos controls equal configured defaults when the operational client was used.
- A failure to confirm traffic termination is a reset failure. Keep the run fenced, do not accept a replacement run, do not publish success, and do not let dashboard clearing make the unresolved process invisible. This is why Task 33 is a prerequisite rather than an optional best effort.
- Fence all cross-service operations by run ID and correlation ID. A reset racing natural traffic completion may observe terminal/no-current and proceed idempotently, but a run-ID mismatch may not abort the new run. Re-read/revalidate lifecycle state around the Task 6 fence rather than acting on a stale initial list.
- PostgreSQL, Redis, BullMQ, the orchestrator process, and Mock ERP cannot participate in one atomic transaction. Record/log the boundary that failed and preserve enough identifiers to retry. Prefer conditional/idempotent operations and truthful partial results over rollback claims across services.
- Mock ERP reset restores the configured global chaos values, not immutable per-run `erpConfig` snapshots already attached to worker confirmation requests. In-flight worker calls may already be sleeping or decided. An existing TPS window can influence decisions until its one-second bucket rolls over, and the provider currently retains old scope entries in its map; the config-store reset does not clear either state. Do not claim the reset rewrites historical run configuration or cancels in-flight HTTP calls.
- Use the shared service token only in headers; never log it or place it in URLs. Use `AbortController` timeouts for both CLI requests, cap/sanitize response bodies in errors, and preserve the common correlation ID in success and failure output. Keep both mutations protected; do not add a public reset endpoint.
- Clearing live metrics must target only reset run IDs. Never `FLUSHDB`, scan unrelated namespaces, delete catalog inventory, remove run history, or close all SSE clients. Queue cleanup remains limited to reset-owned queues/work as established by Tasks 6 and 32.
