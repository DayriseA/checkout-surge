## Donor caveats

- Port assertions and invariants, not donor fixtures, imports, service constructors, or outcome strings. Opus uses `reserveStock` outcomes such as `reserved`/`replayed`, a poller-style `finalizeReadyRuns`, and a pending sentinel that differs from the target's richer pending/accepted promotion lifecycle. GLM uses `apps/api/tests` and `packages/db/tests`, while the target uses singular `test` directories and a consolidated API integration harness.
- Opus's expiry test simulates elapsed TTL by deleting only the idempotency key. Retain that deterministic technique; real-time sleeps would make the suite slow and flaky. Separately keep the target TTL-range assertion tolerant of command latency.
- Concurrent outcomes may complete in any order. Identify the winner by outcome/ID, compare sets and counts, and never assert array position. Use enough contenders to exercise contention without relying on scheduler timing.
- Database duplicate-key races can surface through PostgreSQL unique constraints after Redis has selected one hold. Assertions must distinguish an expected loser/replay path from swallowed unexpected errors and must prove no duplicate durable rows or events remain.
- Integration fixtures share external PostgreSQL/Redis processes. Use the established reset helpers, unique sale-offer/idempotency IDs, `try/finally` server closure, and bounded lock/deferred-promise helpers. Never use arbitrary delays as the synchronization condition; wait for an observable lock/fake checkpoint, and give waits a bounded timeout so failures terminate diagnostically.
