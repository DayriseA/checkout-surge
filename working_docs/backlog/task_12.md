## Task details

- **Priority:** P1
- **Area:** API / idempotency
- **Source:** independent review (medium)
- **Solved elsewhere:** The reference project avoids a second PostgreSQL insert for an in-flight duplicate and supplies the durable shapes needed to recover a race safely. The equivalent `checkout-surge` implementation should treat only the expected same-reservation uniqueness failure as evidence that the competing transaction committed, then re-read the durable reservation/order instead of entering the outage path.
- **Locations:** `apps/api/src/services/reserve-order-service.ts:284`, `apps/api/src/services/postgres-buy-persistence.ts:158`, `packages/db/src/business-outcome-dashboard.ts:70`

Two simultaneous requests with one idempotency key can share the same Redis hold, both miss the durable lookup, and race the non-idempotent insert; the loser's uniqueness violation is misread as an outage and unconditionally writes a pending-reconciliation row even though the durable order exists. That false row counts as pending in business outcomes, so a fully correct run can drain to timeout.

## Standalone reference context

### What the reference project establishes

- `checkout-forge/packages/db/src/redis-inventory.ts`, `reserveStockScript`: the idempotency record is created atomically with the stock decrement. A later request with the same quantity receives `outcome: "idempotent_replay"` and the original `RedisPendingReservationRecord`; it does not receive a new reservation identity. A different quantity receives `idempotency_conflict`.
- `checkout-forge/apps/api/src/services/reserve-order-service.ts`, `responseFromRedisRecord`: when that stored record still has `outcome: "reserved"`, the duplicate request returns `reservation_pending_persistence` using the original reservation rather than attempting another insert. This is how the reference currently avoids the exact concurrent-insert race.
- `checkout-forge/apps/api/src/persistence/order-persistence.ts`, `OrderPersistence.persistReservedOrder`: the reservation, order, and the initial `reservation.secured` and `order.queued` events are committed as one PostgreSQL statement. The durable response contains the committed reservation identity and the order's `publicOrderId`, queued status, and queued timestamp; the returned queue payload also contains the durable order ID, reservation ID, offer ID, correlation/run attribution, quantity, and enqueue timestamp.
- `checkout-forge/packages/db/src/schema.ts`, `reservations` and `orders`: reservation IDs are primary keys, reservation tokens are unique (`reservations_token_unique`), and an order is unique per reservation (`orders_reservation_id_unique`). Thus the shared reservation ID is the durable idempotency identity; a uniqueness error is useful evidence only when it names that expected identity, not when an unrelated generated order/public-order constraint fails.

`checkout-forge` does not expose a generic rule that every uniqueness error means success. Its behavior is narrower: an idempotent duplicate retains the first reservation identity and must converge on the durable row for that identity. `checkout-surge` permits a pending replay to retry persistence, so it must adapt that invariant explicitly at its persistence boundary.

### Current `checkout-surge` failure path

1. `apps/api/src/services/reserve-order-service.ts`, `ReserveOrderService.reserve`, first asks `BuyPersistence.getPersistedBuyByReservationId(decision.reservation.id)`. If a pending replay observes no committed row while the first request is still writing, it calls `reconcilePendingReservation`; the first request concurrently calls `persistNewReservation`.
2. Both methods call `BuyPersistence.persistSecuredReservation`. Their catch blocks currently classify every rejection identically: report a persistence failure, call `recordPendingPersistence`, mark the Redis hold pending, and return `reservation_pending_persistence`.
3. `apps/api/src/services/postgres-buy-persistence.ts`, `PostgresBuyPersistence.persistSecuredReservation`, starts a transaction by inserting the shared hold into `reservations`. Two attempts for the same hold use the same `hold.id` and `hold.reservationToken`. After one transaction commits, the other rejects with PostgreSQL SQLSTATE `23505`, normally naming `reservations_pkey` but potentially naming the reservation-token unique index (`reservations_reservation_token_unique`). The reservation UUID—not the constraint name alone—is the authoritative conflict identity. The losing transaction has rolled back; its order/event inserts did not partially commit.
4. The generic service catch then calls `PostgresBuyPersistence.recordPendingPersistence`. Its upsert writes `status: "pending_reconciliation"` even though `getPersistedBuyByReservationId` would now return the winner's inner-joined reservation/order. It can also regress an existing marker from `reconciled` to `pending_reconciliation`.
5. `packages/db/src/business-outcome-dashboard.ts`, `readBusinessOutcomeSummary`, deliberately counts rows whose status is `pending_reconciliation`. The dashboard query is correct; hiding the bad marker there would mask the persistence bug and leave reconciliation state inconsistent.

### Required adaptation

- Keep PostgreSQL error interpretation in `PostgresBuyPersistence` (or translate it there to a purpose-specific typed result/error); do not teach the route or the dashboard about SQLSTATEs. Treat SQLSTATE `23505` only as a candidate race signal and prove it by re-reading the attempted `hold.id`. `reservations_pkey` is the expected primary conflict and `reservations_reservation_token_unique` can represent the same shared hold; a constraint name by itself must never turn foreign-key, check, public-order-ID, order-ID, token collision, or other failures into idempotent success.
- After the failed transaction has unwound and rolled back, query through `getPersistedBuyByReservationId(hold.id)` on the database connection, outside the aborted transaction. PostgreSQL's unique check waits for the competing transaction: if it emits `23505`, the winner committed; under the normal `READ COMMITTED` behavior a fresh statement can see that row. Never issue the recovery query through the failed transaction handle.
- Accept recovery only when the re-read returns the complete inner-joined reservation and order and their immutable identity agrees with the attempted hold: reservation ID, sale-offer ID, reservation token, quantity, and run attribution. A missing row, an incomplete reservation without an order, or mismatched data is not durable success and must continue through the real persistence-failure/pending path (or surface an integrity error); it must not fabricate a response from the attempted input.
- Return the `PersistedBuy` mapped from the committed rows via `toReservationSummary` and `toOrderSummary`. This preserves the winner's generated order ID/public order ID and durable timestamps. The service should then follow its existing success path: enqueue using that durable order, promote the Redis record, publish the best-effort business-outcome update, and return `idempotent_replay` for the pending replay using the current request's top-level correlation ID.
- In the recovered branch, do not call `recordPendingPersistence` or `markPendingPersistence`, and do not emit the persistence-outage report. The uniqueness collision is expected concurrency, not PostgreSQL unavailability. Queue publication remains outside the database transaction; re-enqueuing the same durable order must continue to use the existing deterministic job identity/deduplication behavior.
- Preserve genuine outage recovery. A connection error, timeout, transaction failure, unexpected `23505`, or expected `23505` whose durable re-read is absent/mismatched must still produce the existing pending response and durable/Redis pending markers. Do not replace the insert with an unconditional `ON CONFLICT DO NOTHING`: without a successful authoritative re-read it cannot distinguish a committed complete buy from an unrelated or incomplete conflict.

### Focused verification

- Add a persistence-boundary test where the insert throws an error shaped like PostgreSQL `{ code: "23505", constraint_name: "reservations_pkey" }`, the fresh reservation-ID query returns a complete matching buy, and `persistSecuredReservation` returns that exact durable buy (including the winner's order/public-order IDs and timestamps).
- Cover the race at the service boundary with a controlled interleaving: two same-key requests share one hold, both durable lookups initially miss, one insert commits, and the other receives the expected uniqueness error. Assert one durable reservation, one order, exactly the two initial events, no `pending_reconciliation` row, no pending Redis state, and `pendingPersistenceCount === 0`; the replay response must use the durable winner's order and finish as `idempotent_replay` rather than pending.
- Assert the recovered loser does not call the persistence-failure reporter, `recordPendingPersistence`, or `markPendingPersistence`, while it does re-enqueue/promote through the normal durable-success path.
- Parameterize negative cases for a non-`23505` outage and for `23505` errors followed by a null or mismatched re-read, including token/public-order/order-reservation constraint names. Each must remain on the genuine failure/pending path and must not return another buy as success. Also cover a reservation-token uniqueness error whose re-read matches the same reservation ID and immutable hold data; it is safe to recover because the row proves identity, not because the token constraint fired.
- Retain the existing pending-reconciliation tests: a real database failure still records a pending row, a later successful retry marks it `reconciled`, and the business-outcome projection counts only genuinely pending rows.
