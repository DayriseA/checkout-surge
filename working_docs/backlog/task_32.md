## Task details

- **Priority:** P1
- **Area:** smoke tooling
- **Source:** independent review (medium) + comparison (worse)
- **Solved elsewhere:** Donor evidence is inlined below. Opus contributes live SSE/inventory checks but uses a direct DB CLI with unsafe active-run semantics; GLM contributes terminal run-history verification and a protected targeted maintenance API but does not remove run-owned BullMQ jobs. Neither donor satisfies this task unchanged.
- **Locations:** `scripts/runtime-smoke-load.mjs:33`, `scripts/runtime-smoke-load.mjs:152`

The load smoke declares success when **traffic** succeeds (which only reaches draining), then its `finally` block immediately deletes the run's durable graph and Redis inventory via direct SQL/keys without removing BullMQ jobs — a slow worker can process surviving jobs after their order and run disappear, and the smoke never proves asynchronous business completion or finalization.

Add a protected, service-owned single-run teardown operation for this workflow rather than repurposing broad retention cleanup. It must reject active/non-terminal runs, verify generated-run and generated-offer ownership, remove the FK-safe durable subtree in a per-run transaction, clean the run's Redis namespaces and remaining BullMQ jobs after the durable commit, and be idempotent enough for `finally` cleanup. The smoke should call it only after observing a terminal run and validating the expected business outcome. This makes GLM's targeted-maintenance advantage an explicit deliverable rather than merely a donor note.

## Required end-to-end scenario and invariants

Use a small deterministic shape with zero ERP chaos, enough stock/traffic to guarantee at least one accepted reservation, and a timeout derived from traffic duration plus the configured drain/finalization windows rather than only a short fixed sleep.

- Readiness is proven before mutation; every request has its own bounded timeout and polling has a hard overall deadline with the last observed run/traffic/business state included in the failure.
- The start response supplies non-empty UUID `runId` and generated `saleOfferId`, and the observed run/correlation never changes to another concurrent run.
- The live SSE path yields at least one contract-valid event attributable to this run. Prefer a sequence that includes inventory/business progress; do not require every possible event because scheduling can coalesce or outrun subscription.
- Live inventory for the generated offer shows business activity using the target fields (`reservedStock > 0`, corroborated by terminal `acceptedReservations > 0`); `reservationsSecuredCount` is an Opus-only field and must not be copied. If the chosen smoke shape intentionally exhausts stock, assert `remainingStock === 0`; otherwise do not label a positive reservation count an inventory drain.
- Traffic is not enough: the immutable history row must be terminal `completed`, have `trafficDeliveryStatus !== "failed"`, `emittedRequests > 0`, `droppedIterations <= plannedRequests`, `confirmedOrders > 0`, and no remaining async blockers (`queuedOrders === 0`, `processingOrders === 0`, `retryingOrders === 0`, `pendingPersistenceCount === 0`). Because finalization itself requires notification drain in the target, also assert `notificationsRecorded >= confirmedOrders` unless the contract changes deliberately.
- Cleanup is attempted only for the exact captured `runId`, only after terminal proof on the normal path. If the smoke times out while the run is active, use the existing protected reset to transition/finalize it, re-observe terminal/absence, and then invoke targeted teardown; never bypass the active guard.
- A successful teardown means the durable run and generated offer/subtree are gone, all listed Redis namespaces are gone, and neither BullMQ queue contains a job with this run ID. Another run/catalog offer and their Redis/jobs remain untouched.
- Repeating DELETE must be safe for `finally` retries. Since Redis/queue cleanup occurs after the durable commit, do not lose cleanup coordinates on a partial failure: persist a small teardown receipt/tombstone containing run ID and sale-offer ID until external cleanup succeeds, or provide an equivalently durable retry mechanism. A plain `deleted:false` after the row vanished is insufficient if the first call failed between commit and Redis/queue cleanup.
- Preserve and report the original verification failure even if cleanup also fails; cleanup failure must still make the smoke non-zero and include the endpoint response/correlation ID. Do not let `finally` mask the business assertion that caused the run to fail.
