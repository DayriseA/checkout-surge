## Task details

- **Priority:** P4 — pulled into the P0 cluster: one design problem with the lifecycle fencing in entries 5 and 6
- **Area:** database
- **Source:** donor comparison (Opus and GLM both graded better than the reference; GPT at parity with an application-level advisory lock)
- **Solved elsewhere — verified donor context:**
  - **Opus (`checkout-surge-opus`) is the closest semantic donor.** `packages/db/drizzle/0002_single_non_terminal_run.sql` creates the hand-authored partial unique index `demo_runs_single_non_terminal_idx` over a constant-valued expression for rows whose status is `starting`, `active`, or `draining`:

    ```sql
    CREATE UNIQUE INDEX "demo_runs_single_non_terminal_idx"
      ON "demo_runs" ((status IN ('starting', 'active', 'draining')))
      WHERE status IN ('starting', 'active', 'draining');
    ```

    Every row selected by the predicate has the indexed value `true`, so the first non-terminal row owns the one available slot. A concurrent insert waits for the winner's transaction and then fails with PostgreSQL SQLSTATE `23505`; a transition to `completed` or `failed` removes the old row from the partial set and releases the slot. Unlike an advisory lock, this also rejects direct SQL, a future repository, or any other writer that does not know the application lock key. Opus deliberately leaves this expression-based index out of `packages/db/src/schema.ts` because it does not round-trip reliably through its Drizzle generation flow; the migration warns that reset/squash/regeneration must preserve it.
  - **Opus' storage adapter shows where the atomic claim and translation belong.** In `apps/api/src/services/postgres-run-store.ts`, `PostgresRunStore.createRun()` inserts the generated `saleOffers` row, the `demoRuns` row in `starting`, and the `demoRunSaleContext` ownership row in one transaction. The `demoRuns` insert is the atomic claim. If that insert violates `demo_runs_single_non_terminal_idx`, `isSingleNonTerminalRunViolation()` recognizes the exact pair `code === "23505"` and `constraint_name === "demo_runs_single_non_terminal_idx"` and throws the port-level `RunAlreadyInProgressError` declared in `apps/api/src/services/run-store.ts`. Because all three writes share the transaction, the loser leaves neither an orphan generated offer nor an ownership row. `RunStartService` catches that typed domain error and maps it to the same clean `409 run_already_in_progress` result as its early read-based overlap check; it does not initialize Redis inventory, delegate traffic, or mark a never-created run failed.
  - **Opus tests pin both the database invariant and its API behavior.** `apps/api/test/api/demo-runs.test.ts` starts two requests concurrently and expects exactly one `202`, one `409 run_already_in_progress`, one durable run, and one load-orchestrator delegation. The same file bypasses the normal repository with a direct second `demoRuns` insert and asserts `{ code: "23505", constraint_name: "demo_runs_single_non_terminal_idx" }`. `apps/api/test/unit/run-start-service.test.ts` injects `RunAlreadyInProgressError` after the fast-path read has passed and asserts the clean 409 plus no inventory initialization, delegation, or failure write.
  - **GLM (`checkout-surge-glm`) supplies a reusable race/error-handling variant.** `packages/db/src/schema.ts` declares `demo_runs_one_current_run_unique` with `uniqueIndex(...).on(sql\`(1)\`).where(...)`, and `packages/db/migrations/0002_one_current_run.sql` materializes it as `ON demo_runs USING btree ((1))`. `packages/db/src/run-lifecycle/run-creation.ts` exposes `ONE_CURRENT_RUN_INDEX_NAME`, wraps generated-offer/run/context creation in one transaction, and translates only that index's `23505` into `RunAlreadyInFlightError`. Its `isOneCurrentRunViolation()` walks up to five `.cause` links because Drizzle may wrap the driver error; this is safer to reuse than assuming the PostgreSQL fields are always on the outer exception. `packages/db/tests/run-creation.integration.test.ts` proves starting and active blockers, exactly one winner from two `Promise.allSettled` creates, rollback of the losing generated offer, and slot release after failure. `apps/api/src/app/services/demo-run-start-service.ts` catches the typed error, re-reads the blocking run, and returns its normal overlap response; `apps/api/tests/demo-run-start.integration.test.ts` verifies one `202`, one `409`, one run, and one delegation.
  - **Do not copy GLM's predicate unchanged.** GLM indexes only `starting` and `active`; it intentionally permits multiple `draining` rows at the database boundary and relies on the application `findBlockingRun` read to stop starts during draining. That leaves an alternate writer able to overlap a new run with draining work and does not meet this task's active-or-draining gate. Use the Opus status set (`starting`, `active`, `draining`) for this repository. GLM's cause-chain inspection, named typed error, single-transaction provisioning, and concurrency tests remain useful.
  - **Adaptation to the base (`checkout-surge`).** The current creation path is `DemoRunService.createAcceptedRun()` in `apps/api/src/services/demo-run-service.ts`. It takes `pg_advisory_xact_lock(hashtext('checkout_surge_demo_run_start'))`, reads `demo_runs` for `starting/active/draining`, then inserts `saleOffers`, `demoRuns`, and `demoRunSaleContexts` in the same transaction. Keep the fast read for a useful conflict payload and the advisory lock if desired as a low-contention application optimization, but make the `demoRuns` insert authoritative by adding a named partial unique index in a new migration under `packages/db/drizzle/` (the current schema originates in `0000_initial_schema.sql`). Either represent the index in `packages/db/src/schema.ts` with a constant SQL expression if the repository's Drizzle tooling preserves it, or follow Opus and document the hand-authored migration as non-regenerable schema; do not create two differently named copies. Catch only `23505` for the chosen index name, including wrapped `.cause` errors, and translate it to the existing `DemoRunValidationError("demo_run_already_active", ...)`/HTTP 409 vocabulary. Let all unrelated unique violations propagate normally.
  - **Migration and lifecycle caveats.** Creating the index will fail if the database already contains two rows in `starting/active/draining`; preflight with `SELECT id, status FROM demo_runs WHERE status IN ('starting', 'active', 'draining') ORDER BY created_at` and resolve inconsistent historical state explicitly rather than silently deleting it in the migration. Keep `draining` in the predicate until the fenced terminal transition from Tasks 5 and 6 commits; only `completed` or `failed` should free admission. The index is an admission invariant, not a replacement for expected-status predicates on lifecycle updates, reset sequencing, startup reconciliation, or user-friendly early gating.
