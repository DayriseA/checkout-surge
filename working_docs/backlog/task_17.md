## Task details

- **Priority:** P1
- **Area:** worker / queue
- **Source:** independent review (medium) + comparison (worse, two topics)
- **Solved elsewhere:** none fully. The verified reference evidence and the safe adaptation are inlined below. Checkout Forge provides a useful enqueue-time resolver for frozen retry options and attempts to apply run concurrency while consuming, but its single mutable BullMQ worker concurrency is process-global, is changed only after a job has been fetched, and is unsafe for mixed-run work. Do not copy it literally.
- **Locations:** `apps/worker/src/application/run-backpressure.ts:18`, `apps/worker/src/runtime/config.ts:23`, `packages/db/src/scripts/seed.ts:235`, `apps/api/src/queue/bullmq-order-process-job-publisher.ts:32`, `apps/worker/src/index.ts:151`

Three connected gaps: (a) the run-scoped semaphore lives inside a BullMQ worker whose global concurrency ceiling is five, so the seeded surge-5k/surge-10k presets requesting eight and ten can never be honored — the runtime cannot execute the frozen policy it reports; (b) enqueue retry attempts/backoff are process-level constants, not derived from the accepted run snapshot; (c) run concurrency is applied around the ERP call **after** jobs are consumed, so backpressure accumulates as invisible in-process waiters instead of visibly backing up in the queue.

## Standalone implementation context

### Frozen contract and current queue path

- `packages/contracts/src/load.ts`, `backpressureConfigSchema`, is the accepted-run contract stored in `demo_runs.config_snapshot`. It currently freezes `queueName`, `physicalQueueName`, `orderProcessConcurrency`, `drainTimeoutSeconds`, and `pendingPersistenceRetryAfterSeconds`, but has no retry fields. Extend this shared contract with a strict nested `retryPolicy: { maxAttempts: positiveInteger; initialBackoffMs: nonnegativeInteger }`. Keep Surge's existing `orderProcessConcurrency` spelling; do not import Forge's differently named `orderProcessingConcurrency` field.
- `packages/db/src/scripts/seed.ts`, `backpressureConfig()`, builds every preset and the public-custom default. It currently freezes only the queue identities, concurrency, and drain/persistence timings. Seed retry values into the same snapshot so a run does not inherit later process-env changes. The public presets request concurrency 5 (`preview-1k`), 8 (`surge-5k`), 10 (`surge-10k`), 5 (`idempotency-check-200`), and 5 (`public-custom`); the admin presets request 5, 4, and 3. In particular, 8 and 10 exceed today's worker default ceiling of 5.
- `apps/api/src/services/reserve-order-service.ts`, `enqueuePersistedBuy()` and `toOrderProcessJob()`, publishes only after the reservation/order are durably persisted. The queue payload includes the frozen-policy lookup key `runId` when the order belongs to a run. Preserve the deterministic `jobId: orderId`, durable replay behavior, and the rule that PostgreSQL/BullMQ publication is not atomic.
- `apps/api/src/queue/bullmq-order-process-job-publisher.ts`, `createOrderProcessJobPublisher()`, validates the payload and currently always adds it with process-level `OrderProcessRetryOptions` (`maxAttempts: 4`, `backoffBaseMs: 500` by default; the composition root supplies `ORDER_PROCESS_MAX_ATTEMPTS` and `ORDER_PROCESS_BACKOFF_BASE_MS`). This is the correct adapter at which to translate the frozen retry policy into BullMQ `attempts` and exponential `backoff.delay`; do not make `ReserveOrderService` or an HTTP route depend on BullMQ types.
- Add an injected run retry-policy resolver/reader at the API queue boundary, backed by `demo_runs.config_snapshot` and composed in `apps/api/src/index.ts`. For a job with `runId`, parse the accepted snapshot and use exactly `retryPolicy.maxAttempts` and `retryPolicy.initialBackoffMs` in `queue.add()`. A job without `runId` continues to use the process defaults. A present `runId` whose run/snapshot cannot be resolved must be treated as an enqueue/integrity failure and flow through the existing partial-publication reporting; silently applying process defaults would violate the accepted run contract.
- `apps/worker/src/persistence/postgres-run-config-reader.ts`, `PostgresRunConfigReader.read()`, already resolves and parses a frozen snapshot by the job's `runId`. Reuse the `RunConfigReader` application port rather than creating database access in the consumer. The retry options embedded in `job.opts` remain authoritative for BullMQ delivery metadata: `apps/worker/src/queue/bullmq-order-process-consumer.ts`, `processJob()`, correctly derives `maxAttempts` from `job.opts.attempts` and passes `attemptNumber`, `attemptsMade`, and `maxAttempts` to the handler.

### Current concurrency defect

- `apps/worker/src/runtime/config.ts`, `loadWorkerConfig()`, gives `ORDER_PROCESS_CONCURRENCY` a default of 5. `apps/worker/src/index.ts` passes that once to `createBullMqOrderProcessConsumer()`, and `apps/worker/src/queue/bullmq-order-process-consumer.ts` constructs one BullMQ `Worker` with that fixed concurrency. BullMQ therefore never hands this process more than five active order jobs, regardless of a run snapshot requesting eight or ten.
- `apps/worker/src/application/run-backpressure.ts`, `RunScopedBackpressureOrderConfirmation.confirm()`, looks up the snapshot only after the job is active and the handler has reached ERP confirmation. Its in-memory semaphore is keyed by `${runId}:${concurrency}` and waits on an array of promise resolvers. Excess jobs remain BullMQ `active` while waiting in the Node process: queue depth/oldest-waiting metrics understate pressure, active locks and shutdown now include work that has not begun, and multiple worker replicas each enforce their own independent limit rather than one run limit.
- Applying the policy only around `OrderConfirmation` also lets already-consumed jobs perform order transition work before admission. Move run-policy admission to the queue consumer boundary, before `handler.handle()`. Remove/bypass the inner confirmation semaphore once queue admission owns the rule; retaining both creates two sources of truth and preserves invisible waiters.

### Required mixed-run-safe admission design

- A single BullMQ worker has one concurrency value; it cannot represent different per-job concurrency policies. Do not mutate `worker.concurrency` from whichever job happened to resolve last, and do not select policy from "the active run." Although `DemoRunService.createAcceptedRun()` serializes starts and permits only one `starting`/`active`/`draining` run, timed-out terminal runs, non-run orders, and queue residue can coexist with a later run. Policy selection must always use the delivered job's own `runId` and frozen snapshot.
- Keep the existing physical queue and add a queue-admission collaborator to `createBullMqOrderProcessConsumer()`. Before invoking the handler, resolve the job's frozen policy and attempt a **non-blocking, distributed** slot acquisition keyed by run ID (for example, a small Redis-backed leased semaphore implemented behind an application port). The limit is `snapshot.backpressureConfig.orderProcessConcurrency`; non-run jobs use a distinct fallback key and the process default. On acquisition, call the handler and release in `finally`.
- If no slot is available, return the job to a visible BullMQ state immediately instead of awaiting an in-process semaphore. Use BullMQ's token-aware delayed/rate-limit mechanism and its corresponding control-flow error so this admission deferral does not count as a failed ERP attempt, consume the job's retry budget, emit an order failure, or invoke `handler.handle()`. Use a small bounded delay/jitter to avoid a hot claim/defer loop. Waiting/delayed queue metrics must then expose the pressure that the current semaphore hides.
- Slot ownership must be safe across worker replicas and crashes. Acquisition/release must be atomic, leases must expire or be reclaimable after a crashed consumer, release must be idempotent and owner-token checked, and Redis keys must expire when idle. A process-local `Map<runId, Semaphore>` is insufficient. Keep Redis construction in `apps/worker/src/index.ts` and queue/infrastructure adapters, not in the handler or route layer.
- Treat `ORDER_PROCESS_CONCURRENCY` as the worker's aggregate admission-scanning ceiling, not as the run policy itself. It must be at least the maximum run concurrency the API can accept so an isolated `surge-5k` or `surge-10k` run can actually reach 8 or 10 active handlers. Add one shared/deployment hard cap (configured consistently in API validation and worker composition), reject accepted snapshots above it, and fail worker startup when its BullMQ ceiling is below that accepted cap. Do not merely change the default from 5 to 10 while leaving custom snapshots unbounded; that recreates the same policy lie at a higher number.
- Under mixed work, each run has its own slot key and therefore its own maximum. The worker ceiling remains an aggregate safety cap, so simultaneous runs may receive less than their individual maxima but must never exceed them. This is intentional: `orderProcessConcurrency` is a maximum, not a throughput guarantee. Non-run work must not borrow or consume a run's slots. Admission order may remain BullMQ FIFO/delayed scheduling; cross-run weighted fairness is outside this task.

An alternative implementation using a dedicated physical BullMQ queue and worker lifecycle per run is acceptable only if all producers, inspectors, reset/obliterate maintenance, finalization queue evidence, readiness, and shutdown paths are updated to discover and aggregate those queues. Changing only the publisher/worker would make queue health and finalization blind. The distributed non-blocking admission gate is the focused adaptation for the existing single-queue architecture.

### Checkout Forge evidence and limitations

- `checkout-forge/apps/api/src/services/run-backpressure-policy-resolver.ts`, `RunBackpressureJobOptionsResolver.resolve`, looks up `run.configSnapshot.backpressureConfig` by `payload.runId`, converts it with `createBackpressureJobOptions()`, and caches the result. `checkout-forge/apps/api/src/queues/order-process-queue.ts`, `BullMqOrderProcessQueuePublisher.enqueue()` and `createBackpressureJobOptions()`, merge those options into `queue.add()` and map `retryPolicy.maxAttempts` to `attempts` plus `retryPolicy.initialBackoffMs` to exponential `backoff.delay`. `checkout-forge/apps/api/src/index.ts` injects the resolver into the publisher. Adapt this dependency direction and option mapping.
- Forge's `demoRetryPolicyConfigSchema` contains exactly `maxAttempts` and `initialBackoffMs`. Its queue integration test, `apps/api/test/order-process-queue.integration.test.ts` (`"uses run-scoped retry and backoff options when provided"`), inspects the real queued job and proves `attempts: 6` and exponential delay `750` override defaults. This is the relevant enqueue regression pattern.
- Forge does **not** solve mixed-run concurrency. `apps/worker/src/queues/order-process-worker.ts`, `createOrderProcessWorker()`, resolves policy inside the processor and assigns `worker.concurrency = backpressureConfig.orderProcessingConcurrency` after BullMQ has already delivered that job. The value is global to the worker, so mixed policies race and the last resolved job changes future fetch capacity for every run. `apps/worker/src/index.ts` also polls the active run every second and mutates the same global value. Its worker integration assertion that concurrency becomes 3 covers only one run and does not prove isolation, queue-visible waiting, or multi-replica enforcement.
- Both Forge policy resolvers retain a `Map` entry forever, including `null` misses. Frozen snapshots make positive entries immutable, but not bounded. In Surge, either read PostgreSQL per enqueue/delivery or use a bounded TTL/LRU cache. Do not cache missing runs indefinitely; expose explicit invalidation on reset/maintenance if a longer positive cache is chosen. The distributed admission keys also need idle TTL/lease cleanup, and shutdown must stop new claims, wait for or release owned leases, then close the BullMQ worker/Redis clients in the existing runtime order.

### Boundaries and non-goals

- Preserve the accepted run snapshot as the only source of per-run policy. Do not read mutable preset rows at enqueue or consumption time, and do not let later environment/preset changes alter already accepted jobs.
- Keep shared schemas/types in `@checkout-surge/contracts`, database reads behind API/worker persistence adapters, BullMQ mechanics in queue adapters, and Redis construction in composition roots. Keep HTTP routes and `ReserveOrderService` free of BullMQ/Redis clients.
- Keep deterministic order job IDs, durable replay, existing order/ERP attempt state transitions, correlation metadata, circuit-breaker behavior, ERP request-timeout selection, notification publication, queue inspection, and finalization semantics.
- Do not turn admission deferrals into retries, ERP attempts, failed jobs, or business events. Do not change retry error classification or terminal-order rules except where they consume the now-frozen `maxAttempts` already present in BullMQ delivery metadata.
- Do not add BullMQ Pro group concurrency, split queues without full observability/maintenance aggregation, implement cross-run fairness, redesign the dashboard, or widen this into general ERP TPS/rate-limiter tuning.
