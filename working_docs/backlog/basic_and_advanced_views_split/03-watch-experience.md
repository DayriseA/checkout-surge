# Task 03 — Watch lifecycle and technical disclosure

Status: Done (2026-09-16) · Depends on: [Task 02](02-result-summary-and-warnings.md) · Next: [Task 04](04-public-run-report.md)

## Outcome

Visitors can follow the simulation before it ends: scenario, phase, stock and order progress lead the page. Advanced preserves the current technical evidence. Report preparation, stale updates and another visitor's shared run no longer obscure or misidentify the selected result.

- [Design contract](design-contract.md) and every Watch row [W01–W18 plus H03](state-coverage.md).
- `apps/web/src/app/watch/page.tsx` and `components/operator-dashboard.tsx`.

The realtime, recovery and lifecycle helpers remain the owners of behavior. This task changes their presentation and, narrowly, the public evidence retained from an existing report lookup.

## Work

1. Recompose every `WatchComposition` phase into the compact five-band layout defined in the design contract (identity line, verdict line, counts row, signal strip, caveat and actions). The whole Basic terminal view must fit about 650 CSS pixels of height at 1536 × 720. Show available stock remaining/reserved and confirmed/awaiting/failed order counts in the counts row, with the order-progress bar inside the confirmed tile under the contract's denominator rules. Preparation and missing readings must not become zero-valued activity.
2. Replace the full frozen configuration at the top with the one-line identity: scenario name, buyers or planned attempts, units, and whose run it is when relevant. Show buyers only where spike configuration supports that wording; preserve attempt-based language for steady traffic. Reuse task 02's result summary for terminal outcomes, including failure explanation and valid next action near the verdict. Rewrite the page subtitle under the h1 in the same plain vocabulary.
3. Build the Basic signal strip: four sparklines (arrivals, units left, processing backlog, confirmations) from the same samples the full charts use, each with its headline value as caption and a text equivalent, and each acting as a contextual link that switches this page to Advanced and focuses that signal's full chart. Reuse the chart primitives in `gold-signals.tsx`; no new chart dependency. Missing samples render the caption as unavailable, not as a flat zero line.
4. Move the remaining public content into Advanced groups: Scenario, Signals, Processing, Consistency, and Connection/shared system. Preserve all four full charts, textual samples, axes/time origins, event markers, ERP observations/protection, lag, inventory details, invariant proof and existing recovery diagnostics. Separate shared physical queue/protection context from run-owned counts.
5. Keep live freshness, interrupted-update warnings and useful processing pauses/uncertainty in Basic. Reuse the existing freshness/ERP story semantics. Avoid duplicated sync warnings, retry controls and repeated counts. Do not put last-known readings behind a reconnect placeholder.
6. Integrate exact saved-result status with the selected run's narrative. For the same run, use one outcome summary and one report action. A known terminal result remains visible while the report is preparing; the link is presented as available only after the lookup confirms availability. Exhausted lookup retains the existing manual retry.
7. Retain the small task-02 summary/qualification subset from the **already-read public detail** in `AcceptedRunResult` when available. Its current adapter throws that data away. Keep the run-ID match guard, stale-response rejection, retry guidance and single-flight/bounded retry owner in `useAcceptedRunResult`. Do not introduce another polling hook, a protected read, or a lookup for any run other than the visitor's accepted one: a shared terminal run without accepted context shows the live verdict and sends the visitor to the saved report for delivery/speed qualifications. Switching modes must not change the lookup target or reset retries.
8. When accepted run A differs from shared run B, render clearly separated “Your result” and “Now running in the shared demo” sections. Use scenario/time where known; if A has only an ID, say its result is being checked without fabricating metadata. Never attach B's counts, freshness or warnings to A. A's report link stays exact.
9. Keep idle, unavailable, reset-recovery, invalid-link and latest-history states actionable. Incomplete cleanup blocks start encouragement and may still have settling work. Provide concise history/demo navigation for an invalid link; do not expose UUIDs in the main Basic narrative.

## Acceptance criteria

- At 1536 × 720, the Basic terminal view (identity, verdict, counts, signal strip, caveat and actions) fits without scrolling, and the four sparklines are visible with text equivalents. Basic follows Preparing → Buyers arriving → Confirming orders → Result with truthful exceptions.
- The W01–W18 branch matrix is covered with meaningful fixtures; there is no generic terminal-success fallback.
- Switching repeatedly during a run preserves its samples, current scope and subscription. It does not recreate an EventSource, issue a start, or restart report retries. A sparkline link opens Advanced on its full chart and moves focus there.
- Same-run completion uses one verdict and report status; report availability never hides a known result. Saved quality warnings appear when the visitor's own exact-run evidence is available.
- Different shared/accepted runs are unmistakably separate, including after reload, terminal retention, reset recovery and delayed result responses.
- All existing public technical sections remain reachable in Advanced; hidden details do not contain the only explanation of a material problem.
