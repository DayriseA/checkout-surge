- **Priority:** P0

- **Source:** independent review (high)

- **Locations:** `apps/worker/src/index.ts:307`, `apps/worker/src/application/order-process-job-handler.ts:139`, `apps/worker/src/queue/bullmq-order-process-consumer.ts:183`

Every ERP-attempt persistence error is classified retryable and rethrown without a terminal transition, and each retry burns the finite BullMQ attempt budget (default four). If PostgreSQL is unavailable while attempt history is recorded — including for ERP-**accepted** confirmations — the job exhausts its budget while the order stays `processing` forever; no recovery scanner resumes it and the run drains to timeout. Needs durable ERP-result semantics plus explicit recovery ownership for externally-successful-but-locally-incomplete work, and a dead-letter/compensation path for attempt exhaustion.

## Inlined donor findings

### Opus ERP idempotency pattern

- `apps/mock-erp/src/services/confirmation-ledger.ts` defines `ConfirmationLedger#get(orderId)` / `remember(orderId, confirmation)` and `InMemoryConfirmationLedger`. It keeps the first successful confirmation for an order and replays the exact response (including the original ERP reference) on redelivery.
- `apps/mock-erp/src/services/erp-confirmation-service.ts`, `ErpConfirmationService.confirm`, performs the ledger lookup **before** latency, throttling, forced-outage, or random-error behavior. A previously accepted order therefore remains accepted even if the ERP is in outage when the worker retries. Only successful confirmations are remembered; transient failures remain eligible for a real retry.
- `apps/mock-erp/src/index.ts` constructs the ledger in the composition root and injects it into the confirmation service. Preserve that dependency direction: no module-level database/Redis client and no ERP behavior in the worker route/queue adapter.
- The associated tests in `apps/mock-erp/test/unit/confirmation-ledger.test.ts` and `apps/mock-erp/test/unit/server.test.ts` pin first-write-wins replay, distinct-order isolation, no second generated ERP reference or simulated delay, and replay during a later forced outage.
- A complementary worker-side pattern exists in the current Checkout Surge shape: `apps/worker/src/application/erp-confirmation-client.ts`, `HttpErpOrderConfirmation.confirm`, first calls `ErpAttemptPersistence.findSuccessfulAttempt`; `apps/worker/src/persistence/postgres-erp-attempt-persistence.ts`, `PostgresErpAttemptPersistence.findSuccessfulAttempt`, reads the latest succeeded `erp_attempts` row for the order. This prevents a second ERP call when the attempt row committed but `transitionToConfirmed` did not. The stable request key is `erp-confirmation:${orderId}`. Keep this fast replay path.

The intended data flow is therefore:

1. Load/validate the durable order and derive one stable confirmation idempotency key from its immutable order ID.
2. Check the worker's durable successful-attempt/result record. If present, skip the network call and resume the local `processing -> confirmed` transaction.
3. Otherwise call ERP with the stable key. ERP atomically returns the first stored success for that key or performs the confirmation once and stores its response before returning it.
4. Persist the successful ERP result/attempt locally, then transition the order to `confirmed`. A crash after either step is safe: ERP replay covers the pre-local-write window; the local successful-result lookup covers the post-attempt/pre-order-transition window.
5. If local persistence is unavailable, transfer ownership to a durable recovery/dead-letter mechanism before the finite `orders:process` delivery is allowed to disappear.

### Opus poison/orphan handling

- `apps/worker/src/services/process-order-service.ts`, `ProcessOrderService.process`, treats the durable order as authoritative. Terminal orders are acknowledged without reprocessing; an already-`processing` order resumes confirmation without emitting another `order.processing`; a missing order is logged as anomalous and returned as `settled`, because retrying cannot create an order that must have existed before enqueue.
- `apps/worker/src/adapters/order-process-worker.ts`, `BullMqOrderProcessWorker`, validates the payload at the consumer boundary and derives `attempt`/`maxAttempts` from BullMQ. Circuit-open work is moved to delayed and throws `DelayedError`, so a deferral does not consume a delivery attempt. Ordinary throws consume the configured budget and the `failed` event currently only logs.
- In Checkout Surge, the equivalent permanent poison errors are already explicit in `PostgresOrderTransitionPersistence.transitionToProcessing`: `OrderNotFoundError` and `OrderJobIdentityMismatchError` (the mismatch exposes `mismatchedFields`). They must not be treated like PostgreSQL unavailability. Classify them at the application/consumer boundary, write or enqueue a dead-letter record containing job ID/name, raw validated payload, reason, mismatched fields where applicable, attempts/correlation ID, and observed time, then acknowledge only after that handoff succeeds. This retains Opus's no-pointless-retry behavior without silently losing the anomaly.

### Donor defects and incomplete pieces that must not be copied

- Opus's `InMemoryConfirmationLedger` is process-scoped. A mock-ERP restart forgets accepted confirmations, so it does **not** cover the crash-after-ERP-success window durably. It also implements `get` then `remember` as separate operations, so concurrent duplicates can both perform the side effect. Replace it with an atomic, durable first-write-wins store keyed by the stable idempotency key (unique constraint plus insert-or-read in one owned persistence boundary), storing enough of the successful response to replay it exactly.
- The worker's local `erp_attempts` lookup alone cannot close the window where ERP accepted but the attempt insert failed; only a durable ERP-side key/result closes that window.
- In `apps/worker/src/application/order-process-job-handler.ts`, `shouldRetryWithoutFailingOrder` currently wins regardless of `hasRemainingAttempts`. `apps/worker/src/index.ts`, `shouldRetryWithoutFailingOrder`, returns true for every `ErpAttemptPersistenceError`, including a successful-attempt lookup outage and an accepted-result write outage. BullMQ still stops after its finite budget, leaving the order `processing`.
- `apps/worker/src/queue/bullmq-order-process-consumer.ts` reports every failed delivery but has no exhausted-attempt callback, dead-letter write, compensation enqueue, or scanner. Logging/reporting is observability, not recovery ownership.
- Opus's missing-order log-and-ack leaves no durable audit fact. Adopt the permanent classification, but require a successful DLQ/audit handoff before acking.
- GLM makes the shared defect explicit in `apps/worker/src/app/services/erp-confirmation.ts` and `apps/worker/src/app/services/order-process-service.ts`: a thrown dependency/persistence error eventually leaves the BullMQ job failed while the order stays `processing`; there is no recovery owner. It is corroboration of the defect, not a donor solution.

## Required adaptation in Checkout Surge

- Keep HTTP/queue adapters thin. Put result/idempotency decisions in the ERP confirmation application service, persistence in an injected adapter, and exhausted-delivery classification/handoff behind an injected recovery/dead-letter port constructed in `apps/worker/src/index.ts`.
- Make the ERP success ledger genuinely durable and atomic. Persist the stable key, order ID, immutable replayable success payload (at least confirmation/reference ID, status, HTTP status, and processed timestamp), and creation time under a unique key. Concurrent same-key requests must converge on one side effect and one response. A reused key for materially different immutable order data must fail as an idempotency conflict, not replay another order's result.
- Preserve the local `findSuccessfulAttempt` short-circuit, but make the successful attempt/result insert idempotent. The existing unique `(order_id, attempt_number)` constraint is delivery-oriented; recovery may revisit the same external success under a later BullMQ attempt, so conflict handling must distinguish replay of the same result from contradictory data rather than surfacing a generic unique violation.
- Split failure policy by facts, not by one broad retry predicate:
  - ERP transient failure with attempts remaining: normal BullMQ retry/backoff.
  - ERP transient failure on the last attempt: persist the existing terminal `erp_retries_exhausted`/order failure outcome; if that terminal write fails, hand it to recovery instead of abandoning `processing`.
  - ERP accepted but local attempt/order persistence incomplete: never mark the business order failed. Carry the stable key and captured successful response in a durable reconciliation job/record, then let a recovery worker/scanner re-read ERP's durable result and idempotently finish the attempt plus `confirmed` transition.
  - Local database failure before the external outcome is known: do not call ERP while the successful-result lookup is unavailable; transfer/retry under the same recovery owner after the finite delivery budget.
  - Missing order, identity mismatch, invalid payload/name: permanent poison; durable DLQ/audit handoff, no ERP call, no repeated normal deliveries.
- Define recovery ownership explicitly. The original job may enter BullMQ's failed set for operator visibility, but a named scanner/consumer must claim exhausted recoverable jobs and re-enqueue them with deterministic IDs so restarts and repeated scans are idempotent. Do not rely on an event-listener promise alone: process death between the `failed` event and enqueue must be recoverable by scanning durable failed jobs/records. Recovery retries must have an operator-visible age/count and a terminal escalation policy; they must not be silently bounded by the same four-attempt budget.
- Ensure run draining observes this state: externally accepted but locally incomplete orders remain unsettled and visible as reconciliation backlog until confirmed or explicitly escalated. Do not falsely convert an accepted ERP result to `failed` merely to make a run finish.

## Boundary tests to add or update

- ERP ledger persistence: restart/recreate the ERP service between first success and replay and receive the same response; concurrent duplicates produce one confirmation; same key plus different immutable payload is rejected; failures are not cached.
- Worker unit tests: accepted-result persistence failure on the last normal attempt does not call `transitionToFailed` and does hand off recovery; lookup failure prevents the ERP call; replayed durable success resumes `transitionToConfirmed`; recovery handoff failure leaves the source job recoverable/failed rather than acknowledged.
- PostgreSQL integration: idempotently record the same external success and finish `processing -> confirmed` after a simulated crash; contradictory replay is detected; attempt/event rows are not duplicated.
- BullMQ integration: exhaust the normal attempt budget while PostgreSQL is unavailable, restore it, run the scanner/recovery consumer, and prove the order reaches `confirmed` without a second ERP side effect. Also prove missing/mismatched/invalid jobs enter DLQ once and do not burn all normal attempts.
- Run-settlement regression: a run with an externally accepted but locally incomplete order remains draining with visible reconciliation pressure, then settles after recovery.
