## Rendering, auth, and accessibility caveats

- HttpOnly cookie state cannot be inferred reliably in a client component. Determine it during SSR, avoid a public-first/admin-after-mount flash, and keep server HTML identical to the client's initial tree to prevent hydration warnings. A successful sign-in or sign-out must invalidate/refresh the server-rendered auth state; a stale client boolean is not authorization.
- Hiding controls is defense in depth, not security. Existing protected proxy routes must continue returning 401 for missing, invalid, or expired sessions, and client request bodies must not select operator mode. Public visitor ownership/budget identity in `lib/server/public-visitor.ts` and the public start proxy is independent of admin identity and must remain intact.
- Confirmation dialogs must trap/restore focus, close on Cancel/Escape when idle, have an accessible name and description that state the exact scope and consequence, expose errors without dismissing the dialog, and prevent duplicate submission while pending. Destructive buttons need descriptive accessible names; checkboxes need labels tied to the run id. Do not use `window.confirm()` or color alone to communicate danger.
