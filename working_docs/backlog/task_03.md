## Task details

- **Priority:** P0
- **Area:** API / Redis / durability
- **Source:** independent review (high)
- **Solved elsewhere:** partially. The useful Opus donor design and its limits are embedded here so this task does not require access to that worktree:
  - `apps/api/src/services/pending-persistence-reconciler.ts` defines `PendingPersistenceReconciler.reconcileSaleOffer(saleOfferId)`. It reads full pending records from Redis, maps them to `reservation_pending_persistence` rows, and inserts with `ON CONFLICT (reservation_id) DO NOTHING`, returning `{ found, materialized }`. This is a good model for a small API application service with explicit database, Redis, and logger dependencies and for making repeated/concurrent reconciliation harmless.
  - The donor makes its Redis sentinel self-sufficient. `packages/db/src/inventory.ts` stores a time-ordered `:pending-persistence` sorted-set member plus a companion `:pending-persistence-records` hash entry containing `correlationId`, nullable `runId`, `idempotencyKey`, `quantity`, `reservationToken`, `securedAt`, and `expiresAt`; `readPendingPersistenceRecords()` rehydrates that payload and skips malformed JSON instead of aborting the whole batch. The current branch differs: `packages/db/src/redis-stock-reservation.ts` stores the full `SecuredReservationHold` in the reservations hash/idempotency value, but the pending sorted set contains only the reservation ID and there is no direct reservation-ID-to-idempotency-key record. An autonomous scanner therefore needs an atomic, bounded way to recover both the hold and its idempotency key (prefer enriching the pending record/index over scanning the whole Redis keyspace). Preserve the existing key-type, TTL, identity, and hold-presence checks in the Lua operations.
  - The donor wires reconciliation into two lifecycle paths. `apps/api/src/services/run-finalization-service.ts` invokes it for a draining run before writing the terminal run result, and `apps/api/src/services/startup-reconciliation-service.ts` invokes it for recoverable draining runs after a restart. `apps/api/src/index.ts` constructs one reconciler and injects it into both services. In this branch, the corresponding integration points are `DemoRunFinalizationService.finalizeRun()` / `finalizeReadyRuns()` in `apps/api/src/services/demo-run-finalization-service.ts`, `DemoRunStartupReconciliationService.reconcile()` in `apps/api/src/services/demo-run-startup-reconciliation-service.ts`, and their construction in `apps/api/src/index.ts`. Reconciliation must run independently of `/buy` and must not call the normal admission path, because `reserveInventoryStock()` intentionally checks run eligibility before replay and rejects all retries once the generated run is closed.
  - Do not copy the donor's stopping point. Its reconciler only materializes an audit row, uses `ON CONFLICT DO NOTHING`, and deliberately leaves the Redis pending sentinel and stock-consuming hold intact. It neither creates the missing durable reservation/order nor releases the stock, never promotes the idempotency record, never enqueues a recovered durable order, and never marks the durable pending row reconciled. Consequently its finalization integration can still terminalize a run with an unresolved hold; it also performs its readiness check before materializing the pending rows and does not recompute readiness afterward. This task requires actual convergence, not merely operator visibility.
  - Reusable resolution flow for this branch: claim/read each pending entry without reopening admission; first query `PostgresBuyPersistence.getPersistedBuyByReservationId()` to handle the "durable commit succeeded but Redis promotion failed" case, then idempotently reassert the deterministic order-processing job and call `promoteReservationIdempotencyToAccepted()` (which removes the pending marker). If no durable buy exists, retry `persistSecuredReservation()` from the recovered hold, then enqueue and promote using the same identities. Keep failures retryable and visible; do not remove the pending record until the durable state and Redis accepted state agree. Account for concurrent reconciliation and a late in-flight request so duplicate order/event creation and duplicate enqueue cannot produce a second logical purchase.
  - Opus also supplies a useful compensation primitive for definitively rejected durable writes. `packages/db/src/reserve-stock.ts` implements `reverseReservation()` as a single idempotent Lua operation: read the quantity from the authoritative stored hold, restore `remainingStock`/`reservedStock`, remove the reservation and expiration entries, delete the idempotency record, append a corrective bounded `inventory.updated` event, and return `not_held` on repetition. `apps/api/src/services/stock-reservation-gate.ts` exposes it as `reverse()`, and `ReserveOrderService.#compensateHold()` uses it only for classified non-retryable persistence errors (for example `run_sale_offer_mismatch`), logging a reversal failure without masking the original rejection. The current branch has no reversal operation, and an autonomous pending-hold reversal must additionally remove/resolve its pending index/metadata atomically; blindly copying the donor script would leave a false pending sentinel.
  - Test ideas carried by the donor are in `apps/api/test/api/pending-persistence-reconciler.test.ts`, `packages/db/test/integration/reserve-stock.test.ts`, and the reserve/finalization/startup service tests: materialize/recover multiple records; repeat reconciliation without duplicates; no-op an empty scan; leave failed attempts discoverable; verify finalization and startup invoke reconciliation; release a definitively rejected hold exactly once; and preserve the original error if compensation fails. Adapt these to assert full convergence in this branch: recovered durable reservation/order/events, one deterministic queue handoff, accepted idempotency replay, cleared pending counts, correct stock counters on reversal, no admission of a new purchase after closure, and no terminal finalization while reconciliation remains unresolved (except under an explicitly documented terminal timeout policy).
- **Locations:** `apps/api/src/services/reserve-order-service.ts:159`, `apps/api/src/services/reserve-order-service.ts:421`, `packages/db/src/redis-stock-reservation.ts:121`

A failed PostgreSQL write leaves a real, stock-consuming Redis hold whose only reconciliation path is another `/buy` with the same key — and the durable run gate rejects retries once traffic completion closes eligibility, so the repair path becomes unreachable exactly when it is needed. Pending-insert and accepted-promotion failures are swallowed; no autonomous scanner exists. Build an autonomous, idempotent reconciler that runs after admission closes without admitting new purchases.
