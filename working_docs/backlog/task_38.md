Locally constructed web errors return only `{code, message}` instead of the shared error payload, backend requests never forward a browser correlation ID, and reconstructed responses discard the backend `x-correlation-id`. On the API side, server hooks normalize correlation only onto a request property and response header — not the request logger — so routine request logs also cannot be queried by the correlation value returned to the client; fix propagation end to end in one pass.

## Standalone implementation context

### Canonical contracts and donor pattern

- `packages/contracts/src/error.ts` is the target owner of the public error contract. Its current `errorPayloadSchema` is strict about the envelope but `code` is only `z.string().trim().min(1)`. Introduce and export a duplicate-free stable code tuple/schema/type (the donor calls these `ERROR_CODES`, `ErrorPayloadCodeSchema`, and `ErrorPayloadCode`) and use that schema for `errorPayloadSchema.code`. Do not copy the donor list blindly: inventory every code currently emitted by this repository and include the established vocabulary, including the web-local codes `admin_passphrase_not_configured`, `admin_passphrase_required`, `admin_session_secret_not_configured`, `admin_session_required`, `control_token_not_configured`, `invalid_json`, `invalid_request`, `backend_unavailable`, and `invalid_backend_response`, plus existing API/Mock ERP/load-orchestrator codes such as `internal_error`, `control_token_required`, and `chaos_config_exceeds_caps`. Reuse an existing canonical synonym rather than preserving two spellings where callers can be migrated atomically.
- The envelope remains the existing strict shape: `{ code, message, details?, correlationId, timestamp }`, where `details` is JSON data, `correlationId` satisfies the shared normalized correlation schema, and `timestamp` is an ISO instant. `packages/contracts` owns code vocabulary and payload validation; services and the BFF own status selection and safe human-facing messages; `packages/logger` owns `x-correlation-id`, normalization/generation, and child-log creation.
- The donor's concrete contract pattern is `packages/contracts/src/errors.ts`: `ERROR_CODES` feeds a Zod enum used directly by `ErrorPayloadSchema.code`, with contract tests proving all declared values parse, the tuple is duplicate-free, and unknown/typo/drifting values such as `notfound` fail. Its helpers `validationErrorPayload` and `buyErrorPayload` always add the correlation ID and timestamp. Adapt this idea to the existing lower-camel exports (`errorPayloadSchema`) rather than renaming unrelated public APIs.
- The donor's reusable hook is `applyCorrelationId(app)` in `apps/api/src/app/plugins/correlation-id.ts`, mirrored in `apps/mock-erp/src/app/plugins/correlation-id.ts` and `apps/load-orchestrator/src/app/plugins/correlation-id.ts`. Each decorates `FastifyRequest.correlationId`, normalizes or generates from `x-correlation-id` in `onRequest`, and echoes the chosen ID on the reply. Each root factory calls it before error handlers and route registration. In this repository, extract the duplicated hook currently embedded in `apps/api/src/server.ts`, `apps/mock-erp/src/server.ts`, and `apps/load-orchestrator/src/server.ts` into an appropriately shared logger/Fastify helper or small service-local plugin pattern, then apply it at all three composition roots. Keep infrastructure construction and root wiring in those factories.
- Extend the hook beyond the donor: bind the selected ID to the logger used by routine Fastify request/route logs, not only exceptional log calls. After the hook runs, `request.log.info/warn/error(...)` must already carry `correlationId` without every route restating it. Use the supported Fastify request-child-logger mechanism for the installed Fastify version (or a typed per-request child assignment if that is the supported API); do not mutate the application-wide Pino logger or leak one request's ID into another. The affected routine logs include `apps/mock-erp/src/routes/chaos-routes.ts` update/reset logs and `apps/mock-erp/src/routes/confirmation-routes.ts`; the API and load-orchestrator error logs should inherit the same binding and no longer need an ad hoc correlation field merely to be searchable.

### Web BFF propagation and response rules

- Update `apps/web/src/app/lib/server/backend-proxy.ts`, the common boundary used by the protected Next route handlers. Resolve one BFF correlation ID from the incoming browser `Request` using `correlationIdHeaderName` and the logger package's normalization/generation policy. Functions that can construct local failures (`requireAdminPassphrase`, `requireAdminSession`, `readJsonRequest`, `validateJson`, `requireControlServiceToken`, and `proxyJson`) need access to that request-scoped ID; adjust their inputs/call sites or pass a small request context rather than generating a different ID at each helper.
- `jsonError` must return a payload validated by `errorPayloadSchema`, including `correlationId` and `new Date().toISOString()`, and must set `x-correlation-id` on the browser-facing response. Do not return exception text from a failed backend fetch: map it to the stable `backend_unavailable` code and a non-leaking message; details may contain only intentionally safe diagnostic context.
- For `proxyJson`, forward only the normalized correlation header in addition to the explicitly supplied allow-listed headers (content type, accept, and the server-owned control token). Never forward browser cookies, the admin passphrase/session secret, authorization headers, or arbitrary browser headers to a backend. Server-owned secrets remain server-side.
- Preserve an upstream error response as an opaque canonical `ErrorPayload` only after validating it with `errorPayloadSchema`; preserve its HTTP status. If a non-success upstream body is malformed/non-JSON, synthesize a BFF `invalid_backend_response` envelope with the BFF request correlation ID and HTTP 502. Do not pass arbitrary upstream JSON errors through to the browser.
- When reconstructing any upstream response with `Response.json`, copy the upstream `x-correlation-id` to the browser response. For a valid canonical upstream error, require the response-header and body correlation values to agree when both are present; a missing response header may be recovered from the validated body. Treat a disagreement as `invalid_backend_response` rather than presenting two trace IDs. For successful bodies, use the normalized upstream response header when present, otherwise retain the BFF request ID. The response header returned to the browser is the authoritative lookup key and must match any `correlationId` present in the response body.

### Boundary and propagation caveats

- Normalization happens once per inbound HTTP boundary: accept a usable browser/upstream ID within the existing `correlationIdSchema` limits or generate a UUID. Blank, array-like, oversized, or otherwise invalid values must not reach logs or headers unchanged. Do not lowercase IDs if the existing shared normalizer preserves case; changing normalization semantics would be a separate cross-service compatibility change.
- Correlation ID is trace context, not identity, authorization, idempotency, or run ownership. Continue to validate the admin session and service token independently, and continue to use explicit `runId`/idempotency keys for their existing purposes. A caller-controlled correlation value must never grant access or select another visitor's data.
- Preserve the chosen ID across asynchronous boundaries already owned by the workflow: API-to-load-orchestrator calls, worker/queue jobs, Mock ERP calls, persisted attempts/events, and realtime payloads should keep using their explicit contract fields and `x-correlation-id` headers. Do not infer a run ID from a correlation ID. When a route currently replaces the request ID from a validated body (notably load-orchestrator start, and buy-path body fallback), update the bound request logger and reply header together or establish the header as authoritative; never let header, body, and routine logs silently diverge.
- Do not add distributed tracing infrastructure, browser telemetry, new authentication behavior, queue redesign, or a general HTTP client framework. This task is the targeted canonical-envelope/correlation repair at the shared contract, BFF, and three existing HTTP composition roots.
