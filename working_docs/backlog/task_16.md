Notification jobs use a deterministic ID and retain failed jobs, so the recovery scanner's re-add is silently deduplicated against the dead job while every scan reports success. Missing notifications block finalization, so a temporary persistence problem can permanently fail the run. Remove failed-job retention for this queue or make the scanner clear/replace dead jobs before re-adding.

## Standalone implementation context

### Verified current data flow and exact defect

- `apps/worker/src/application/order-process-job-handler.ts`, `publishNotificationRecordJobWithoutFailingOrder()`, runs only after `transitionToConfirmed()` has committed the authoritative order outcome. It deliberately catches notification publication failures so a post-confirmation side effect cannot retry or undo an already confirmed order. Preserve that separation.
- `apps/worker/src/queue/bullmq-notification-record-publisher.ts`, `createBullMqNotificationRecordPublisher()`, builds the `NotificationRecordJob` and adds it under the deterministic ID `${job.orderId}-email`. It gives the job three attempts by default with exponential backoff, retains up to 1,000 completed jobs, and currently also retains up to 1,000 failed jobs through `removeOnFail: 1000`.
- BullMQ job IDs remain unique while the old job record exists. After all attempts fail, a retained failed job still owns `${orderId}-email`. A later `queue.add()` with that ID resolves to/deduplicates against the existing job rather than throwing or scheduling a fresh delivery. Therefore this is not represented as a publication failure.
- `apps/worker/src/application/notification-recovery-scanner.ts`, `scanOnce()`, asks its persistence port for confirmed orders missing notifications, calls the same publisher for each candidate, and increments `published` whenever that promise resolves. Against a retained failed job, every scan therefore returns and logs `published: 1, failed: 0` even though no new attempt is queued.
- `apps/worker/src/persistence/postgres-notification-recovery-persistence.ts`, `PostgresNotificationRecoveryPersistence.findConfirmedOrdersMissingNotifications()`, is the durable source of recovery candidates. It left-joins confirmed orders to the `email` notification row, orders candidates oldest-first, and reconstructs the original job identity plus the durable `confirmedAt`. The candidate correctly remains visible on every scan; only BullMQ's retained ID prevents progress.
- `apps/worker/src/queue/bullmq-notification-record-consumer.ts` validates the contract and delegates to the handler. A transient database failure from the handler exhausts the BullMQ attempts and reaches the consumer's `failed` listener, which already logs the job ID, attempt count, and correlation ID. The logging is important because the preferred fix removes the failed queue record.
- `apps/worker/src/persistence/postgres-notification-record-persistence.ts`, `PostgresNotificationRecordPersistence.record()`, locks and validates the durable order, requires it to be confirmed, and inserts the notification with `onConflictDoNothing` on `(orderId, channel)`. The notification row and `notification.recorded` event are transactional, and a replay reports `{ recorded: false }`. This durable idempotency is the safety net that allows recovery redelivery.
- `apps/api/src/services/demo-run-finalization-service.ts`, `businessDrainBlockers()`, adds `missing_notifications` while `notificationsRecorded < confirmedOrders`. Before the configured drain timeout the run stays `draining`; after timeout `deriveFailureReason()` produces `business_drain_timeout`. Thus a transient notification persistence outage can become a terminal run failure even after the database recovers, because the scanner never actually replaces the dead job.

### Reference evidence and what to adapt

At the verified `checkout-forge` reference head, `apps/worker/src/queues/simulated-notification-queue.ts` also uses `${orderId}-email`, three exponential-backoff attempts, `removeOnComplete: { count: 1_000 }`, and `removeOnFail: { count: 1_000 }`. `apps/worker/src/services/order-processing-service.ts` likewise treats notification enqueue as best-effort after confirmation, and `OrderProcessingPersistence.recordSimulatedNotification()` makes the durable write idempotent. However, Forge has no scanner that republishes missing notifications, so its retention policy does not provide a recovery solution and must not be copied as proof that the current combination is safe.

Forge's useful finalization behavior is diagnostic rather than queue recovery: `apps/api/src/services/demo-run-finalization-service.ts`, `getFinalizationDecision()`, distinguishes a missing notification at drain timeout as `simulated_notification_timeout`. Surge currently uses the broader `business_drain_timeout`. Do not widen this task into finalization-vocabulary or contract changes; the relevant lesson is that missing notification evidence is real terminal business evidence, making reliable recovery before the timeout essential.

The preferred focused adaptation is to keep the deterministic job ID and set this notification queue's `removeOnFail` to immediate removal (`true`). A failed delivery should still use all configured attempts/backoff first; only the terminal failed job record is removed. Once it is gone, the next durable recovery scan can add `${orderId}-email` again. Keep `removeOnComplete: 1000`: retaining successful jobs prevents needless duplicate queue work, while the durable notification row removes completed orders from scanner candidates.

An explicit failed-job replace path is acceptable only if failed-job retention is a firm operational requirement. In that design, the BullMQ publisher/recovery-specific adapter must fetch the deterministic job, inspect its state, remove it only when it is terminal `failed`, then add the replacement while handling races with active/delayed/completing jobs. Do not put BullMQ job-state operations into `notification-recovery-scanner.ts`; that application service should continue to depend on a publisher port rather than queue internals. This alternative is more complex and race-prone than immediate failed-job removal, so prefer `removeOnFail: true` unless retained queue diagnostics are explicitly required.

### Strengths and boundaries to preserve

- Keep the notification on its dedicated queue and keep notification failure from failing or re-confirming the order-processing job.
- Keep the deterministic per-order/channel ID. Replacing it with a random recovery ID would permit concurrent duplicates and discard useful enqueue deduplication; database idempotency would limit durable duplication but would not prevent unnecessary queue load.
- Keep the scanner's durable PostgreSQL query, oldest-first batch limit, non-overlapping interval execution, per-candidate failure isolation, and shutdown behavior. Do not add an in-memory retry ledger or treat scanner counters as durable completion evidence.
- Keep `PostgresNotificationRecordPersistence` identity validation, confirmation guard, transaction, and unique-conflict handling. Do not weaken these because redelivery becomes possible.
- Keep finalization blocked until the durable notification count catches up. Do not “fix” recovery by ignoring `missing_notifications`, increasing the timeout, or marking an enqueue acknowledgement as a recorded notification.
- Keep queue construction in the worker composition/queue adapter boundary. No BullMQ, Redis, or PostgreSQL operations belong in the API finalization service or HTTP routes.
- Immediate failed-job removal trades BullMQ's failed-job history for recoverability. Preserve operational evidence through the existing consumer failure log (job ID, attempts, correlation ID); adding a separate durable dead-letter/audit system is outside this task.
