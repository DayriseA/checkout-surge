## Verified target boundary

- `packages/contracts/src/demo.ts` currently owns one strict `runHistoryDetailResponseSchema`. It embeds the full `demoRunSnapshotSchema` plus four `{ records, totalCount, limit, truncated }` collections. The row schemas expose: orders (`orderId`, `publicOrderId`, `saleOfferId`, `correlationId`, quantity/status/failure/timestamps); ERP attempts (`attemptId`, `orderId`, `publicOrderId`, `correlationId`, attempt number/status/HTTP/error/latency/timestamps); notifications (`notificationId`, `orderId`, `publicOrderId`, channel/status/time); events (`eventId`, event name, `source`, `saleOfferId`, `correlationId`, optional order/public-order IDs, time).
- `apps/api/src/routes/run-history-routes.ts::registerRunHistoryRoutes` serves `GET /demo/runs/history/:runId` anonymously and calls the same `RunHistoryController.detail` used for the complete DTO. Only `DELETE /demo/runs/history` invokes `requireControlServiceToken`; there is no protected detail route today.
- `apps/api/src/services/run-history-service.ts::RunHistoryService.detail` selects the summary and demo-run rows, then executes eight queries for the four recent-record collections and their counts (`detailRecordLimit = 20`). `toRunHistoryOrderOutcome`, `toRunHistoryErpAttempt`, `toRunHistoryNotification`, and `toRunHistoryEventTimelineEntry` copy sensitive identifiers/correlation data into the public response.
- `apps/web/src/app/lib/api.ts::getRunHistoryDetail` calls the API detail path directly with `cache: "no-store"`. `apps/web/src/app/run-history/[runId]/page.tsx` has no admin-session branch, and `apps/web/src/app/components/run-history-detail.tsx` renders the row collections. Existing admin-session and control-token proxy helpers are demonstrated by `apps/web/src/app/api/admin/demo/runs/history/route.ts`, but that route currently protects deletion only.

## Required implementation shape

1. Split the shared contract into a deliberately named public detail response and an admin detail response. Keep the existing row schemas only in the admin contract. Prefer a new explicit admin detail path constant rather than changing the meaning of the anonymous path; preserve the current public URL for compatibility. If retaining `runHistoryDetailResponseSchema` as a compatibility alias, make it alias the narrowed public schema so old consumers cannot silently keep receiving rows.
2. Public allowlist: immutable `summary` rollups; public lifecycle timestamps/status; only configuration values already intentionally shown to anonymous visitors; aggregate order counts by status (and failure code only if the code vocabulary is demonstrably public and bounded); aggregate ERP attempt counts by status plus nullable average/p95 latency; notification count (optionally bounded channel/status counts); event count (optionally bounded event-name counts). Return explicit zeroes and nullable latency for empty sets. Keep response `timestamp`. Do not include collection `records`, `limit`, or `truncated`, because those imply a sample and provide no value once rows are removed.
3. Public denylist: internal `orderId`, `attemptId`, `notificationId`, `eventId`; `saleOfferId`; every persisted/request `correlationId`; event `source`; per-order `publicOrderId` (public-facing does not mean safe for cross-run enumeration); attempt number, HTTP status/error and individual latency/timestamps; per-row channel/status/timestamps; all row-level order/event timestamps and failure details; reservation tokens, idempotency keys, raw payloads, and free-form diagnostics. Review `demoRunSnapshotSchema` rather than carrying it wholesale: in particular omit `saleOfferId` and prefer a purpose-built public run snapshot/config projection.
4. Add a separate controller/service method for admin detail and put its route behind `requireControlServiceToken` before doing any database work. The web-facing admin proxy must require `requireAdminSession`, obtain the configured control token, forward control headers, validate the admin schema, and use `cache: "no-store"`. Anonymous server/page code must validate/render only the public schema. Do not infer authorization from a client flag or merely hide sensitive DOM sections.
5. Calculate public aggregates without fetching the 20 most recent rows. Use grouped/count/average inputs at the database boundary and a deterministic percentile strategy consistent with the existing database/tooling, or reuse trustworthy immutable `businessOutcomeSummary` totals where their capture semantics match the label. Do not mix terminal snapshot counts with later live-table counts without naming the observation time. The admin method may retain the bounded recent-row queries and truncation metadata.

## Privacy, compatibility, and operational constraints

- Treat correlation IDs as tracing secrets at this boundary: continue request/response correlation headers and error envelopes per platform conventions, but never expose persisted row correlation IDs inside anonymous detail data. Ensure logs do not serialize admin rows or the public DTO source rows.
- Aggregate buckets must use closed contract enums or an explicit `other` bucket; never turn arbitrary error/source strings into attacker-controlled object keys. Avoid small-cell row reconstruction: do not add “latest”, “first”, or sample records, and do not publish combinations of identifier-like dimensions. Counts alone are acceptable for this demo surface; document any future minimum-cell suppression separately rather than inventing it here.
- Both public and admin detail responses are run-specific and mutable until terminal capture/reconciliation is settled. Keep `no-store` end to end and do not add shared/CDN caching. If caching is introduced later, public and admin URLs/keys must be distinct and authorization headers/cookies must participate in cache policy so an admin representation can never poison the public cache.
- This is an intentional breaking DTO reduction for anonymous consumers. Update every in-repo fixture/import/render path atomically; strict schemas should reject legacy row fields. Preserve public route status/error behavior (including 404) and list/delete contracts. Do not weaken UUID validation or the existing delete authorization.
