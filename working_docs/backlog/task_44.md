## Current implementation and cost ownership

- `packages/db/src/redis-stock-reservation.ts` already keeps the losing buy path cheap and durable. Its Lua script reads `inventory:{saleOfferId}:reservation-outcomes`, atomically `HINCRBY`s `api_sold_out_decision`, writes `api_sold_out_decision_latest_observed_at`, and returns `sold_out` without creating a reservation, idempotency record, PostgreSQL row, or per-loser dashboard event. `packages/db/src/redis-inventory.ts` exposes that cumulative count and timestamp as `InventoryStatus.soldOutPressure`. Preserve this atomic source of truth.
- `apps/api/src/services/reserve-order-service.ts` currently turns the Redis `sold_out` decision directly into the HTTP rejection. There is no injected live-observation port on that branch. Fresh accepted reservations schedule a best-effort business-outcome update with `setImmediate`; the successful buy response does not await the projection, but each scheduled task still performs the full work below.
- `packages/db/src/business-outcome-dashboard.ts::publishBusinessOutcomeDashboardUpdate()` runs `readBusinessOutcomeSummary()` and `readConsistencyLagSummary()` concurrently and then publishes one full `business.outcome.updated`. The summary performs nine logical counts (secured reservations; sold-out aggregate; queued, processing, retrying, confirmed, failed orders; pending persistence; notifications), while lag adds two aggregate joins. A normal order can trigger this after API acceptance, worker `processing`, `retrying`/`failed` or `confirmed`, and notification recording. Moving API acceptance off-response therefore protects latency but does not bound PostgreSQL work or queued `setImmediate` tasks.
- `apps/worker/src/application/order-process-job-handler.ts` awaits an update after each fresh transition; `notification-record-job-handler.ts` awaits one after a fresh notification. `apps/worker/src/index.ts` and `apps/api/src/index.ts` compose both paths directly with `publishBusinessOutcomeDashboardUpdate()`. Dashboard failure is non-fatal, but its latency still occupies worker handler time and database pool capacity.
- `apps/api/src/services/demo-run-service.ts::RedisDashboardTrafficMetricStore.append()` writes all samples in one `RPUSH`, then separately awaits `LTRIM` to `recentMetricLimit` and a 24-hour `EXPIRE`. `DemoRunService.ingestMetrics()` then loops over the batch and awaits `publishDashboardEvent()` once per sample. Thus an input batch of `N` samples costs three sequential Redis commands for recovery plus `N` sequential Pub/Sub round trips. `packages/db/src/redis-dashboard-events.ts` validates and publishes only one event at a time.
- `packages/contracts/src/dashboard-events.ts` currently makes `business.outcome.updated` a full replacement containing `saleOfferId`, `outcome`, and `consistencyLag`; `apps/web/src/app/components/operator-dashboard.tsx::applyDashboardEvent()` replaces both projections. The same reducer appends each `traffic.metric` to a 20-sample client window. Any delta/coalesced contract must be explicit; do not send a delta in a field the client interprets as an absolute snapshot.
- `apps/api/src/services/dashboard-recovery-service.ts` independently re-reads authoritative inventory, business outcome, lag, and recent metrics. Keep recovery and terminal finalization authoritative even if live delivery becomes lossy/coalesced.

## Verified `checkout-forge` patterns

### Sold-out aggregate

- `apps/api/src/services/sold-out-dashboard-metric-aggregator.ts::SoldOutDashboardMetricAggregator` owns two `Map<string, SoldOutAggregate>` instances keyed by `JSON.stringify([runId ?? null, saleOfferId])`. `totals` supports process-local snapshot reads; `pending` contains the current publication interval. Each entry holds `saleOfferId`, nullable `runId`, `count`, and `latestObservedAt`.
- `observeSoldOutRejection()` is synchronous: it normalizes `count` to a nonnegative integer, increments `totals`, and, when a publisher exists, increments `pending`. It performs no Redis/PostgreSQL read and does not await network I/O. `ReserveOrderService` calls it only for a fresh Redis `sold_out` result, after constructing the rejection and before returning it; idempotent replay does not increment it.
- The default `flushIntervalMs` is exactly `500`. The constructor starts one `setInterval`, calls `unref()`, and each tick snapshots `pending`, clears it, and emits one aggregate per `(runId, saleOfferId)`. The event is `dashboard.metric.observed` with `metricName: "inventory.sold_out_rejection"`, interval `value`, `unit: "rejections"`, `observedAt: latestObservedAt`, optional `runId`, and dimensions `{ saleOfferId, outcome: "sold_out", aggregation: "flush_interval" }`. Top-level `timestamp` is flush time.
- Publication is advisory. `DashboardRealtimePublisher.emit()` validates synchronously and starts an unawaited Redis `PUBLISH`; failures are logged. `close()` flushes pending observations before clearing the timer. `clearRun()` removes one run and `clear()` is used by demo reset. `apps/api/src/index.ts` constructs exactly one aggregator and injects it into reservation, snapshot, and reset services.
- This donor state is not durable or cluster-wide. A crash loses the current half-second delta and all `totals`; two API instances publish independent interval deltas; `close()` starts fire-and-forget publishes and cannot prove delivery before Redis closes. Forge can tolerate this because realtime is advisory, but its `DashboardSnapshotService` also reads sold-out totals from that same process-local map, so restart/multi-instance recovery is incomplete.

### Windowed metric publication

- `checkout-forge/apps/load-orchestrator/src/load-runner.ts::LoadRunner` uses `pendingMetrics: DashboardMetric[]`, `pendingMetricRun`, `metricFlushTimer`, and `metricFlushInFlight`. Defaults are `metricFlushIntervalMs = 500` and `metricMaxBatchSize = 250`.
- Every adapted point is appended by `queueCurrentRunMetrics()`. `scheduleMetricFlush()` owns at most one unref'd timeout and will not schedule while a flush is in flight. `flushMetricStream()` removes at most 250 samples, awaits one `streamMetrics({ run, metrics })`, logs/drops a failed batch, clears the single-flight flag, and schedules another interval if work remains. An empty metrics array is deliberately queued at lifecycle changes so current-run state reaches the API even without samples.
- `apps/api/src/services/load-metric-stream-service.ts::observeLoadMetrics()` accepts the batch, updates recovery state once, emits one `load.run.updated`, and calls the nonblocking publisher once per metric. It throttles live run-state PostgreSQL writes with `persistedLiveRunStateByRunId`; the same `starting`/`active` status is persisted at most once per 1,000 ms per API process.
- This is publication-window batching, not correct event-time rate aggregation. Forge's metric adapter still maps raw k6 points imperfectly; task 30 owns fixed event-time request-rate/latency/failure windows and their units. Forge also has no explicit maximum for `pendingMetrics`, no HTTP deadline, and `resetMetricBuffer()` can discard queued data while an in-flight flush is not awaited. Reuse the bounded single-flight shape, not these omissions.

### Cheap business-outcome progress

- Forge does not publish a full business-outcome summary on each transition. `packages/contracts/src/events.ts::orderStatusUpdatedEventSchema` defines `order.status.updated` as `{ type, correlationId, timestamp, payload: { publicOrderId, eventName, customerStatus, runId?, saleOfferId? } }`.
- `apps/api/src/services/reserve-order-service.ts` emits `order.queued` only after durable order persistence, queue enqueue, and Redis idempotency response storage. It separately emits `inventory.remaining` from the atomic reservation result, avoiding a status re-read.
- `apps/worker/src/services/order-processing-service.ts::emitOrderStatus()` emits `order.processing`, `order.confirmed`, `order.failed`, or `erp.attempt.failed` after the corresponding persistence operation. Confirmation separately emits `order.consistency_lag` from `enqueuedAt` to completion. These are small, write-derived events; no transition handler queries all reservations/orders/attempts/notifications to construct a summary.
- Durable snapshot and terminal paths still query PostgreSQL. The optimization is a separation of concerns: transition-shaped realtime progress is cheap and advisory; recovery/finalization computes an authoritative aggregate. Do not infer that Forge maintains an exact restart-safe live aggregate.

## Concrete adaptation for this repository

1. Add a small API-owned sold-out publication service and inject a narrow synchronous observation port into `ReserveOrderService`. Call it only after the atomic stock gateway returns a fresh `sold_out`; never add a Redis read/write, database write, or awaited publish to the loser response. Keep the Lua-maintained cumulative hash as recovery truth.
2. Coalesce sold-out observations by `(runId, saleOfferId)` on an explicit 500 ms boundary and emit at most one live signal per dirty scope per interval. Prefer publishing the cumulative Redis count/timestamp, or an explicitly labeled interval delta plus a reducer that adds it exactly once. Because the current UI displays `InventoryStatus.soldOutPressure.rejectionCount` as an absolute value, a narrow cumulative event is safer across reconnects and duplicates. Do not overload `traffic.metric` without defining whether `value` is an interval delta or cumulative total and teaching the reducer that meaning.
3. Coordinate the event shape with task 27. Task 27 owns general `inventory.updated` wiring and notes that a full `InventoryStatus` requires several Redis reads. This task should not perform that full read per loser. Either task 27's bounded inventory scheduler performs one coherent read per interval and naturally carries sold-out pressure, or this task adds a narrow contract-valid `inventory.sold_out_rejection` signal. There must be one scheduler/producer, not parallel full-inventory and sold-out pollers.
4. Make timers and buffers lifecycle-owned in `apps/api/src/index.ts` (or a dedicated composition-owned service): one timer per process, `unref()`, explicit `flush()/close()`, reset/run cleanup, and logged best-effort failures. Use a single-flight flush with a dirty-during-flush bit so a slow Redis operation cannot overlap timers or lose observations made during the read/publish. Bound retained scopes and delete terminal/reset scopes.
5. Treat restart and scale semantics explicitly. Process-local pending deltas may be lost and duplicated across API replicas; the existing Redis cumulative counter is not. For multiple API instances, either publish cumulative values (idempotent max/newer-timestamp replacement), use a short Redis lease for one coalescing publisher, or have each interval atomically claim a shared delta. Document lease expiry/owner crash behavior. Never require exactly-once Pub/Sub delivery; recovery must repair the display from `getInventoryStatus()`.
6. Keep task 30 responsible for converting raw k6 points into fixed event-time windows. At this task's boundary, make transport batching bounded and single-flight: accept already-windowed `MetricSample`s, retain an explicit maximum number of samples/batches, define drop/coalesce policy by metric name and run, and ensure at most one Redis publish operation is in flight per publisher. Latest-value coalescing is appropriate for dashboard gauges; terminal k6 totals must not be derived from this lossy buffer.
7. In `RedisDashboardTrafficMetricStore.append()`, issue `RPUSH`/`LTRIM`/`EXPIRE` as one Redis transaction/pipeline and handle an empty sample list without an invalid `RPUSH`. In `DemoRunService.ingestMetrics()`, avoid `N` awaited round trips. Either publish a contract-level metric batch and fan it out once, or enqueue validated individual events behind the bounded single-flight publisher. Preserve each sample's timestamp, run/correlation scope, name, value, and unit; recovery remains capped at the newest 20 displayed samples and durable Redis retention remains bounded by `recentMetricLimit`/24 hours.
8. Replace per-transition calls to `publishBusinessOutcomeDashboardUpdate()` with a coalescing projection boundary or explicit transition events. The least disruptive option is a per-scope dirty scheduler: mutation handlers mark `(runId, saleOfferId)` dirty after durable state changes; at most once per configured window, one single-flight task runs the existing summary/lag readers and publishes the current full replacement. If a transition arrives during the read, retain dirty and run once more after the interval. This preserves the current contract/reducer while reducing eleven logical aggregate queries per transition to at most one projection read per dirty scope/window/process.
9. A transition-event design may instead mirror Forge, but it requires a new strict contract carrying a stable transition/event identity, entity identity, `runId`, `saleOfferId`, correlation, status/event name, and occurred/persisted timestamp. The browser must deduplicate and reject regressions/out-of-order transitions, and aggregate counters need status-from/status-to semantics or an authoritative periodic refresh. Do not have the browser guess old state. Keep `business.outcome.updated` as a full snapshot if it remains in use.
10. Keep mutation ownership unchanged: API marks business outcome dirty only after a fresh durable reservation/order enqueue (not plain idempotent replay); worker does so only after a persistence method reports a fresh processing/retry/terminal transition; notification worker does so only when `recorded` is fresh. Projection or publish failure must never change the buy response, retry decision, durable order status, or notification acknowledgement.
11. Coalescer state spanning API and worker processes needs a declared deployment bound. Independent per-process coalescers cap work by `instanceCount / window`, but can still duplicate SQL reads. If a global cap is required, use a shared Redis dirty-set/lease or one dedicated projection consumer. A lease holder must re-read PostgreSQL after claiming dirty work, publish a cumulative snapshot, and tolerate duplicate claims after expiry. Do not maintain authoritative counters only in process memory or apply non-idempotent increments from at-least-once BullMQ deliveries.
12. On shutdown, stop accepting observations, clear timers, await the current flush, then flush the final dirty scopes within a bounded deadline before closing Redis/PostgreSQL. On crash, accept loss of advisory signals and rely on recovery. On startup, do not replay fabricated deltas; the first dashboard recovery or dirty projection must read authoritative Redis/PostgreSQL state.

## Scope and non-goals

- Do not alter stock-gate correctness, idempotency, durable order transitions, BullMQ retry semantics, terminal run summaries, or finalization reconciliation.
- Do not put Redis/PostgreSQL clients or batching logic in routes. Application services expose observation/dirty ports; DB/Redis adapters perform reads and transport; `apps/*/src/index.ts` remains the composition and cleanup root.
- Do not promise replay or exactly-once delivery from Redis Pub/Sub. Live events are advisory and bounded; `/dashboard/recovery` and terminal summaries remain authoritative.
- Do not redefine traffic rate windows here. Task 30 owns event-time aggregation; this task owns bounded persistence/publication of the samples it produces. Task 27 owns the complete live gold-signal wiring and UI prominence; share its inventory/queue publisher rather than duplicating it.
- Do not broadly optimize the recovery queries or recent-completion N+1 reads. This task removes them from per-transition burst frequency; query-shape optimization can be separate unless profiling shows the once-per-window projection still violates the configured budget.
