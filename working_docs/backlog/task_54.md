# Task 54: Add composite indexes matching run-scoped filters plus chronological sort

## Implementation record

- **Status:** Implemented; focused clean-migration/catalog coverage and representative test-database benchmarks pass.
- **Completed scope:** Added the four exact `(run_id, chronological_timestamp DESC, created_at DESC)` declarations to `schema.ts`, append-only migration `0012_run_history_chronological_indexes`, its journal entry, and a PostgreSQL catalog assertion covering table ownership, key order, and sort direction. No application query or response behavior changed.
- **Decisions:** The indexes are non-partial so schema and migration remain simple and consistent while still supporting nullable-column equality predicates. Existing single-column run indexes are retained because production-like run counts, maintenance-delete patterns, index sizes, and write/vacuum costs have not been measured sufficiently to justify dropping deployed indexes in the same migration. `order_events_occurred_at_idx` and all unrelated indexes remain. No reservation-pending-persistence index was added because there is no matching production chronological read.
- **Migration convention and rollout:** The repository has journal metadata but no snapshots; Task 55 owns restoring the valid historical snapshot chain, so Task 54 follows the Task 53 convention and adds only the next journal entry rather than inventing an orphan snapshot. The pinned postgres-js Drizzle migrator wraps pending migrations in one transaction, making `CREATE INDEX CONCURRENTLY` invalid without a runner redesign. Migration `0012` therefore uses ordinary `CREATE INDEX`; a populated rollout must plan for stronger locks, index-build duration, and disk headroom. Rollback is limited to dropping the four new indexes.
- **Representative evidence:** `EXPLAIN (ANALYZE, BUFFERS)` ran only on the package-isolated `checkout_surge_test_db`, inside rollback-only transactions. The main fixture loaded 20,000 coherent rows in each history table across four runs, with 5,000 rows in the measured run. After indexing, orders improved from 1.621 ms / 116 execution buffers to 0.076 ms / 4 buffers; ERP attempts from 8.719 ms / 556 buffers to 0.141 ms / 64 buffers; and notifications from 8.028 ms / 552 buffers to 0.166 ms / 64 buffers. Each post-change plan used the intended composite with `run_id` as `Index Cond`, read 20 history rows, and removed the explicit top-N sort. The initial event fixture grouped runs into contiguous time blocks and exposed a legitimate competing-plan case: PostgreSQL retained `order_events_occurred_at_idx` and filtered 15,000 rows. A corrected 20,000-row, four-run interleaved timeline retained that unscoped index and showed the new composite reading 20 rows directly, removing the incremental sort, and reducing execution buffers from 68 to 65; warm-cache execution time was effectively unchanged (0.212 ms before, 0.207 ms after). Tests intentionally assert catalog shape, not planner nodes.

## Verified current state and target adaptation

The schema ownership boundary is `packages/db/src/schema.ts`; a new forward-only Drizzle migration under `packages/db/drizzle/` must carry the deployed database change, with the corresponding journal/snapshot metadata generated by the repository's normal migration workflow. Do not edit `0000_initial_schema.sql` in place because environments may already have applied it. The currently cited definitions in that baseline are single-column `orders_run_id_idx`, `erp_attempts_run_id_idx`, `order_events_run_id_idx`, and `reservation_pending_persistence_run_id_idx`; `simulated_notifications_run_id_idx` has the same limitation. `order_events_occurred_at_idx` cannot satisfy both the run filter and ordering by itself.

The actual bounded detail reads are in `apps/api/src/services/run-history-service.ts`, `RunHistoryService.detail`:

- orders: `WHERE orders.run_id = ? ORDER BY orders.queued_at DESC, orders.created_at DESC LIMIT 20`;
- ERP attempts (joined to `orders` by the order primary key): `WHERE erp_attempts.run_id = ? ORDER BY erp_attempts.finished_at DESC, erp_attempts.created_at DESC LIMIT 20`;
- simulated notifications (joined to `orders`): `WHERE simulated_notifications.run_id = ? ORDER BY simulated_notifications.recorded_at DESC, simulated_notifications.created_at DESC LIMIT 20`;
- order-event timeline (left joined to `orders`): `WHERE order_events.run_id = ? ORDER BY order_events.occurred_at DESC, order_events.created_at DESC LIMIT 20`.

Declare matching B-tree indexes in the relevant `pgTable` index arrays and emit equivalent migration SQL:

- `orders_run_id_queued_at_created_at_idx` on `(run_id, queued_at DESC, created_at DESC)`;
- `erp_attempts_run_id_finished_at_created_at_idx` on `(run_id, finished_at DESC, created_at DESC)`;
- `simulated_notifications_run_id_recorded_at_created_at_idx` on `(run_id, recorded_at DESC, created_at DESC)`;
- `order_events_run_id_occurred_at_created_at_idx` on `(run_id, occurred_at DESC, created_at DESC)`.

`run_id` must be first: equality on a run is the selective prefix, after which PostgreSQL can read the timestamp suffix in the requested direction and stop after 20 rows. Keep both sort expressions in query order. Explicit `DESC` is preferred for legibility and exact planner matching, although a PostgreSQL B-tree can scan an all-ascending definition backward. Do not substitute the Forge ERP `(started_at, attempt_number)` suffix or Forge's `id` tie-breaker without also intentionally changing and testing the service ordering contract.

All four `run_id` columns are nullable because the same tables may contain non-run traffic. A partial `WHERE run_id IS NOT NULL` form is valid and can reduce index size/write amplification while still serving these equality predicates; use it consistently only after confirming the migration/schema DSL and project database version emit the intended predicate. A non-partial composite is also correct. Do not add status to these history indexes: status is neither filtered nor sorted in these reads and placing it before the timestamp would break the desired ordering. Avoid `INCLUDE` columns unless measurements demonstrate heap-fetch cost warrants much wider indexes; these projections select most row fields, so covering indexes are unlikely to be economical.

The composite's leftmost `run_id` prefix also supports the companion `count(*) WHERE run_id = ?`, maintenance deletes, and other run-only probes. After the new indexes are proven in representative data, assess whether the old run-only indexes are redundant and remove them in the same migration or a later low-risk migration; retaining both permanently adds write and vacuum cost. Do not drop unrelated indexes such as order foreign-key lookup, uniqueness, status, sale-offer, correlation, or the event-name index. The standalone `order_events_occurred_at_idx` serves a different unscoped access path and should only be removed with evidence that no such path exists.

`reservation_pending_persistence` is not currently read as a chronological run-scoped queue in production code. Current production uses are run/status counts, reservation-id reconciliation, and run-scoped maintenance deletion. Therefore do not copy Forge's `(run_id, secured_at, id)` index merely on speculation. For the existing dashboard count `WHERE run_id = ? AND status = 'pending_reconciliation'`, first compare a general `(run_id, status)` index with a smaller partial index on `(run_id) WHERE status = 'pending_reconciliation'`; choose based on actual status distribution and whether reconciled rows are retained. Add `(run_id, secured_at, created_at/id)` only together with a real chronological query whose exact ordering it matches. Likewise, the paginated history list in `RunHistoryService.list` is not run-scoped: it orders `demo_run_summaries` by `(captured_at DESC, created_at DESC)`. Improving that separate index is out of this task unless explicitly added to scope.

Describe and review these plans; this task explicitly does not authorize running `EXPLAIN` against a database during backlog enrichment.

For a populated deployment, creating ordinary indexes takes stronger locks and can delay writes. Decide with operations whether the forward migration needs `CREATE INDEX CONCURRENTLY`; if so, account for PostgreSQL's prohibition on running it inside a transaction and the migration runner's transaction behavior. Build new indexes before dropping redundant ones, monitor duration/disk headroom, verify validity after interruption, and keep rollback limited to dropping newly introduced indexes (concurrently where appropriate). Index changes must not alter result ordering or API payloads.
