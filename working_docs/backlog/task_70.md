## Task details

- **Priority:** P4
- **Area:** API / crash recovery
- **Source:** donor comparison (Opus graded better; GPT at parity) + independent review (note)
- **Solved elsewhere:** Opus provides three useful, verified patterns, but they must be adapted rather than copied wholesale.
  - `checkout-surge-opus/apps/api/src/services/startup-reconciliation-service.ts` — `StartupReconciliationService.reconcile()` obtains `listNonTerminalRuns()` once and wraps the processing of each returned run in its own `try/catch`, logging `runId` and continuing. `#recoverDrainingRun()` leaves the lifecycle state unchanged and immediately calls `PendingPersistenceReconciler.reconcileSaleOffer(saleOfferId)` so Redis-accepted holds become durable before the finalization poller next runs. `#failInterruptedRun()` marks `starting`/`active` runs failed, then performs eligibility close and immutable-summary capture as separately best-effort, idempotent steps. This is strong on per-run availability and immediate draining recovery, but its `markFailed -> close -> summary` sequence is not transactional, a failed `markFailed` is not distinguished from a concurrent/no-op transition, and it shares this task's review limitation: it assumes every `starting`/`active` run is irrecoverable and can freeze an incomplete projection.
  - `checkout-surge-opus/apps/api/src/services/run-finalization-service.ts` — `RunFinalizationService.finalizeReadyRuns()` likewise isolates each `DrainingRunCandidate`; `#finalizeIfReady()` reconciles pending persistence before reading finalization input, uses a guarded `draining` terminal transition, and writes the summary only when that transition won. This is the better model for restart/finalization races. Its settle timeout deliberately permits terminalization with unsettled work, so it is not proof that an interrupted active run has a complete traffic or business outcome.
  - `checkout-surge-opus/packages/db/src/run-sale-eligibility.ts` — `RUN_SALE_ELIGIBILITY_TTL_SECONDS`, `openRunSaleEligibility()`, and `closeRunSaleEligibility()` give every opened eligibility record a 24-hour Redis TTL; close changes an existing record only and preserves that TTL, so a missed close cannot authorize traffic forever and a late close cannot recreate an expired key. `packages/db/test/integration/run-sale-eligibility.test.ts` verifies a positive TTL. The fixed 24-hour constant is defense-in-depth, not a lifecycle deadline, and is not derived from run configuration.
- **Target data flow and adaptation:**
  - Startup composition is `apps/api/src/index.ts`: it awaits `DemoRunStartupReconciliationService.reconcile()` before starting `finalizationPoller` and before `server.listen()`. Preserve this ordering. A failure to list non-terminal runs may remain a startup-level reconciliation failure; once the list exists, one corrupt config, PostgreSQL read/write error, Redis error, or summary error must not prevent later runs from being attempted. Return/log counts should describe successful effects separately from discovered candidates and include per-run failures rather than implying all discovered runs were reconciled.
  - The current target implementation is `apps/api/src/services/demo-run-startup-reconciliation-service.ts`. `reconcile()` selects `starting|active|draining`; its interrupted loop closes eligibility, parses `configSnapshot`, reads business outcomes, snapshots Redis inventory, fabricates `interruptedTrafficSummary()` with zero emitted/completed/accepted traffic, and calls `PostgresTerminalDemoRunSummaryWriter.write(...)`, which performs the guarded terminal transition and immutable summary write. The draining loop only closes eligibility. Refactor into a small per-run workflow with an outer per-run isolation boundary. Keep snapshot/summary failures local to that run and ensure retries remain safe under the writer's allowed-current-status guard and one-summary-per-run invariant.
  - Reuse or extract the existing pending-persistence reconciliation boundary rather than reaching into Redis from startup orchestration. The target currently has retry/promotion behavior in `ReserveOrderService.reconcilePendingReservation()` and Redis pending markers in `@checkout-surge/db`; startup needs an injected, run/sale-offer-scoped reconciler callable for every recovered `draining` run. Reconcile before declaring the run recovered and before the finalization poller can freeze its summary. A missing `saleOfferId` must be logged/recorded as an explainable per-run recovery failure, not silently counted as recovered. Repeated reconciliation must not duplicate reservations/orders, must tolerate already-promoted/missing markers, and must leave failed items pending for a later retry.
  - Eligibility belongs in `packages/db/src/redis-inventory.ts`: `runSaleEligibilityKey()`, `initializeInventory()`, `setRunSaleEligibility()`, and `isRunSaleEligible()`. The target deliberately keeps the JSON eligibility key and inventory hash field `runSaleStatus` synchronized in one Redis operation; retain that invariant. Add expiry when initializing/opening an `accepting` run and when repairing an accepting record, in the same `MULTI`/Lua operation as the value/state change. Closing must not refresh the lifetime or resurrect a missing eligibility key, and an absent/expired key must remain ineligible. Choose a documented/configured TTL comfortably beyond the maximum legitimate run plus drain/finalization/retry window; validate it as a positive integer and test using Redis TTL rather than wall-clock sleeps. Redis expiry uses server time, whereas injected `now()` is only for durable timestamps/summaries—do not mix the two clocks or calculate a potentially negative client-side TTL from a stale timestamp.
  - Do not preserve the current blanket `starting|active -> failed with synthetic zero traffic` rule. Before terminalizing, distinguish runs that provably never delegated traffic from runs whose worker/orchestrator may still deliver completion or whose durable business rows already prove accepted work. Coordinate with the existing completion-ingest/finalization ownership: either leave potentially live work in a recoverable non-terminal state until its completion/settle boundary is known, or extend the contract/persistence vocabulary to store traffic/business fields as explicitly partial/unknown. Never encode “not observed by the restarted API” as zero. If a guarded transition loses to completion/finalization, reread and treat the run as already handled; do not close eligibility or write the losing projection. Immutable summary creation must occur only after the winning terminal transition and after pending persistence has been reconciled or explicitly represented as unresolved.
- **Isolation, restart, and race requirements:**
  - Per-run isolation does not mean per-step inconsistency is success: record which stage failed (`pending_reconciliation`, lifecycle decision/transition, eligibility close, projection read, summary write), log `runId`/`saleOfferId`, and continue with other runs. Eligibility close may remain best-effort because TTL is the safety backstop, but a failed pending reconciliation must prevent that run's immutable summary from being finalized as complete.
  - Make every stage restart-safe. Selection by non-terminal status, guarded compare-and-set transitions, idempotent pending promotion, non-resurrecting close, and unique summary-per-run must make a second boot converge without duplicate artifacts. Counters are attempt-local and must not claim effects on guarded no-ops.
  - Account for startup racing a late completion callback, a worker still persisting orders, and the first finalization-poller tick. Startup-before-listen does not stop external workers. The lifecycle transition is the authority that chooses the winner; summary inputs must be read after that decision at the appropriate settlement boundary. TTL expiry is only fail-closed authorization cleanup, never evidence that a run is terminal or settled.

Contract/schema changes are in scope only if required to represent partial/unknown recovery truth; avoid a broad run-history redesign.
