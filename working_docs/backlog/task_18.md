Three related failures: (a) the public web start route forwards to the API without the service token, and the API accepts public starts directly, so the proxy is not actually the trust boundary; (b) the API trusts a caller-supplied visitor-ID header, so a direct caller rotates values to bypass the per-visitor start budget (a focused test currently **pins** this behavior); (c) the budget path increments counters first and throws after, so rejected over-limit attempts consume future budget with no release path.

## Standalone implementation brief

### Current checkout-surge behavior to replace

- `apps/web/src/app/lib/server/public-visitor.ts` already creates an `HttpOnly`, `SameSite=Lax` visitor cookie containing `<uuid>.<HMAC-SHA256>`, verifies it with a timing-safe comparison, rotates malformed cookies, and fails with 503 when `PUBLIC_CLIENT_COOKIE_SECRET` is absent. However, `resolvePublicVisitorIdentity()` returns only the raw UUID.
- `apps/web/src/app/api/demo/runs/start/route.ts` validates the public start body, calls `resolvePublicVisitorIdentity()`, and forwards `x-operator-mode: public` plus that raw UUID in `x-public-visitor-id`. Unlike the admin start proxy, it neither calls `requireControlServiceToken()` nor forwards `x-control-service-token`.
- `apps/api/src/routes/demo-run-routes.ts` protects only an asserted `admin` mode. `deriveRunStartPrincipal()` treats all other calls as public and copies `x-public-visitor-id` verbatim into `publicVisitorId`; therefore a direct API caller can mint a new budget principal on every request. The focused test `apps/api/test/api.test.ts` named `uses the trusted public visitor header instead of browser-supplied JSON` currently proves the unsafe contract by sending the arbitrary value `signed-visitor-1` without a service token and expecting a 202 plus that value in the service command. Replace this expectation; do not preserve it as compatibility behavior.
- `RedisPublicRunBudgetStore.consume()` in `apps/api/src/services/demo-run-service.ts` runs an ioredis `MULTI` that increments the global and visitor counters, sets TTLs, and only then compares the returned counts with the limits. Both an over-limit visitor attempt and an over-limit global attempt leave increments behind. A global denial also leaves the visitor increment behind.
- `DemoRunService.startRun()` performs config and policy validation before constructing `consumePublicBudget`, but `createAcceptedRun()` invokes it inside the PostgreSQL transaction after the advisory-lock overlap check and before product lookup/inserts. PostgreSQL rollback cannot undo Redis. Missing-product, insert, inventory-initialization, orchestrator-delegation, response-validation, or other post-reservation failures can therefore burn budget. Later failures mark an accepted run failed where possible, but there is no budget compensation path.

### GLM visitor-credential design (verified donor behavior)

The reusable GLM design defines one shared credential codec in its contracts package and makes the API verify the credential independently rather than trusting the forwarding header:

- Cross-service contract: `packages/contracts/src/admin-access.ts` defines `VISITOR_ID_HEADER = "x-visitor-id"`, cookie name `csv-visitor`, and the wire value `<visitor UUID>.<issuedAt epoch-ms>.<hex HMAC-SHA256>`. `signVisitorId()` signs the canonical `${visitorId}.${issuedAt}` message. `parseSignedVisitorId()` requires exactly three fields, a non-negative integer timestamp, and a UUID. `verifyVisitorId()` rejects absent/malformed values and secrets shorter than 16 UTF-8 bytes, recomputes the HMAC, compares equal-length byte buffers with `timingSafeEqual`, and returns only the verified `{ visitorId, issuedAt }`; it returns `null` rather than throwing.
- Web issuance: `apps/web/lib/visitor-id.ts` wraps those shared helpers. The web side issues the signed value into an `HttpOnly`, `SameSite=Lax`, path `/` cookie and forwards the complete signed value, not the extracted UUID. `apps/web/lib/proxy.ts` attaches it only for public starts. Signing failure leaves the credential absent so the API, not a caller-provided fallback, decides fail-closed.
- API configuration: `apps/api/src/app/config.ts` supplies the same `PUBLIC_CLIENT_COOKIE_SECRET` as `publicClientCookieSecret`. The secret stays server-side; tests use dummy values and no document or log should contain a real one.
- API validation order: the thin route `apps/api/src/app/routes/demo-run-start.ts` resolves operator mode, reads the signed header, and passes it unchanged to the start service. In `apps/api/src/app/services/demo-run-start-service.ts`, public execution first calls `verifyVisitorId(config.publicClientCookieSecret, visitorIdValue)`. Missing, malformed, tampered, or unverifiable values return 403 `forbidden` before preset lookup, config construction, or Redis budget consumption. Only `verified.visitorId` becomes the budget key. The service then loads the public policy, checks preset visibility, validates the accepted config and public-custom caps, and only then consumes budget immediately before run creation. Admin execution skips visitor verification and public budget consumption.
- Focused donor tests: `packages/contracts/tests/admin-access.test.ts` covers sign/parse/verify, malformed values, tampering, and weak secrets. `apps/api/tests/demo-run-start.integration.test.ts` covers valid signed public starts and fail-closed missing/invalid credentials, then per-visitor and cross-visitor global budget denial. The route tests also show a GLM limitation: public starts remain directly callable without the service token if they possess a valid signed credential. Thus GLM solves spoofable visitor identity, but it does **not** by itself restore the web proxy as the only run-start channel.

Adapt this design to checkout-surge's existing names rather than copying its vocabulary wholesale. Prefer a single shared pure sign/parse/verify contract used by both servers, or equivalently forward the existing signed cookie value and add an API-side verifier with exactly the same canonical bytes. Do not forward only `PublicVisitorIdentity.id`. Add `PUBLIC_CLIENT_COOKIE_SECRET` to API startup validation/composition and fail closed when it is absent, weak, or mismatched. Preserve constant-time MAC comparison and UUID/schema validation.

### checkout-forge service-token and budget-reservation design (verified reference behavior)

The reference makes the web route the run-start channel and models budget use as a reversible reservation:

- `apps/web/src/app/api/control/load-runs/route.ts` derives `admin` versus `public` from the server-validated admin session, never the request body. It forwards to the internal API path with `buildControlHeaders(config, operatorMode)`, which in `apps/web/src/app/web-access.ts` always adds both `x-control-service-token` and the resolved operator-mode header. Public requests additionally carry the server-derived visitor identifier. `CONTROL_SERVICE_TOKEN` is required server-side configuration and is never returned to browser code.
- `apps/api/src/routes/demo-runs.ts` registers only `/internal/demo/runs/start` and calls `requireControlAccess({ adminOnly: false })` before parsing the start. Missing token is 401 `service_auth_required`; wrong token is 403 `invalid_service_token`; a mode other than `public|admin` is 400; admin-only routes additionally reject public mode. This is the relevant channel contract: authentication of the web proxy happens before trusting either mode or visitor assertions.
- The same route resolves and validates the request/policy before reserving. For a public principal it calls `PublicRunBudgetService.reserveStart()`, stores `{ visitorId, policy }` only when allowed, calls `DemoRunStartService.startRun()`, and returns 202 on success. Its catch path calls `releaseStart()` when a reservation exists before mapping the primary start error. The release is best-effort (`.catch(() => undefined)`), so the original failure is not masked.
- `apps/api/src/services/public-run-budget-service.ts` owns Redis. `reserveStart()` passes the visitor and global fixed-window keys, both limits, and the window length to one Lua `EVAL`. The script reads both counts first; if the visitor count is already at its limit it returns `{"visitor", TTL}` without incrementing either key, and if the global count is at its limit it returns `{"global", TTL}` without incrementing either key. Only an allowed decision increments both counters and sets expiry on first use. This gives an atomic check-and-reserve decision under concurrent requests and returns a retry-after duration for 429 responses.
- `releaseStart()` uses a second Lua script over both keys. Each positive counter is decremented and a counter is deleted at zero, preventing negatives. `apps/api/test/public-run-budget-service.integration.test.ts` proves reserve, denial without overspend, release/re-reserve, global denial across visitors, and fixed-window rollover against Redis. Route tests cover compensation when downstream start creation rejects.

The reference is a design donor, not a drop-in implementation. Address these caveats when adapting it:

- Its release recomputes the window from the current clock. A failure crossing a window boundary could release the new window instead of the one originally reserved. Return an opaque reservation handle (at minimum the exact window/key identity and visitor) from `reserve`, and release that handle.
- Plain decrement compensation is not intrinsically idempotent. A double release could free another successful request's slot. Prefer a unique reservation ID recorded/consumed atomically by Lua, or otherwise make the application ownership invariant explicit and test that a reservation can be released only once.
- In Redis Cluster, a multi-key Lua script requires both keys in the same hash slot. Use an intentional hash tag/key strategy if clustered Redis is supported; otherwise record the standalone-Redis assumption.
- Best-effort compensation preserves the original error but silently leaking a slot is operationally relevant. Keep the primary error, yet log/measure release failure with correlation ID and non-secret reservation metadata so it can be diagnosed. Do not recursively retry without an idempotent release contract.
- Decide and document what consumes budget: this task's requirement is non-burning **accepted starts**, not rejected attempts. Reserve only after authentication and all request/policy/cap/overlap validation that can precede acceptance, retain it on the 202 success path, and compensate every subsequent path that rejects the caller. A durable run later failing after an already-returned 202 remains an accepted start and should not be released merely because its asynchronous execution fails.

### Required adaptation and ownership mapping

1. **Shared contract / configuration:** retain the existing header constants where practical, but redefine the visitor header value as a signed credential with a shared schema/codec. Add API-side `PUBLIC_CLIENT_COOKIE_SECRET` configuration and startup validation. Never expose either signing secret or control token to browser code, response bodies, logs, or persisted run snapshots.
2. **Web API route:** `apps/web/src/app/api/demo/runs/start/route.ts` must obtain `CONTROL_SERVICE_TOKEN` via the existing server-only `requireControlServiceToken()`, forward it with `x-operator-mode: public`, and forward the complete signed visitor credential. Missing web token/signing configuration must fail before the upstream call. Continue issuing/rotating the secure visitor cookie and propagating `Set-Cookie` only from the same-origin response.
3. **API route:** keep the route thin. Require a valid control service token for **all** run starts before trusting operator mode or visitor headers. A direct tokenless public call must be rejected and must not reach `DemoRunService`. Resolve admin/public only from the authenticated proxy assertion. Pass the still-signed visitor credential to the application service rather than converting it to an unverified ID in the route.
4. **Application service:** independently verify the public credential and use only the verified UUID as the per-visitor principal. Authentication/credential failures must occur before Redis or PostgreSQL mutation. Preserve admin bypass of public budgets and public-custom limits only after authenticated admin mode has been established. Keep config, preset visibility, public policy/caps, and overlap validation ahead of reservation where architecture permits.
5. **Budget adapter:** replace `PublicRunBudgetStore.consume(): Promise<void>` with an explicit reserve/release contract whose allowed result carries release identity and whose denied result carries the stable per-visitor/global reason (and retry-after if exposed by existing error contracts). Implement atomic check-and-increment of both keys in one Lua operation or an equivalent single Redis atomic primitive. Denial must mutate neither counter. Release exactly the successful reservation on every synchronous rejection after reservation, including transaction/persistence or other start-acceptance failure; never release a denied or successful-202 start.
6. **Failure semantics:** compensation must be scoped around the full post-reservation acceptance region, not only one insert call. Preserve the original mapped HTTP error if release fails, while emitting safe correlated diagnostics. Ensure compensation cannot decrement below zero, cross budget windows, or execute twice for one reservation.

### Threat boundary and non-goals

- The service token authenticates the trusted server-side web proxy; the signed visitor credential authenticates the proxy's visitor assertion to the API. Both are required for a public start. Neither mechanism identifies a human, prevents a visitor clearing cookies, or replaces deployment-layer network controls/rate limiting. Cookie clearing remains a known limitation of anonymous per-visitor budgets; the global cap is the backstop.
- HMAC credentials are bearer values: theft permits replay until rotation/expiry. The GLM credential carries `issuedAt` but does not enforce age. If checkout-surge retains its year-long cookie, document that lifetime explicitly; if an expiry is added, validate it in both web and API with clock-skew tests. Secret rotation/revocation beyond current environment-secret deployment is not required here.
- Do not move Redis/Drizzle calls into the route, change admin-session authentication, redesign public runtime-policy vocabulary, add user accounts/device fingerprinting/CAPTCHA, or broaden this task into load-orchestrator/runtime behavior.
- Do not count malformed, unauthorized, over-cap, overlapping, or otherwise rejected starts as accepted budget usage. Do not weaken the existing deployment hard caps, public-custom caps, correlation propagation, or admin budget bypass.

### Focused verification to implement

- Shared credential tests: valid round trip; wrong/weak/missing secret; malformed field count/UUID/signature; tamper; constant-format parsing; and expiry/skew only if expiry is introduced. Assertions must use fixture secrets, never real values.
- Web proxy tests: public start forwards the service token, public mode, correlation behavior, and a signed (not raw UUID) visitor value; valid cookie remains stable; malformed cookie rotates; missing control token or signing secret returns 503 without calling fetch; response never exposes either secret.
- API route/service tests: missing/wrong service token rejects both public and admin starts before service invocation; mode cannot be asserted without the token; valid proxy token plus valid signed public credential succeeds; missing/tampered/wrong-secret credential fails closed before budget/persistence; rotating arbitrary raw headers no longer creates principals; authenticated admin still bypasses public budget.
- Redis/service tests: concurrent reservations cannot exceed either limit; visitor denial changes neither visitor nor global count; global denial changes neither count; successful release restores both; release is exact-window and idempotent; TTL/window rollover is deterministic; release never goes negative. Cover the configured Redis topology assumption.
- Workflow compensation tests: overlap and validation failures before reserve do not touch Redis; persistence/start-acceptance failure after reserve releases once; release failure preserves the primary HTTP error and emits safe diagnostics; a successful 202 retains its slot. Update/remove the current API test that calls `x-public-visitor-id: signed-visitor-1` without a token and expects acceptance.
