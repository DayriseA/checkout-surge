## Task details

- **Priority:** P3

- **Solved elsewhere (source-verified):** `checkout-forge/packages/db/src/schema.ts` defines the donor invariants in the `reservations`, `orders`, and `erpAttempts` table callbacks, and `checkout-forge/packages/db/drizzle/0000_initial_schema.sql` contains their emitted SQL. The exact semantics are: `reservations_released_requires_released_at` requires `released_at IS NOT NULL` when status is `released`; `reservations_expired_requires_expired_at` does the same for `expired`; `orders_confirmed_requires_confirmed_at` and `orders_failed_requires_failed_at` require their matching terminal timestamp; `orders_in_progress_requires_processing_at` requires `processing_at` for `processing`, `confirmed`, and `failed`; `orders_terminal_timestamps_after_queued_at` rejects a non-null `confirmed_at` or `failed_at` earlier than `queued_at`; and `erp_attempts_finished_after_started` requires `finished_at >= started_at`. `checkout-forge/packages/db/test/lifecycle-timestamp-invariants.integration.test.ts` proves both rejection cases and valid/equal-time cases. These are one-way implications, not exact-state encodings: the donor deliberately permits timestamps on earlier/other states, permits both terminal timestamps simultaneously, does not compare terminal timestamps with `processing_at`, and does not require release/expiry timestamps to follow `secured_at`.
- **Reference limit / independent finding:** checkout-forge does **not** enforce ERP-attempt or order-event agreement with the referenced order. Its `erpAttempts` and `orderEvents` rows still carry independently supplied `run_id` and `correlation_id`; its event table also independently carries `reservation_id` and `sale_offer_id`. The donor's `order_events_run_sale_context_fk` and `0001_run_attribution_triggers.sql` only prove that a `(run_id, sale_offer_id)` pair is a valid generated-run context. They do not prove agreement with `orders`, and `erp_attempts` has no `sale_offer_id` with which to apply that guard. Treat attribution agreement as a checkout-surge-specific extension, not behavior copied from the reference.
- **Target mapping:** add the donor-equivalent checks to the matching callbacks in `packages/db/src/schema.ts` (`reservations`, `orders`, and `erpAttempts`) and emit them in the next append-only Drizzle migration after `packages/db/drizzle/0001_order_secured_reservation_invariant.sql`; update `packages/db/drizzle/meta/_journal.json` and the generated snapshot according to the repository's migration convention. Preserve the existing enum names (`reservation_status`, `order_status`) and UUID `run_id` type. The current API write in `apps/api/src/services/postgres-buy-persistence.ts` creates a `secured` reservation and `queued` order with null lifecycle-transition timestamps. `PostgresOrderTransitionPersistence.transitionToProcessing`, `.transitionToConfirmed`, and `.transitionToFailed` in `apps/worker/src/persistence/postgres-order-transition-persistence.ts` set the required timestamps in status order, so no normal write-path change should be needed for the donor checks.
- **Attribution guard design:** cross-row agreement cannot be expressed by a PostgreSQL `CHECK`. Add focused database triggers (or an equivalently strong relational design) for `erp_attempts` and order-linked `order_events`. For an ERP attempt, lock/read `orders` by `NEW.order_id` and require `NEW.run_id IS NOT DISTINCT FROM order.run_id` and `NEW.correlation_id IS NOT DISTINCT FROM order.correlation_id`. For an event with non-null `order_id`, require its `reservation_id`, `sale_offer_id`, `run_id`, and `correlation_id` to agree with that order. Use `IS DISTINCT FROM` so nullable `run_id` is compared correctly. Existing `0001_order_secured_reservation_invariant.sql` already guarantees an order agrees with its secured reservation on offer, run, correlation, and quantity, so the event-to-order check transitively covers reservation attribution when both IDs are present. Also guard updates to the parent order's attributed columns, or document those columns as immutable and enforce that immutability; an insert-only child trigger otherwise allows a later parent update to invalidate existing children. Raise a stable constraint name and SQLSTATE (`23514` is consistent with migration 0001) so tests can assert the database boundary.
- **Order-event edge cases:** `order_events.order_id` and `reservation_id` are nullable and currently use `ON DELETE SET NULL`; reservation-only events must remain possible. Apply order agreement only when `order_id` is present. Decide explicitly whether a non-null `reservation_id` without an order must agree directly with `reservations` on sale offer, run, and correlation; if included, define precedence when both IDs are present and require the order's `reservation_id` too. Do not accidentally turn nullable event links into required links or change delete behavior. The application producers currently provide coherent values: `PostgresBuyPersistence.persistSecuredReservation`, `appendTransitionEvent` in `postgres-order-transition-persistence.ts`, `PostgresErpAttemptPersistence.recordAttempt` in `apps/worker/src/persistence/postgres-erp-attempt-persistence.ts`, and notification persistence all derive attribution from the durable order/job. The guard is defense in depth against direct SQL, regressions, and malformed jobs.
- **Migration, backfill, and rollout:** audit existing rows before validating constraints: released/expired reservations missing their timestamp; confirmed/failed orders missing terminal or processing timestamps; terminal timestamps before `queued_at`; ERP attempts with `finished_at < started_at`; and ERP/event attribution mismatches using `IS DISTINCT FROM`. Do not invent historical timestamps silently. Either repair from trustworthy order events/audit data, quarantine/delete demonstrably bad demo data under an explicit policy, or stop deployment with a diagnostic query. For a populated production table, add check constraints `NOT VALID`, deploy compatible writers, repair rows, then `VALIDATE CONSTRAINT` to reduce the blocking scan; note that new/updated rows are still checked while a constraint is not valid. Create attribution functions/triggers only after the mismatch audit/backfill, because triggers do not validate old rows. Install child-write guards before parent-update immutability/preservation guards, then verify both directions. Keep schema declarations and migration SQL synchronized even if hand-written `NOT VALID`/validation staging cannot be represented directly by Drizzle.

Cover each donor constraint name; equality at the timestamp boundaries; queued orders with null transition timestamps; valid processing/confirmed/failed rows; mismatched and null-vs-non-null ERP `run_id`; ERP correlation mismatch; each order-event attribution field; reservation-only and unlinked event policy; child updates as well as inserts; and attempted parent attribution mutation after children exist.
