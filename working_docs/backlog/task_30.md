## Verified Opus pattern

The donor is `checkout-surge-opus` at the recorded `ai/opus-4.8` worktree. Its useful implementation is organized as follows:

- `apps/load-orchestrator/src/services/k6-output.ts` keeps `parseK6OutputLine()` pure. It accepts only valid k6 `Point` records for `http_reqs`, `http_req_duration`, and `http_req_failed`, normalizes a valid event timestamp, maps them to the three reserved `traffic.*` names, and leaves rate derivation to the stream object.
- `apps/load-orchestrator/src/services/traffic-metric-stream.ts` introduces `TrafficMetricStream`. Its state is `#lineBuffer`, `#buckets: Map<number, WindowBucket>`, `#maxWindowStartMs`, and a configurable `#windowMs` (default `1_000`). `WindowBucket` contains `requestCount`, `failureSum`, `failureCount`, `latencySum`, and `latencyCount`.
- `TrafficMetricStream.push(chunk)` retains the trailing text after the last newline, parses only complete lines, and returns samples only for closed windows. `flush()` parses a final unterminated line and emits the still-open windows in start-time order.
- A point uses event time, not receipt time: `windowStartMs = Math.floor(Date.parse(observedAt) / windowMs) * windowMs`. The newest observed window acts as a watermark. `#closeElapsedWindows()` emits and deletes buckets strictly older than `#maxWindowStartMs`; the newest window stays open until a later window is observed or `flush()` is called. Emitted timestamps are the aligned window start.
- `#emitWindows()` calculates `traffic.scheduled_request_rate` as `requestCount / (windowMs / 1000)`, latency as `latencySum / latencyCount`, and failure rate as `failureSum / failureCount`. Thus four request points in a two-second window become `2 requests/s`, and one failed observation among four failure observations becomes `0.25`. It emits no metric whose denominator is zero.
- `apps/load-orchestrator/src/services/traffic-run-service.ts` creates one `TrafficMetricStream` per run, reports each batch returned by `push()` while k6 is active, then awaits reporting of `flush()` before sending completion. This ordering prevents the final partial window from being stranded behind the terminal report.
- `apps/load-orchestrator/src/services/k6-runner.ts` uses a file tail because that donor writes k6 JSON to a temporary file. `K6OutputTail` keeps a file handle and byte position, drains appended bytes in 64 KiB reads, decodes concatenated bytes once per pump, and awaits `onOutput`. A promise chain plus self-scheduling `setTimeout` serializes reads, so a slow consumer cannot overlap another tick; process close stops the timer, awaits the active pump, performs one final read, and closes the handle.
- `apps/load-orchestrator/src/services/traffic-reporter.ts` gives every metrics/completion POST its own `AbortController`, aborts after an injected `requestTimeoutMs` (default 5 seconds), clears the timer in `finally`, and logs and swallows network, abort, and non-2xx failures because telemetry is best effort.

The reference `checkout-forge` is not a better live-rate donor. Its `apps/load-orchestrator/src/metric-adapter.ts` replaces every `http_reqs` point with the configured scheduled rate and still forwards each `http_req_failed` observation directly. Its terminal summary (`load-runner.ts`, `deriveRequestRate()`) does derive total requests divided by observed elapsed time, but that end-of-run average is not a bounded live window and would hide short surge changes. Preserve the useful distinction: configured/scheduled rate is a target; this task's dashboard value is an observed rate.

## Concrete adaptation for this repository

1. Separate live window state from `K6RunAccumulator`'s terminal totals. Add a small per-run aggregator beside `k6-output-parser.ts` (or extract a dedicated application module) whose input is validated k6 points and whose output is zero or more `MetricSample`s. Do not make terminal completion depend on already-aggregated dashboard samples; `K6RunAccumulator` must still observe every raw point for planned/emitted/dropped counts, response classifications, latency p95, and delivery grading.
2. Use fixed, event-time windows with an explicit width (default one second), aligned by epoch as in Opus. Accumulate the `http_reqs` deltas for the numerator, divide by the full configured window duration in seconds, and emit unit `requests_per_second` (or the exact existing contract-approved equivalent). Treat the value as achieved/observed throughput even though the reserved metric name remains `traffic.scheduled_request_rate`; changing shared metric vocabulary is outside this task.
3. For `http_req_failed`, accumulate the finite `0`/`1` values and divide by the number of failure observations in the same window, matching Opus and k6's one-rate-observation-per-request stream. Do not publish a failure ratio until its denominator exists. Keep request-count and failure-observation counts distinct so missing or malformed points cannot be silently presented as a more certain denominator than was actually observed.
4. Decide latency behavior explicitly. The Opus implementation emits a window mean for `traffic.latency`, which is coherent with the two rate samples and is reusable. Keep the terminal latency collection/calculation unchanged. Do not accidentally turn a live mean into p95 or alter the completion schema.
5. Integrate window closure into `SpawnK6Runner.attachProcessHandlers()`. Because this repository already consumes stdout, do not copy the donor's temporary-file tail. Instead, preserve newline framing and serialize consumption/forwarding with an awaited async loop or an explicit bounded promise/queue that pauses the readable while downstream work catches up. On process termination, wait for the stdout reader to finish, flush the final unterminated/last open window, wait for the final metric send, and only then build/send completion and remove the temp directory. Maintain the existing report-once guard for `error` followed by `close`.
6. Make metric flushing single-flight and observable to `close()`: at most one API send may mutate/drain a batch at a time, samples arriving during a send belong to a subsequent batch, and `close()` must await the active send plus the final queued batch. Bound buffered samples or batches and define the overflow policy; silently starting unlimited concurrent requests is not acceptable backpressure.
7. Add an injected per-request deadline to `HttpLoadApiClient` (or an equivalent forwarding adapter). Create a fresh abort controller/timer for each attempt, pass its signal to `fetch`, and clear the timer on all outcomes. A timed-out metrics batch follows the existing best-effort metric-error policy. A timed-out completion attempt must reject into `sendCompletionWithRetry()` so its existing bounded exponential retry policy can proceed; each retry needs a fresh signal and deadline. Exhausted retries remain logged as they are now.
8. Update `RequestSurgePanel` and its focused view test so the headline says, for example, `Observed HTTP request rate`, and formats the rate as requests per second. Continue selecting the newest request-rate sample; do not calculate a second client-side window over already-windowed producer values.

## Required edge decisions and caveats

- Validate `windowMs` as finite and greater than zero. Validate timestamps before bucket arithmetic. Prefer rejecting malformed timestamps over silently assigning wall-clock receipt time, because mixing clock domains changes bucket membership and can create misleading rates.
- Opus assumes mostly ordered k6 event timestamps. Its watermark deletes old buckets, but a late point for an already-emitted window can recreate and immediately re-emit a duplicate partial window. Make the policy explicit: either ignore points at or before the finalized watermark (appropriate for ordered local k6 stdout) or support a small bounded lateness horizon. Never retain arbitrary historical buckets indefinitely.
- Bound `#lineBuffer`/line length if implementing chunk-level framing. A producer that never sends a newline must not grow memory without limit. Node `readline` already preserves split lines for the current stdout path, but completion must wait until its final partial line has been delivered; tests should exercise a JSON line split across chunks and an unterminated final line.
- Counting Opus `http_reqs` points is correct for normal k6 output where each delta is `1`; summing valid nonnegative point values is more faithful to the current accumulator and avoids assuming that invariant. Whichever rule is chosen must be tested and documented. Do not use configured target rate as a fallback for an empty observed window.
- A fixed full-window denominator makes the final short window conservative: one request in a one-second bucket is `1 request/s` even if the process stopped 100 ms into it. This is stable and comparable to other windows. Do not divide the final bucket by wall-clock time since its first event unless adopting and testing a different explicit partial-window contract.
- The existing terminal `latencies` array is unbounded over the whole run to support p95. Window aggregation should delete finalized live buckets and must not worsen that memory profile; replacing terminal percentile storage is a separate concern.
- Fetch abort is cooperative. The timeout must settle the application-level attempt and release its timer; do not assume it proves the remote API did not accept the request. Completion retries can therefore duplicate delivery and must continue relying on the API's idempotent run identity. Do not add metric retries without an idempotency/deduplication decision.
- Preserve graceful degradation: malformed/unsupported k6 lines remain ignored, metric forwarding failure does not change k6's traffic outcome, non-zero exit and spawn error reporting stay intact, and completion is still attempted exactly once at the lifecycle level (with its existing internal retry attempts).

## Implementation record (2026-07-13)

### Status

Implemented at the load-orchestrator application and dashboard presentation boundaries. Terminal totals/outcomes remain raw and independent; live traffic metrics now use bounded fixed event-time aggregation and ordered delivery before lifecycle completion.

### Decisions and completed scope

- Added a dedicated per-run live-aggregator module with a validated one-second default window, leaving raw parsing/terminal accumulation and incremental framing in separate focused modules. It sums valid nonnegative request deltas over the full window duration, emits mean latency and the fraction of valid `0`/`1` failure observations, aligns strict contract-valid ISO timestamps to the epoch window start, and emits only finite metrics with a denominator. Overflow-causing observations are ignored and a non-finite derived aggregate is omitted. The final short window uses the full configured duration.
- Retains one active window. Observing a newer window finalizes the active one; points for finalized or older windows are ignored. Malformed timestamps, non-finite/negative request or latency values, invalid failure observations, and unsupported points do not enter live aggregation. Terminal accumulation and p95/outcome classification remain unchanged.
- Replaced callback `readline` handling with serialized async stdout consumption and a bounded 64 KiB line framer. Split chunks and a final unterminated line are preserved; oversized lines are discarded until newline. Completion awaits stdout drain, final live-window flush, and metric drain before its single lifecycle report.
- `MetricBatcher` is single-flight and defaults to ten batches of buffered samples. Size-triggered runner calls await the send and apply stream backpressure. Samples arriving during a send retain order for a later batch; overflow drops and reports the newest sample. `close()` waits for the active send and final queued partial batch. Send errors remain best-effort.
- `HttpLoadApiClient` gives every request a fresh validated deadline and abort signal. A timeout settles even if `fetch` ignores abort, and timers clear in all outcomes. Metric timeout is contained by the batcher; completion timeout enters the existing bounded retry with a fresh request signal.
- `RequestSurgePanel` presents only `requests_per_second` samples as `Observed HTTP request rate`, formats them as `requests/s`, and names the production runtime's shared one-second producer window for mean latency/failure fraction. Older raw `requests` samples remain in the awaiting state rather than being mislabeled observed.
