## Task details

- **Priority:** P0
- **Area:** buy hot path / API / Redis
- **Source:** independent review (medium, scalability-critical) + comparison (worse, two topics)
- **Solved elsewhere (standalone donor context):** GLM provides a useful Redis-first mechanism, but not a safe lifecycle implementation to copy verbatim.
  - The donor implementation is in `checkout-surge-glm/packages/db/src/inventory/reservation-gate.ts`: `RESERVE_STOCK_LUA`, `ensureReserveStockRegistered()`, and `reserveInventory()`. Its separate projection adapter is `checkout-surge-glm/packages/db/src/inventory/run-eligibility.ts`: `setRunEligibilityActive()` writes `inventory:{saleOfferId}:run-eligibility` as a hash with `owningRunId` and `acceptingTraffic=1`; `clearRunEligibility()` deletes it. `checkout-surge-glm/apps/api/src/app/services/reserve-order-service.ts#createReserveOrderService().reserve()` calls the Lua gate before any PostgreSQL operation, so `not_initialized` and `sold_out` return without a database checkout. Only `secured`/`replay` proceeds to durable lookup or persistence.
  - GLM passes seven keys to the script: `:state`, `:reservations`, `:reservation-expirations`, `:events`, `:reservation-outcomes`, `:idempotency:{idempotencyKey}`, and `:run-eligibility`. Its 15 arguments are, in order: idempotency key, quantity, reservation ID, reservation token, sale-offer ID, run ID, secured-at ISO time, expires-at ISO time, order ID, public order ID, queued-at ISO time, current ISO time, expiry epoch milliseconds, idempotency TTL seconds, and event-list maximum length. The script returns one JSON object discriminated by `outcome`: `secured` includes the caller-generated durable facts plus post-decrement `remainingStock`/`reservedStock`; `replay` returns the stored facts; `sold_out` and `not_initialized` return sale-offer/run identity; `conflict` additionally returns the idempotency key and stored/requested quantities.
  - GLM's check order is: existing idempotency replay/conflict; run-sale eligibility hash ownership and `acceptingTraffic`; inventory state existence; sold-out aggregate; winning mutations (stock counters, hold, expiry, bounded event, idempotency record). Do **not** copy that order. Closure must be checked before idempotency so a retry cannot replay an accepted result after the sale closes. Preserve the stronger order already present in `checkout-surge/packages/db/src/redis-stock-reservation.ts#reserveInventoryScript`: validate quantity and state shape; validate `saleOfferId`, inventory scope, owning `runId`, and `runSaleStatus === "accepting"`; only then inspect idempotency; validate auxiliary key types, reservation uniqueness, counters, and timestamps; then decide sold-out or atomically create the hold. Malformed or absent projection/state must throw or reject fail-closed and must never fall through to stock mutation.
  - GLM registers an ioredis custom command once per Redis connection with `defineCommand()` and a `WeakSet`. There is no explicit `SCRIPT LOAD` call: ioredis uses the script SHA for `EVALSHA`, and on `NOSCRIPT` (first use, Redis restart, or `SCRIPT FLUSH`) falls back to `EVAL`, which both executes and loads the body; later calls use `EVALSHA` again. Adapt that connection-scoped registration to the current `CheckoutSurgeRedis` gateway, or implement explicit startup `SCRIPT LOAD` plus one `NOSCRIPT` reload-and-retry. In either design, bound the retry to `NOSCRIPT` only, do not retry arbitrary Redis/script errors, do not create a module-level client, and test script-cache flush/restart behavior. The current `reserveInventoryStock()` sends `reserveInventoryScript` with `redis.eval(...)` on every request, so it is the concrete call site to replace.
  - GLM's lifecycle wiring is unsafe. `checkout-surge-glm/apps/api/src/app/services/demo-run-start-service.ts` writes eligibility only after activation, `traffic-completion-ingestion-service.ts` moves the durable run to `draining` without closing eligibility, and `run-finalization-service.ts` clears eligibility only after a terminal transition and only best-effort. Thus fresh buys remain eligible throughout draining, a failed/missed delete can leave a terminal run buyable, and the Lua idempotency-first ordering also permits closed-run replays. Do not copy its separate boolean payload lifecycle. Couple this task to task 05's compare-and-set lifecycle transitions: the same successful transition that ends acceptance (`starting|active -> draining`, or any allowed state -> terminal during failure/reset/reconciliation) must close the Redis projection, and a stale/failed lifecycle transition must not reopen it.
  - The current repository already has the better projection shape to build on. `checkout-surge/packages/db/src/redis-inventory.ts#initializeInventory()` stores `inventoryScope`, `runId`, and `runSaleStatus` in the same per-offer `:state` hash consumed by the reservation Lua script; `setRunSaleEligibility()` atomically updates that hash and the reverse `demo-run:{runId}:sale-eligibility` record. `checkout-surge/apps/api/src/services/demo-run-service.ts`, `demo-run-startup-reconciliation-service.ts`, and `demo-maintenance-service.ts` contain the close call sites. Keep those fields as the hot-path authority, make closure ordering agree with task 05, and remove the redundant PostgreSQL `PostgresGeneratedRunSaleGate` path from `generated-run-sale-gate.ts`, `ReserveOrderService`, and `apps/api/src/index.ts` once Redis covers the same ownership/status rule. Do not add GLM's winning-path `findRunSaleOwnership()` query: the goal is to remove database eligibility probes, and the current Redis ownership check plus existing durable constraints must remain authoritative enough to reject mismatched attribution.
  - Preserve catalog semantics: a catalog inventory accepts a request only without `runId`; generated-run inventory requires the exact owning `runId` and `runSaleStatus="accepting"`. Missing state, wrong scope, wrong/missing run ID, closed status, malformed fields, and ineligible replays must not mutate counters, holds, events, idempotency records, or sold-out aggregates and must not touch PostgreSQL. A valid sold-out request may update only the existing aggregate sold-out counters/timestamp in Redis.
  - Focused verification (to implement with the change): extend `packages/db/test/integration/db.integration.test.ts` around `reserveInventoryStock()` for active ownership, missing/wrong/closed run projection, closure-before-replay, catalog/run-ID mismatch, sold-out aggregation, concurrent last-unit contention, and `SCRIPT FLUSH`/`NOSCRIPT` recovery. Extend `apps/api/test/reserve-order-service.test.ts` and the `/buy` cases in `apps/api/test/api.test.ts` with spies/instrumentation proving PostgreSQL persistence/lookup is called zero times for ineligible, closed, malformed/not-initialized, idempotency-conflict, quantity-invalid, and sold-out outcomes. Include a lifecycle race test proving a draining/terminal transition closes acceptance and a late activation acknowledgement cannot reopen it.
  - For the accepted-path half, baseline `checkout-surge/apps/api/src/services/postgres-buy-persistence.ts#persistSecuredReservation()`: today one transaction issues four logical SQL statements (reservation insert/returning, order insert/returning, one multi-row event insert, and an unconditional pending-reconciliation update), in addition to transaction begin/commit. Measure this with query instrumentation under the winning path, record both logical statements and wire round trips, inspect `EXPLAIN (ANALYZE, BUFFERS)` for the relevant indexed predicates, and state the justified budget in the implementation handoff. Consolidation may use a single parameterized CTE/batched statement or eliminate a provably unnecessary fresh-path reconciliation update, but it must preserve the all-or-nothing reservation/order/two-event invariant, returned response facts, idempotent pending reconciliation, ownership constraints, and the existing partial-failure path. Do not move durable writes outside the transaction, enqueue before commit, merge BullMQ/Redis promotion into the database transaction, or weaken failure reporting merely to reduce the count.
- **Locations:** `apps/api/src/services/generated-run-sale-gate.ts:10`, `apps/api/src/services/reserve-order-service.ts:159`

Every generated-run request performs a PostgreSQL gate query before Redis — including the ~9,000 expected sold-out losers of surge-10k against a 10-connection API pool — making PostgreSQL the first hot-path bottleneck against the 10k-in-1s target. The durable gate currently provides real safety (stale-run rejection), so the replacement must preserve fail-closed semantics.

The accepted path also performs more synchronous PostgreSQL work than the reference: after Redis accepts, it opens a transaction and issues separate reservation, order, lifecycle-event, and pending-reconciliation operations. Preserve the transactional boundary, but profile the actual query plan and consolidate round trips where doing so does not obscure invariants or weaken failure handling. Acceptance criteria should cover both halves of this item: rejected/ineligible/sold-out traffic does not touch PostgreSQL, and the winning path has an explicitly measured and justified persistence round-trip budget.

## Implementation record

- **Status:** Implemented.
- **Completed scope:** Removed `PostgresGeneratedRunSaleGate` and its API/service wiring. The buy workflow now reaches Redis before any PostgreSQL operation and preserves projection validation before idempotency. Registered the reservation Lua body as an ioredis connection-scoped command; ioredis sends `EVALSHA` after registration and performs its bounded built-in `NOSCRIPT` fallback to `EVAL`. Added `SCRIPT FLUSH` recovery coverage. Kept the durable generated-run admission lock and lifecycle/status check around accepted persistence. A successful `starting|active -> draining` CAS closes Redis immediately after its transaction returns, before outcome reads, inventory snapshotting, or finalization enrichment; duplicate completion repairs eligibility only after observing authoritative `draining`, while stale transition losers do not reopen Redis. Failure handling reads authoritative state after the terminal writer and closes any `completed`/`failed` run, including existing-summary repair where no new summary was inserted; a run that remains non-terminal is not closed. Delayed activation cannot reopen a closed projection. Added route- and service-level zero-persistence instrumentation plus rejection, ownership, closure/replay, contention, and lifecycle-race coverage.
- **Persistence budget and decisions:** Debug instrumentation measured fresh catalog persistence as four logical SQL statements (reservation insert/returning, order insert/returning, two-event multi-row insert, indexed pending-reconciliation update) and six operational PostgreSQL wire round trips including `BEGIN`/`COMMIT` (seven on a brand-new postgres-js connection when its one-time type-bootstrap `SELECT` is included). Generated-run admission adds advisory lock, durable ownership/status read, and advisory unlock, for nine operational PostgreSQL round trips through enqueue serialization. The prior generated path redundantly repeated the run lookup with `SELECT ... FOR UPDATE` inside the transaction; the revised reserved-session path omits that lookup because the session advisory lock remains held and terminal transitions use the same lock, reducing it from ten to nine without weakening serialization. Direct persistence calls that do not hold admission still retain the transactional `FOR UPDATE` guard. The indexed reconciliation update remains one round trip because pending retries need it and splitting fresh/retry persistence APIs would add invariant risk for a marginal gain. Writes and both events remain in one transaction; enqueue remains after commit.
- **Query plans:** PostgreSQL 17 `EXPLAIN (ANALYZE, BUFFERS)` used `demo_runs_pkey` for run ownership/status (`shared hit=1`, execution `0.096 ms`), `reservations_pkey` plus `orders_reservation_id_unique` for durable replay lookup (`shared hit=2`, execution `0.116 ms` on the empty probe), and `reservation_pending_persistence_reservation_id_unique` for reconciliation update (`shared hit=2`, execution `0.209 ms` on the empty probe). These measurements are test-container observations, not production latency claims.
