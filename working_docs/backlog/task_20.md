## Standalone implementation context

### Current request and trust flow

- `apps/web/src/app/api/admin/session/route.ts` exposes `POST(request)`. It delegates to `requireAdminPassphrase(request)`, then `createAdminSessionCookie()`, and returns `{ authenticated: true }` plus `Set-Cookie`. The candidate is currently taken from the `x-admin-passphrase` header (the exported `adminPassphraseHeaderName` in `apps/web/src/app/lib/control-paths.ts`), so preserve the existing browser contract unless intentionally migrating the caller and its tests together.
- `apps/web/src/app/lib/server/backend-proxy.ts` currently owns unrelated proxy, auth, cookie, and configuration concerns. `requireAdminPassphrase()` trims both values and uses ordinary string equality. Missing `ADMIN_DASHBOARD_PASSPHRASE` already returns `503 admin_passphrase_not_configured`; a mismatch returns `401 admin_passphrase_required`. `createAdminSessionCookie()` separately returns `503 admin_session_secret_not_configured` when `ADMIN_SESSION_SECRET` is absent.
- `createAdminSessionCookie()` signs only a decimal expiry timestamp as `<expiresAtMs>.<base64url-HMAC>` and serializes `Max-Age`, `Path=/`, `HttpOnly`, and `SameSite=Lax`; it never adds `Secure`. By comparison, `apps/web/src/app/lib/server/public-visitor.ts` adds `Secure` when `new URL(request.url).protocol === "https:"`.
- `hasValidAdminSession()` reads the cookie, parses and checks the attacker-controlled expiry, and only then calculates and constant-time compares the HMAC. Reverse that trust order: split structurally, calculate/compare the signature over the still-opaque payload, and decode/parse/check version and expiry only after authentication. A malformed value, wrong signature, unsupported version, non-finite timestamp, future-invalid timestamp, or expired token must fail closed without throwing.
- `parsePositiveInteger(process.env.ADMIN_SESSION_MAX_AGE_SECONDS, 8 * 60 * 60)` silently replaces malformed, zero, or negative configured values with eight hours. Treat absence (if the documented default remains supported) separately from a present-but-invalid value. Parse configuration once at the env boundary and either fail startup or make login unavailable with a stable 503; do not mint a cookie under an operator typo.
- Every current protected handler repeats `requireAdminSession(request)` followed by `requireControlServiceToken()` before parsing and proxying: ERP chaos update/reset and the admin demo reset, runtime-policy update, preset list/save/duplicate/copy, run start/history delete/cleanup routes under `apps/web/src/app/api/admin/**/route.ts`. This is correct today but omission-prone when another route is added. Some `GET` handlers are intentionally reads; apply CSRF enforcement to unsafe methods while still applying session gating to every private admin read.

### Reusable donor design

Use the ideas below, adapted to the current paths and response vocabulary; do not import donor files or rely on their line numbers.

- Opus's pure core is `apps/web/src/lib/admin-session.ts`: `verifyPassphrase(candidate, expected)` SHA-256 hashes both strings to fixed-length buffers and calls `timingSafeEqual`; `signAdminSession({ secret, nowSeconds, maxAgeSeconds })` creates a versioned `{ v, iat, exp }` payload; `isValidAdminSession({ token, secret, nowSeconds })` verifies the HMAC over the encoded segment before JSON decoding; and `authenticateAdmin(...)` returns a discriminated success or stable `401`/`503` failure. Its `apps/web/src/lib/admin-auth.ts` is thin env/clock/cookie glue and sets the admin cookie to `HttpOnly`, `Path=/`, `SameSite=Strict`, `Secure` in production, and the configured `Max-Age`. `apps/web/src/app/api/admin/session/route.ts` only parses input, invokes the pure decision, maps status, and sets the cookie. Keep this separation, but retain Surge's existing endpoint/header and error-envelope compatibility where practical.
- The fixed-length digest comparison closes the current length-dependent string comparison. It is an equality check, not password storage: the configured passphrase remains a high-entropy server secret and must never be logged, returned, embedded in a limiter key, or sent upstream. Avoid trimming only one side; preferably reject empty configuration at config load and define explicitly whether surrounding whitespace is part of the credential.
- Opus's exact cookie policy is stronger for this same-site admin surface: `SameSite=Strict`, `HttpOnly`, `Path=/`, positive `Max-Age`, and `Secure` for hosted HTTPS. Adapt `createAdminSessionCookie` to accept the request (or an injected cookie policy) so local HTTP remains usable while HTTPS always emits `Secure`. Do not trust an arbitrary client-supplied `x-forwarded-proto`; use the canonical deployment URL/trusted-proxy normalization, or a production environment policy. Clearing a cookie, if/when logout is added, must repeat the same name/path/SameSite/Secure scope.
- GLM's central layer is split between `apps/web/lib/admin-session-access.ts:isAdminRequest()`, `apps/web/lib/admin-proxy.ts:requireAdmin()`/`proxyResponse()`, and `apps/web/lib/proxy.ts:buildProxyHeaders()`/`proxyToService()`. Each `apps/web/app/api/admin/**/route.ts` calls the shared guard, while the proxy builder alone adds the service credential and admin operator-mode assertion. For Surge, expose one shared server-side admin-proxy entry/guard that performs the session check, unsafe-method Origin check, service-token availability check, and privileged upstream-header construction. Route handlers should supply only the destination/method/schema/body and must not be able to obtain or forward the control token before that guard succeeds. Keep public proxying separate so an admin principal cannot be selected from browser-controlled body/header data.

### Online-guessing controls (not present in any comparison branch)

Add an explicit `AdminLoginAttemptLimiter` boundary around the session `POST`; do not bury a Redis/client singleton in the route or pure session module. The route/application service should receive a limiter through server composition, while the pure authentication decision remains deterministic.

- Enforce both a per-client bucket and a low-volume global bucket for this single shared admin account. Per-IP alone is bypassed by distributed sources; global-only throttling lets one attacker deny all administrators. Use a bounded sliding window/token bucket (with an optional short capped backoff after failures), return a uniform `429` body and `Retry-After`, and do not reveal which bucket fired. Keep the chosen limits/configuration explicit and covered by tests.
- Count every syntactically valid credential attempt that reaches verification, including wrong credentials and attempts made while signing configuration is unavailable if doing otherwise would create a configuration oracle. Never include the candidate or expected passphrase in storage/logs. Successful login may clear or reduce the client's failure state, but must not reset the global abuse history.
- Derive the client key only from a trusted network identity. Honor `Forwarded`/`X-Forwarded-For` only behind a configured trusted proxy and select the documented hop; otherwise use the platform-provided peer identity. When no trustworthy IP exists, place attempts in a shared `unknown` bucket rather than accepting a spoofable header. Hash IP keys before persistent storage if operational policy requires it.
- A process-local map is acceptable only for a documented single-instance development fallback: it resets on restart and is ineffective across replicas/serverless isolates. Production enforcement needs a shared atomic store with expiry. Specify fail-closed versus a tightly bounded emergency fallback for store outages; silently disabling the limiter is not acceptable. Avoid long account lockouts, which turn the login endpoint into an easy denial-of-service target.
- Perform the limiter admission check before expensive work, still use fixed-length constant-time credential comparison for admitted attempts, and make wrong-credential responses broadly uniform. Timing cannot be perfectly identical across `429`, `503`, and `401`, but secret-dependent comparison paths must not branch on string length/content.

### CSRF and Origin posture

`SameSite=Strict` is defense in depth, not the whole policy. For `POST`, `PUT`, `PATCH`, and `DELETE` under `/api/admin`, require an `Origin` that exactly matches a configured canonical dashboard origin/allowlist (scheme, host, and port). Reject a missing, opaque (`null`), malformed, or cross-origin value with a stable `403` before proxying. Do not use substring/suffix matching, and do not construct trust from unvalidated `Host` or forwarded headers. This includes session creation and any future logout endpoint as well as cookie-authenticated proxy mutations. `GET`/`HEAD` must remain side-effect free; they need session authorization where private but not a CSRF token.

If deployment requirements genuinely include cross-site embedding or multiple dashboard origins, keep the allowlist explicit and add a synchronizer/double-submit CSRF token rather than weakening to `SameSite=None` plus permissive Origin behavior. Because these endpoints are browser-facing only, rejecting unsafe requests without `Origin` is preferred; any non-browser automation exception must be a separately authenticated route, not a general bypass.

### Adaptation map and ownership

- Extract the pure token/passphrase/login decision from `apps/web/src/app/lib/server/backend-proxy.ts` into a focused server-only admin-session module. Inject clock, parsed config, and limiter dependencies; keep environment reads and cookie serialization at the adapter/composition boundary.
- Make `apps/web/src/app/api/admin/session/route.ts` a thin adapter: validate Origin and credential shape, ask the limiter for admission, call the pure authenticator, record the outcome, set the hardened cookie, and map `200`, `401`, `429`, `503`, or `403` without exposing internal reasons or secrets.
- Replace the repeated session/token/header sequence in protected admin proxy handlers with the centralized guard/proxy abstraction. Route-specific contract parsing and response-schema validation stay in each route or the existing generic `proxyJson`; the centralized layer owns authorization, CSRF admission, and privileged headers.
- Preserve current service-side enforcement: the browser admin cookie is consumed only by the web tier, while `CONTROL_SERVICE_TOKEN` (and the admin operator-mode header where required) is added only after the session/Origin gate. Never forward the cookie or passphrase to API, Mock ERP, or load services.
- Keep malformed configuration handling centralized. Missing/invalid passphrase, signing secret, canonical Origin config, limiter config/store, or max age must produce the documented unavailable behavior (or fail startup) rather than silently weakening security. A missing control token remains the existing stable 503 and no upstream fetch occurs.
- Non-goals: replacing the demo passphrase with user accounts/OIDC, password hashing/storage, broad proxy rewrites, changing backend authorization contracts, or adding unrelated rate limits. Key rotation is also not required by this task: with one signing secret, rotation intentionally invalidates all outstanding sessions. If rotation is later added, identify keys without trusting unsigned payload data, verify against a bounded current/previous key set before payload parsing, use constant-time signature comparisons, and retire the previous key no later than the maximum session lifetime.
