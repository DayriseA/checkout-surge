## Source-of-truth and drift discipline

1. Inspect the current target tree, workspace/package manifests, Compose files, route registrations, shared contracts, and focused tests before changing prose. Code and checked-in runtime configuration are the source of truth for what exists; passing focused verification is the evidence for what is locally operable. Neither roadmap phase labels nor donor prose proves readiness.
2. Classify material statements as **implemented**, **locally verified/demoable**, **known gap**, or **future/optional**. “Implemented” means the code path exists; “locally verified” additionally requires an applicable check or documented manual observation. Do not collapse these categories into “complete.”
3. Preserve design rationale and invariants that remain valid, but rewrite modal/specification prose (`must`, `should`, “to build,” “completed system”) when the referenced behavior has landed. Conversely, do not convert an intended guarantee to present tense merely because adjacent infrastructure exists.
4. Prefer stable file/section/command references over brittle line numbers. Keep terminology aligned with shared contracts and actual lifecycle/status vocabulary. If implementation and docs disagree, correct the docs only when code is clearly authoritative; otherwise record the discrepancy as a known gap for the owning task.
5. Treat hosted deployment, production hardening, benchmark evidence, horizontal scaling, the optional Go comparison, and future CI/E2E tracks as separate readiness claims. The Docker Compose reference runtime being locally demoable does not establish any of them.
