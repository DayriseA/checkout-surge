## Standalone implementation context

### Current base: exact inert and mismatched paths

- `docker-compose.yml`, service `api.environment`, currently supplies all of the following:
  - Deployment/API-owned traffic caps: `DEMO_MAX_BUYERS=100000`, `DEMO_MAX_TOTAL_REQUESTS=100000`, `DEMO_MAX_REQUESTS_PER_SECOND=10000`, `DEMO_MAX_TRAFFIC_DURATION_SECONDS=300`, `DEMO_MAX_TRAFFIC_START_DELAY_SECONDS=30`, `DEMO_MAX_PRE_ALLOCATED_VUS=10000`, and `DEMO_MAX_VUS=10000`.
  - Finalization behavior: `DEMO_RUN_DRAIN_TIMEOUT_SECONDS=300` and `DEMO_RUN_FINALIZATION_POLL_INTERVAL_SECONDS=5`.
  - DB-backed public budget bootstrap: `PUBLIC_RUN_BUDGET_WINDOW_SECONDS=300`, `PUBLIC_RUN_BUDGET_PER_VISITOR_MAX_STARTS=2`, and `PUBLIC_RUN_BUDGET_GLOBAL_MAX_STARTS=6`.
  - DB-backed public-custom bootstrap: `PUBLIC_CUSTOM_MAX_TOTAL_REQUESTS=10000`, `PUBLIC_CUSTOM_MAX_BUYERS=10000`, `PUBLIC_CUSTOM_MAX_REQUESTS_PER_SECOND=1000`, `PUBLIC_CUSTOM_MAX_TRAFFIC_DURATION_SECONDS=120`, `PUBLIC_CUSTOM_MAX_TRAFFIC_START_DELAY_SECONDS=10`, `PUBLIC_CUSTOM_MAX_PRE_ALLOCATED_VUS=1000`, `PUBLIC_CUSTOM_MAX_VUS=1000`, `PUBLIC_CUSTOM_MAX_STARTING_STOCK=1000`, `PUBLIC_CUSTOM_MAX_ERP_LATENCY_MS=2000`, `PUBLIC_CUSTOM_MIN_ERP_MAX_TPS=1`, `PUBLIC_CUSTOM_MAX_ERP_MAX_TPS=100`, and `PUBLIC_CUSTOM_MAX_ERP_ERROR_RATE=0.25`.
- `apps/api/src/runtime/config.ts:ApiConfig` / `loadApiConfig()` reads none of the deployment caps, none of the `PUBLIC_RUN_BUDGET_*` or `PUBLIC_CUSTOM_*` values, and not `DEMO_RUN_DRAIN_TIMEOUT_SECONDS`. Of the variables above it reads only `DEMO_RUN_FINALIZATION_POLL_INTERVAL_SECONDS`. Therefore Compose's API assignments are silently inert even though `apps/api/.env.example` and `docs/local_development.md` describe them as API knobs.
- `packages/db/src/scripts/seed.ts:buildPublicRuntimePolicy()` is the actual consumer of every `PUBLIC_RUN_BUDGET_*`, `PUBLIC_CUSTOM_*`, and `DEMO_MAX_*` value. `backpressureConfig()` is the only consumer of `DEMO_RUN_DRAIN_TIMEOUT_SECONDS`. These run in the `runtime-setup` image (`Dockerfile`, stage `runtime-setup`, invoking DB migrate then seed), but `docker-compose.yml`, service `runtime-setup.environment`, currently receives only `*app-env`; none of these variables is in that anchor. Compose overrides consequently never reach their consumer.
- The seed inserts `publicRuntimePolicies.id = "active"` with `onConflictDoNothing`. Thus even a correctly wired setup env only affects the first seed; later `.env` changes intentionally cannot replace an admin-edited durable policy. This is appropriate for mutable public budget/custom policy, but not for deployment hard caps.
- `packages/db/src/scripts/env.ts:optionalIntegerEnv()` uses `Number.parseInt`, accepts prefixes such as `"12oops"`, and permits zero/negative values. `optionalNumberEnv()` similarly accepts numeric prefixes. Cross-field rules are not checked while seeding. Contract parsing catches some individual/range errors later, but the API has no boot-time read/validation of the persisted active policy.
- The API's effective consumers are in `apps/api/src/services/demo-run-service.ts`: `RedisPublicRunBudgetStore.consume()` uses `policy.publicRunBudget`; `validateAcceptedRunSnapshot()` enforces `policy.deploymentHardCaps` and then `policy.publicCustomLimits`; and `validatePublicRuntimePolicyUpdate()` checks public traffic limits against hard caps plus `minErpMaxTps <= maxErpMaxTps` and `maxPreAllocatedVus <= maxVus`. `DemoRunService.readPublicRuntimePolicyRow()` currently returns the DB row unchanged, so all these consumers use the caps frozen into that row by the first seed.
- Drain behavior is also frozen into seeded preset snapshots. `packages/db/src/scripts/seed.ts:backpressureConfig()` writes `backpressureConfig.drainTimeoutSeconds`; `apps/api/src/services/demo-run-finalization-service.ts` derives the deadline from `config.backpressureConfig.drainTimeoutSeconds`; `startApiServer()` constructs `DemoRunFinalizationService` without an API drain-timeout dependency. Merely adding the env field to `ApiConfig` is insufficient unless this consumer is rewired.
- The web server has the same silently-lazy configuration class. `apps/web/src/app/lib/server/backend-proxy.ts` reads `API_BASE_URL`, `MOCK_ERP_BASE_URL`, `ADMIN_DASHBOARD_PASSPHRASE`, `ADMIN_SESSION_SECRET`, `ADMIN_SESSION_MAX_AGE_SECONDS`, and `CONTROL_SERVICE_TOKEN` per request; `apps/web/src/app/lib/server/public-visitor.ts` reads `PUBLIC_CLIENT_COOKIE_SECRET` per request; and `apps/web/src/app/lib/api.ts` separately reads backend URLs per call. Invalid/missing values therefore become request-time fallbacks or 503s rather than preventing an unhealthy deployment from starting.

### Required ownership and boot behavior

1. Make API/deployment invariants explicit in `apps/api/src/runtime/config.ts`. Add typed config for the seven `DEMO_MAX_*` traffic caps and `DEMO_RUN_DRAIN_TIMEOUT_SECONDS`, preserving the defaults listed above. Parse the fields according to their contract: strictly positive integers except `DEMO_MAX_TRAFFIC_START_DELAY_SECONDS`, which permits zero. Do not use `parseInt`-style prefix parsing. Validate `maxPreAllocatedVus <= maxVus` and any relationships imposed by the shared traffic schemas. Keep the existing poll interval as a separate API runtime value.
2. Make the API config's hard caps authoritative on every process start, not a value that becomes authoritative only after seeding. Inject them into `DemoRunService` (or a small policy service owned by the API application layer), and use them for run validation, admin-policy responses, and admin-policy-update validation. Because the current public contract embeds `deploymentHardCaps` inside `PublicRuntimePolicy`, hydrate/replace that field at the API persistence boundary with the current API config rather than trusting the stale stored copy. A broader response-contract redesign to Forge's separate `hardCaps` object is out of scope unless a compatibility migration is intentionally included.
3. Before `buildApiServer()`/`listen`, load `publicRuntimePolicies.id = "active"`, parse it with `publicRuntimePolicySchema`, overlay the current deployment hard caps, and run the same complete policy validator used by updates. Startup must fail with field-specific, non-secret diagnostics if public limits/defaults do not fit the new deployment caps, if VU or ERP min/max relations are inverted, or if the active row is absent/malformed. Do not silently clamp persisted admin policy. Tightening deployment caps below the durable public policy must require an operator policy change (or explicit setup/reset), which avoids starting with unenforceable advertised limits.
4. Keep `PUBLIC_RUN_BUDGET_*` and `PUBLIC_CUSTOM_*` as bootstrap inputs for the durable, admin-tunable policy. Wire those variables to `runtime-setup.environment`, their actual seed owner. Remove them from `api.environment` unless the API startup validator deliberately consumes them; leaving them there would continue to advertise a live override that does not exist. Preserve `onConflictDoNothing` so rerunning setup does not erase admin changes, and document that changing these bootstrap values requires a fresh database or an admin policy update. Seed-time parsing must be strict and must validate the assembled policy with `publicRuntimePolicySchema` plus the same cross-field validator before insertion.
5. Move drain timeout to its real runtime owner. Add `demoRunDrainTimeoutSeconds` to `ApiConfig` and pass it explicitly from `startApiServer()` to `DemoRunFinalizationService`; use that deployment value for finalization deadlines so a restart applies a changed timeout without reseeding. Avoid maintaining two authoritative timeout values. If the snapshot field must remain for persisted-contract compatibility, clearly treat it as historical/display data and stop using it as the runtime ceiling. Note the compatibility consequence: after a restart, already-draining runs will follow the currently deployed timeout, matching an environment-backed operational invariant.
6. Add one server-only web runtime-config module and load it once during web bootstrap (for example through Next's server instrumentation hook), then inject/import the validated immutable values in `backend-proxy.ts`, `public-visitor.ts`, and `app/lib/api.ts`. Validate backend URLs, a strictly positive `ADMIN_SESSION_MAX_AGE_SECONDS`, and the presence of the production secrets/tokens used by these paths. Do not log secret values. Preserve testability by exporting a pure loader that accepts an env object; tests should not rely on mutating `process.env` after module initialization.
7. Update ownership documentation beside each service. `apps/api/.env.example` should label `DEMO_MAX_*`, drain timeout, and poll interval as API startup/runtime knobs. Root/setup documentation should label `PUBLIC_RUN_BUDGET_*` and `PUBLIC_CUSTOM_*` as first-seed defaults owned by `runtime-setup`, with admin policy as the post-bootstrap source of truth. Compose and docs must not list a variable under a service that cannot consume it. Opus's `apps/api/.env.example` grouping is a useful wording model, but retain this base's environment-backed public bootstrap contract.

### Validation relationships and compatibility notes

- Compare each public traffic limit to its same-dimension deployment cap: buyers, total requests, requests/second, duration, start delay, preallocated VUs, and max VUs. Also require public `maxPreAllocatedVus <= maxVus`, deployment `maxPreAllocatedVus <= maxVus`, and `minErpMaxTps <= maxErpMaxTps`; keep error rate in `[0, 1]`. Validate `publicCustomDefaults` through `validateAcceptedRunSnapshot(..., { operatorMode: "public", enforcePublicCustomLimits: true })` so defaults fit both hard and public caps.
- Preserve zero where it is meaningful: traffic start delay and ERP latency may be zero; positive-only parsing would reject valid current defaults/overrides. Request counts, buyers, duration, VUs, budgets, drain timeout, and ERP TPS bounds remain strictly positive.
- Do not overwrite the durable mutable policy on every API boot. The environment owns hard operational ceilings; PostgreSQL owns admin-tunable public budget, public-custom defaults, and public-custom limits after bootstrap.
- Keep routes thin and configuration/policy work outside route modules. Infrastructure reads and startup validation belong in the API composition root plus a focused application/persistence service; web route handlers should consume a validated config object/module rather than parse environment variables.
- Preserve existing public/admin response shapes unless all contract, web, and API callers are migrated together. Never include tokens, passphrases, cookie secrets, database URLs, or raw environment snapshots in startup errors/logs.

### Focused verification to implement

- API config unit tests: all documented defaults; every override maps to the intended `ApiConfig` field; malformed suffixes, fractional integers, negative values, and invalid zero values fail; zero-valued start delay succeeds; drain timeout is consumed; deployment preallocated VUs greater than max VUs fails.
- Policy unit/service tests: each of the seven public-vs-deployment cap pairs fails with a field-specific error; ERP and VU min/max inversions fail; invalid/default snapshots fail; a valid persisted mutable policy is overlaid with current env hard caps; changing hard caps between simulated boots changes enforcement without reseeding; tightening below the persisted policy prevents startup rather than clamping or listening.
- Seed/config tests: the setup env reaches every `PUBLIC_RUN_BUDGET_*` and `PUBLIC_CUSTOM_*` field, strict parsers reject trailing junk and invalid ranges, the assembled policy is validated before insert, and reseeding does not overwrite an existing admin policy.
- Drain-timeout tests at `DemoRunFinalizationService`: explicit API config controls the deadline, including an already-draining run after simulated restart; no test should rely on the seeded snapshot value as the active timeout after the ownership change.
- Web runtime-config unit tests: valid URLs and positive max age parse; missing required production secrets/tokens and malformed URLs/numbers fail at bootstrap; consumers receive the parsed values; diagnostics name keys but never values. Update existing tests that mutate `process.env` after import to pass a config fixture or reset the loader explicitly.
- Static/config checks: render Compose config and assert `DEMO_MAX_*`/drain variables are on `api`, bootstrap `PUBLIC_*` variables are on `runtime-setup`, and no advertised variable is assigned only to a non-consumer. Run the repository's normal typecheck/lint plus the focused API, DB, contracts, and web unit suites; infrastructure integration tests are needed only if the policy persistence/startup read boundary changes.
