## Verified reference evidence (standalone)

The reference implementation is in `checkout-forge/apps/load-orchestrator`; the target implementation is in `checkout-surge/apps/load-orchestrator`. The names and lifecycle models differ: Forge calls its workflow `LoadRunner` and keeps a `LoadTrafficRunState`, whereas Surge starts traffic through `TrafficExecutionService`/`SpawnK6Runner` and reports a `TrafficCompletionReport`. Adapt behavior to Surge's existing contracts rather than importing Forge's whole lifecycle.

### Abort route, process ownership, and state transitions

- Forge defines the control boundary in `checkout-forge/apps/load-orchestrator/src/server.ts`. `LoadRunnerPort` exposes `getCurrentRun()`, `startRun()`, and `abortCurrentRun()`; `POST /load/runs/current/abort` parses `loadRunAbortRequestSchema`, requires the same control-service token as start, propagates the correlation ID, delegates once, validates `loadRunAbortResponseSchema`, and returns 200. A mismatched requested run becomes `LoadRunConflictError` and HTTP 409. Missing authentication is rejected. The body is optional and supports `{ runId?, reason?, correlationId? }`; `reason` is trimmed and capped at 500 characters.
- The reference response has three explicit outcomes: `no_current_run`, `current_run_already_terminal`, and `current_run_aborted`, plus `requestedRunId`, `currentRun`, `observedAt`, and `correlationId` (`checkout-forge/packages/contracts/src/load.ts`, `loadRunAbortRequestSchema`, `loadRunAbortOutcomeSchema`, and `loadRunAbortResponseSchema`). No current run is an idempotent 200 no-op. Supplying a run ID is a fence: aborting `run-other` must not clear or signal the actual current run.
- Forge's process owner is the long-lived `LoadRunner` instance, not the route. Its fields in `checkout-forge/apps/load-orchestrator/src/load-runner.ts` include `currentRun`, `childProcess`, the current execution plan and diagnostics, metric buffers, and a pending completion report. `startRun()` rejects a second `starting`/`active` run, initializes state as `starting`, and asynchronously executes it. Immediately before spawn, `spawnK6()` rechecks run identity, transitions to `active`, starts k6 with an argv array, and assigns the exact returned child to `this.childProcess`.
- The child callbacks are identity-fenced. `close`/`error` clear the field only when `this.childProcess === child`; both callbacks also verify `currentRun.runId === capturedRunId` before changing lifecycle or reporting completion. This prevents a late callback from an old child from completing a newer run. After a successful non-cancelled close, Forge maps exit code 0 to `succeeded`, any other code to `failed`, stamps `endedAt`/`exitCode`/`errorMessage`, and submits the terminal traffic report.
- `abortCurrentRun()` first handles no-current, run-ID mismatch, and already-terminal cases. For a matching `starting`/`active` run it snapshots the child, clears current run/execution-plan/diagnostic/metric and pending-report state, then calls `child.kill("SIGTERM")` when a child exists and `!child.killed`. Because the cleared run-ID guard makes later `close`/`error` callbacks no-ops, an aborted process does not publish an ordinary success/failure completion after recovery has taken ownership. It logs the run ID and caller-supplied reason.
- Relevant reference coverage is `checkout-forge/apps/load-orchestrator/test/load-orchestrator.test.ts`: no-current abort is idempotent; a mismatched ID throws without clearing the active run; and a matching active child is terminated, produces no traffic report, and permits another start. HTTP coverage in `test/load-orchestrator-routes.api.test.ts` verifies authenticated success, empty-current success, already-terminal behavior, mismatch 409, correlation propagation, and unauthenticated rejection.

Do not preserve two weaknesses of the donor. First, `child.killed` means Node successfully sent a signal, not that the OS process exited. Forge clears ownership and returns before `close`, so it can accept a replacement while the old k6 still sends traffic. Second, it sends SIGTERM once with no timeout/escalation and targets only the direct child. Surge must retain ownership until exit is observed (or an explicitly reported cancellation failure), use bounded SIGTERM-to-SIGKILL escalation, and prevent a new start during that interval.

### Real k6 readiness

- Forge's `SpawnK6ExecutableChecker` in `checkout-forge/apps/load-orchestrator/src/k6-readiness.ts` executes the configured binary directly as `binaryPath, ["version"]` with `stdio: "ignore"`. Exit 0 is ready; a spawn error, non-zero exit, or a 3-second timeout is unavailable. Timeout sends SIGKILL. `server.ts:checkK6Executable()` exposes the result as `k6_binary_executable`, including `binaryPath` and a failure message, and readiness returns HTTP 503 when it is unavailable.
- Direct execution is the important behavior: it verifies both explicit paths and PATH lookup using the same process environment as a real run. Surge's current `runtime/readiness.ts:k6BinaryCheck()` only uses `fs.access(X_OK)` when the string contains `/`; the common `K6_BINARY=k6` case always reports degraded without resolving or executing it. It also treats backslashes/Windows paths differently from its tests.
- Forge centralizes direct spawning in `spawn-executable.ts`. On Windows it detects a Node shebang in an explicit script and invokes that script with `process.execPath`; otherwise it calls `spawn(command, args)` normally. This helper is useful for test fixtures and cross-platform script shims, but no shell is involved and the configured binary must never be concatenated into a command string.

Surge should inject the executable checker/spawn dependency and timeout for deterministic tests. Settle once across `error`, `close`, and timeout: the Forge checker can resolve on timeout and later run its close callback, which Promise semantics harmlessly ignore, but explicit once-only cleanup is clearer and avoids listener/timer leaks. A readiness timeout must kill and reap the probe as far as Node permits; unref the timer only if doing so cannot leave the health request unresolved.

### Bounded stderr and completion diagnostics

- Forge reads k6 stderr as lines, logs each line, and retains only the newest 50. `load-runner.ts:rememberK6StderrLine()` truncates each retained line to 500 characters, removes the oldest lines when the cap is exceeded, and separately tracks total observed lines and how many lines were truncated. The terminal report contains `stderrLines`, `stderrLineCountObserved`, `stderrLineCountRetained`, `stderrRetainedLineLimit`, `stderrLineTruncationLength`, and `stderrLineTruncatedCount`. Its contract enforces retained count equals array length, observed count is at least retained count, and truncated count does not exceed observed count.
- The reference test emits 55 lines, the last longer than 500 characters, and proves that the diagnostics retain lines 6-55, report `55/50`, and count one truncation. This is a bounded diagnostic sample, not merely bounded logging.
- Surge currently handles stderr chunks in `application/k6-runner.ts:attachProcessHandlers()` and only logs `chunk.toString("utf8")`. Chunk boundaries are not line boundaries: one logical line can be split between chunks and one chunk can contain several lines. Use a line decoder (`readline` over the stream or an equivalent incremental decoder), preserve the final unterminated line, and keep the bounded collector per execution rather than as module/global state.
- Surge's `K6RunAccumulator.completionReport()` currently emits only `{ startedAt, completedAt }` in `loadRunDiagnosticsSummary`. Replace the permissive `jsonObjectSchema` at `packages/contracts/src/load.ts:trafficCompletionReportSchema` with a focused diagnostics schema (or compose a typed core with explicitly supported recovery metadata), then thread the typed summary through completion persistence. Existing reset/startup-reconciliation code adds its own interruption fields to this JSON; do not accidentally make those failure-only summaries unparsable. Either make runner diagnostics nullable/optional at the broader stored-summary boundary or define a discriminated/extension-safe stored diagnostic contract while keeping the orchestrator completion payload strict.

### System and k6 facts useful for under-delivery

Forge collects diagnostics before writing/spawning the scenario in `checkout-forge/apps/load-orchestrator/src/load-run-diagnostics.ts:collectLoadRunDiagnostics()`. Independent probes run concurrently and degrade to `null` rather than failing the load run:

- `nproc`: positive integer returned by `nproc`.
- `ulimitNofile`: positive integer returned by the constant command `sh -lc "ulimit -n"`.
- `processMaxOpenFiles`: `{ soft, hard }` parsed from the `Max open files` row in `/proc/1/limits`.
- `networkDiagnostics`: Linux `/proc/sys/net/ipv4/ip_local_port_range` normalized to one space-separated string, plus nonnegative integer values from `tcp_tw_reuse` and `tcp_timestamps`; the whole object is null only when every value is unavailable.
- `k6Version`: the first non-empty line from direct `k6 version` output.
- `executionPlan`: the exact resolved executor and capacity assumptions. Forge records either constant-arrival-rate fields (`trafficMode`, `ratePerSecond`, `startDelaySeconds`, `durationSeconds`, `plannedEmittedAttempts`, `preAllocatedVUs`, `maxVUs`) or per-vu-iterations fields (`trafficMode`, `buyerCount`, `duplicateEachBuyerAttempt`, `iterationsPerVu`, `plannedEmittedAttempts`, `startDelaySeconds`, `maxDurationSeconds`).

The command helper has a 1-second timeout, kills timed-out probes with SIGKILL, accepts successful stdout or stderr (some version tools print to stderr), and truncates captured command output to 2,000 characters. Proc reads catch unsupported/unreadable files and return null. These facts help explain dropped iterations or request shortfall: CPU/VU capacity, file-descriptor limits, ephemeral-port/TCP reuse settings, exact k6 build, and the actual executor/VU plan are captured beside the delivery summary and stderr instead of inferred after the container disappears.

For Surge, derive the execution plan from the same resolved values used by `generateK6Script()` so diagnostics cannot disagree with the generated scenario. Its existing config vocabulary differs: steady arrival nests `k6Vus.{preAllocatedVus,maxVus}`, while buyer spike uses `quantityPerAttempt` and the generated iterations count. Record the actual defaulted VU values chosen by script generation, not just the optional request fields. Collect diagnostics once per run and carry the immutable object into the accumulator/completion path; do not rerun probes after under-delivery is observed because the environment may have changed.

2. **Application workflow (`apps/load-orchestrator/src/application/traffic-execution-service.ts`)**: make this long-lived service the single authority for one current execution and the `starting -> active -> cancelling -> absent` control transition. Reserve the run ID before awaiting filesystem/spawn work so concurrent starts conflict and an abort racing startup is remembered. Fence all mutations by run ID/execution generation. Do not let the route coordinate state or hold a child handle.
3. **Process adapter (`apps/load-orchestrator/src/application/k6-runner.ts`)**: return/retain a run-scoped execution handle that exposes the spawned child and an exit promise, or expose an explicit `cancel(runId)` port while keeping the child private. A cancel during temp-file creation must prevent spawn; a cancel between spawn and publication must immediately signal that exact child. Ensure completion and work-directory cleanup still happen at most once across `error`, `close`, and cancel races.
4. **Kill semantics**: for a matching current run, suppress metric acceptance and normal completion publication, send SIGTERM once, wait a short configurable grace period for `close`, then send SIGKILL if still alive and await a bounded final reap window. `child.killed` is not proof of exit. Keep the execution slot occupied while cancelling; respond success only when the child closed or when there was provably no child because startup was cancelled. If termination cannot be confirmed, return an operational error and keep the slot fenced rather than reporting success and starting overlapping traffic. Clear timers/listeners. Document that Node signals on Windows do not have POSIX semantics and that killing a direct process may not kill a detached process tree; spawn k6 non-detached, without a shell, and add platform-specific tree handling only if tests/runtime show descendants.
5. **HTTP route (`apps/load-orchestrator/src/server.ts`)**: register the abort path beside start, reuse `requireControlServiceToken()`, parse `{}` when the optional body is absent, overwrite/echo the canonical correlation ID consistently, call only `TrafficExecutionService.abortCurrent()`, return 200 for idempotent no-current and successful confirmed abort, 409 for a run-ID mismatch/current-run conflict, and a 5xx operational response when termination cannot be confirmed. Never expose this mutation without the control token or accept a caller-selected command/signal.
6. **Readiness (`apps/load-orchestrator/src/runtime/readiness.ts`)**: replace the slash/access heuristic with an injected bounded direct `k6 version` checker for every configured value. Keep the existing API readiness check. Exit 0 is `ok`; spawn error, timeout, signal exit, or non-zero exit is `unavailable`, making `/health/ready` return 503. Avoid shell resolution and include a safe failure message without environment dumps.
7. **Diagnostics (`apps/load-orchestrator/src/application/load-run-diagnostics.ts` or another focused application/runtime adapter)**: collect the nullable system/k6 fields above with bounded direct subprocesses and proc reads. 8. **Completion (`k6-runner.ts` and `k6-output-parser.ts`)**: retain the latest 50 stderr lines at 500 characters per line, maintain the separate observed/retained/truncated counts, and merge them with the immutable initial diagnostic facts only when building `TrafficCompletionReport`. The API already persists the object through `DemoRunService` into finalization and terminal summary rows; update types/tests at those boundaries rather than adding DB access to the orchestrator.

## Required invariants and race/security caveats

- At most one execution slot may be `starting`, `active`, or `cancelling`. Do not return a successful start as `active` until spawn succeeded and the handle is owned. A second start during cancellation is 409.
- An abort with `runId=A` can only affect A. A late close/error/stdout/stderr callback from A can neither clear nor complete B. Metrics and completion for A are suppressed once cancellation owns A.
- No-current abort is idempotent. A mismatched run ID is not an idempotent no-op because silently killing whatever happens to be current would let reset A terminate run B.
- Aborting before spawn, during spawn publication, during active output, concurrently with natural close, and twice concurrently must each settle once, remove the correct temp directory once, and leave no timers or unresolved promises. Define which caller observes success when natural close wins; never emit both a cancel response and duplicate completion side effects.
- Keep all process execution argv-based with `shell: false` (the Node default). Never interpolate `K6_BINARY`, a reason, URL, run ID, or diagnostic path into a shell command. Only the fixed `ulimit -n` probe may use `sh -lc`, with no user-controlled text.
- Stderr can contain internal URLs, identifiers, response bodies, or secrets. Cap it before persistence/logging, avoid logging environment or command output on probe failure, and ensure raw retained stderr is exposed only through the repository's intended trusted diagnostics surface. If public run history later exposes the stored JSON, add redaction or a public-safe projection rather than returning raw lines blindly.
- Linux proc/sys diagnostics are best-effort. Missing tools/files, containers without `/proc`, Windows, macOS, malformed values, and probe timeouts yield null fields and do not fail traffic. Readiness for k6 itself is different: inability to execute `k6 version` is unavailable because a run cannot start successfully.
- Diagnostics are explanatory evidence, not a reason to weaken the existing traffic-delivery classifier. Preserve current `complete | warning | degraded | failed` thresholds and notes unless a separate task changes policy.

Cover Windows-style configured paths at the pure decision boundary without starting a real process.
- **Diagnostics tests with injected command/proc readers**: successful values, stdout/stderr version output, malformed/missing proc values as null, fixed command/output time and size bounds, exact resolved plans for both traffic modes, split/multiple/unterminated stderr lines, 55-line rolling retention, 500-character truncation, and immutable per-run isolation across sequential runs.

Update recovery/reset fixtures that intentionally store non-runner diagnostic metadata so the chosen stored-summary contract remains compatible.
