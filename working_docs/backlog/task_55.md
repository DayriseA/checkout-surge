## Target mapping and required implementation

The target already has the right central abstraction, but not all of the donor's packaging/path guarantees. `packages/db/src/migrations.ts::runDatabaseMigrations` is used by both `packages/db/src/scripts/migrate.ts` and `packages/db/src/scripts/test-db-migrate.ts`, and `packages/db/src/testing.ts::resetTestDatabase` also delegates to it. Preserve this single path. Change its default migration-folder resolution from `path.resolve(process.cwd(), "drizzle")` to a location derived from the module URL so `tsx src/...` and compiled `dist/...` resolve the same checked-in directory; retain the explicit `migrationsFolder` option used by integration suites. Ensure the runtime artifact still contains that directory: the root `Dockerfile` explicitly copies `packages/db/drizzle` for the `runtime-setup` image, while `packages/db/package.json#files` currently lists only `dist` and must include `drizzle` if the package artifact is expected to carry migrations.

Restore a valid Drizzle metadata chain under `packages/db/drizzle/meta/` for every registered migration, not just a snapshot of today's schema with invented historical ancestry. At minimum the journal's existing `0000_initial_schema` and `0001_order_secured_reservation_invariant` entries need corresponding `0000_snapshot.json` and `0001_snapshot.json` with the correct dialect/version and linked `id`/`prevId` values. Generate metadata with the repository's pinned `drizzle-kit` (`packages/db` uses `^0.31.10`) from `packages/db/src/schema.ts`; do not copy the donor's snapshots or UUIDs because its schema, Drizzle version, table names, and migration history differ. Review the generated SQL and metadata before accepting them: custom functions/triggers are invisible to the TypeScript schema and therefore cannot be recovered from snapshot generation.

Split the custom SQL currently appended to `packages/db/drizzle/0000_initial_schema.sql` into clearly named, journaled incremental migration(s). The first block is `set_updated_at()` plus ten `*_set_updated_at` triggers (lines beginning around 407). The second is `enforce_demo_run_sale_context_offer_purpose()`, `enforce_run_owned_sale_offer_attribution()`, and their six ownership triggers (beginning around 455). Keep the later `packages/db/drizzle/0001_order_secured_reservation_invariant.sql` as its own already-journaled invariant migration unless regeneration demonstrates a metadata repair is needed; it defines `enforce_order_backing_secured_reservation()`, `preserve_order_backing_secured_reservation()`, and two triggers. Use descriptive migration headers that state these objects are hand-authored and invisible to Drizzle snapshots, and add the same preservation warning near `schema.ts`/`drizzle.config.ts` as appropriate.

Do not casually rewrite deployed history. A database that has recorded `0000_initial_schema` will not rerun edits made to that file, whereas a fresh database will. If the blocks are physically removed from `0000`, the new incremental migration must converge both starting states: fresh installs have no triggers, while upgraded installs already have them. Make trigger installation idempotent for that transition (for example, explicitly `DROP TRIGGER IF EXISTS` on the correct table before `CREATE TRIGGER`, while `CREATE OR REPLACE FUNCTION` replaces functions) and preserve every existing trigger name, table, firing event/column list, SQLSTATE (`23514`), and error contract. Do not drop functions before their dependent triggers without an intentional dependency order. Inspect the actual Drizzle migration transaction behavior for this pinned version and keep each migration safe as a unit; never assume DDL rollback or statement breakpoints provide cross-migration atomicity.

Migration concurrency remains owned by Drizzle's migrator and its journal table; do not add a second home-grown runner or execute SQL directly from tests. The test reset's filesystem lock serializes destructive resets for one test database, but it is not a production/deployment migration lock. Confirm the migrator's PostgreSQL locking/transaction semantics before documenting concurrent deploy safety, and ensure operators run one setup/migration job if the library does not guarantee it. Application processes must remain backward compatible during rollout: moving an unchanged trigger from historical SQL to an incremental migration must not create a window where ownership or timestamp enforcement is absent, rename database objects, or require coordinated API/worker changes.
