The API's start delegation has no deadline; completion delivery retries five times then logs and discards the only handoff that can move the run to draining (and then deletes its work directory); orchestrator shutdown tracks neither child k6 processes nor pending deliveries; and the API has no traffic watchdog for starting/active runs. A transient outage or orchestrator restart can wedge the only allowed run indefinitely. Fix with a durable completion outbox plus idempotent ingest, and/or an API-side watchdog that reconciles execution evidence independently. Design the orchestrator control surface once — the cancellation endpoint (entry 33) and the reset traffic-aborter (entry 34) share it.

## Implementation record

- **Status:** Revised after independent correctness review; implementation and focused verification complete.
- **Ownership design:** The orchestrator uses a persistent, atomic single-slot execution journal. It records acceptance before spawn, fences a different run ID, records executing state, durably stores completion before delivery, continuously retries pending delivery, and converts accepted/executing state found after restart into a truthful failed completion. The slot remains owned until API acknowledgement.
- **Start ambiguity:** Every start and status HTTP call has a bounded deadline. Status returns the durable acceptance time. Unconfirmed outcomes leave the durable API intent in `starting`; the API lifecycle poller safely replays that exact run-ID/config intent until the orchestrator accepts it or reports its existing ownership.
- **API ingest/recovery:** The first completion report remains authoritative in the unique finalization row. The initial claim and draining transition are atomic, but acknowledgement is delayed until idempotently re-drivable enrichment, reservation-outcome upsert, sale closure, and finalization have run. Redelivery reconstructs work from the first stored report rather than trusting a conflicting duplicate. API startup no longer fails orchestrator-owned `starting`/`active` rows and continues repairing `draining` admission/reconciliation state.
- **Lifecycle/runtime:** The long-lived runner tracks live preparation and the spawned child by identity. Output, error, close, and reap ownership is attached immediately after spawn and before the fallible `executing` journal transition; failure of that transition terminates and definitively reaps the child before releasing the slot. `error` records the failure but completion cannot be persisted or acknowledged until `close` proves OS exit. Concurrent same-run preparation joins the existing operation, while orphan `accepted` evidence is retried. Preparation and completion journal failures retain in-memory persistence/cleanup ownership for serialized periodic retry, and shutdown fails truthfully until that evidence is durable. Temporary scripts are removed only after the report is fsync-backed. Docker Compose mounts a named orchestrator state volume; local configuration has a repository-local default.
- **Future control compatibility:** Execution ownership and run-ID status fencing live below routes in the long-lived runner/service boundary, leaving Task 33 cancellation and Task 34 reset to reuse the same slot/child identity rather than create a second process registry. Their cancellation/readiness/diagnostic/reset behavior was not implemented here.
