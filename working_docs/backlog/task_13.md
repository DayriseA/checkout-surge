## Task details

- **Priority:** P1
- **Area:** API / idempotency / contract
- **Source:** independent review (medium) + comparison (worse)
- **Solved elsewhere:** `checkout-forge` replays a stored copy of the original accepted response (apart from replacing the top-level correlation ID for the retry). `checkout-surge-opus` demonstrates the complementary crash-consistency rule: classify a replay from committed durable truth, not from a Redis pending sentinel. ## Standalone reference context

### What `checkout-forge` establishes

- `checkout-forge/apps/api/src/persistence/order-persistence.ts`, `OrderPersistence.persistReservedOrder`, constructs the acceptance at the moment the reservation/order transaction commits. Its stable customer-facing facts are `outcome: "reservation_secured"`, the secured reservation identity/token/quantity/expiry/secured time, the queued order's public ID/status/time, and `customerStatus: "reservation_secured"`.
- `checkout-forge/apps/api/src/services/reserve-order-service.ts`, `stripCorrelationId`, `storeRedisReservationResponse`, and `responseFromRedisRecord`, store that response under the idempotency record after persistence and queue publication. A same-payload retry spreads the stored response back out unchanged and injects only the retry's correlation ID. It does **not** relabel the result as an idempotent replay or rebuild it from the order-status read model.
- `checkout-forge/packages/db/src/redis-inventory.ts` defines the stored record as `{ outcome, quantity, response }`. `reserveStockScript` atomically creates the initial `{ outcome: "reserved", quantity, reservation }` record with the stock decrement; `storeReservationResponseScript` later replaces it with the acceptance snapshot. `checkout-forge/apps/api/test/thin-vertical-slice.api.test.ts`, `replays duplicate buy requests without creating a second reservation`, asserts that both calls return `outcome: "reservation_secured"`, share the reservation token and public order ID, and create one reservation and one order.

This is evidence for the public replay invariant, not an implementation to copy wholesale. Forge's response snapshot exists only in Redis and is written after the durable transaction and enqueue. A crash before that replacement leaves the initial `reserved` record, whose replay is conservatively reported as pending even if PostgreSQL committed; Redis loss/expiry also loses the snapshot. Forge changes the top-level correlation ID on replay, so “byte-faithful” deliberately excludes request-scoped correlation. Durable PostgreSQL data must remain the authority in this repository.

### What `checkout-surge-opus` establishes

- `checkout-surge-opus/apps/api/src/services/buy-persistence.ts`, `BuyPersistence.isOrderPersisted({ orderId })`, makes committed order existence the replay authority. `checkout-surge-opus/apps/api/src/services/postgres-buy-persistence.ts`, `PostgresBuyPersistence.isOrderPersisted`, performs a primary-key existence probe, so an in-flight or rolled-back transaction reads absent and a committed order reads present.
- `checkout-surge-opus/apps/api/src/services/reserve-order-service.ts`, `#replayResponse` and `#isDurableOrderPersisted`, return secured only when that durable order exists; absence or a failed existence read returns pending-persistence. This avoids the race in which a duplicate arrives after Redis accepted the hold but before the original failure path has written a pending sentinel.
- Opus's gate record carries `reservationId`, `reservationToken`, `orderId`, `publicOrderId`, `quantity`, `securedAt`, and `expiresAt`, allowing it to reconstruct the original queued acceptance without reading mutable order columns. Its unit tests cover a committed replay, a still-pending replay, the concurrent pre-sentinel window, and a failed PostgreSQL existence read.

Opus is also only a selective donor. It rebuilds the top-level timestamp from the retry's `now`, so it does not satisfy this task's stable-timestamp requirement. It does not re-enqueue on replay, whereas current `checkout-surge` intentionally re-asserts the deterministic order job to heal a crash/failure after PostgreSQL commit but before BullMQ handoff. Preserve that existing healing behavior and its ordering relative to Redis promotion.

### Current `checkout-surge` replay flow and leak

1. `packages/db/src/redis-stock-reservation.ts` atomically returns the original `SecuredReservationHold` for a same-key/same-payload decision. The internal Redis outcomes `reservation_pending_persistence` and `idempotent_replay` describe workflow state; they need not become different successful HTTP representations.
2. `apps/api/src/services/reserve-order-service.ts`, `ReserveOrderService.reserve`, calls `BuyPersistence.getPersistedBuyByReservationId(decision.reservation.id)`. When it finds a durable buy, it re-enqueues the deterministic order job, promotes the Redis record, and calls `acceptedResponse("idempotent_replay", persisted, input.correlationId, now)`.
3. `apps/api/src/services/postgres-buy-persistence.ts`, `PostgresBuyPersistence.getPersistedBuyByReservationId`, inner-joins `reservations` and `orders` and maps the full live rows through `toReservationSummary` and `toOrderSummary`. The latter includes mutable `status`, `processingAt`, `confirmedAt`, `failedAt`, `failureCode`, and `failureMessage`.
4. Consequently, the same `/buy` retry can return `order.status: "queued"`, `"processing"`, `"confirmed"`, or `"failed"`, plus terminal metadata, depending only on when it arrives. `acceptedResponse` additionally exposes `outcome: "idempotent_replay"` and `timestamp: retryNow`, even though the original acceptance used `outcome: "reservation_secured"` and the hold's secured time. `/buy` has become a timing-dependent order-status read; the dedicated status path should remain the only place that exposes downstream progress.

The durable acceptance facts already exist without consulting current state: from `reservations`, use `id`, `saleOfferId`, `correlationId`, `runId`, `quantity`, `reservationToken`, `expiresAt`, and `securedAt`; from `orders`, use `id`, `publicOrderId`, `saleOfferId`, `reservationId`, `correlationId`, `runId`, `quantity`, and `queuedAt`. For the replay projection, `reservation.status` is the original literal `"secured"`, `order.status` is the original literal `"queued"`, and terminal/failure timestamps and fields are absent. The original acceptance timestamp is the durable `securedAt`/`queuedAt` instant, not the retry clock. If a later task ever permits the two initial timestamps to differ, persist an explicit acceptance timestamp/snapshot rather than guessing between them.

### Required adaptation

- Keep the route thin and implement the mapping at the persistence/application-service boundary. Prefer an explicit acceptance projection/DTO (for example, a purpose-named `PersistedBuyAcceptance`) returned by the reservation-ID lookup over returning a generic live `OrderSummary`. The SQL projection should select only immutable acceptance columns, or the mapper must explicitly discard all mutable order-state columns.
- Every successfully persisted replay must return the same public success discriminator as the first call: `outcome: "reservation_secured"`, `simulatedStatus: "reservation_secured"`, secured reservation, and queued order. Remove `"idempotent_replay"` from the public accepted-response contract and route status switch if it has no remaining public producer, while retaining internal Redis decision vocabulary where it is useful. Do not confuse public replay fidelity with entry 40's internal duplicate-attempt accounting.
- Set the top-level `timestamp` from the original durable acceptance instant (`reservation.securedAt`, which currently also supplies `order.queuedAt`). Do not pass retry `now` into a durable accepted replay. A newly reconciled pending reservation uses the time embedded in the original Redis hold, not the time of the reconciliation request.
- Preserve request correlation semantics deliberately: the top-level `correlationId` and response header identify the current HTTP attempt, as Forge does, while the nested durable reservation/order correlation IDs remain the original accepted workflow's correlation IDs. Do not rewrite persisted identity/attribution to make the nested objects look current. Document and test this intentional exception to otherwise stable replay content.
- Preserve the current crash-healing sequence for a found durable order: re-enqueue the existing deterministic job, then promote the Redis idempotency state without hiding durable success, then return the acceptance-shaped response. Use durable order/reservation IDs and timestamps for that job and response. Do not generate new identities, re-persist an already committed buy, publish a second business outcome, or expose the worker's latest state.
- Preserve the pending distinction. A replay with no complete durable reservation/order must not fabricate a queued acceptance from the Redis hold alone. The pending reconciliation/race behavior is owned by tasks 12 and the existing pending-persistence workflow; this task only changes the shape of a replay once durable acceptance is known. A database read failure must not be interpreted as proof of durable success.
- Validate the projected object with `buyResponseSchema` at the service boundary. Keep the dedicated order-status/read-model path responsible for `processing`, `confirmed`, `failed`, terminal timestamps, and failure details.

## Scope and non-goals

This task is limited to the public accepted-response contract, durable acceptance projection, replay response shaping, and focused tests at those boundaries. Do not turn `/buy` into an order-status endpoint; change worker transitions, Redis stock/idempotency conflict semantics, pending-persistence reconciliation, queue job identity, or promotion/error-handling policy; add duplicate-attempt accounting or finalization logic (task 40); or introduce a general event-sourced rebuild of historical responses. Do not copy Forge's Redis-only response cache as the replay authority or Opus's no-re-enqueue behavior. Preserve the fast reservation/slow confirmation split and existing crash recovery while making a durable replay represent the original acceptance.
