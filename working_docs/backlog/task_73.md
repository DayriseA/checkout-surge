GLM deliberately has no per-client backlog, so it is evidence for reconnect/opening/cap behavior, not a donor for drain-aware buffering.
  - **Target state and adaptation (`checkout-surge`):** `apps/api/src/realtime/dashboard-event-fanout.ts` (`DashboardEventFanout`) already starts a single lazy heartbeat interval when the first client connects, stops it when the last client leaves or on shutdown, emits `retry: <ms>\n: connected\n\n` as the opening frame, sends `x-accel-buffering: no`, validates event envelopes before serialization, and removes a client when an initial, event, or heartbeat write throws or returns `false`. Preserve those established target wire shapes and option names rather than copying donor envelopes, named `event:` fields, route structure, logger types, configuration objects, or Redis ownership. The missing refinement is a **bounded, per-client, drain-aware FIFO queue** integrated into the existing fanout/client abstraction: after a write first reports backpressure, later complete SSE frames queue in publication order; `drain` resumes FIFO delivery; exceeding a configurable finite frame/byte bound closes and unregisters only that client. Define the bound and its zero/invalid-value handling explicitly, remove `drain`/close listeners during every teardown path, make close idempotent, and ensure a late `drain` cannot write after disconnect or shutdown.
  - **Behavioral constraints and caveats:** A `false` return from Node's `write()` means data was accepted into the writable buffer but the high-water mark was reached; do not enqueue that same frame again or ordering/duplication breaks. Heartbeats and events must share the same per-client ordering path so a heartbeat cannot overtake queued events. One slow or throwing client must not block fan-out to healthy clients, and queue memory must be bounded per client and in aggregate by the separate client cap. Overflow/disconnect is best-effort loss followed by native `EventSource` reconnect; do not invent replay, `id:`, `Last-Event-ID`, acknowledgement, or delivery guarantees. The retry directive is only a browser reconnect hint, not server retry logic. `X-Accel-Buffering: no` is an Nginx-compatible hint, not proof that every CDN/load balancer flushes; deployment proxy timeouts and buffering still require configuration. The in-memory registry, timer, cap, and queues are **per API instance**: multi-instance deployments need the existing shared publication path to feed every instance, and the effective fleet-wide client/memory limit is the sum of instance-local limits unless enforced elsewhere. Client-cap admission remains owned by entry 19; this task must consume/preserve that result and must not implement a competing cap.

## Implementation record

- **Status:** Complete.
- **Completed scope:** Added a bounded per-client FIFO shared by event and heartbeat frames, drain-aware flushing, listener cleanup, and explicit positive frame/UTF-8-byte configuration. Wired the limits through API startup, Compose, the API environment example, and local-development documentation. Expanded deterministic fanout and runtime-config coverage.
- **Decisions:** `write() === false` marks that frame accepted and transitions the client to backpressured state; only later frames are queued. Defaults are 32 queued frames and 262144 queued UTF-8 bytes per client. The exact configured limits are allowed, while the next enqueue crossing either limit closes only that client. Zero, negative, fractional, non-finite, and otherwise invalid limits are rejected rather than interpreted as disabled or unbounded.
