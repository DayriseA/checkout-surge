- **Solved elsewhere:**
  - `checkout-forge/apps/web/src/app/dashboard-live-state.ts` (`useLiveDashboard`, `recoverDashboardState`, `recoveryRetryDelayMs`) owns the integration state machine. Every authoritative read enters `recovering`; success applies the snapshot, clears any timer, and returns the visible connection status to `live`; failure records the coordinator's sync issue, shows `Live sync issue, attempting to recover...`, and schedules another authoritative read after 3 seconds. Mount performs the first read, SSE open/reconnect and terminal-run events can request reads, and unmount clears the timer.
  - `checkout-forge/apps/web/src/app/dashboard-recovery-coordinator.ts` (`createDashboardRecoveryCoordinator`) serializes recovery with `activeRecovery`, exposes explicit `recoveryFailed` through `hasSyncIssue()`, discards realtime events while an authoritative snapshot is in flight, and repeats the read until a recovery window completes without a discarded event. A failed read closes the in-flight window but preserves the sync-issue state; later live events may still apply while the scheduled authoritative retry is pending.
  - `checkout-forge/apps/web/src/app/dashboard-recovery-retry.ts` (`createDashboardRecoveryRetryScheduler`) is a single-shot timer abstraction: duplicate `schedule()` calls coalesce, the timer clears its own scheduled marker before invoking `onRetry`, and `clear()` cancels it. `dashboard-recovery-retry.test.ts` pins coalescing, firing, and cancellation; `dashboard-recovery-coordinator.test.ts` pins serialization, discard/follow-up behavior, failure state, post-failure live events, and terminal-run deduplication.
  - Forge caveat: its fixed 3-second delay is simple but is not exponential backoff, has no jitter or attempt ceiling, and provides no attempt/next-retry metadata beyond the status string. Its terminal-run ID set is never pruned. Copy the state-machine guarantees, not necessarily those limitations.
  - `checkout-surge-glm/apps/web/lib/api-client.ts` (`ReadResult<T>`, `readApiProjection`) supplies the complementary uniform degraded-read model: all projection reads are non-throwing and distinguish contract-valid service down-states (`unavailable`) from network, timeout, unexpected HTTP, invalid JSON, and invalid-contract failures (`unreachable`). `getDashboardRecovery`, inventory, queue, ERP, history, and preset readers all use that vocabulary.
  - `checkout-surge-glm/apps/web/lib/client-recovery.ts` (`fetchDashboardRecovery`) preserves the same vocabulary for the browser recovery path, and `apps/web/app/dashboard/recovery/route.ts` translates the server read result across the same-origin boundary. `components/watch/live-watch.tsx` (`triggerRecovery`) coalesces concurrent triggers and dispatches `recovery-start` / `recovery-complete`; `lib/dashboard-state.ts` (`watchReducer`) keeps the degraded recovery result renderable and implements discard-plus-follow-up. GLM caveat: it retries only when reconnect, terminal-event, or discarded-event follow-up signals arrive; a degraded completion result does not itself schedule another attempt, so it is a consistency/visibility donor rather than the active-loop donor.
  - Target adaptation: keep Surge's existing `BackendRead<T>` vocabulary and `readProxyJson()` behavior in `apps/web/src/app/lib/client/proxy-json.ts`; do not introduce GLM's parallel `ReadResult` types. Extend `OperatorDashboard` in `apps/web/src/app/components/operator-dashboard.tsx` around `refreshRecovery`, `recoveryPromiseRef`, `recoveryFollowUpRequestedRef`, and `discardedLiveEventDuringRecoveryRef`. Today `readProxyJson()` resolves failures as `{ status: "unavailable", reason, httpStatus? }`, so the promise does not reject: retry decisions must inspect the returned `BackendRead`, not rely on `catch`.
  - Required target flow: a trigger starts at most one authoritative `/api/dashboard/recovery` read; additional triggers during it request one follow-up. Continue discarding live events during the read and require a follow-up afterward. An `available` result atomically replaces recovery state, clears sync-issue/retry state, and cancels any scheduled retry. An `unavailable` result remains visible in `RecoveryStatusPanel`, marks an explicit sync issue, and schedules a bounded retry. When the timer fires it must clear its scheduled identity before calling `refreshRecovery`, allowing a subsequent failure to schedule the next attempt. Manual refresh, SSE open, terminal events, successful public-run start, and the timer must all share the same coalescing path.
  - Retry policy: put the policy and timer lifecycle behind a small independently testable helper or tightly scoped hook boundary rather than adding more intertwined branches to the component. Use a bounded delay policy (document initial delay, maximum delay, multiplier, and whether jitter is intentionally omitted for deterministic UI tests); reset the attempt counter only after an authoritative success. Never create overlapping timers or fetches. Clear timers on success and component unmount. Retry transient/degraded reads, including transport failures, 5xx/non-JSON/contract mismatch represented by `unavailable`; do not silently overwrite the reason shown to the operator. If a deliberate non-retryable class is introduced, define and test it from `httpStatus` rather than guessing from reason text.
  - Idempotency and ordering: recovery is GET-only and safe to repeat, but responses can still race unless all triggers use the existing single-flight mechanism. Preserve the authoritative-snapshot rule: do not replay events discarded during recovery, and do not let a stale timer or older completion clear a newer issue. A failure with a discarded event must not recurse immediately in a tight loop; schedule the retry and preserve/coalesce the follow-up intent so the next successful window finishes with a stable authoritative read.
  - Visibility and recovery finalization: keep the last failure reason visible while waiting, distinguish `refreshing now` from `retry scheduled`, and expose an honest sync-issue/retrying label even if SSE reports connected. On success, clear the error/retry indication, reset backoff, retain the fresh recovery payload, and return to the connection-derived healthy state. On unmount, abort only local scheduling/updates; this task does not require adding request cancellation unless needed to prevent post-unmount state writes.

## Implementation record

- **Status:** Completed on `dev`; independent review passed.
- **Ownership/location drift:** Recovery orchestration already lived in `apps/web/src/app/components/realtime/use-dashboard-recovery.ts`, so implementation remained there with an adjacent scheduler rather than moving behavior back into `operator-dashboard.tsx`.
- **Retry policy:** Deterministic exponential backoff with a 1,000 ms initial delay, 2x multiplier, 30,000 ms maximum, and intentionally no jitter for predictable operator behavior and fake-timer tests. Every `BackendRead` unavailable class is retryable; no reason-string or HTTP-status classification was added.
- **State-machine decisions:** Manual, SSE-open, scoped-event, discarded-event follow-up, and timer triggers share the existing single-flight refresh path. A failed window retains coalesced follow-up intent for the scheduled retry; a successful window resets retry state and performs at most one immediate stabilizing follow-up. Pending timers are cancelled when another trigger starts a read, timer identity clears before callback invocation, local updates stop after unmount, and locally initiated recovery remains authoritative over later prop snapshots.
- **Architecture:** Public start still navigates to `/watch`; the fresh route snapshot and native EventSource open continue to trigger recovery without coupling the start surface to this retry loop.
- **Verification:** Focused scheduler, hook, proxy classification, retry UI, dashboard phase, and dashboard control-surface tests passed (56 tests across 6 files). The hook coverage includes Strict Mode effect replay preserving the initial attempt-1/1,000 ms policy, post-local-activity prop changes preserving an already scheduled retry, and unmount cancelling an already scheduled retry. `pnpm --filter web type-check` passed. `pnpm --filter web lint` initially reported two `noUnsafeFinally` findings; guarded finalization replaced the unsafe returns and the final lint rerun passed.
