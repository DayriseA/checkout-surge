## Standalone implementation context

### Current Surge behavior and destructive call sites

- `packages/db/src/testing.ts:assertDedicatedTestDatabaseUrl()` parses the URL and accepts it when `databaseName.includes("test")`. It is called by `resetTestDatabase()`, `acquireTestInfrastructureLock()`, and `createTestDatabaseIfMissing()`, but it checks neither `NODE_ENV` nor host/port. Consequently `checkout_surge_latest`, `contest_production`, and any development database whose name happens to contain `test` are authorized for create/migrate/truncate operations.
- `resetTestDatabase()` acquires its per-URL filesystem lock internally, calls `createTestDatabaseIfMissing()`, calls `runDatabaseMigrations()`, then truncates the constant `resettableTables` with `RESTART IDENTITY CASCADE`. Migration does not repair a trigger/function/table that a previous test removed when the corresponding migration is already recorded as applied. The constant currently names 15 business tables and silently omits any future table until manually updated.
- `packages/db/src/migrations.ts:runDatabaseMigrations()` delegates to `drizzle-orm/postgres-js/migrator`. Preserve that migrator and its actual journal schema/table semantics; do not paste Forge's hand-written SQL-file runner or assume Forge's public `__drizzle_migrations` layout.
- `scripts/run-with-test-env.mjs` only calls `buildTestEnv()` and `runCommand()`. `scripts/env-utils.mjs:buildTestEnv()` merges `.env.test.example`, `.env.test`, and the caller environment, then `applyPackageTestIsolation()` suffixes the database and selects a Redis logical database. It performs no destructive-target assertion. Because the caller environment wins, a pre-existing `NODE_ENV` or `TEST_DATABASE_URL` can override the committed test defaults.
- Direct DB-package reset call sites are `packages/db/test/integration/db.integration.test.ts` and `business-outcome-dashboard.integration.test.ts`. API and worker integration suites also import the same helper through `@checkout-surge/db/testing`; notably, API/worker fault-path tests create or remove triggers/functions, so an interrupted cleanup can poison a later suite while the journal still looks current. `scripts/reset-test-infra.mjs` is a separate Docker-volume reset path; keep its Compose-scoped behavior separate from the per-database schema reset.

### Exact donor behavior worth retaining

- GLM's `scripts/run-with-test-env.mjs:assertIsolated(databaseUrl, redisUrl)` runs after test env loading and before package URL rewriting/spawn. It parses both URLs, exits on an invalid URL, rejects an explicit PostgreSQL port `5432`, and rejects an explicit Redis port `6379`; its diagnostics direct contributors to host ports `56432` and `6380`. This is valuable as an early, fail-closed check before any test process can perform damage.
- GLM's check compares `URL.port` literally. For `postgresql://host/db`, `URL.port` is empty even though PostgreSQL uses 5432, so normalize omitted ports by protocol. Conversely, CI service containers and devcontainers commonly expose a dedicated test PostgreSQL service at `postgres-test:5432` internally; port 5432 alone is not proof that a target is development state.
- Forge's `packages/db/src/testing.ts:assertTestEnvironment(action)` requires `process.env.NODE_ENV === "test"` and is called by `resetTestDatabase()`, `migrateTestDatabase()`, `truncateTestDatabase()`, and `ensureTestDatabaseExists()`. `acquireTestInfrastructureLock()` has the same environment check. This is a second gate at the destructive boundary, so direct imports cannot bypass wrapper validation.
- Forge's `resetTestDatabase(sql)` first ensures the database exists. It truncates only when both `appliedMigrationsMatchJournal()` and `schemaFingerprintMatchesMigratedSchema()` return true; otherwise it rebuilds `public` from migrations and records a fresh journal/fingerprint. `truncateTestDatabase()` discovers all `public` tables through `pg_tables` and excludes only `__drizzle_migrations` and `__test_schema_fingerprint`, eliminating the fixed business-table list.
- Forge stores one SHA-256 value in `public.__test_schema_fingerprint`. `computeSchemaFingerprint()` creates sorted canonical detail rows for public columns (type, nullability, default), constraints (`pg_get_constraintdef`), indexes (`indexdef`), triggers (table, name, action), and functions (name plus an MD5 of `pg_get_functiondef`), joins them with newlines, then hashes the result. The fingerprint table is created before computing/storing the baseline, so its own shape participates consistently. The migration comparison hashes journal-listed SQL files and compares the ordered expected hashes with the ordered applied hashes.
- The fingerprint marker is drift evidence, not authorization to destroy a database. Its presence must never bypass environment, URL-name, or development-endpoint checks. Forge's fingerprint also does not cover every possible PostgreSQL object (for example enum labels, views/materialized views, sequences independent of column defaults, RLS policies, grants, extensions, or procedures); adapt the canonical query to every schema object the Surge migrations/tests can mutate, or explicitly rebuild for unsupported object classes.

### Required fail-closed decision model

Apply defense in depth at both the command wrapper and every destructive DB entry point. A target may be created, migrated, dropped/rebuilt, or truncated only when all non-bypassable conditions hold:

1. The URL is valid, has a non-empty database name, and `NODE_ENV` is exactly `test` at the destructive helper boundary.
2. The decoded database name matches the repository convention exactly: `checkout_surge_test` or a package-isolated suffix such as `checkout_surge_test_api`/`_worker`/`_db`. Use an anchored allowlist expression, not substring matching. Do not accept lookalikes such as `checkout_surge_latest`, `contest_production`, `checkout_surge_test_backup`, path tricks, or an empty/encoded separator.
3. The test wrapper normalizes the effective PostgreSQL and Redis ports and rejects the known local development endpoints before spawning. Keep PostgreSQL and Redis checks together because integration reset setup is destructive to both stores. Re-run the PostgreSQL protection in `assertDedicatedTestDatabaseUrl()` so a direct helper import has equivalent protection.
4. If the target database already exists, verify `current_database()` is the already-validated expected name after connecting and before destructive SQL. Do not infer safety from `TEST_DATABASE_URL` merely being the variable name or from `__test_schema_fingerprint` existing.
5. While holding Surge's existing per-database lock, compare the applied Drizzle journal with the migration files and compare the live schema with the stored migrated fingerprint. Only a double match permits dynamic truncation; either a missing marker, malformed/multiple marker row, journal mismatch, or fingerprint mismatch selects a full schema rebuild from reviewed migrations. Store the new fingerprint only after the rebuild completes successfully.

Keep the reset decision, rebuild, fingerprint write, and truncate inside the same lock. Discover truncation targets from PostgreSQL rather than maintaining `resettableTables`; exclude only migration metadata and the fingerprint marker, quote every discovered identifier, and assert that the discovered set is sensible before issuing one `TRUNCATE ... RESTART IDENTITY CASCADE`. A zero-table result on a supposedly current fingerprint is corruption and should rebuild/fail, not silently report a clean reset.

### Port exception and bypass policy

- Default local execution must reject loopback/local development PostgreSQL on effective port 5432 and Redis on effective port 6379. Error text should name the variable, host/port, expected isolated endpoint, and remediation, but must not echo credentials.
- Support dedicated CI/devcontainer services that legitimately use their internal default ports with one narrowly named, explicit opt-in (for example `ALLOW_TEST_DEFAULT_PORTS=1`). The opt-in may waive only the port deny. It must not waive `NODE_ENV=test`, strict database naming, URL validity, database identity, journal checks, or fingerprint checks. Document it beside CI/devcontainer configuration and do not put it in `.env.test.example` as a normal local default.
- Prefer recognizing an explicitly configured test service endpoint where topology makes that reliable, but do not silently trust arbitrary non-5432 ports: a development database can run anywhere. There is no bypass for the name or environment gates. Production code paths and `DATABASE_URL` are never valid reset targets.

### Deterministic rebuild and race caveats

- A schema mismatch must rebuild, not attempt to patch drift in place. Use the same reviewed migration order and statement handling as normal Surge migrations, then synchronize/verify its real Drizzle journal and store the post-migration fingerprint. Update `docs/automated_testing_infrastructure.md` so its claimed journal-plus-fingerprint behavior describes the implementation precisely.
- Schema rebuild must restore hand-authored functions and triggers as well as Drizzle-declared tables. Fingerprinting must detect the chaos case that removes or changes a trigger/function while leaving migration metadata intact.
- Filesystem locking serializes cooperating local Node processes only. It does not protect another machine/container with a different filesystem, a manual SQL session, or a process that ignores the helper. Per-package databases reduce contention, but the implementation should use a PostgreSQL advisory lock (derived from database identity) or document/enforce single-writer CI lanes if cross-container concurrency is possible. Keep the existing local lock even if a DB lock is added, and acquire locks in one consistent order.
- Rebuild operations that drop `public` can leave a partial schema if migration fails. Never write the fingerprint marker early; the next reset must see missing/mismatched metadata and retry rebuilding. Ensure all clients used for reset are closed in `finally`, and release the lock only after reset or failure cleanup completes.
- The fingerprint is a snapshot of schema shape, not data. Dynamic truncation remains responsible for all ordinary table data and sequences; migration/fingerprint metadata remains intact. Tests that create temporary public tables must either be included in dynamic truncation or force a rebuild according to the chosen supported-object policy.

- Update `docs/automated_testing_infrastructure.md`, `.env.test.example` comments, and CI/devcontainer examples to state the strict database naming rule, effective-port guard, narrow port exception, marker semantics, and rebuild-on-drift behavior.
