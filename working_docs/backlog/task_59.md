## Current target behavior and adaptation

- `packages/db/src/redis-inventory.ts::inventoryKeys()` defines the same per-sale-offer list key, `inventory:{saleOfferId}:events`. `initializeInventory()` deletes the existing inventory namespace, then appends an initialization `inventory.updated` payload and trims with its file-local `inventoryEventHistoryLimit = 100`. Initialization events contain the stock snapshot and source but intentionally omit reservation-only `reservationCount` and `reservedQuantity` fields.
- `packages/db/src/redis-stock-reservation.ts::reserveInventoryScript` appends one contract-shaped `inventory.updated` JSON object only after a fresh hold succeeds. It includes `saleOfferId`, allocated and post-mutation stock counters, `reservationCount: 1`, `reservedQuantity`, `source`, and `occurredAt`; unlike Forge, it deliberately does not place correlation or reservation identifiers in this diagnostic list. Sold-out, invalid, closed/wrong-run, conflict, and idempotent-replay outcomes do not append. The TypeScript `reserveInventoryStock()` wrapper passes its separate file-local `inventoryEventHistoryLimit = 100` into Lua as `ARGV[7]`, which Lua validates as a positive integer before `LTRIM -limit -1`.
- Raise the target retention to **500** for both initialization and reservation writes. Define one DB-package-owned constant (or otherwise one unambiguous source of truth) used by both modules so the two trim paths cannot silently diverge; keep the limit an implementation policy unless operators have a demonstrated need to tune it at runtime. Preserve `RPUSH` plus negative-index `LTRIM`, chronological insertion order, atomic reservation mutation/event append/trim, and contract validation.
- The current repository has no production reader of `inventoryKeys(...).events`; tests inspect it with `LLEN`/`LINDEX`. Dashboard recovery calls `getInventoryStatus()` and realtime delivery uses the separate Redis Pub/Sub dashboard channel, so this change must not wire the list into SSE, dashboard recovery, run history, order-event persistence, or workflow decisions. Update `docs/redis_inventory_hot_path.md`, whose current text promises a cap of 100, to state the 500-entry diagnostic window when implementation occurs.

## Operational tradeoffs and caveats

- Retention is per sale offer, so Redis cardinality remains one list key per initialized offer; only list length grows, from at most 100 to at most 500 elements. Memory is `O(active-or-not-reset offers × 500 × serialized event size)` plus Redis list overhead, approximately a fivefold worst-case increase for this key. Do not claim a fixed byte budget without measuring the actual serialized payload and Redis encoding in the deployed version.
- These inventory namespace keys have no TTL. Catalog inventory can therefore retain its last 500 events indefinitely, and generated-run data remains until explicit initialization/reset/maintenance removes the namespace. Increasing the cap does not solve lifecycle cleanup. Adding TTLs, global eviction, archival, or a new retention configuration surface requires a separate lifecycle/operability decision because expiring individual keys could break the Redis inventory authority.
- The window measures successful updates, not elapsed time: it can cover seconds during a surge or a long period at low traffic. It is not a complete audit trail, and concurrent callers receive only Redis/Lua serialization order rather than an application-level sequence number. PostgreSQL order/reservation events remain the durable business record.
- Keep Surge's existing public-safe payload shape. Do not add Forge's `correlationId` or `reservationId`, reservation tokens, idempotency keys, customer data, headers, or raw request/error content merely to improve debugging. Anyone granted direct Redis access can inspect the retained payloads, so a larger window increases the duration/volume of any fields already present even though it introduces no new field.
- `LTRIM` keeps storage bounded but does not provide a reader, export command, age-based expiry, alert, or Redis memory telemetry. Operational usefulness still depends on authorized Redis tooling. Document the key and cap; do not present it as a supported public API. If runtime configurability is proposed, it must be a validated positive bounded integer with a documented default and deployment/memory implications, not an unchecked Lua argument.
