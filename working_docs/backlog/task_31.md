## Current implementation and ownership boundary

- `apps/api/src/services/demo-maintenance-service.ts` owns reset and retention cleanup. `cleanupOldRuns()` computes the cutoff, newest retained IDs, and active IDs, then selects `deletableRuns` using only run status/age/retention. It derives `runIds` before checking ownership. Inside one bulk transaction it joins `demo_run_sale_contexts` and `sale_offers` only to derive `generatedSaleOfferIds`; all run-scoped rows and every selected `demo_runs` row are nevertheless deleted. Consequently a terminal run pointing at a catalog offer loses the run and history while merely preserving the catalog offer.
- `apps/api/test/demo-maintenance-service.test.ts`, test `leaves catalog sale offers untouched when an old terminal run references one`, currently asserts the defective result: `deletedRunCount: 1`, a missing run row, and a surviving catalog offer. Correct behavior is to skip the entire catalog-backed run graph and report no run deletion.
- `packages/db/src/redis-inventory.ts` owns the Redis inventory vocabulary. `inventoryKeys(saleOfferId)` covers the fixed `inventory:{saleOfferId}:*` keys and dynamic idempotency children; `runSaleEligibilityKey(runId)` is the separate `demo-run:{runId}:sale-eligibility` key. `initializeInventory()` deletes a previous inventory namespace, creates the generated-run state/outcomes/events and eligibility payload, but assigns no TTL to the persistent inventory or eligibility keys.
- The existing private `deleteInventoryNamespace(redis, inventoryPrefix)` already uses cursor-based `SCAN MATCH ${inventoryPrefix}:*` plus `UNLINK`, which is important because an explicit fixed-key list would miss `inventory:{saleOfferId}:idempotency:{idempotencyKey}` and any later namespace children. Promote/reuse this implementation through a package-owned cleanup helper instead of duplicating key knowledge in the API service.
- Keep routes thin. `apps/api/src/routes/admin-maintenance-routes.ts` already protects `POST /admin/maintenance/cleanup-runs` with `requireControlServiceToken()` and delegates to `DemoMaintenanceService.cleanupOldRuns()`. This task changes the service/persistence behavior behind that existing protected surface; it must not put Drizzle or Redis cleanup in the route.
- Task 32 owns the protected single-run teardown endpoint and smoke-tool integration. This task should leave it reusable per-run durable and Redis helpers, but must not add the new route, alter smoke tooling, or clear shared BullMQ queues.

## Verified GLM pattern

The selective donor is `checkout-surge-glm` at the recorded `ai/glm-5.2` worktree. The relevant implementation is self-contained in these files:

- `packages/db/src/run-lifecycle/run-maintenance.ts` exports `cleanupOldGeneratedRuns()`, `deleteGeneratedRun()`, and `deleteRunRedisState()`. The application-facing functions receive database and Redis dependencies explicitly; no infrastructure client is constructed at module scope.
- `cleanupOldGeneratedRuns()` orders runs newest-first, retains the first `keepLatest`, excludes `starting`/`active`/`draining`, requires a non-null offer, then reads the candidate offers and keeps only those whose `sale_offers.purpose` is `generated_run`. A candidate with a missing or catalog offer is removed from the cleanable set, so neither its run nor its history is touched. Cleanable rows are reversed for oldest-first reporting.
- Each cleanable run executes `deleteGeneratedRunSubtree()` in its own `db.transaction(...)`. One failing/corrupt run therefore rolls back only its own durable deletion instead of rolling back a previously successful batch. The result is appended only after that run's transaction commits.
- `deleteGeneratedRunSubtree()` makes the FK order explicit: delete `simulated_notifications`, `order_events`, and `reservation_pending_persistence`; delete `orders` (which cascade `erp_attempts`) before `reservations` because orders restrict their reservation; delete the run (cascading run-owned contexts/finalizations/summaries/outcomes); finally delete the generated sale offer after all RESTRICT references are gone.
- `deleteRunRedisState(redis, runId, saleOfferId)` deletes all inventory keys for the offer plus the per-run traffic-metrics key. Both bulk cleanup and the donor's targeted `deleteGeneratedRun()` call it only after the durable transaction commits. Redis failure is treated as best effort and cannot roll back PostgreSQL.
- `apps/api/src/app/services/maintenance-service.ts` is a thin application service: `cleanupRuns()` composes the persistence operation, logs deleted run IDs, and projects the response; `deleteRun()` similarly owns the targeted workflow and audit behavior. `apps/api/src/app/routes/admin-maintenance.ts` only verifies the control-service token, parses input, calls the service, and maps the result. Reuse this ownership shape for Task 32 rather than exposing database helpers directly.
- Donor tests in `packages/db/tests/run-maintenance.integration.test.ts` prove catalog-backed candidates are skipped with both run and offer preserved, the full FK subtree is deleted, active/null-offer runs are preserved, Redis state is removed, and targeted cleanup affects exactly one run. `apps/api/tests/admin-maintenance.integration.test.ts` proves the token gate, retention behavior, catalog protection, and that maintenance does not obliterate the shared queue.

The reference `checkout-forge/packages/db/src/demo-run-cleanup.ts` is not the safe implementation to copy. `cleanupDemoRuns()` classifies only active versus non-active runs, derives offer IDs directly from those runs, bulk-deletes all selected run graphs in one transaction, and deletes those offers without verifying `sale_offers.purpose = 'generated_run'`. It also has no Redis dependency or Redis namespace teardown. Its explicit table ordering is useful corroboration, but GLM's ownership guard and Redis handling are the stronger design.

## Concrete adaptation for this repository

1. Select cleanable ownership, not merely deletable run IDs. Extend the candidate query in `DemoMaintenanceService.cleanupOldRuns()` to join `demoRunSaleContexts` on both `runId` and the run's `saleOfferId`, join `saleOffers`, and require `saleOffers.purpose = "generated_run"` before a run can enter the deletion loop. Retain the current terminal (`completed`/`failed`), cutoff, newest-run, and active-run rules. A missing context, null/mismatched offer, or catalog offer means the entire run graph is preserved.
2. Carry `{ runId, saleOfferId }` pairs from that ownership query. Do not compute a broad `runIds` set and later use purpose only for offer deletion. The response's `deletedRunCount` must count successful generated-run deletions, not preliminary age/status candidates; `deletedSaleOfferCount` must reflect offers actually returned by the guarded delete.
3. Extract a small per-run durable deletion function at the existing maintenance/persistence boundary and call it in one transaction per candidate. Re-check the run/context/offer ownership inside the transaction, or make the guarded run/offer deletes conditional and count their returned rows, so a concurrent ownership/status change cannot turn a stale candidate into an unsafe delete. A skipped candidate contributes no counts.
4. Preserve an FK-safe order suited to the current schema: delete `simulatedNotifications`; `erpAttempts`; `orderEvents`; `orders`; then `reservations`; `reservationPendingPersistence`; then the run-owned `demoRunReservationOutcomes`, `demoRunFinalizations`, and `demoRunSummaries`; delete `demoRunSaleContexts`; delete `demoRuns`; finally delete `saleOffers` with an additional `purpose = "generated_run"` predicate. `orders` must precede `reservations` because `orders.reservationId` is RESTRICT; the offer remains last because multiple business tables and the run/context restrict it. Explicit deletion of cascade-owned rows is acceptable and keeps the ordering auditable.
5. In `packages/db/src/redis-inventory.ts`, expose one package-owned helper for a generated run's persistent Redis state. It should validate/use `runId` and `saleOfferId`, scan and `UNLINK` the entire `inventory:${saleOfferId}:*` namespace through the existing cursor loop, and `UNLINK` `demo-run:${runId}:sale-eligibility`. Keep namespace construction in `@checkout-surge/db`; the API service must not hand-build Redis keys. Make repeated calls safe when keys are already absent.
6. After each per-run PostgreSQL transaction commits, invoke that Redis helper for the same `{ runId, saleOfferId }`. Never remove Redis first: a later FK failure would leave a still-durable run without live inventory. Decide and test the partial-failure contract explicitly. The closest GLM behavior is best-effort teardown with a structured warning containing `runId` and `saleOfferId`, followed by cleanup of later candidates; do not silently swallow errors. Because this repository's persistent inventory and eligibility keys have no fallback TTL, the warning must make the orphan actionable. Adding/refreshing a safe generated-run namespace TTL may be considered only if its lifetime is derived from the run/sale lifecycle and cannot expire during a valid long-running run; an arbitrary short TTL is not a substitute for explicit cleanup.
7. Keep traffic metrics scoped correctly. This repository's `RedisDashboardTrafficMetricStore.record()` already refreshes `demo-run:{runId}:traffic-metrics` to a 24-hour TTL, unlike inventory and eligibility. Immediate deletion could be added later to a generalized run-state helper, but it is not the indefinite leak identified here and must not require moving the private traffic-key builder across package boundaries in this task.
8. Leave authorization and transport behavior unchanged: the existing control-token-protected bulk route remains the only surface changed here, correlation ID normalization and response schema remain intact, and no destructive operation is added to `RunHistoryService` or an unprotected route. Task 32 can reuse the per-run primitives for its dedicated, idempotent, terminal-only endpoint and BullMQ cleanup.

## Required safety decisions and caveats

- Define retention over the same population as today: determine the newest `keepLatest` run IDs before ownership filtering, then only delete old generated-owned candidates outside that retained set. Do not silently reinterpret `keepLatest` as "latest generated runs only" unless contracts/docs are deliberately changed.
- Terminality/age/retention and ownership are all deletion preconditions. Catalog protection means preserving the run, summary, finalization, outcomes, events, reservations, orders, notifications, pending-persistence rows, context (if any), and offer—not merely preserving the offer row.
- Per-run transactions improve fault isolation but are not a cross-store transaction. PostgreSQL is authoritative and commits before Redis teardown. Logging a Redis failure is essential because retrying bulk selection later cannot rediscover a run already deleted from PostgreSQL; the cleanup helper should remain callable with the captured IDs for operational retry and for Task 32.
- Do not copy GLM's fixed `allInventoryKeys()` approach verbatim. This repository deliberately supports dynamic idempotency keys, so prefix scanning is required. Continue using `SCAN`, never blocking `KEYS`, and use `UNLINK` to avoid synchronous deletion cost.
- GLM comments say abandoned keys expire via TTLs, but its persistent inventory/run-eligibility keys also intentionally lack TTLs. Treat that comment as an unsafe fallback assumption, not a guarantee to reproduce. The correctness requirement here is explicit deletion of every owned persistent namespace.
- Do not clear or obliterate shared BullMQ queues during retention cleanup. Old terminal runs should have no live work, and broad queue clearing could destroy unrelated current-run jobs. Targeted remaining-job cleanup belongs to Task 32's single-run workflow.
