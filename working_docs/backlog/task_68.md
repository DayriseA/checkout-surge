  - `checkout-surge-glm/package.json` defines `type-check:test` as `turbo type-check:test`, and `checkout-surge-glm/turbo.json` declares the corresponding Turbo task with test/source/config inputs.
  - No workspace `package.json` under `checkout-surge-glm/apps/*` or `checkout-surge-glm/packages/*` defines a `type-check:test` script, and GLM has no root `tsconfig.test.json`. Turbo therefore has no package task to schedule: the root command can exit successfully after checking zero test files. Merely copying that script or retaining the unused Turbo task is not a fix.
  - In the target, `package.json` instead defines `type-check:test` as the real compiler invocation `tsc -p tsconfig.test.json --noEmit`. `tsconfig.test.json` extends the strict root settings, supplies the Node/Vitest/DOM test environment, and includes root/package/app Vitest configs plus `packages/**/*.test.ts` and `apps/**/*.test.ts`. This is the useful implementation to preserve.
  - The target's `turbo.json` also declares `type-check:test`, but the root script does not call Turbo and no workspace package exposes that task. Do not treat the Turbo declaration as evidence that test sources are gated; either remove the dead declaration as cleanup or redesign the task as a genuine per-package graph, but the latter is not required for this repair.
  - The target failure is in `apps/api/test/reserve-order-service.test.ts`, in the test proving a scheduled business-outcome refresh does not delay the reservation response. `resolveRefresh` starts as `(() => void) | null` and is assigned inside a `Promise` executor passed through `vi.fn`; TypeScript control-flow analysis does not use that nested callback assignment to prove the variable callable at the later `resolveRefresh?.()` expression, so the optional call is narrowed to an uncallable `never` even though the Vitest runtime executes the executor and all 18 tests can pass through transpilation.
  - Fix the fixture without weakening compiler settings or adding a broad cast. A narrow direction is to declare a definitely-assigned resolver (`let resolveRefresh!: () => void`), assign it in the `new Promise<void>` executor, and invoke it directly after the existing flush. An equally explicit small deferred helper is acceptable if it preserves the test's ordering and rejection behavior. Keep the assertion that the response settles before the refresh is released.
  - Make the root static type-check gate own this check: compose the existing production `turbo run type-check` and the real root `type-check:test` command so `pnpm type-check` runs both and returns non-zero if either fails. Keep `pnpm type-check:test` as the focused developer command. Do not hide it only inside an infrastructure-dependent API/integration lane; compiling tests is a deterministic, Docker-free static check and belongs beside production type checking. If a future CI workflow invokes individual checks rather than `pnpm type-check`, it must invoke `pnpm type-check:test` explicitly.
  - Preserve shell and exit-code semantics. Use package-script composition that works in the supported host-native Windows, Dev Container, and Codespaces shells (the repository already uses `&&` in pnpm scripts); the second command must run only after production type checking succeeds, and either command's non-zero status must propagate. Avoid backgrounding, pipelines that mask the compiler status, watch mode, `||` fallbacks, or Turbo configurations that report success when no package task exists. Run from the workspace root so `tsconfig.test.json`, workspace resolution, and the root TypeScript/Vitest dependencies are used.
  - Focused verification: statically confirm that `tsconfig.test.json` includes `apps/api/test/reserve-order-service.test.ts`; run `pnpm type-check:test` and confirm it discovers that file and exits zero after the resolver repair; introduce/revert a temporary deliberate type error in that test if needed to prove the command returns non-zero; then run `pnpm type-check` to prove the authoritative static gate includes both production and test-source compilation. Run the focused API service test to preserve the deferred-refresh behavior, but do not require PostgreSQL/Redis merely to validate the type-check wiring. In CI, assert the same bounded `pnpm type-check` command is a required/fail-fast check rather than relying on green Vitest transpilation.
  - Scope is limited to the resolver fixture, root scripts/config needed to make test compilation unavoidable, and documentation/CI wiring if such a workflow exists when implemented.
