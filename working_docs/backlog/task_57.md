- **Solved elsewhere:** `checkout-forge/packages/db/src/schema.ts` is the verified reference pattern. It imports contract types from `@checkout-forge/contracts` and applies them directly to Drizzle `jsonb(...).$type<T>()` columns: `DemoPresetDisplay`, `DemoTrafficConfig`, `DemoInventoryConfig`, `DemoErpConfig`, and `DemoBackpressureConfig` on `demoPresets`; `DemoRunConfiguration` on `demoRuns.configSnapshot`; the load/finalization summary types on `demoRunFinalizations`; projections derived from `DemoRunSummary` on `demoRunSummaries`; and `PublicRuntimePolicy` on the runtime-policy row. This gives inserts and selected rows the contract-derived TypeScript shapes at the persistence boundary. It does **not** make PostgreSQL validate JSON at runtime: Drizzle's `$type<T>()` is compile-time metadata only.

  The checked-out donor worktrees do not substantiate the recorded “Opus and GLM are at parity” claim. `checkout-surge-opus/packages/db/src/schema.ts` uses a generic `Json` type for preset config, run snapshots, and summaries. `checkout-surge-glm/packages/db/src/schema.ts` deliberately defines `json(name).$type<unknown>()` and documents validation as a contracts-layer concern. Neither is a direct implementation donor for this task; at most, they illustrate the failure mode being removed. The named commit heads could not be independently confirmed with Git in the sandbox because repository ownership is marked unsafe, so implementation must re-check the actual branch heads before borrowing anything.

  **Current target contracts and mapping:** `packages/contracts/src/entities.ts` owns `demoPresetDisplaySchema`/`DemoPresetDisplay`, while `packages/contracts/src/load.ts` owns `trafficConfigSchema`/`TrafficConfig`, `inventoryConfigSchema`/`InventoryConfig`, `erpRunConfigSchema`/`ErpRunConfig`, `backpressureConfigSchema`/`BackpressureConfig`, `acceptedRunConfigSnapshotSchema`/`AcceptedRunConfigSnapshot`, `trafficHttpSummarySchema`/`TrafficHttpSummary`, and `trafficDeliverySummarySchema`/`TrafficDeliverySummary`. `packages/contracts/src/demo.ts` owns `businessOutcomeSummarySchema`/`BusinessOutcomeSummary` and composes the public `runHistorySummarySchema`; `packages/contracts/src/inventory.ts` owns `terminalInventorySnapshotSchema`/`TerminalInventorySnapshot`. Map those types to `demoPresets.display`, `trafficConfig`, `inventoryConfig`, `erpConfig`, and `backpressureConfig`; `demoRuns.configSnapshot`; and the corresponding `demoRunSummaries` columns. `publicRuntimePolicies.policy` should likewise use `PublicRuntimePolicy`, already defined in `packages/contracts/src/demo.ts`.

  The remaining finalization/summary fields are not yet strongly modeled in this target. `trafficCompletionReportSchema` currently describes `trafficOutcomeSummary`, `httpTimingBreakdownSummary`, `loadRunDiagnosticsSummary`, and `apiRequestLifecycleSummary` only as `jsonObjectSchema`, and `TerminalDemoRunSummaryInput` mirrors the latter three as `Record<string, unknown>`. Preserve that honest generic type unless this task first adds named, structurally meaningful contract schemas and inferred types with contract tests; do not invent local DB-only interfaces. `orderEvents.payload` is event-polymorphic and is not one of the cited preset/run JSON columns, so leave it generic unless a separate task introduces a discriminated event-payload contract.

  **Existing data flow and validation gaps:** admin preset requests are parsed by route contracts, then `DemoRunService` writes request/source JSON through `demoPresets`; preset rows are converted by `toDemoPresetContract()`, which validates only when producing an API response. Run startup builds and parses an accepted snapshot before inserting `demoRuns.configSnapshot`, but reads are inconsistent: `PostgresRunConfigReader.read()` parses with `acceptedRunConfigSnapshotSchema`, as do selected `DemoRunService` paths, while other consumers pass the generic selected value into response parsers. `PostgresTerminalDemoRunSummaryWriter.write()` parses HTTP and delivery summaries before insert but writes business outcome, inventory, and generic diagnostic objects directly. `RunHistoryService.toRunHistorySummary()` validates the selected public projection with `runHistorySummarySchema`; malformed stored JSON therefore fails late on that read path, while internal selections remain typed only as `JsonRecord`. The change should make every insert/select compile against the shared type and retain runtime parsing at trust boundaries.

  **Runtime validation requirement:** importing inferred contract types into `packages/db/src/schema.ts` and using `$type<T>()` prevents ordinary TypeScript callers from writing the wrong shape and removes casts/generic records from inferred selects, but it neither validates existing rows nor protects raw SQL, old binaries, migrations, or untyped external writers. Keep the existing Zod parsing on API inputs, worker reads, and public response construction. Where DB rows can predate the contract or are otherwise untrusted, parse at the DB-adjacent reader/writer or service boundary with the matching schema and surface a deliberate corruption error; do not rely on a TypeScript annotation as validation.

  **Compatibility, migration, and versioning:** changing only `$type<T>()` requires no SQL migration because the physical columns remain `jsonb`. Before tightening types, audit seed data, fixtures, and existing persisted rows against the selected schemas, including defaults materialized by Zod and nullable versus optional fields. A legacy malformed row will compile after the schema change but can still throw when parsed. Decide explicitly whether deployment may fail fast with an identifiable corrupt-row error, requires a one-off data repair/backfill, or needs a versioned/union schema during rollout. Do not silently coerce or discard unknown fields. If persisted JSON is expected to evolve independently, add an explicit version discriminator and migration policy in contracts rather than weakening the column back to `Record<string, unknown>`.

  **Implementation boundary:** contracts own schemas and inferred public types; `@checkout-surge/db` owns the Drizzle column declarations and may import contract types (the dependency already exists in `packages/db/package.json`); API/worker services retain runtime parsing and workflow policy. Replace the shared `jsonObject()` helper where columns need different types, or make it generic only if each call supplies an explicit contract type. Remove `JsonRecord` only if no legitimate generic JSON columns remain. Do not duplicate contract shapes in `schema.ts`, move workflow logic into the DB package, add PostgreSQL clients to services, or broaden this task into event-payload modeling, new summary semantics, or unrelated JSON columns.

  **Focused verification:** add compile-time coverage at the DB boundary proving valid contract-shaped inserts/selects infer correctly and representative invalid preset config, run snapshot, summary, inventory, and runtime-policy writes fail TypeScript (for example with narrowly placed `@ts-expect-error`). Add/update contracts tests only for any newly introduced named summary schemas. Add a DB integration test that round-trips valid typed JSON for presets, runs, finalizations/summaries, and policy without shape loss; add a service/reader test showing a deliberately malformed legacy row is rejected by runtime parsing with the intended error behavior. Run `@checkout-surge/contracts` tests/type-check, `@checkout-surge/db` type-check and integration tests, and the focused API/worker tests for `DemoRunService`, `RunHistoryService`, terminal finalization, and `PostgresRunConfigReader`.
