Keep `ErrorPayload`, the strict object behavior, field names, optionality, and JSON wire shape unchanged. Re-export through the existing `packages/contracts/src/index.ts` wildcard; do not add a second error module or import app code into contracts.

### Compatibility, status, and security rules

- This is vocabulary governance, not an envelope migration. Existing consumers must continue to receive the same code spelling, message, `details`, correlation ID, timestamp, strictness, and HTTP status. Status selection remains with the emitting route/error handler (`mapDemoRunError`, API/Mock ERP/load-orchestrator handlers, and BFF); do not encode status in `ErrorCode`, conflate `404` with a universal code, or adopt the donor's `HttpErrorEnvelopeSchema` wrapper.
- Unknown codes must fail `errorPayloadSchema` at trusted producer and upstream-response validation boundaries. They must not be silently coerced to a known code or passed through to browsers. At a boundary that cannot trust an upstream payload, map schema failure to the existing safe `invalid_backend_response`/502 behavior; at an unexpected local exception, retain the existing `internal_error`/500 behavior. Never expose parser text, stack traces, backend exception messages, secret/token values, or arbitrary upstream JSON while reporting an unknown code.
- Preserve established spellings for backwards compatibility unless every producer, consumer, fixture, and documented mapping can be migrated atomically. Do not normalize near-synonyms merely for aesthetics (`run_not_found` and `run_history_detail_not_found` currently describe different resources). Adding a future code is an intentional shared-contract change with a contract test, not a reason to restore `z.string()` or add a catch-all such as `unknown`.
- Task 38 owns canonical-envelope completion and correlation propagation through the web BFF. Coordinate with it: if task 38 has landed, include its added local BFF codes in the inventory and type its helpers; if not, this task may add the vocabulary needed by task 38 but must not independently redesign proxy headers, authentication, logging, or correlation flow. `public-visitor.ts` currently emits a short `{code,message}` response; govern its code now, but envelope repair remains task 38 unless required to keep contract parsing coherent.

### Scope and non-goals

- In scope: the shared code tuple/schema/type, wiring it into the existing strict payload, typing canonical HTTP error producers, preserving existing mappings, and focused contract/consumer tests.
- Out of scope: changing HTTP statuses or human messages, inventing a new envelope/wrapper, redesigning route/service error handling, translating worker-domain failure records into HTTP errors, distributed tracing, correlation/logging work owned by task 38, authentication changes, database migrations, or broad client refactors.
