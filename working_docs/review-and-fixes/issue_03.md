# Issue 03 — Compose probes exhaust the shared SSR recovery rate-limit bucket and leave Start permanently disabled

## Classification

- Priority: P0
- Status: Fix implemented, regression-tested, and reference-runtime verified
- Affected path: Public home page, Watch/Admin initial recovery, Compose health signaling

## Resolution status (2026-07-18)

The probe, identity, error-handling, and sticky-client-state failure chain has been removed in code:

- The web app now exposes a cheap web-owned `/health` route that performs no product-page rendering or downstream API calls. Both the direct web and Caddy proxy Compose probes use this route, so the proxy check still verifies the intended proxy-to-web path without consuming dashboard recovery admission.
- Public, Watch, and authenticated Admin server rendering no longer calls dashboard recovery without a visitor credential. Each mounted browser converges through the existing same-origin recovery BFF, which mints or reuses the HttpOnly HMAC-signed visitor cookie and ignores caller-supplied visitor identity headers.
- Web backend reads now check HTTP status before success-contract parsing. Non-2xx responses must match the shared `ErrorPayload`; safe status, code, correlation ID, and bounded delta-seconds `Retry-After` metadata are retained, while malformed responses become generic failures rather than exposing schema diagnostics.
- Public, Watch, and Admin now share one recovery controller. Requests are single-flight, automatic failure recovery stops after six attempts, exponential delays respect valid `Retry-After` guidance, and a visible manual retry resets the browser-local attempt budget.
- Starting, active, and draining runs are polled once every 30 seconds so a later terminal state converges even when no SSE event arrives. Idle or terminal recovery stops polling, keeping routine reads below the default per-visitor allowance.
- Public availability failure is displayed separately from `run in progress`, and Start remains blocked only until authoritative recovery establishes a non-blocking state.
- The opt-in `runtime:soak:recovery` command probes direct-web and proxy-to-web health for strictly more than two configured limiter windows, verifies the public route remains reachable, and confirms two fresh signed BFF visitors recover independent idle state. Static health/probe tests establish the zero-recovery-call boundary, while deterministic component coverage proves a `429` bootstrap followed by `200 idle` enables both public Start paths without reload or extra requests.
- Runtime topology, local development, architecture, and access-protection documentation now describe the implemented health, signed-identity, retry, polling, and soak behavior.

## Issue observed

On a freshly started, otherwise idle reference runtime, the public page repeatedly rendered in a broken state:

- all Start controls were disabled;
- the status pill incorrectly said `run in progress`;
- recovery was reported unavailable;
- the page displayed a large raw Zod validation error generated by parsing an API `429` payload as a successful recovery payload.

The API logs showed the first 12 recovery calls from the web container succeeding, followed by repeated `429` responses until the rate-limit window reset. The page itself still returned HTTP 200, so Compose considered the web/proxy healthy while the primary interaction was unusable.

After the rate-limit window reset, a direct same-origin BFF recovery request returned `200` with an idle projection. The already-rendered public page nevertheless stayed disabled because it had no automatic recovery path; a reload was required.

This is deterministic in the standard Compose topology and breaks the first screen before a user starts a run.

## How to reproduce

1. Start the reference runtime and wait for Compose to report it healthy.
2. Leave it idle for at least one minute, or open the public page after the health probes have been running.
3. Open `/` in a browser.
4. Inspect API logs for dashboard recovery decisions and the page's server-side request result.

The failure repeats by rate-limit window: successful probe-induced recovery calls consume the source allowance, then later calls receive `429` until the window changes.

## Identified cause

Several behaviors combine into one end-to-end availability defect.

### 1. Health probes execute the full dynamic public page

Both the web service and proxy health checks request `/` every five seconds (`docker-compose.yml`). The Next.js root page is `force-dynamic` and calls `getPublicDemoSurface`, which fetches presets, policy, and dashboard recovery (`apps/web/src/app/page.tsx`, `apps/web/src/app/lib/api.ts`).

This means a nominally cheap liveness/readiness probe performs user-facing control-plane work twice every five seconds.

### 2. Server-side recovery calls collapse onto one rate-limit identity

The server-side recovery call does not carry the signed visitor credential used by the same-origin BFF. The API falls back to source IP identity (`apps/api/src/routes/dashboard-routes.ts`, `apps/api/src/runtime/dashboard-source-identity.ts`). All server renders arrive from the web container address, so the probes and real anonymous visitors share one source bucket.

The configured cap is 12 calls per source per 60 seconds. Two probes every five seconds can produce about 24 calls per minute, guaranteeing exhaustion even with no user traffic. Raising or removing the limiter would only conceal the identity/probe error and weaken the protection introduced for recovery.

### 3. The web API helper parses error payloads as success payloads

`readJson` parses the response body with the requested success schema without first checking `response.ok` or parsing the shared error contract (`apps/web/src/app/lib/api.ts`). A valid API `429 ErrorPayload` therefore becomes a verbose Zod exception exposed in the product UI.

### 4. Initial recovery failure is sticky and mislabeled

`PublicDemoEntry` receives the initial surface as immutable props. An unavailable initial recovery blocks starting, but the component has no bounded retry/single-flight convergence behavior. Its status label maps any start block to `run in progress`, conflating an active run with a failed availability check (`apps/web/src/app/components/public-demo-entry.tsx`).

## Recommended actions

1. Add or use a cheap web health endpoint that does no API calls and no dynamic product-page rendering. Point both the web and proxy Compose probes at it while preserving a proxy-to-web connectivity check.
2. Route interactive browser recovery through the credentialed same-origin BFF, or provide an equivalently trusted server-derived signed identity. Do not trust caller-supplied browser identity headers.
3. Make the web HTTP helper branch on HTTP status before success-schema parsing. Parse the shared `ErrorPayload` for non-2xx responses and expose only a safe message, status, correlation ID, and relevant `Retry-After` metadata.
4. Add bounded, single-flight recovery for an initially unavailable page and for an active run that may have become terminal. Respect `Retry-After`, avoid request storms, and retain a visible manual retry action.
5. Represent `recovery unavailable` separately from `run in progress` in the existing status area. Keep Start safely blocked until an authoritative idle state is obtained.
6. Add Compose/runtime tests that soak the idle stack for more than two limiter windows and then load the public page.
